# 单 Issue 可信待验收交付

## 用途

把一个**用户选定的 Issue**变成一份可以按版本复核的待验收交付：先核实唯一变更、唯一仓库和要求版本，再交给原生 Teamflow 执行，最后用实际代码版本绑定验证与独立审查。

本 Skill 只补企业语义与证据边界，**不接管**排程、任务状态、授权判断和关闭判定。执行事实归原生 Teamflow，业务事实归企业系统（DevOps / Gitee），两者都不由本 Skill 重建。

## 何时使用

**由用户显式触发**（`userInvocable: true`、`modelInvocable: false`）。模型不得自行进入本流程，也不得把本 Skill 的存在当成对写动作的授权。

适用：用户点名一个 Issue 或从变更入口选定 Issue，并要求"做出一份可信的待验收交付"。
不适用：普通查询、只读排查、单个文件的修改、发布/合并/关闭 Issue 等动作请求。

## 依赖与短路

以下任一缺失时**停止并说明缺哪一项、影响哪些步骤、下一步做什么**，不要用提示词补齐能力：

| 依赖 | 缺失时的表现 | 下一步 |
|---|---|---|
| `forge_gitee_issue_read` / `forge_devops_change_context` | 拿不到 Issue 与变更 | 在 DevOps 配置页核对企业 CLI 与凭据 |
| 原生 Teamflow 工具 | 无法交接执行 | 安装/启用 Teamflow；本 Skill 不提供替代执行器 |
| `forge_gitee_delivery_snapshot` | 无法绑定代码版本 | 不生成交付候选；只报缺口 |
| 已授权工作区 | 不知道在哪工作 | 请用户确认 worktree，不猜目录、不切主目录 |

短路优先级高于"先把流程跑起来"：宁可只报阻塞，也不要产出一份没有版本或没有关联的"交付"。

## 只读关联核实

启动执行前必须拿到：**恰一个变更、恰一个代码仓库、范围、验收条件、依赖、可复核的要求版本**。每条结论都要标明读取来源（哪个工具、哪次读取）。

调用参数、标题相似度、模型推断和用户口头补充只能标为**声明**，不能标成独立核验。缺关联、多变更、多仓库、入口与读取结果冲突、读取失败时：只做只读澄清，展示冲突对象与缺失信息，**不自行挑第一个**，不写回"修正"的关联。用户补充线索后必须**重新读取**，不能沿用上一轮结论。

## 原生交接

把已核实的范围、验收、提交要求和来源交给原生 Teamflow；由原生决定阶段与管理澄清关卡，本 Skill **不声称跳过**任何未支持的阶段，也不臆造参数。相同 Issue、仓库与要求版本再次进入时先查已有 run：运行中只跟踪，可续跑的原生续跑一次，已完成先核对版本。查询不完整或存在多个候选就暂停并请用户决定。

细节见 `references/handoff.md`（关联、次数与暂停规则）。

## 证据边界

交付候选要求：真实关联、实际版本一致、必需本地验证通过、独立只读审查通过。原生 `completed` 只证明执行状态，不证明以上任何一条。

- 版本以 `forge_gitee_delivery_snapshot` 的 `contentId` 为准；只有分支名、runId 或不可复核的文本**不合格**。
- 代码、测试、依赖或验收要求变化后，旧验证与旧审查**不得自动沿用**。
- 本 Skill 的输出是证据摘要，不是硬门禁，也不能替代用户验收结论。

细节见 `references/evidence.md`（版本、验证、审查与来源分层）。

## 加载指引

主正文保持精简；需要动手时再按需读取：

- `references/handoff.md` — 关联核实、run 查询、单次交接与暂停规则。
- `references/evidence.md` — 版本绑定、验证记录、独立审查与失效判定。

`references/` 只是按需材料，不是第二份业务真源；两者冲突时以企业读取结果与原生执行记录为准。
