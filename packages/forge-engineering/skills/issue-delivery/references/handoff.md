# 交接规则：关联、run 与次数

## 1. 关联核实（只读）

按顺序做，每一步都要留下"读了什么、读到什么"：

1. 读 Issue：`forge_gitee_issue_read({target:'<owner/repo>#<编号>'})`。得到标题、正文、状态、`web_url`。
2. 读变更：`forge_devops_change_context({target:'<变更号>'})` 或 `forge_devops_query({action:'change.read',target})`。
3. 交叉核对：Issue 所属仓库、变更所属仓库、用户指定的仓库三者必须**同一个**。
4. 取范围、验收、依赖与要求版本；要求版本优先用平台真实修订标识。平台没有修订字段时，只能对**完整的权威读取载荷**计算内容摘要，并明确标注"内容版本，非平台修订号"。

不满足唯一性时停止，向用户列出：读到的候选、冲突字段、缺失字段，以及下一步需要补哪一条线索。

## 2. 已有 run 查询

- 用 `teamflow_status({runId})` 直查已知 run；不带参数只能列出**当前工作区最近的少量 run**，不能当作"历史上没有别的 run"的证明。
- 命中多个候选、需求摘要无法唯一匹配、或查询失败：暂停并请用户决定，**不要**先启动再去重。
- 完整的 Issue↔run 绑定若无法取得，如实说明该能力缺口；不要自建映射表或第二任务库。

## 3. 次数约束（可由调用记录直接核对）

| 场景 | 新启动次数 | 续跑次数 |
|---|---|---|
| 关联已核实、无既有 run | ≤ 1 | 0 |
| 相同 Issue / 仓库 / 要求版本再次进入，run 运行中 | 0 | 0 |
| 可续跑的中断 run（用户当次许可） | 0 | ≤ 1 |
| 已完成 run | 0 | 0 |
| 关联冲突 / 多候选 / 查询失败 / unknown | 0 | 0 |

请求结果 `unknown` 时先查再决定，不重发 start / resume。

## 4. 交接内容

交给原生 requirement 的内容：已核实的范围与验收、来源（Issue 链接、变更号、读取时间）、提交要求（首行为权威变更号）、企业约束。**不要**添加平台不存在的参数来"表达"这些要求，也不要用特殊模式假装跳过 PRD 或确认关卡。

分支策略：只在用户已授权的 worktree 内沿用当前分支。宿主提出额外决策时如实转给用户，不代用户批准。

## 5. 工作区守卫

启动、续跑、提交、交付前都核对：真实 cwd、Git 根、分支、是否授权 worktree。错位（会话目录不是目标仓库、仓库不符、分支被未经授权改变）时**停止**：不自动切主目录、不 stash、不提交、不清理别的工作树，把冲突报告给用户。
