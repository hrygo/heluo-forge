# 证据规则：版本、验证、审查与失效

## 1. 版本绑定

用 `forge_gitee_delivery_snapshot({})` 读取当前工作区版本。成功时至少记下：`workspaceId`、`commit`、`tree`、`contentId`、`dirty`、`observedAt`。

- `contentId` 覆盖暂存、未暂存、删除、重命名、模式与未跟踪内容；它才是"这次验的是哪份代码"。
- 只有分支名、runId、或一段无法复核的文字，**不构成版本**。
- 快照返回 `unknown`（截断、超时、采样期间发生变化）或 `failed`（非仓库、空 HEAD、未支持形态、拿不到调用根）时，不得把它写成"已绑定版本"。

## 2. 本地验证记录

逐条记录：命令、起止时间、执行者（工具/宿主）与版本、目标版本（`commit` + `contentId`）、退出码或断言结果、证据位置。

- 必需验证失败、未运行、或无法定位目标版本时，不得宣称"验证通过"。
- 既有跳过项单列来源，不计入通过；本需求的验收用例要求 0 失败、0 跳过。
- 不靠缩小覆盖、删用例或只跑子集来凑绿。

## 3. 独立只读审查

审查必须发生在**与实现分离**的上下文，并且能证明该上下文是只读的（例如写入被拒绝的实测记录）。

- 记录实际审查者/模型、上下文标识、被审版本、发现与结论。
- 实现者自报、调用方传入 `pass`、或实现上下文自审，都不算独立审查。
- 没有可用的隔离能力时明确写"未审查"，不伪造第二审查者。
- 修复回到实现上下文；修改后**重新快照并复审**，旧的审查结论不能套到新版本上。

## 4. 失效判定

以下任一变化都使旧证据失去自动适用资格：代码、测试、依赖声明、验收要求、提交（即使树相同）。

处理方式：保留旧证据为历史，为新版本重新取验证与审查；未知差异按"未覆盖"处理，不把用户对旧版本的确认迁移到新版本。

## 5. 来源分层

每一条结论都要能回到原始记录，并标出来源类型：

| 来源 | 含义 |
|---|---|
| repository-source | 仓库源码/契约本身 |
| local-execution | 本机真实执行（如真实 git、`node --test`） |
| host-execution | 宿主真实调用记录 |
| enterprise-read | 企业系统真实只读返回 |
| fixture / mock | 夹具或仿真，不等于真实链路 |
| declaration | 调用方或模型声明，未经独立核验 |

标 `enterprise` 或"发现即存在"不构成真实证据。真实企业 CLI、凭据/授权、IAM、受保护仓库规则、Windows/麒麟实机未验证时逐项标 `NOT RUN`，并写明影响；本地宿主链路通过不能改写成企业生产可用。

## 6. 交付摘要

一条摘要串联：变更、Issue、仓库、相关 run、实际 `commit`/已有 PR、验证、独立审查、依赖与未验项。分列**执行结果 / 候选交付 / 用户验收 / CI / 合入 / Issue 状态 / 业务结束状态**；未知保持未知。

"待验收"不代表可关闭，也不映射为关闭四项全通过；AI 只能提出"待用户验收"，用户对实际版本的明确结论才是人工意见。
