A

争议从哪来

网关团队反馈两点：一是云厂商都用静态 Key，兼容性更好；二是当前按令牌接入，统计、限流、限额与 FinOps 不好做。

第一条要分开看。云厂商用静态 Key 是面向公网的权衡，河洛到网关是内网、双方可控的链路，不构成必须。第二条是真问题，但根因是聚合键，不是凭据形态——按令牌值计桶会在刷新后清零，按 sub 聚合就没有这个问题。

本页把两种形态放在同一张表上算清楚，再给采用条件。

C

主方案：令牌直通

结论：客户端不持长期凭据，网关只验证不推断。

关键约束：aud 含网关标识；算法白名单；内省缓存 ≤60 秒；kid 未命中返回 503；结果未知不重放。

D

备选：控制台手工签发

结论：用户在网关控制台建 Key，再手工粘贴进 DSH。网关不新增接口，DSH 不写签发流程。

到期或泄露时：用户在控制台撤销或重建，再回到 DSH 重新粘贴。

G

一个被忽略的事实

网关控制台能"通过 IAM 统一登录"，说明它已经是 IAM 的 OIDC 客户端，具备回调、令牌校验与会话管理能力。

也就是说，主方案最难的那一步——网关验签——技术前提已经存在，剩下的是配置与联调，不是从零建设。这一点应当在下次沟通中明确，它把"主方案做不了"变成"主方案没排期"。

H

治理并没有变难

关注点 主方案 备选

限流 键为 sub 与 consumer 键为 Key 或主体

真正的差别只有一条：不要按凭据值聚合。这条写进契约，两种形态都成立。

I

关键设计：凭据抽象

结论：DSH 侧不要二选一，用同一接口承载两种来源，切换只改配置。

接口只需三件事：取凭据、判断是否可刷新、失败后是否可自动重试。静态 Key 实现"不可刷新、401 需人介入"，令牌实现"可刷新、401 至多重试一次"。

触发 动作
G1 前无法完成验签联调 试点启用备选，主方案并行推进
试点人数 ≤100 且周期 ≤3 个月 手工轮换成本可接受
人数超过 200 或需季度轮换 必须切回主方案
安全评审要求长期凭据登记 备选须补登记与轮换台账

采用期须同时满足五条。TTL ≤90 天；控制台可见最近使用与撤销；每设备一把并标设备名；DSH 存系统凭据库；401 引导重建。
