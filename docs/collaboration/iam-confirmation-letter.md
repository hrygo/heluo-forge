## 1. 结论（平台内部）

本函为面向企业统一身份与访问管理（IAM）团队的**独立专项问询函**，专用于推进研发助手（Heluo Forge / DSH）在企业内网实现**企业 IAM 独占统一登录与令牌全生命周期管控**。

本方案已由架构决策明确以下原则：
1. **企业 IAM 独占**：企业内网禁用官方 DeepSeek 账号体系、公网模型路由与第三方 API Key，企业 IAM 是助手获取企业模型与工具能力的唯一凭据入口；
2. **公共原生客户端安全基线**：客户端作为双端（Windows 11 与银河麒麟 Linux）分发的 Native 桌面/Web 应用，遵循 RFC 8252 规范，采用“系统浏览器 + Loopback 本地回调（`http://127.0.0.1:<port>/iam/callback`）+ 授权码及 PKCE（S256）”，不存储 Client Secret；
3. **分资源授权与最小特权**：模型访问令牌与工程平台访问令牌实施严格的 Audience/Resource 隔离，防范跨系统越权；
4. **单飞互斥与安全生命周期**：客户端在本地凭据锁内实施 single-flight 互斥刷新，支持刷新令牌轮换（Rotation）、重用检测、主动撤销（RFC 7009）与会话登出联动。

目前处于方案推进的关键阶段，仍有 OIDC 元数据端点规范、RFC 8707 资源参数支持、令牌轮换机制与测试租户矩阵等 18 项技术约束亟待 IAM 团队书面澄清与确认。

## 2. 确认范围与职责边界（平台内部）

### 2.1 确认范围

- **协议与端点**：OIDC 1.0 vs OAuth 2.0 支持程度、Discovery 元数据、正式颁发/验签端点、JWKS 签名算法白名单（RS256/ES256/PS256）与密钥轮换机制。
- **客户端注册与回调**：Public Client 登记规则、Client ID 范围、Loopback 地址（`127.0.0.1`）及端口策略。
- **人员身份与声明（Claims）**：ID Token / UserInfo 校验基线、稳定不可变人员唯一标识（`sub` 与工号）、部门与角色预设映射、离职调岗目录同步时效。
- **分资源授权（Audience 隔离）**：RFC 8707 `resource` 参数支持度、模型网关专属令牌绑定、替代方案（Scope 隔离或多客户端预注册）。
- **令牌生命周期与并发**：Access Token / Refresh Token 时效（TTL）、多进程/多请求并发刷新、Refresh Token 轮换与旧令牌重用检测（Grace Period）。
- **撤销与退出联动**：RFC 7009 撤销端点能力（Refresh/Access 级联失效）、RP-Initiated Logout 支持与浏览器企业 SSO 会话终结。
- **网关协同与网络环境**：JWT 自包含验签 vs Introspection 内省、双端系统代理、企业自签 CA 证书链、EDR/防火墙策略。
- **联调与演练资源**：测试环境租户、包含离职/停用/无权限在内的测试账号矩阵、上线审批 SLA。

### 2.2 职责边界

| 事项 | 平台组（研发助手客户端）职责 | IAM 团队职责 | AI 模型网关职责 |
|---|---|---|---|
| 身份认证 | 调用系统浏览器拉起 IAM，校验 state/nonce/PKCE，接收本地回调 | 提供高可用 OIDC 登录页、多因素认证与公共客户端授权 | 不参与登录流程，仅消费令牌 |
| 凭据存储 | 本机凭据库加密存储，防跨进程并发竞争，内存镜像 | 维护权威用户会话、发放并记录 Grant | 不存储用户凭据 |
| 令牌校验 | 本地校验 ID Token 结构与时钟；不直接校验 Access Token | 提供 JWKS 元数据与内省端点，维护公钥轮换 | 本地 JWKS 验签或实时内省，校验 aud/exp/scope |
| 权限与额度 | 解析人员工号与角色映射预设，不参与服务端决策 | 维护人员组织关系与角色权威源，提供目录同步 | 按工号与 consumer 实施双维度额度计量与限流 |
| 撤销与登出 | 用户退出时触发 RFC 7009 撤销并清理本地状态 | 实时注销 Refresh Token，终结 SSO 会话 | 接收撤销事件或依赖 short-lived 令牌自然失效 |

**背景与目的**

我们正在为企业内网研发人员部署智能研发助手客户端（Heluo Forge）。为落实企业信息安全与统一治理要求，研发助手将企业统一登录（IAM）作为内网的**唯一登录方式**，不保留任何公网模型或官方账户登录旁路：
- **认证交互流程**：员工在研发助手点击登录后，客户端调用系统默认浏览器打开企业统一登录页，员工完成企业身份认证（含 MFA）；认证通过后浏览器重定向至本机监听地址（`http://127.0.0.1:<port>/iam/callback`），客户端在本地接收授权码并换取令牌。客户端全程不接触、不留存员工账号密码。

- **安全与最小特权**：为防范跨系统越权，客户端需实现“一资源一令牌”隔离，并支持令牌的主动撤销与安全登出。

为确保系统集成顺畅、运行稳定合规，现梳理以下 18 项具体技术确认事项。无法支持的能力请直接说明限制，以便我们启动备选架构设计，无需承诺尚未规划的开发。

**材料安全要求：** 请勿在本函中填写真实密码、个人隐私数据或生产密钥。示例请使用 `corp.example`、`user-demo` 占位；测试账号及内部地址请通过企业受控工单传递。

### 第一组：认证协议与客户端登记（阻塞项，首期联调前置）

#### CONF-IAM-01｜认证协议形态（纯 OAuth 2.0 vs OIDC 1.0）与身份凭据

- **真实问题：** 平台需要知道登录成功后如何获取经过权威背书的员工身份。单纯 OAuth 2.0 仅解决授权（返回 Access Token），客户端无法直接信赖由第三方解析的身份；而 OIDC 提供经 IdP 签名的 ID Token。
- **请确认事项：** 企业统一身份服务是严格遵循 OpenID Connect Core 1.0，还是私有/纯 OAuth 2.0？是否提供经过 IdP 私钥签名的标准 ID Token？若仅提供 OAuth 2.0，客户端如何通过可信端点（如 `/userinfo` 或 `/me`）获取经过认证的员工工号与真实姓名？
- **期望提供：** 所遵循的 OIDC / OAuth 2.0 规范说明文档、标准端点清单及身份返回格式说明。

#### CONF-IAM-02｜本机授权码登录、系统浏览器拉起与 Loopback 回调机制

- **真实问题：** 客户端运行在员工办公电脑（Windows 与银河麒麟 Linux）。根据 RFC 8252（OAuth 2.0 for Native Apps），桌面应用不得内嵌 Webview 收集密码，必须调用系统默认浏览器打开统一登录页，并在认证后重定向至本机 Loopback 回调接口。
- **请确认事项：** 是否全面支持基于系统浏览器 + `127.0.0.1` 本地回调的授权码模式（Authorization Code Flow with PKCE S256）？是否强制要求 HTTPS 或允许 HTTP Loopback？回调地址对本地端口是否有固定限制，还是支持端口动态分配？
- **期望提供：** Native 客户端登录接入说明、允许的回调 URL 规范及防火墙/端口要求。

#### CONF-IAM-08｜公共客户端（Native Public Client）注册规则与 Redirect URI 策略

- **真实问题：** 由于客户端为分发至每位员工本机的桌面应用，无法在客户端安全保护 Client Secret（任何下发到本地的密钥均视为公开泄露）。
- **请确认事项：** 是否允许将研发助手登记为公共客户端（Public Client，`token_endpoint_auth_method=none`），强制且仅使用 PKCE（S256）进行凭据交换？客户端登记粒度是“全企业共用一个全局 `client_id`”，还是按设备/租户动态注册？Redirect URI 的登记规则为何：支持使用 `http://127.0.0.1:<port>/iam/callback` 吗？端口是否允许为通配符/动态端口，还是必须预先登记固定端口（或一组连续候选端口）？
- **期望提供：** 公共客户端登记指引、管理平台申请入口、Redirect URI 匹配校验规则。

#### CONF-IAM-09｜OIDC Discovery 元数据、端点清单与 JWKS 密钥轮换策略

- **真实问题：** 客户端与后端模型网关需动态加载 IdP 配置，并基于公开公钥对 ID Token 及 JWT Access Token 进行验签，杜绝密钥硬编码。
- **请确认事项：** IAM 是否提供标准的 OpenID Provider Configuration 元数据端点（`/.well-known/openid-configuration`）？请提供以下正式内网端点地址：Issuer URL、Authorization Endpoint、Token Endpoint、JWKS URI、Revocation Endpoint、End Session Endpoint。签名算法允许哪些（如 RS256、ES256、PS256）？是否明确强制拒绝 `none` 算法与对称算法（HS256）？JWKS 轮换时，新旧 `kid` 的平滑过渡窗口是多久？客户端/网关应如何设置 JWKS 缓存时限（TTL）？
- **期望提供：** 内网测试/生产环境 Discovery 响应 JSON 示例、端点清单、签名算法列表及公钥轮换机制说明。

#### CONF-IAM-10｜ID Token 声明（Claims）核验基线与人员工号/角色映射

- **真实问题：** 客户端需在本地对 ID Token 进行严格的密码学与上下文校验，防止跨应用仿冒或重放；同时需提取稳定的员工工号与角色映射预设。
- **请确认事项：** ID Token 规范中必须强制核验哪些 Claims（`iss`、`aud`、`nonce`、`exp`、`iat`、`auth_time`）？允许的时钟漂移偏差（Clock Skew）是多少（推荐不超过 ±60 秒）？员工稳定不可变唯一标识是哪个 Claim（`sub` 是否稳定且不随手机号/工号变更，或工号位于独立 Claim 如 `employee_id` / `username`）？企业部门、用户组或角色的 Claim 字段名称与数据结构为何（如 `groups: string[]` 或 `roles`）？此 Claim 是否会在用户组织变动时实时刷新？
- **期望提供：** 标准 ID Token Payload 结构示例、各 Claim 语义定义文档、角色映射关系说明。

### 第二组：分资源授权与网关协同（阻塞项，调用链路隔离）

#### CONF-IAM-03｜业务服务分资源授权（一资源一令牌）与权限隔离

- **真实问题：** 研发助手既要访问 AI 模型网关（高频调用、消耗模型算力），又可能访问 DevOps 或代码资产服务。若使用单一宽泛令牌，会导致严重的权限扩散风险。
- **请确认事项：** IAM 是否支持在授权与刷新时按具体目标服务申请相互隔离的访问令牌（一资源一令牌）？若不支持，IAM 推荐如何做好模型网关与企业现有工程系统之间的权限隔离与越权防护？
- **期望提供：** 多资源授权接入建议、Scope 划分策略、令牌隔离技术方案文档。

#### CONF-IAM-11｜RFC 8707 Resource 参数支持与 Audience 约束

- **真实问题：** RFC 8707（Resource Indicators for OAuth 2.0）允许客户端在请求 Token 时显式传入 `resource` 参数，从而使颁发的 Access Token 严格绑定目标服务的 Audience，服务方校验 `aud` 确保令牌专卡专用。
- **请确认事项：** 统一认证服务是否原生支持 RFC 8707 `resource` 参数？若不支持，模型网关如何准确鉴别“当前令牌专用于模型服务而非其他业务系统”？若必须使用替代方案，是建议通过 `scope` 进行隔离，还是为不同资源预先注册独立的 Client ID？请给出推荐的 scope 命名规范、audience 取值规则，以及后续 Token Exchange（RFC 8693）的可行性评估。
- **期望提供：** `resource` 或 `scope` 隔离最佳实践、Audience 配置说明及示例请求/响应报文。

#### CONF-IAM-15｜访问令牌形态（JWT vs Opaque）与网关验签方式

- **真实问题：** 企业模型网关需要对进站请求的 Access Token 进行高吞吐、低延迟的鉴权。
- **请确认事项：** 颁发的 Access Token 是自包含的 JWT 结构，还是需要向 IAM 反向查询的透明令牌（Opaque Token）？模型网关应采用“本地基于 JWKS 公钥验签”，还是调用 IAM 内省端点（Introspection Endpoint）？请给出 Access Token 的典型 Payload 结构（如 `sub`、`aud`、`client_id`、`exp`、`scope` 等）；若需调用 Introspection，IAM 对高并发内省查询的吞吐量与缓存推荐（如缓存 ≤60 秒）有何要求？网关本地验签时，若遇到未匹配的 `kid`，IAM 建议网关返回 503（密钥轮换中暂不可用）还是 401（认证失败）？
- **期望提供：** Access Token 真实 Payload 示例、Introspection 接口文档及高并发缓存优化建议。

### 第三组：令牌生命周期、并发与注销（运行安全与稳定性）

#### CONF-IAM-05｜访问令牌与刷新令牌有效时限（TTL）与撤销机制

- **真实问题：** 客户端需根据 Access Token 与 Refresh Token 的生命周期规划自动续期与超时提示，并在用户退出时完成失效处理。
- **请确认事项：** Access Token 的标准有效时长是多久（如推荐 15~60 分钟）？Refresh Token 的有效时长是多久（如 7 天、30 天，或具备滑动过期）？在会话尚未到期时，系统管理员或用户本人是否有途径主动撤销已签发的令牌？
- **期望提供：** 令牌生命周期配置策略文档、会话超时规则及主动注销渠道说明。

#### CONF-IAM-06｜令牌并发刷新、进程互斥与多端会话影响

- **真实问题：** 桌面客户端可能存在多进程并发调用模型，若两个并发请求同时检测到 Access Token 即将过期，会触发并发刷新。
- **请确认事项：** IAM 服务端如何处理同一客户端短期内的并发 Refresh Token 请求？某一个并发刷新成功后，是否会导致并发中的其他请求失效？刷新某单一服务的令牌是否会波及同一用户在其他系统或浏览器的现有活跃会话？
- **期望提供：** 并发刷新处理机制说明、服务端的互斥或幂等设计建议。

#### CONF-IAM-12｜刷新令牌轮换（Rotation）、重用检测（Reuse Detection）与并发容忍

- **真实问题：** 现代安全规范（OAuth 2.1 / BCP 212）建议对 Public Client 实行 Refresh Token Rotation（每次刷新废除旧 Refresh Token 并下发新 Refresh Token），并对旧 Token 重用报警视为会话窃取。
- **请确认事项：** 企业 IAM 是否开启了 Refresh Token Rotation？每次刷新时是否必须传递 `offline_access` scope？服务端是否具备旧 Refresh Token 重用检测能力？一旦检测到重用，返回什么标准错误码（如 `invalid_grant`）？服务端是否存在短暂的时间窗口（Grace Period，如 5~10 秒），以容忍因网络抖动导致的并发刷新或响应丢包，避免误判为会话失陷而强制用户登出？
- **期望提供：** Refresh Token 轮换策略文档、重用检测处理逻辑及 Grace Period 配置说明。

#### CONF-IAM-13｜RFC 7009 令牌撤销（Token Revocation）端点与级联失效

- **真实问题：** 用户在研发助手点击“退出登录”或设备报失时，客户端必须向 IdP 发起主动撤销以阻断后续调用。
- **请确认事项：** IAM 是否提供标准的 RFC 7009 撤销端点（`/oauth/revoke`）？该端点支持撤销 Refresh Token、Access Token 还是两者均支持？撤销 Refresh Token 时，是否会级联使该会话下已签发的所有有效 Access Token 立即失效？撤销成功、撤销失败以及对已撤销令牌重复调用的 HTTP 状态码与响应体分别是什么（RFC 7009 要求对已撤销或无效令牌同样返回 200 OK）？从发起撤销到全网关生效的最大延迟是多少？
- **期望提供：** RFC 7009 撤销端点接口规范、级联失效机制说明及状态码约定。

#### CONF-IAM-14｜RP 发起注销（RP-Initiated Logout）与浏览器 SSO 会话联动

- **真实问题：** 员工在桌面客户端登出后，浏览器端的企业 SSO 会话若仍处于保持状态，其他人员在此电脑上重新点击登录可能无需输密直接登录旧账号。
- **请确认事项：** IAM 是否支持 OpenID Connect RP-Initiated Logout 1.0？注销端点（`end_session_endpoint`）调用时是否需要携带 `id_token_hint`？注销后的重定向地址 `post_logout_redirect_uri` 是否允许为 Loopback 地址（`http://127.0.0.1:<port>/iam/logout-callback`）且需提前登记？调用该端点后能否彻底终结系统浏览器中的全局企业 SSO 会话？在登录授权时是否支持传入 `prompt=login` 以强制用户重新输入凭据？若不支持 RP 登出，请明确客户端本地清空凭据即代表会话终结的业务边界。
- **期望提供：** RP-Initiated Logout 接口说明、`prompt` 参数支持情况及登出最佳实践。

### 第四组：目录同步、错误码与网络环境（运维与工程保障）

#### CONF-IAM-04｜员工组织关系权威源与离职/调岗权限变更时效

- **真实问题：** 企业安全与合规要求员工离职、调岗或冻结账号后，研发助手的模型调用权限必须在可控时间内被切断。
- **请确认事项：** 员工账号、工号、归属部门与所属群组的权威数据源为何（如 HR 系统、Active Directory、LDAP、企业微信等）？当员工在权威源中被禁用、离职或调岗后，该状态变更多久能同步至 IAM 认证中心与令牌颁发体系？已签发未过期的 Access Token 如何阻断？
- **期望提供：** 组织架构同步架构说明、离职/冻结同步延迟 SLA、令牌实时黑名单机制。

#### CONF-IAM-16｜端点错误码映射、限流保护与客户端重试约定

- **真实问题：** 客户端网络层需要依据精准的 HTTP 状态码与 OAuth 错误码，严格区分“偶发网络故障可自动重试”与“凭据失效/被盗必须阻断重登”，防止死循环刷新导致账号锁定或网关雪崩。
- **请确认事项：** 请提供 Authorize、Token、Refresh、Revoke 各端点返回的详细错误码映射（如 `invalid_request`、`invalid_client`、`invalid_grant`、`unauthorized_client`、`unsupported_grant_type`、`invalid_scope`、`temporarily_unavailable` 等）及对应的 HTTP 状态码。IAM 对认证与刷新接口的限流阈值是多少？触发限流时返回 429 还是其他状态码？是否包含 `Retry-After` 响应头？推荐的客户端超时时间是多长？
- **期望提供：** 端点错误码详表、限流规则及推荐的客户端异常处理策略。

#### CONF-IAM-17｜双端终端环境、网络代理、企业自签证书与 EDR 策略

- **真实问题：** 研发助手部署在约 800 台研发终端上，包含 Windows 10/11 与银河麒麟 Linux V10 SP1（x86_64 与 aarch64 双架构），终端普遍受企业安全软件管控。
- **请确认事项：** 终端访问 IAM 认证端点与 Discovery 服务时，是否必须经过特定的企业正向代理或反向网关？是否需要预装企业专用的自建 CA 根证书（用于 TLS 检验或流量审计）？客户端在本机侦听 `127.0.0.1` 接收 OAuth 回调，是否会受到终端防火墙、杀毒软件或 EDR（端点检测与响应）的拦截？测试与生产环境的前置网络策略及开通流程为何？
- **期望提供：** 双端网络连通性要求、自签根证书安装指南、EDR/防火墙白名单配置建议。

#### CONF-IAM-07｜联调测试环境与基础联调账号

- **真实问题：** 方案实施需提前进入本地仿真实测与联调，验证授权码拉起、本地回调与令牌解析。
- **请确认事项：** 能否提供一个可供研发团队直接连通的内网 IAM 测试/沙箱环境？能否开通 1~2 个专属的测试账号及配套的测试 Client ID，供团队调试授权登录、令牌获取与过期拦截流程？
- **期望提供：** 测试环境访问地址、测试 Client 凭据及测试账号信息。

#### CONF-IAM-18｜测试租户账号矩阵、全生命周期演练与上线审批 SLA

- **真实问题：** 为确保系统上线后的高可用与高安全，必须在预发环境演练各种极端异常与权限变更场景。
- **请确认事项：** 能否在测试环境中提供包含以下状态的完整测试账号矩阵：① 正常活跃员工账号、② 具备不同角色/部门的账号、③ 已在企业目录中被冻结/停用的账号、④ 令牌已被管理员主动撤销的账号、⑤ 明确未被授权使用 AI 模型的账号？是否支持平台组演练 Refresh Token 轮换、重用告警、RFC 7009 撤销及 RP 登出？正式客户端注册审批、测试账号开通及生产环境 Client 上线各自的服务承诺时限（SLA）是几个工作日？审批流程需要哪些部门负责人参与？

## 5. 失败模式与平台侧处理（平台内部，不随函转发）

针对 IAM 团队回函中可能出现的“不支持”或“有条件支持”情况，平台组预置以下技术应对措施，确保方案具备弹性：

| 潜在不支持或受限场景 | 平台侧应对与兜底方案 | 架构影响与代价 |
|---|---|---|
| 仅支持纯 OAuth 2.0，无 OIDC / ID Token | 登录换 Token 后，客户端调用 `/userinfo` 或 `/me` 端点获取人员主体，并在本地合成会话上下文；网关校验 Access Token 有效性 | 增加一次 HTTP 网络请求；需确认用户信息端点的高可用与吞吐量 |
| 回调端口必须固定，不支持随机端口 | 客户端在固定端口（如 `18443`）启动 Loopback 监听；启动前先探活，若端口冲突给出明确系统弹窗指引关闭冲突进程 | 遇到端口占用的极端情况下用户体验受损 |
| 不支持 RFC 8707 `resource` 参数 | 方案 A：在 IAM 为模型网关与工程服务分别预注册 Client ID；<br>方案 B：采用单客户端 + 细粒度 `scope`（如 `model:invoke`），网关强校验 scope | 方案 A 需维护多个凭据；方案 B 需网关与 IAM 统一 scope 字典 |
| 不支持 Refresh Token 轮换或重用检测 | 客户端在本地使用单飞互斥锁（Single-Flight Mutex）严格防止并发刷新；依赖短期 Access Token（≤1 小时）控制暴露窗口 | 若 Refresh Token 泄露，服务端无法通过重用检测感知异常，依赖管理员主动冻结账号 |
| 不提供 RFC 7009 撤销端点 | 客户端“退出登录”仅执行本地强清理（清除凭据记录与内存镜像）；在账户界面提示“本地会话已结束，服务端凭据自然过期失效” | 存在未过期 Access Token 在剩余有效期内仍能调用网关的窗口期 |
| 不支持 RP-Initiated Logout | 客户端仅执行 `logoutMode=local`；登录链接带 `prompt=login` 参数强制用户重新输密，防止公共办公机账号混用 | 无法远程销毁浏览器现存的全局企业 SSO 会话 |
| Access Token 仅支持 Opaque（透明字符串） | 模型网关无法执行本地 JWKS 验签，必须调用 IAM Introspection 端点；网关层配置 30~60 秒的高性能本地缓存 | 网关 QPS 受制于 IAM 内省吞吐上限；撤销生效存在最大 60 秒延迟 |
| 强制公共客户端使用固定 Client Secret | 与安全及 IAM 团队沟通桌面应用逆向风险；若无法放开，仅能将 Client Secret 视为“应用安装标识”而非保密凭证 | 无法防范恶意仿冒请求，需配合内网 IP 白名单或终端合规策略 |
