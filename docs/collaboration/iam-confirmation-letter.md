## 1. 结论（平台内部）

本函是 IAM 问题、已有答复及补充确认的统一记录。§4 保留原 21 项问题、已有答复和支撑材料；本轮对外使用 §9，先说明业务需求，再列原函覆盖情况和需补充确认的内容，不另起 IAM 新函或重新编号。

企业内实施团队正在会同厂商开展 AI 网关实施。涉及身份对应、模型调用、停用和退出的配合事项，由相应团队确认产品能力及配合条件，企业内实施团队协调并汇总处理。

本方案已由架构决策明确以下原则：
1. **企业 IAM 独占**：企业内网禁用官方 DeepSeek 账号体系、公网模型路由与第三方 API Key；企业 IAM 负责 DSH 登录与可信人员授权；模型路线待 IAM/网关评审，若保留静态 Key 由网关签发，但不能代替运行时人员认证；
2. **公共原生客户端安全基线**：客户端（涵盖 Windows 原生应用与 Linux 本机 Web 服务）均分发部署于员工个人电脑本地，无法安全保护服务端 Client Secret，目标形态遵循 RFC 8252 公共原生客户端 + PKCE（S256）。但 2026-10-26 厂商 6.0.3/6.3 回函明确当前不支持公共客户端与 PKCE，内部校验回函 §02 仅称 PKCE 能力、§08 未答；V1 因此按机密客户端 + 系统钥匙串落地，PKCE/公共客户端只作后续条件；
3. **分资源授权与最小特权**：网关与其他受控服务保持目标资源隔离；按 IAM 实际支持的 resource 或 audience/client 登记方式核验，不强制新增协议扩展；
4. **单飞互斥与安全生命周期**：客户端在本地凭据锁内实施 single-flight 互斥刷新，需核实刷新令牌轮换（Rotation）、重用检测及单授权主动撤销，不能把本地锁或全局登出当作等效保证；
5. **首轮部分答复提取与待最终核实声明**：截至 2026-10-22，内部项目组已从首轮沟通中提取并整理了部分技术结论（涉及 OIDC 协议形态、HR 目录同步时效、Access Token 有效期、Discovery 端点与 JWKS 结构、RT 轮换与重用检测、RFC 7009 撤销边界、RP 登出联动等）。**特别标注：所有提取内容均为内部项目组提供，待 IAM 公司/团队最终核实并正式回函确认为准**。当前仍存在 CONF-IAM-02 / 08（Public Native Client 免 Secret 登记与 Loopback 端口通配规则）等关键阻塞项尚未答复，以及 CONF-IAM-05（Refresh Token 是否支持长周期滑动过期）需进一步协商。

原函包含 21 项问题，其中 18 项由厂商答复，3 项（CONF-IAM-07、17、18）由企业内团队组织环境、网络和测试；涉及产品能力的部分仍请厂商配合确认。本轮只补充未明确的业务边界，已有答复的内容继续沿用原记录及其核实状态。

## 2. 确认范围与职责边界（平台内部）

### 2.1 确认范围

- **协议与端点**：OIDC 1.0 vs OAuth 2.0 支持程度、Discovery 元数据、正式颁发/验签端点、JWKS 签名算法白名单（RS256/ES256/PS256）与密钥轮换机制。
- **客户端注册与回调**：Public Client 登记规则、Client ID 范围、Loopback 地址（`127.0.0.1`）及端口策略。
- **人员身份与声明（Claims）**：ID Token / UserInfo 校验基线、稳定不可变人员唯一标识（`sub` 与工号）、部门与角色预设映射、离职调岗目录同步时效。
- **分资源授权（Audience 隔离）**：RFC 8707 `resource` 参数支持度、模型网关与其他资源的令牌绑定、替代方案（Scope 隔离或多客户端预注册）。
- **令牌生命周期与并发**：Access Token / Refresh Token 时效（TTL）、管理端会话吊销、多进程/多请求并发刷新、Refresh Token 轮换与旧令牌重用检测（Grace Period）。
- **撤销与退出联动**：RFC 7009 撤销端点能力（Refresh/Access 级联失效）、RP-Initiated Logout 支持与浏览器企业 SSO 会话终结。
- **服务鉴权与网络环境**：模型网关目标 Access Token 的 JWT 验证或 Introspection 内省、双端系统代理、企业自签 CA 证书链、EDR/防火墙管控策略。
- **联调与演练资源**：测试环境沙箱与多状态测试账号矩阵演练（由平台组与内部团队提供与保障）。
- **多因素认证**：MFA 强制策略、`acr_values`/`max_age` step-up、许可方式与失败/取消语义。
- **运营审计与生命周期联动**：登录/授权/撤销审计事件、保留期与 SIEM 对接；SCIM 2.0 出站停用联动与许可。

### 2.2 职责边界

下表区分产品与企业内实施职责；IAM、网关各确认自身能力与配合条件，企业内实施团队协调共同事项并汇总，不遗漏跨系统依赖。

| 事项 | 平台组（研发助手客户端）职责 | IAM 团队职责 | UAG 模型网关职责（参考） |
|---|---|---|---|
| 身份认证 | 系统浏览器登录、回调及登录结果校验 | 核实公共客户端接入与可信人员身份 | 核实模型请求的当前人员认证；不能从控制台登录推定 |
| 凭据存储 | 系统凭据库保护会话与可选 Key，不进入上下文/日志 | 核实授权、刷新与撤销生命周期 | 管理可选 Key 及应用凭证；两路线策略均待确认 |

| 权限与额度 | 展示状态/入口，本地预设不代替服务端授权 | 提供稳定人员映射，确认跨客户端 subject 语义 | 模型/用途、成员/团队预算、网络及 C4 控制 |

**背景与目的**

我们正在为企业内网研发人员部署智能研发助手客户端（Heluo Forge），企业统一身份是唯一人员登录入口。希望实现以下业务效果：

- 个人研发统一通过 DSH；当前调用者必须是合法员工，不能借用他人的访问资格。公司账号登录成功与模型访问开通是两件事。

- 离线退出应清楚显示服务端尚未确认；服务故障时，只有仍能保证授权有效与撤权时限的访问才可继续。
- 身份在 DSH 与模型网关之间可以可靠对应，账号改名、变更或重新建立不能误认成另一个人；应用 Agent 的创建责任与人员实时登录要求分开管理，应用开通由网关团队确认。

### 第一组：认证协议与客户端登记（阻塞项，首期联调前置）

#### CONF-IAM-01｜认证协议形态（纯 OAuth 2.0 vs OIDC 1.0）与身份凭据

- **真实问题：** 平台需要知道登录成功后如何获取经过权威背书的员工身份。单纯 OAuth 2.0 仅解决授权（返回 Access Token），客户端无法直接信赖由第三方解析的身份；而 OIDC 提供经 IdP 签名的 ID Token。
- **请确认事项：** 企业统一身份服务是严格遵循 OpenID Connect Core 1.0，还是私有/纯 OAuth 2.0？是否提供经过 IdP 私钥签名的标准 ID Token？若仅提供 OAuth 2.0，客户端如何通过可信端点（如 `/userinfo` 或 `/me`）获取经过认证的员工工号与真实姓名？是否支持 `response_type=code` 并禁用隐式流（Implicit Flow）？
- **期望提供：** 所遵循的 OIDC / OAuth 2.0 规范说明文档、标准端点清单及身份返回格式说明。

#### CONF-IAM-02｜本机授权码登录、系统浏览器拉起与 Loopback 回调机制

- **真实问题：** 客户端运行在员工办公电脑（Windows 与银河麒麟 Linux）。根据 RFC 8252（OAuth 2.0 for Native Apps），桌面应用不得内嵌 Webview 收集密码，必须调用系统默认浏览器打开统一登录页，并在认证后重定向至本机 Loopback 回调接口。
- **请确认事项：** 是否全面支持基于系统浏览器 + `127.0.0.1` 本地回调的授权码模式（Authorization Code Flow with PKCE S256）？是否强制要求 HTTPS 或允许 HTTP Loopback？回调地址对本地端口是否有固定限制，还是支持端口动态分配？授权码的有效期与一次性使用（重放拒绝）策略为何？
- **期望提供：** Native 客户端登录接入说明、允许的回调 URL 规范及防火墙/端口要求。

#### CONF-IAM-08｜公共客户端（Native Public Client）注册规则与 Redirect URI 策略

- **真实问题：** 由于客户端为分发至每位员工本机的桌面应用，无法在客户端安全保护 Client Secret（任何下发到本地的密钥均视为公开泄露）。
- **请确认事项：** 是否允许将研发助手登记为公共客户端（Public Client，`token_endpoint_auth_method=none`），强制且仅使用 PKCE（S256）进行凭据交换？客户端登记粒度是“全企业共用一个全局 `client_id`”，还是按设备/租户动态注册？管理端配置 Redirect URI 时是否允许登记无固定端口的回环地址（如 `http://127.0.0.1:<port>/iam/callback` 或无端口前缀形式）？新增或变更 Redirect URI 的审批流程与时限如何？是否需要管理员 consent（应用授权）？
- **期望提供：** 公共客户端登记指引、管理平台申请入口、Redirect URI 匹配校验规则。

#### CONF-IAM-09｜OIDC Discovery 元数据、端点清单与 JWKS 密钥轮换策略

- **真实问题：** 客户端与受控研发服务需动态加载 IdP 配置，并基于公开公钥对 ID Token 进行验签，杜绝密钥硬编码；本轮包括模型网关目标 Access Token 的验证元数据（若为 JWT）；不可从 ID Token 公钥样例推定 AT 的验证能力。
- **请确认事项：** IAM 是否提供标准的 OpenID Provider Configuration 元数据端点（`/.well-known/openid-configuration`）？请提供以下正式内网端点地址：Issuer URL、Authorization Endpoint、Token Endpoint、JWKS URI、Revocation Endpoint、End Session Endpoint。签名算法允许哪些（如 RS256、ES256、PS256）？是否明确强制拒绝 `none` 算法与对称算法（HS256）？JWKS 轮换时，新旧 `kid` 的平滑过渡窗口是多久？客户端/未来 MCP 服务应如何设置 JWKS 缓存时限（TTL）？Issuer 是否稳定（是否包含租户路径）？
- **期望提供：** 内网测试/生产环境 Discovery 响应 JSON 示例、端点清单、签名算法列表及公钥轮换机制说明。

#### CONF-IAM-10｜ID Token 声明（Claims）核验基线与人员工号/角色映射

- **真实问题：** 客户端需在本地对 ID Token 进行严格的密码学与上下文校验，防止跨应用仿冒或重放；同时需提取稳定的员工工号与角色映射预设。
- **请确认事项：** ID Token 规范中必须强制核验哪些 Claims（`iss`、`aud`、`nonce`、`exp`、`iat`、`auth_time`）？允许的时钟漂移偏差（Clock Skew）是多少（推荐不超过 ±60 秒）？员工稳定不可变唯一标识是哪个 Claim（`sub` 是否稳定且不随手机号/工号变更，或工号位于独立 Claim 如 `employee_id` / `username`）？企业部门、用户组或角色的 Claim 字段名称与数据结构为何（如 `groups: string[]` 或 `roles`）？此 Claim 是否会在用户组织变动时实时刷新？`aud` 是否等于 `client_id`？`sub` 是否为 pairwise（不同 client 是否得到不同的 `sub`）？
- **期望提供：** 标准 ID Token Payload 结构示例、各 Claim 语义定义文档、角色映射关系说明。

- **本轮补充：请确认 DSH 与网关跨客户端的稳定人员对应方式、pairwise sub 情况，以及改名、调岗、账号删除重建是否改变映射；不用邮箱或客户端自报 owner 作为可信依据。**

#### CONF-IAM-20｜多因素认证（MFA）强制策略与 Step-up

- **真实问题：** 研发助手面向企业研发人员，登录安全依赖 IAM 的 MFA 策略；若 MFA 只能全局开关、无法按应用或风险等级配置，公共办公机与高权限岗位无法差异化管控。
- **请确认事项：** IAM 是否支持按应用（client）、用户组或风险等级强制 MFA？是否支持通过 `acr_values` 或 `max_age` 要求 step-up 认证或强制重新输入凭据？支持哪些 MFA 方式（OTP、短信、推送、生物识别等）？MFA 能力是否包含在标准版内，还是需要单独模块与许可？MFA 失败、超时或用户取消时返回哪些错误码，客户端如何区分“用户取消”与“认证失败”？
- **期望提供：** MFA 策略配置说明、step-up 参数支持情况、许可方式与错误码清单。

### 第二组：模型网关目标授权与其他资源隔离（阻塞项，调用链路隔离）

#### CONF-IAM-03｜业务服务分资源授权（一资源一令牌）与权限隔离

- **真实问题：** 研发助手需向模型网关提供当前人员的可信授权，并与其他受控服务隔离；未来如另行启用 MCP，其资源授权仍单独核验。
- **请确认事项：** IAM 是否支持在授权与刷新时按具体目标服务申请相互隔离的访问令牌（一资源一令牌）？若不支持，IAM 推荐如何做好工程服务与未来 MCP 之间的权限隔离与越权防护？请给出推荐的 scope 命名规范、audience 取值规则，以及 Token Exchange（RFC 8693）的可行性评估。
- **期望提供：** 多资源授权接入建议、Scope 划分策略、令牌隔离技术方案文档。

#### CONF-IAM-11｜RFC 8707 Resource 参数支持与 Audience 约束

- **真实问题：** RFC 8707（Resource Indicators for OAuth 2.0）允许客户端在请求 Token 时显式传入 `resource` 参数，从而使颁发的 Access Token 严格绑定目标服务的 Audience，服务方校验 `aud` 确保令牌专卡专用。
- **请确认事项：** 统一认证服务是否原生支持 RFC 8707 `resource` 参数，使签发的 Access Token 严格绑定目标业务服务的 `aud` 声明？若一个换票请求中携带多个 `resource` 参数，IAM 的处理策略为何（签发合并多 aud 的单令牌，还是报错拒绝要求分别换票）？目标业务服务的 Audience 命名规范与注册约束为何？本轮包含模型网关；若不支持 resource，请说明可达到同等目标隔离的 audience/client 配置。
- **期望提供：** `resource` 协议参数规范、多资源换票行为说明及 Audience 配置文档。

#### CONF-IAM-15｜访问令牌形态（JWT vs Opaque）与资源服务验证方式

- **真实问题：** 模型网关需要验证当前用户的 Access Token；不能从 ID Token 的 RS256 样例推定 Access Token 格式与用途。
- **请确认事项：** 颁发的 Access Token 是自包含的 JWT 结构，还是需要向 IAM 反向查询的不透明令牌（Opaque Token）？模型网关等资源服务应采用“本地基于 JWKS 公钥验签”，还是调用 IAM 内省端点（Introspection Endpoint）？请给出 Access Token 的典型 Payload 结构（如 `sub`、`aud`、`client_id`、`exp`、`scope` 等）；若需调用 Introspection，IAM 对高并发内省查询的吞吐量与缓存推荐（如缓存 ≤60 秒）有何要求？资源服务本地验签时，若遇到未匹配的 `kid`，IAM 建议返回 503（密钥轮换中暂不可用）还是 401（认证失败）？
- **期望提供：** Access Token 真实 Payload 示例、Introspection 接口文档及高并发缓存优化建议。

### 第三组：令牌生命周期、并发与注销（运行安全与稳定性）

#### CONF-IAM-05｜访问令牌与刷新令牌有效时限（TTL）及管理端会话吊销

- **真实问题：** 客户端需根据 Access Token 与 Refresh Token 的生命周期规划自动续期与超时提示，并在用户退出时完成失效处理。
- **请确认事项：** Access Token 的标准有效时长是多久（请说明可配置范围及最坏授权窗口）？Refresh Token 的有效时长是多久（如 7 天、30 天，或具备滑动过期）？Refresh Token 是否有绝对最长寿命？在会话尚未自然到期前，系统管理员在 IAM 管理控制台是否有途径主动查询并强制吊销指定用户或终端的有效会话（客户端主动 API 撤销与 SSO 注销见 CONF-IAM-13、14）？
- **期望提供：** 令牌生命周期配置策略文档、会话超时规则及管理端强制注销渠道说明。

- **本轮补充：请给出 IAM 实际停用后的最坏阻断时延，以及刷新是否仍会成功。五分钟为端到端上限，包含同步、各层缓存与时钟容差，不预先指定 AT/RT 寿命；原提取的两小时 AT 不能单独证明达标。**

#### CONF-IAM-06｜令牌并发刷新、进程互斥与多端会话影响

- **真实问题：** 桌面客户端可能存在多进程并发调用受控研发服务；模型网关路线同样依赖可信人员授权，需核实刷新后代及多端隔离。
- **请确认事项：** IAM 服务端如何处理同一客户端短期内的并发 Refresh Token 请求？某一个并发刷新成功后，是否会导致并发中的其他请求失效？刷新某单一服务的令牌是否会波及同一用户在其他系统或浏览器的现有活跃会话？是否对同一用户的多端登录数量设上限或互踢策略？
- **期望提供：** 并发刷新处理机制说明、服务端的互斥或幂等设计建议。

#### CONF-IAM-12｜刷新令牌轮换（Rotation）、重用检测（Reuse Detection）与并发容忍

- **真实问题：** 现代安全规范（RFC 9700 / BCP 240）建议对 Public Client 实行 Refresh Token Rotation（每次刷新废除旧 Refresh Token 并下发新 Refresh Token），并对旧 Token 重用报警视为会话窃取。
- **请确认事项：** 企业 IAM 是否开启了 Refresh Token Rotation？每次刷新时是否必须传递 `offline_access` scope？公共客户端获取 Refresh Token 是否需要管理员同意或额外配置？服务端是否具备旧 Refresh Token 重用检测能力？一旦检测到重用，返回什么标准错误码（如 `invalid_grant`）？服务端是否存在短暂的时间窗口（Grace Period，如 5~10 秒），以容忍因网络抖动导致的并发刷新或响应丢包，避免误判为会话失陷而强制用户登出？
- **期望提供：** Refresh Token 轮换策略文档、重用检测处理逻辑及 Grace Period 配置说明。

#### CONF-IAM-13｜RFC 7009 令牌撤销（Token Revocation）端点与级联失效

- **真实问题：** 用户在研发助手点击“退出登录”或设备报失时，客户端必须向 IdP 发起主动撤销以阻断后续调用。
- **请确认事项：** IAM 是否提供标准的 RFC 7009 撤销端点（`/oauth/revoke`）？该端点支持撤销 Refresh Token、Access Token 还是两者均支持？撤销 Refresh Token 时，是否会级联使该会话下已签发的所有有效 Access Token 立即失效？撤销成功、撤销失败以及对已撤销令牌重复调用的 HTTP 状态码与响应体分别是什么（RFC 7009 要求对已撤销或无效令牌同样返回 200 OK）？从发起撤销到所有受控服务生效的最大延迟是多少？内省端点是否立即反映撤销结果？
- **期望提供：** RFC 7009 撤销端点接口规范、级联失效机制说明及状态码约定。

- **本轮补充：请说明能否只撤销当前设备对应的授权及所有轮换/并发产生的刷新后代，而不影响其他设备。服务端接受撤销（含异步入队）后五分钟内，已发及窗口内新发 AT 均不得用于新模型请求，RT 后代不得继续延长；需说明竞态、接受时间及完成证据。离线清理不是服务端成功，恢复后如何安全补偿待确认；随机安装实例标识不能作为撤销授权。**

#### CONF-IAM-14｜RP 发起注销（RP-Initiated Logout）与浏览器 SSO 会话联动

- **真实问题：** 员工在桌面客户端登出后，浏览器端的企业 SSO 会话若仍处于保持状态，其他人员在此电脑上重新点击登录可能无需输密直接登录旧账号。
- **请确认事项：** IAM 是否支持 OpenID Connect RP-Initiated Logout 1.0？注销端点（`end_session_endpoint`）调用时是否需要携带 `id_token_hint`？注销后的重定向地址 `post_logout_redirect_uri` 是否允许为 Loopback 地址（`http://127.0.0.1:<port>/iam/logout-callback`）且需提前登记？调用该端点后能否彻底终结系统浏览器中的全局企业 SSO 会话？在登录授权时是否支持传入 `prompt=login` 以强制用户重新输入凭据？是否支持 Back-Channel Logout 或 Session Management，以便客户端感知全局登出？若不支持 RP 登出，请区分其与单授权撤销的能力；本地清空不代表服务端授权已终结。
- **期望提供：** RP-Initiated Logout 接口说明、`prompt` 参数支持情况及登出最佳实践。

- **本轮补充：默认退出不终结浏览器全局企业 SSO，也不影响其他设备。请区分单授权撤销与 RP 全局登出；不能以全局登出来补足单授权撤销。重新登录时的账号选择/强制认证另说明；不预设所有退出都强制浏览器登出。**

### 第四组：目录同步、错误码与网络环境（运维与工程保障）

#### CONF-IAM-04｜员工组织关系权威源与离职/调岗权限变更时效

- **真实问题：** 企业安全与合规要求员工离职、调岗或冻结账号后，研发助手的企业模型与工具调用权限必须在可控时间内被切断；从 IAM 实际停用或网关封禁起五分钟内须拒绝新模型请求；HR 到 IAM 同步时延另计，人工工单不能替代该上限。
- **请确认事项：** 当员工在权威源中被禁用、离职或调岗后，该状态变更多久能同步至 IAM 认证中心与令牌颁发体系（通常同步周期与时延）？当账号状态置为停用或权限变更时，已签发未过期的 Access Token 是否具备服务端实时阻断手段（如分布式令牌黑名单或强制内省拦截）？
- **期望提供：** 组织架构同步机制说明、离职/冻结同步时延说明、令牌实时阻断机制。
- **备注（平台内部）：** 员工账号、工号与归属部门的权威数据源由平台组内部确认；面向下游系统（AI 网关）的停用出站联动规范见 CONF-IAM-19。

#### CONF-IAM-19｜SCIM 2.0 用户生命周期出站与停用联动

- **真实问题：** 离职/停用后若只依赖令牌自然过期与手工撤销，AI 网关个人凭据会保留到 TTL 结束，形成权限窗口；需确认 IAM 能否向 UAG 等下游系统出站同步。
- **请确认事项：** 是否支持通过 SCIM 2.0（RFC 7643/7644）向下游系统出站同步用户生命周期，尤其是通过标准 `PATCH` 或 `PUT` 请求将用户资源的 `active` 置为 `false`（用户资源端点 ID 段以 `{id}` 表示）？出站认证方式（OAuth client credentials / Bearer）、目标端登记与 IP/TLS 要求为何？从 HR/AD 停用到 SCIM 推送的时延、失败重试/退避/幂等/死信与全量对账机制如何？同步哪些字段（`userName`、`externalId`、`emails`、`groups`），若不同步 group 如何映射部门/团队？停用是否同时撤销该用户已签发的 IAM Access/Refresh Token 与浏览器 SSO 会话？SCIM 出站是否为独立模块或需额外许可？若产品不支持 SCIM 出站，是否有事件 webhook、LDAP 同步或定时对账等等效机制及各自时延？
- **期望提供：** SCIM schema、示例请求、错误处理说明、重试/对账机制与许可说明。

- **本轮补充：不强制 SCIM 作为唯一路径，请给出实际支持机制的端到端最坏时延；HR→IAM 与 IAM 实际停用→网关阻断分别测量，后者总计不超过五分钟。应用责任人停用如何通知责任交接，不能误作要求其在运行时在线。**

#### CONF-IAM-16｜端点错误码映射、限流保护与客户端重试约定

- **真实问题：** 客户端网络层需要依据精准的 HTTP 状态码与 OAuth 错误码，严格区分“偶发网络故障可自动重试”与“凭据失效/被盗必须阻断重登”，防止死循环刷新导致账号锁定或受控服务雪崩。
- **请确认事项：** 请提供 Authorize、Token、Refresh、Revoke 各端点返回的详细错误码映射（如 `invalid_request`、`invalid_client`、`invalid_grant`、`unauthorized_client`、`unsupported_grant_type`、`invalid_scope`、`temporarily_unavailable` 等）及对应的 HTTP 状态码。IAM 对认证与刷新接口的限流阈值是多少？触发限流时返回 429 还是其他状态码？是否包含 `Retry-After` 响应头？推荐的客户端超时时间是多长？`error_description` 是否可向用户展示？
- **期望提供：** 端点错误码详表、限流规则及推荐的客户端异常处理策略。

- **本轮补充：IAM、JWKS/内省或状态同步故障时，哪些缓存仍能同时保证授权有效和五分钟撤权？请给出最坏上限；不接受令牌过期或状态过旧后仍无限放行。**

#### CONF-IAM-17｜双端终端环境、网络代理、企业自签证书与终端管控策略【平台组内部确认】

#### 4.5.2 真实 ID Token 结构与 Payload 字段样例（内部团队验证，OCR 图 2 / 图 6 核验）

实测获取的 ID Token 由 IdP 私钥签名，签名算法固定为 `RS256`，有效期标准为 2 小时（7200 秒）：

```json
// Header
{
  "alg": "RS256",
  "kid": "iamsso"
}

// Payload（内部实测脱敏样例）
{
  "jti": "3fe2b0ec-4c6d-4339-be75-fbac609cb252",
  "iss": "http://<corp-iam-host>/esc-sso/oidc",
  "aud": "TST2",
  "exp": 1792662392,
  "iat": 1792655192,
  "nbf": 1792654892,
  "sub": "001902",
  "authType": "PWD",
  "sid": "59139C1F4DAC87429A79435BC55AFC380E92B197BEA44DA4FA533734330F21DF318242146087EFA7CCA7465F3F6BC38B308",
  "state": "",
  "nonce": "235689",
  "at_hash": "BySCCqzyFwaM+q7eEMcZ8Q==",
  "preferred_username": "001902"
}
```

**字段核验特征**：
1. **员工身份标识**：员工工号映射在 `sub` 及 `preferred_username` 字段（如 `"001902"` 或 `"001904"`）；ID Token 内不含部门与角色 Claim。用户类型由记录来源决定，内部回函明确其未在 ID Token 或 UserInfo 暴露，字段名、枚举、暴露方式与改写语义均待确认。sub 当前等于工号，仅在单账号生命周期内稳定；转正更换工号并新建账号时当前会更换 sub，终身稳定承诺待厂商书面确认，不能沿用旧账号授权。
2. **时钟与有效时限**：`exp - iat = 7200` 秒（整 2 小时）；`nbf` 较 `iat` 提早 300 秒（容忍 5 分钟客户端时钟倒退）。
3. **验签要求**：必须基于 `jwks_uri` 提取公钥验证签名，严格校验 `iss`、`aud`（等于分配的 client_id）、`nonce` 与有效时限。

#### 4.5.4 关键技术结论与架构影响分析（内部团队验证）

1. **退出登录闭环机制（CONF-IAM-13 & 14 组合应对）**：
   - *事实*：RFC 7009 撤销端点明确**不支持撤销 Refresh Token**，仅能撤销 Access Token。内部回函称支持 RP-Initiated Logout 端点，但“调用后能否彻底终结系统浏览器全局 SSO”在原文仍是待答问题，已发 AT/RT 是否级联也未证明。账号离职/禁用时 AT/RT 实时作废是内部回函口径；厂商 6.0.3 回函把“已发 AT 实时阻断”列为“需产品确认、按不具备规划”，两者冲突，V1 不按实时作废设计。
   - *当前评审影响（2026-10-28 复核）*：只撤 AT 加全局 RP 登出无法证明“当前授权及其全部刷新后代撤销、其他设备不受影响”。本地立即清理仍是必要动作；需由 IAM 补充单授权撤销能力和五分钟上限，缺失则相应路径不开放。

2. **业务分资源授权与模型网关验签（CONF-IAM-03 / 11 / 15 联动）**：
   - *事实*：Access Token 为**不透明令牌（Opaque Token）**，且 IAM 未提供标准 RFC 7662 内省端点，Token 内不包含 `aud` 或 `scope`；**不支持 RFC 8707 `resource` 参数**。内部回函称 IAM 另提供「令牌有效性校验接口」供业务系统查询阻断；厂商回函未确认该接口的正式端点、鉴权、容量与可用性，不能当作已交付能力。
   - *架构影响*：若该有效性回查接口可用，网关可据此阻断已作废/已过期令牌，把越权窗口从 2 小时 TTL 压到接口调用时延；但厂商未确认端点、鉴权、容量与故障语义，不能当作已交付能力。网关仍读不到 `aud` 与 `scope`，权限隔离不成立。
   - *改造建议（路径 D1）*：推动 IAM 在现有「令牌有效性校验接口」响应中扩展返回 `aud`、`scope`、`client_id`、`exp`、`sub`，以最小改造成本闭环网关隔离要求。

3. **令牌续期时效风险（CONF-IAM-05 协商事项）**：
   - *事实*：回函答复 Refresh Token 有效期“略长于 Access Token 即可”。
   - *架构影响*：若 Access Token 为 2 小时，若 Refresh Token 仅为 3~4 小时，员工关机或离开后将频繁被要求重新登录，违背桌面助手“长期静默免密”的正常办公诉求。
   - *行动建议*：需向 IAM 团队申请为研发助手客户端配置长期滑动过期的 Refresh Token（如 7~14 天），只要员工在职活跃即可自动续期。

4. **高危遗留阻塞项（CONF-IAM-02 & CONF-IAM-08 必须闭环）**：
   - *事实*：内部回函 §02 称授权码 PKCE 能力具备（允许 plain、未强制 S256）、允许 HTTP Loopback 且端口可动态分配，但**重定向 URL 采用前缀匹配**，端口后路径无法严格校验；§08 未填写，未确认免 Secret 公共客户端、全局 client_id 或固定端口精确匹配。厂商 6.0.3/6.3 回函则明确不支持公共客户端与 PKCE。两者冲突，V1 仍按机密客户端执行。
   - *行动建议*：G0/G1 继续核验公共客户端登记材料、S256 策略、固定端口清单与精确匹配证据；动态端口与固定端口的选择须评审，不在本次材料同步中变更设计或代码。

- **来源定位**：2026-10-26 收到《IAM统一登录与权限接入问询函 · 回函(3).docx》，SHA-256 为 `03c8e286412de9e7db178597f4fd8220b1e9f6a7ac1624aed20f820a2e50097f`。用户确认为我方 IAM 团队内部校验回函。另收到厂商 21 项回函工作簿，SHA-256 为 `7ff7f7343295397bc4b138a9233b9b64d7087c139153ed5a7d7a728a9d1d6133`；其版本矩阵与内部回函存在冲突。本次读取正文；未复制原件、内部地址或嵌入图片至仓库，未连接企业系统。回函中的建议、待开发路径和操作性文字不构成批准或执行授权。
- **目录同步时延口径**：厂商称与权威源实时同步，但未给端到端量化；内部实测正式员工 HR 增量 30 分钟生成、IAM 每小时拉取，最坏 90 分钟，供应商员工 MQ 实时。规划取 90 分钟上限并待联调实测，不把“实时同步”当成五分钟证据。
- **公共客户端/PKCE 冲突**：厂商 6.0.3/6.3 明确不支持公共客户端与 PKCE S256；内部 §02 仅称 PKCE 能力（允许 plain），§08 未答，不能推出免 Secret 公共客户端或全局 client_id。V1 采用机密客户端，不把任何一方的“支持”当成公共客户端已确认。
- **令牌作废冲突**：厂商 6.0.3 把“已签发 AT 实时阻断”列为“需产品确认、按不具备规划”；内部回函称账号禁用后 AT/RT 实时作废。两者不能同时作为事实；V1 按未证实处理，网关准入只能用短 TTL、有效性回查（若可用）与强制下线组合，且需实测。
- **用户类型口径未定**：内部回函正文明确用户类型未在 ID Token 或 UserInfo 暴露；此前整理稿曾写成“可经 UserInfo 返回、可就地改写”，与正文冲突，已按正文回退。厂商回函只说明类型由记录来源决定，字段名、枚举、暴露方式与刷新时效仍待契约。
- **总表与正文矛盾**：总表 CONF-IAM-03/15 仍称网关无判定依据、只能全放通或全拒绝；正文 §03/15 明确已有仅返回有效性的校验接口。本台账并列记录该冲突，按正文细化为“可回查有效性，受众与权限仍不可判定”；须由 IAM 责任人统一正式口径。接口存在不证明网关已经接入，更不证明当前调用人身份、DSH 用途及五分钟阻断均满足。
- **回调匹配待证**：正文 §02 称现网前缀匹配、端口可动态分配；另有材料称预登记固定端口列表后可精确匹配路径，但 §08 未填写、无配置或反向用例。需证明相似路径、额外后缀及未登记端口均被拒绝；本次不将此候选配置当成已验能力。
- **资源隔离建议未获批**：D1 扩展回查字段、D2 结构化 AT、D3 独立 client 与 D4 resource 均为改造候选，不是当前能力。文内同时出现 D1/D2 二选一与顺序依赖表，需澄清最小依赖。仅补字段不等于已建立可信资源绑定；网关必须实际校验受众，不能采用正文“网关漏校验时 aud 隔离仍成立”的断言。用户类型与资源受众也须分别明确语义，不能直接把类型塞入 aud 当成既定契约。
- **刷新与退出未闭环**：正文 §06 未填写，§12 仅称支持轮换与旧 RT 重用检测、返回 invalid_grant；所谓“仅作废对应旧 AT、无 Grace Period、并发仅首个成功”均不能作为已确认事实。须确认重用是否影响新 RT/AT、超时丢失响应的恢复方式。§14 只明确支持登出端点与不强制 id_token_hint；全局 SSO 终结、AT/RT 后代、传播时延和其他授权隔离均未证明，不能用全局登出替代当前设备这次授权退出。
- **错误码证据边界**：正文 §16 未填写；厂商回函只给标准错误码集，限流、Retry-After 与状态映射随对接文档交付。所谓“5 个自述实测场景”不在两份原始回函正文中，不能记为已确认。未实现限流不等于所有入口永不返回 429，前置代理/网关行为仍待确认。客户端不得因 200 或 302 就认定登录成功。
- **仍缺材料**：用户类型字段契约及暴露方式、虚拟用户维护接口鉴权与回收责任、有效性接口路径/鉴权/吞吐/缓存/故障上限、CONF-IAM-19/20/21 的接口与许可细节，以及责任人、部署版本和正式书面依据。虚拟用户能力不自动替代应用 Agent 受控开通及独立凭证要求。

## 5. 失败模式与平台侧处理（平台内部，不随函转发）

下表是能力缺口的处置原则，不是默认获准的降级方案。

| 能力缺口 | 处理要求 | 影响 |
|---|---|---|
| 不能安全登记公共原生客户端/PKCE | IAM 提供可核验等效安全路径；不得把共享 Client Secret 当作可保密凭据 | 接入关键前置未闭环，不开放 |
| 不支持 resource | 核验 audience/client 等效目标隔离；不能只加客户端 scope 文本 | 增量配置与成本待评审 |
| AT 为不透明令牌 | 确认内省容量、认证、缓存及故障规则 | 端到端五分钟仍须成立 |
| 只撤一个 AT、不撤刷新后代 | 要求单授权生命周期能力及竞态语义；本地擦除或全局 SSO 登出不足替代 | 当前设备退出不通过，不开放相应路径 |
| 停用联动或状态服务时延过大 | 核验可兑现的等效机制与窗口；手工工单、长寿命 Key 或旧缓存不作兜底 | 撤权要求不通过 |
| 不支持全局 RP 登出 | 不影响默认“只退出当前授权”的目标，但单授权撤销必须成立 | 不能把两类登出混为一谈 |
| 故障、审计或测试资料不足 | 明确未确认，记录责任、计划与影响；独立工作可继续 | 不以回函或离线测试代替准入证据 |

## 6. 核验与采用判据（平台内部，不随函转发）

- **独立转发性**：本轮 §9 可从“主题”至署名完整使用，按业务需求、原函覆盖、补充问题、答复与协调安排的顺序组织，不夹带内部参数方案或测试材料。

- **门禁对齐**：
  - **G0 门禁**：确认 OIDC 协议基线（01/02）、公共客户端模式（08）、MFA 基线（20）、资源隔离方向（03/11）、网关目标令牌验证方式（15）及初步联系人。

  - **G2 门禁**：完成全套测试账号矩阵演练（平台组内部组织，CONF-IAM-18），验证实际停用起五分钟阻断（04/19）、上游同步独立计时、令牌轮换与重用拦截（12）、当前授权及刷新后代五分钟撤销（13）、与全局 RP 登出隔离（14）、审计事件对接（21）及终端双端网络证书策略（17）。
- **结论严谨性**：仅在收到具备权限的责任人书面签字/正式邮件回函并完成实测后，方可将相应参数回写至 L3 接口契约，不以“口头答复”或“原则支持”作为门禁通过依据。

**主题：关于 DSH 登录及 IAM 与 AI 网关配合事项的补充确认**

IAM 团队：

结合企业内正在开展的 AI 网关实施，现对 DSH 的统一登录及模型调用补充以下需求。请对照原问询和前期答复，明确 IAM 已支持的内容、仍需核实的事项和实施安排。

这里的 **DSH 是我们面向企业研发场景定制化的 DeepSeek Harness**，员工使用公司 IAM 账号登录，用它辅助编码、代码评审和研发问答。本函请确认 IAM 能提供的身份、登录与凭证管理能力；涉及网关配合的，请列明条件，由企业内实施团队协调确认。

### 9.1 业务需求

- **确认当前是谁在使用。** 员工在 DSH 登录后，网关能可靠识别当前调用人。如使用个人 Key，张三不能使用李四的 Key；能登录公司账号，也不代表已经开通模型权限。账号改名或删除后重建，不能误认成另一个人。
- **个人研发与应用调用分开管理。** 个人研发统一使用 DSH。后台应用 Agent 则按应用和环境受控开通，记录创建人和使用责任，但运行时不要求创建人一直登录。员工在 DSH 中交互使用 Agent，仍按个人研发管理；应用凭证不能成为个人绕过 DSH 的入口。
- **停用后五分钟内阻止新调用。** 个人账号在 IAM 中实际停用，或网关管理员实际封禁个人、应用访问后，最迟五分钟内拒绝受影响的新模型请求，不能通过继续续期延长使用。这是到各网关节点拒绝新请求的总时限，各环节不能分别再加五分钟；HR 等人员系统到 IAM 的同步时间另计。创建人账号停用本身不直接等于应用停用；如当前责任人离职或停用，由责任团队办理交接或决定停用。已经由服务端接收、正在返回内容的请求可按原有最长执行时间结束，后续每次新请求都要重新检查。
- **退出默认只影响当前电脑的这次登录。** 本地立即停止企业调用、清理登录状态及运行时凭据副本，并取消本地在途请求。服务端受理撤销请求后，最迟五分钟内，退出前已取得的、以及利用这次旧登录状态继续续期得到的全部访问凭证都不能用于新请求；即使凭证被复制到别处使用，也适用同一时限。其他电脑的独立登录、浏览器中的其他企业系统、独立应用 Agent 不受影响，不默认撤销长期个人 Key。本地断开连接不代表后台一定停止生成，也不承诺已发生的调用不计费。
- **离线或故障时如实处理。** 离线退出仍立即完成本地清理，并提示服务端尚未确认；五分钟从服务端受理时开始计算。IAM 或相关服务发生故障时，只有仍能确认访问有效、并保证上述停用和退出时限的调用才可继续，否则应拒绝，不能改为只凭 Key 放行。
- **具备可核对的记录。** 能对应到具体员工或应用，查明登录、续期、退出、停用及网关拒绝结果；保留必要记录，不记录 Key、登录凭证或模型请求/响应正文。企业内团队与厂商共同完成实际环境中的验证。

以上说明业务效果，不预先指定技术实现。应用开通、IP 白名单、模型权限和额度等要求已在《DSH 和应用 Agent 调用 AI 网关补充问询函》列明；本函仅补齐 IAM 产品依据，网关侧能力另函确认，企业内实施团队汇总跨系统结论。
