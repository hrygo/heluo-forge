## 1. 结论

七封函按收件人的系统和决策职责分别成文，可独立复制，由用户填写并自行发送。正文不要求收件人理解项目内部编号、门禁或打开仓库；回函后仍需核验、联调和有权签署，不因回复“支持”自动准入。

## 2. 范围与非目标

本文只组织询问及回函，不替代各域技术契约。覆盖身份、网关与模型、DevOps、Gitee、IT、安全、PMO与业务七域；不代发、不申请真实凭据、不收集个人名单、不承诺排期、不代替团队批准，不扩大一期范围。

## 3. 现状与约束（平台内部，不随函转发）

范围仍为3部门800人、7类角色、Windows与银河麒麟各半，每人独立实例；23项需求、14项验收及6项指标不变。人数不是并发数，客户端治理不替代资源服务端授权；双端秘密隔离、企业接口和容量均未实测。正文采样7天、元数据180天只是未批准提议，未批准不启用正文采样。

| G0 | 方案方向及负责人 | 方向、责任、依赖及测试计划；P0要求的前置实测另交证据，不以回函替代 |

### 4.2 IAM 团队询问函

**主题：** 请确认研发助手的统一登录、分资源授权及联调安排

**主送：** 企业身份与访问管理（IAM）团队，答复岗位/联系人：[发函人填写]

**发函日期 / 回函期限：** [发函人填写] / [发函人填写]

我们拟为本机研发助手接入企业统一登录，由系统浏览器完成授权，再分别访问模型和工程服务。贵团队负责身份与令牌签发，请确认客户端登记、资源隔离、令牌生命周期和联调条件；本函为确认请求，不代表已承诺或批准。

| 问题ID | 请确认事项 |
|---|---|
| CONF-IAM-01 | 现有服务是OAuth授权，还是兼有OpenID Connect（OIDC）身份认证？可提供哪些发现、验签、受保护身份查询或令牌内省能力？纯OAuth时如何取得可信用户身份，而不把访问令牌当作身份令牌？ |
| CONF-IAM-02 | 是否支持不内置客户端密钥的授权码登录、PKCE S256（防授权码截获校验）、系统浏览器及`127.0.0.1`回调？注册、动态/固定端口和回调防伪有何要求？两类流程均校验state，OIDC另做相应身份令牌校验。 |
| CONF-IAM-03 | 授权与刷新是否支持按目标服务申请令牌（RFC 8707 resource）？若不支持，能否按目标受众audience注册多个客户端，仍保持一资源一令牌？替代方式是否增加授权交互，权限范围如何限定？ |
| CONF-IAM-04 | 稳定用户标识及部门/角色的权威来源是什么？转组、停用、离职或角色缺失多久传播、如何处理？客户端角色不作业务授权依据，请确认各资源服务端仍独立核权。 |
| CONF-IAM-05 | 访问/刷新令牌有效期、最长会话、轮换、重用检测、撤销及生效延迟是什么？请区分客户端退出与已签发令牌失效。访问令牌不超过60分钟仅为我方建议，请给现值或可行替代。 |
| CONF-IAM-06 | 多资源使用共享还是独立刷新凭据？刷新一个资源会否替换其他资源所需凭据、收窄权限或使旧令牌失效？双进程并发、网络失败及授权失效时应如何串行刷新、重试或重新登录？ |
| CONF-IAM-07 | 谁负责登记、身份映射和撤销链路？测试环境、最小权限测试身份的受控申请方式、联调窗口及依赖计划是什么？请勿在回函中附真实凭据。 |

**请提供：** 脱敏协议/注册说明、占位身份与资源权限样例、刷新/轮换/撤销及失败处理说明、测试申请方式。先确认方向、负责人和窗口；接口联调前明确参数与生命周期，试点开放前确认正式注册和泄漏处置流程。

**回函请按编号填写：** 结论（支持/有条件/不支持/待验证）、限制或替代、材料编号/版本、责任岗位、完成计划及待协调事项。

感谢协助；不具备的能力请直接说明，我们据此调整接入路径。
