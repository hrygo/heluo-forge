## 1. 结论（平台内部）

插件市场方案：使用企业私有 npm 作为唯一安装包来源，由 CI 自动检查并收录兼容的稳定版插件。
本问询函用于向企业 npm 私服管理员、CI 运维及终端团队**摸底确认现有基础设施能力**，不要求对方新增系统或采购产品。

## 2. 确认范围（平台内部）

- **确认事项**：私有 npm 入口与网络限制、版本不可变（防篡改）、CI 流水线排他与定时调度、静态索引托管、Windows / 银河麒麟终端基线。
- **免责与边界**：无需新建复杂的审批后台，只需确认既有系统的配置、命令输出或管理规则。

## 3. 使用说明（平台内部）

1. 仅复制 §4 中从“主题”到署名的正文发送给对接团队，内部说明及门禁信息不随函转发。
2. 涉及敏感内网地址或凭据时请走企业受控渠道，回函中请使用脱敏占位符。
3. 若某项能力暂不支持，请如实告知，平台将据此调整方案或关闭对应特性。

## 4. 正文（可独立转发）

### 主题

插件市场企业接入与基础设施能力确认（私有 npm、CI 与终端基线）

### 背景与目的

我们计划在企业内网落地 DSH 编程助手的插件市场，方便内部开发者下载并安装自研与精选插件。
所有插件安装包统一走企业私有 npm 制品库，并通过 CI 流水线自动完成兼容性检查与索引发布。
为了确保插件能安全下载且不引入网络与供应链风险，需要贵团队协助确认内网私有 npm、CI 流水线以及客户端环境的现有能力。

### 问题清单

**A. 私有 npm 与网络策略**

- **E-01 私服地址与公网回源**：企业私有 npm 的内网访问 URL 是什么？如果内网找不到某个依赖包，私服是否会回源到公网拉取？（内网安全要求：内部插件不得回落公网拉取）。
- **E-02 证书与网络链路**：客户端拉取包是否需要配置企业自签 CA 证书或走特定的网络代理？是否存在 HTTP 重定向？
- **E-03 读写认证方式**：CI 自动拉包和发布包分别使用什么认证方式（Token 或服务账号）？是否支持最小权限配置（如仅授予指定 Scope 的写入权限）？

**B. 权限与版本防篡改**

- **E-04 访问控制与拦截**：私服能否按包名或 Scope 限制访问？若某个插件被下线或未在白名单内，私服能否直接拒绝下载？
- **E-05 版本防篡改（不可变）**：同一个包的同一版本号（例如 `plugin@1.0.0`）发布后，私服是否禁止重复上传覆盖？若需撤回或误删恢复，流程是怎样的？

**C. CI 流水线与托管**

- **E-06 CI 排他与调度**：现有 CI 流水线是否支持任务排他锁（单写防冲突）、运行中取消、定时调度及失败告警？
- **E-07 静态索引托管**：插件市场的索引文件（JSON）存放在哪套内网 HTTP/HTTPS 静态服务？更新时是否支持原子替换？

**D. 终端与发行预置**

- **E-08 终端操作系统基线**：企业开发人员常用的 Windows 版本与银河麒麟（ARM64）系统基线是什么？系统预装的 Node/环境版本是什么？
- **E-09 客户端预置与展示资源**：统一分发的客户端能否预置核心市场插件？自研插件的中英文名称、图标由谁验收？

### 回函方式

请对上述问题逐项给出：**结论**（支持／不支持／部分支持）、**实际配置或证据**、**前提限制**及**责任人**。
