## 1. 结论

- 能力基线按 ADR-32 固定为 IAM 6.0.3 版本反馈，最新评审（2026-11-21 V0.3）作为**问题清单的来源**，不作为能力事实的来源：它据厂商回函得出的“不支持 public/PKCE”“回调须逐字精确匹配”等结论，与企业团队较新日期的书面答复冲突时不采信。
- 本函提出 **9 项**需 IAM 书面确认。截至 2026-11-23，**3 项已答复**（授权参数处理、回调边界、密钥生命周期），**6 项待答复**：多实例档位、会话失效通知、UserInfo 字段、有效性回查、五分钟撤权，以及随回调缺口新增的 `redirect_uri` 校验整改。
- 已答复的三项改变了设计前提：S256 可正常发码（省略参数会退化为 `plain`）；OIDC 授权流程**不校验** `redirect_uri`；`client_secret` 轮换与回滚各有至少 2 分钟传播窗。前两项按 [ADR-33](../architecture/platform-architecture.md#14-架构决策记录) 把回调合法性移到客户端、由 S256 兜底。
- 最新评审的 12 项遗漏点中，5 项转为对 IAM 的具体问题，3 项由 6.0.3 反馈直接结案，2 项属我方改动，2 项转 AIGS 演进线（对应见 §5）。
- 同一版本内答复冲突时取企业 IAM 团队较新日期的书面答复；无先后可取时按“不假设能力存在”处理。该规则记录在 [ADR-32](../architecture/platform-architecture.md#14-架构决策记录)，如需改优先级由此处修订。
- 我方接入基线维持机密客户端；答复只影响回调形态、身份字段、密钥运维与网关判权方式，不改变登录路径本身。

## 2. 能力基线（IAM 6.0.3 反馈为准）

下表是设计与配置所依据的能力集合，全部来自本仓库已登记的企业书面答复。写法为“能力结论 + 依据编号”，不重复原文。

| 域 | 6.0.3 反馈结论 | 依据 | 我方据此的配置或设计 |
|---|---|---|---|
| 客户端登记 | 按应用登记，不支持按范围（部门/批次）区分；全企业共用一个 `client_id`。我方范围前提为仅 DSH 使用、不与其他应用共用 | 最终确认函 1.1、C1 | 单客户端冻结；租户/部门级隔离不作为前提 |
| 密钥生命周期 | 支持系统随机生成与人工输入，均需后管手动操作；无推送机制；更新后旧 secret 最迟 2 分钟失效；不支持新旧并存；回滚靠重填旧值 | E3（§4.5.9）、最终确认函 1.2、D2 | 终端预置、IAM 不分发；轮换与回滚各留 2 分钟传播窗，窗口内暂停刷新 |
| 客户端认证 | 刷新必须携带 `client_secret`，缺失在刷新令牌校验前返回 401 | C2、问询函 §4.5.4 | 机密客户端为登录基线（ADR-31） |
| PKCE | S256 可正常发码；`plain` 与 `S256` 均可用、不强制；省略参数时按 `plain` 处理；厂商 6.0.3 回函所称“不支持 PKCE”与实测不符 | E1（§4.5.9）、问询函 §4.5.4 | 固定使用 S256 且显式携带参数，不提供 `plain` 降级 |
| 回调登记 | 管理台按前缀登记（`http://127.0.0.1:`、`http://127.0.0.1/`，`https` 可用；固定端口与多端口另行支持）。OIDC 授权流程**不校验** `redirect_uri`，登记不产生拒绝；OAuth 流程才校验 | E2（§4.5.9）、最终确认函 1.3、2026-11-06 补充确认 | 登记只作留痕；回调合法性由客户端校验，S256 为唯一边界（ADR-33） |
| HTTP 回环 | 生产允许 HTTP loopback，无额外白名单、终端管控或审批 | 最终确认函 1.4 | 不引入额外终端策略前提 |
| 访问令牌 | 不透明令牌，`7200` 秒；不含 `aud`/`scope`；无标准内省端点（RFC 7662）；另有“令牌有效性回查接口”，端点与容量未答 | 问询函 §4.5.2、§4.5.4 | 网关判权只用有效性回查＋短 TTL＋事件通道，不假设 JWT 验签 |
| 刷新令牌 | 滑动 `7300` 秒、无绝对有效期；每次刷新重新计时；轮换并即时作废旧值；重用返回 `invalid_grant` 且仅拒绝当次；并发首个成功、其余 `invalid_grant`；刷新成功后旧 AT 实时作废 | C9、C10、C11、D3、最终确认函 3.4 | 锁内 pending、锁外单飞刷新；收到 RT 缺失即要求重登 |
| 撤销 | 仅 `GET /idp/oauth2/revokeToken?access_token=...`：不校验调用方、令牌自证、幂等、实时；成功 `result=true`，失败 `result=false` + `errcode=2002`；只能撤访问令牌，RT 不可撤销 | D1、C3、C4 | 退出用 `access_token_query`；界面与审计区分“AT 已撤销 / RT 未撤销” |
| 全局登出 | RP 登出作用于当前浏览器会话，其他会话不受影响；同会话内其他应用令牌一并作废 | C6、C7、§4.5.1 | 默认不调用全局登出；只用按令牌撤销 |
| 会话失效通知 | 无 back-channel logout 或会话失效推送的记录；门户退出后客户端能否感知未答 | 答复未见（负向） | 不假设能感知；以短 TTL 与主动撤销兜底，见 FB-IAM-05 |
| 身份 | `sub` 即工号；改名、转岗、禁用再启用不变；离职再入职为新账号；ID Token 不含部门与角色，也无独立 `employee_id` | C8、问询函 §4.5.2 | 属主绑定只用 `sub`；审计不跨账号合并 |
| 多实例 | 同一员工多端登录“支持”，未说明并存、后踢前还是先占 | 最终确认函 3.3 | V1 不依赖多端策略；档位待 FB-IAM-04 |
| UserInfo | 工号、姓名分别位于 `work_no`、`pinyin`（2026-10-28 答复）；另有 `employeeNumber`/`name`/`givenName` 的旧记录，两口径未闭拢 | 最终确认函 3.2、问询函 §4.5.1 | 映射配置化、默认不投影；字段见 FB-IAM-06 |
| 签名与密钥 | 仅 `RS256`，`kid=iamsso`，明确不支持 JWKS 轮换 | 问询函 §4.5.2、§4.5.3 | 公钥静态缓存；不实现密钥轮换适配 |
| 分资源授权 | 不支持 RFC 8707 `resource`；未登记参数（`resource`、`login_hint`、额外 scope）被静默忽略；访问令牌不含 `aud`/`scope` | E1（§4.5.9）、问询函 §4.5.4 | `gatewayResource` 留空；不以参数是否报错判断其是否生效 |
| 授权范围 | 换票响应直接返回 `refresh_token`，未把 `offline_access` 列为必要条件 | 问询函 §4.5.1 | 模板显式设置 scopes；插件默认值含该项，必须显式覆盖 |
| 目录同步 | 厂商称实时；内部实测 HR 增量 30 分钟生成、IAM 每小时拉取，最坏 90 分钟；供应商员工走 MQ | 问询函 §4.5.5 | 规划按 90 分钟上限，不以“实时”为依据 |
| 错误与限流 | 正文 §16 未填写；仅标准错误码集，限流与 `Retry-After` 随对接文档交付 | 问询函 §4.5.5 | 不假设 429 与重试语义，按未知处理 |

| 回调须逐字精确匹配 | 与 6.0.3 反馈（前缀登记、端口可随机）不符；固定端口精确匹配只是可选形态 |
| 机密客户端来源缺失、官方行未补全 | 与本仓库当前实现不符，剩余工作是终端预置与登记，不再是 IAM 侧问题 |
| 6.3.0 与 6.0.3 的差异说明 | 基线已固定 6.0.3；6.3.0 差异待版本升级立项时另行问询 |

## 7. 答复方式与判据

| 项 | 要求 |
|---|---|
| 格式 | 按 FB-IAM-01~08 编号逐条；每条给出结论、依据（配置项或文档章节）、已知限制 |

## 8. 未验证声明

本函的全部判断来自本仓库静态代码与既有答复记录，未连接目标 IAM 与企业网关，未做任何真实换票、撤权或回调验证。§2 的能力基线是**书面答复层面的基线**，不是实测结论；任何一项在企业环境跑通前，都不构成准入证据。
