## 1. 拟发正文：背景与需求

**主题：关于 AI 网关实施中 DSH 和应用 Agent 调用需求的补充确认**

AI 网关团队：

结合行内正在开展的 AI 网关实施，现补充 DSH 和应用 Agent 的模型调用需求。请对照下述场景，确认网关支持情况、实施安排和需要补充的能力。

这里的 **DSH 是我们面向企业研发场景定制化的 DeepSeek Harness**，员工使用公司 IAM 账号登录，用它辅助编码、代码评审和研发问答。统一使用 DSH，是为了形成一致的研发方法，减少多套工具带来的维护工作；同时，也要支持应用中的 Agent 自动调用模型。

前期材料已介绍用户通过 IAM 登录网关控制台、创建 API Key（下文简称 Key）的方式。以下在此基础上说明两类场景的具体需求，不预先指定实现方式。涉及 IAM 配合的，请说明网关需要哪些身份信息、状态或接入条件，由行内实施团队协调确认。

### 1.1 场景一：员工通过 DSH 使用模型

员工在自己的电脑上登录 DSH，进行日常研发。具体需求如下：

1. **个人只能使用自己的 Key。** 例如，张三登录 DSH 后，只能使用张三的 Key；即使填入李四的 Key，也应被网关拒绝。不能只在创建 Key 时登记归属，还需要在调用时确认使用人。
2. **这类访问只允许通过 DSH。** 不能把个人 Key 直接配置到其他编程助手中使用。识别 DSH 采用简单、可维护的方式即可；首期不要求防范有权限的人刻意复制全部凭据、仿冒 DSH。
3. **用户可以选择设置 IP 白名单。** 用户可以给自己的访问增加来源限制，但不能放宽企业统一的网络要求。
4. **登录与模型开通分开管理。** 能登录 DSH，不代表已经获准使用模型；模型权限和个人、团队额度仍由网关管理。一个人使用多台电脑或更换 Key，不能重新获得一份个人额度。

以上按目前已有的 Key 使用方式描述需求。如现有产品有更简便的方式，能够确认使用人并达到同样效果，请一并提出，不要求必须保留个人静态 Key。

### 1.2 场景二：应用中的 Agent 自动调用模型

例如，一个后台应用需要持续调用模型，此时没有员工在 DSH 中操作。这类调用与员工日常研发分开管理，具体需求如下：

1. **为指定应用和环境单独开通。** 例如，同一应用的测试环境与生产环境分别使用各自的凭证。
2. **开通需要审批或由获授权的管理员办理。** 普通用户不能自行开通一个不受限制的应用 Key，再拿去其他编程助手使用。
3. **记录创建人及使用责任。** 保留最初创建人，同时明确责任团队和当前责任人。人员变化时可以交接，不能留下无人负责的应用凭证。
4. **调用时不要求创建人在线。** 运行时按已批准的应用使用要求判断，不要求创建人保持 IAM 或 DSH 登录。创建人退出 DSH，不应直接中断独立应用的正常调用；责任人离职时须办理交接或决定停用。
5. **默认设置 IP 白名单。** 只允许指定的应用出口 IP 访问；确需不设白名单或放宽限制时，由有权限的人审批。
6. **默认有效期为 90 天。** 更长时间需审批；支持人工更换、撤销和责任交接。更换时可以安排必要的短暂停用时间，不要求零中断。

员工在 DSH 中交互使用的 Agent，仍按场景一管理，不能因为叫“Agent”就改用不受个人研发限制的凭证。

### 1.3 两类调用还需满足的使用与管理要求

- **停用后及时阻止新调用。** 个人账号在 IAM 中实际停用，或网关管理员实际封禁个人、应用访问后，最迟五分钟内拒绝受影响的新模型请求，不能通过继续续期延长使用。这是从上述起点到各网关节点拒绝新请求的总时限，各环节不能分别再加五分钟。HR 等人员系统到 IAM 的同步时间另计。创建人账号停用本身不直接等于应用停用；如当前责任人离职或停用，由责任团队办理交接或决定停用。应用被实际封禁后适用上述时限。
- **退出 DSH 默认只结束当前电脑的这次登录。** 本地立即停止企业调用、清理登录状态及运行时凭据副本，并取消本地正在进行的请求。服务端受理这次登录的撤销请求后，最迟五分钟内，这次登录已取得的、以及利用旧登录状态继续续期得到的全部访问凭证，都不能再发起新请求；即使凭证被复制到别处使用，也适用同一时限。其他电脑的独立登录、浏览器中的其他企业系统和独立应用 Agent 不受影响，不默认撤销长期个人 Key。
- **离线退出要如实提示。** 本地可以立即退出，但应提示服务端处理尚未确认。上述五分钟从服务端受理时开始计算，不能从离线点击退出时开始承诺。
- **已经接收的请求与后续请求分开处理。** 服务端已经接收、正在逐步返回内容的请求，可以按现有最长执行时间结束；后续每次新的模型请求都应重新检查。用户本地取消连接，不代表后台一定已停止生成，也不要求已发生的调用免费。
- **故障时不能省略必要检查。** IAM 或相关服务故障时，只有仍能确认访问有效、并保证上述停用和退出时限的请求才可继续；否则应拒绝，不能改成只检查 Key 就放行。
- **统一在网关控制台管理。** Key、应用开通、审批、IP 白名单、更换和责任交接都在网关侧管理。DSH 展示状态、错误提示及控制台入口，不再建设一套管理后台。已有到期提醒等功能可以直接复用，不要求另建自动更换系统。
- **保留必要的用量和操作记录。** 能查到谁或哪个应用调用了什么模型、用了多少额度，以及谁办理了开通、变更或交接。模型请求只转到机构内的模型服务；网关和模型服务均关闭请求、响应正文的日志记录，不记录 Key 等秘密信息。

## 2. 请逐项确认是否支持

请网关团队按以下编号回复。已支持的说明配置和适用版本；不能完全支持的说明网关侧差距、处理建议和实施安排。需要 IAM、模型服务或其他行内系统配合的，请列明所需条件，由行内实施团队协调核实。

### CONF-GW-09｜能否限制个人只能使用自己的 Key？

是否支持场景一的“张三登录后不能使用李四的 Key”？调用时能否确认当前使用人，并与 Key 归属核对？DSH 与网关中的账号如何对应，账号改名或删除后重建是否有影响？如果不用个人 Key 也能达到同样效果，请介绍现有方式。

### CONF-GW-10｜能否让个人研发访问只用于 DSH？

是否支持把个人研发访问限定给 DSH，使 Key 直接放入其他编程助手时不能使用？用户决定沿用 DSH 默认 User-Agent，不替换客户端标识；网关侧以包含 `deepseek-harness` 子串作为候选识别方式，请确认是否支持及适用的调用入口。请说明匹配是否区分大小写，以及缺失、空值、重复 User-Agent、多个值、格式异常和边界情况如何处理，提供允许与拒绝的脱敏示例。此识别不能替代当前使用人身份验证及 Key 归属核对。首期接受有权限者刻意仿冒的风险，不要求复杂的防伪机制；上述候选方式尚未经网关确认或联调验证。

### CONF-GW-11｜能否为应用和环境分别开通自动调用？

是否已有适合后台应用 Agent 的账号或凭证管理功能，可以按应用、环境分别开通，且不要求创建人持续登录？能否避免个人 Key 和应用 Key 换一个调用入口后就绕过各自限制？

### CONF-GW-12｜能否控制应用开通、变更和责任交接？

是否支持由管理员或获授权人员审批、开通应用调用？普通用户能申请什么、修改什么？能否防止其自行改为不受限制的通用 Key，并记录审批、变更和责任交接过程？

### CONF-GW-13｜能否分别管理模型权限和额度？

是否支持登录成功后仍需单独开通模型权限？个人、团队和应用分别如何设置额度？同一员工多设备使用或更换 Key 后，能否继续共用同一份个人额度？是否能提供按人去重的首次调用、日活等统计？

### CONF-GW-14｜能否设置上述两类 IP 白名单？

是否支持个人自选增加 IP 限制，以及应用默认限制出口 IP、例外需审批？支持单个 IP 还是地址段，由谁修改？经过代理或转发时，能否判断实际访问来源，防止只靠调用方自己填写的 IP 就通过检查？

### CONF-GW-15｜停用或封禁后，能否在五分钟内阻止新调用？

是否支持 §1.3 的五分钟要求？请说明网关如何获知并处理人员停用、各节点最迟何时生效，以及继续续期是否会延长使用时间。请给出网关侧同步、缓存及相关处理的最坏耗时，并列明满足总时限所需的 IAM 配合条件；HR 到 IAM 的同步时间由行内实施团队另行核实。应用凭证实际封禁的处理请一并说明，不能将人员停用与应用停用混为一谈。

### CONF-GW-16｜退出 DSH 时，能否只结束当前电脑的这次登录？

是否支持 §1.3 的退出要求？服务端受理撤销请求后（包括受理后排队处理），能否在五分钟内阻止这次登录取得的、以及利用旧登录状态反复续期得到的全部访问凭证继续使用，同时不影响其他电脑的独立登录、全局企业登录及独立应用？被复制到其他位置使用的这次登录凭证也应失效，不能仅以设备标识或 IP 判断退出范围。请说明网关如何使相关访问失效、能提供哪些处理结果，以及需要 IAM 和 DSH 配合的条件。离线退出恢复网络后，网关能否配合安全补办、如何反馈结果？未确认前由 DSH 提示服务端尚未完成确认。

### CONF-GW-17｜IAM 等服务故障时，能否仍守住使用限制？

能否按调用类型继续确认个人身份或应用资格、允许用途和有效状态，并保证停用、退出的五分钟时限？可以继续多久，哪些情况必须拒绝？是否会出现检查失败后只凭 Key 继续放行的情况？

### CONF-GW-18｜能否管理应用 Key 的有效期和更换？

是否支持默认 90 天、更长需审批、到期失效、人工更换、主动撤销及责任交接？已有到期提醒吗？更换时能否新旧 Key 短时并存，还是需要安排短暂停用？两种方式均可说明，不要求零中断。

### CONF-GW-19｜正在返回内容的请求，取消或报错后如何处理？

是否支持按 §1.3 区分已经接收的请求与后续新请求？请说明最长执行时间、本地取消后后台是否继续生成及如何计费。错误信息能否区分登录、Key、权限、IP、额度和服务故障？网关是否会自动重试，调用方怎样避免重复请求、重复扣费？

### CONF-GW-20｜能否满足记录要求，需要多少改动和投入？

两类调用是否都能提供必要的用量、操作记录，并在网关及模型服务关闭请求/响应正文日志？请说明哪些能力已有、哪些需配置或开发，能否复用控制台管理；如采用不同接入方式，是否都能满足同样要求？还请说明对容量、响应时间和可用性的影响，以及开发、许可、联调和后续维护的投入。

每项回复请列明：**是否支持、适用版本、限制、配置说明或脱敏示例**。涉及其他系统的，请分别列出网关已具备的能力、所需配合条件及尚待核实的事项。需要补充配置、联调或开发的，请明确负责人、预计时间和额外费用。对尚不能确定的事项，请列出待核实内容及反馈安排。

请将上述需求纳入当前 AI 网关实施评估，明确网关侧对接人和联调安排。行内实施团队负责协调相关系统，并组织确认接入方式和验收安排；暂不能满足的关键要求，应列入问题清单并明确处理计划，相应调用在问题解决前暂不开放。

### 3.1 跨函问题对应与协调（平台内部）

以下仅供行内实施团队汇总两侧答复，不随网关正文转发。网关函面向网关团队，IAM 补充确认面向 IAM 团队；两侧各答自身能力与配合条件。共同事项由实施团队按下表关联证据、形成一份端到端结论，已有明确答复直接引用，不重复索取资料。

| 共同事项 | 统一结论记在哪一项 | IAM 侧需补充的依据（沿用原编号） | 网关侧需确认的结果 |
|---|---|---|---|
| 当前人员识别及个人 Key 归属 | CONF-GW-09 | CONF-IAM-03/09/10/11/15：可验证的调用人身份、跨系统对应、目标服务区分 | 在实际模型调用中验证身份；如保留 Key，核对归属；CONF-GW-13 复用同一人员对应关系管理额度 |
| 停用、封禁的五分钟时限 | CONF-GW-15 | CONF-IAM-04/05/16/19：实际停用、状态传递、续期限制及最坏耗时 | 各节点在总时限内拒绝新请求，列出网关实际封禁的起点 |
| 当前这次登录的退出及离线处理 | CONF-GW-16 | CONF-IAM-05/06/12/13/14/16：撤销范围、续期凭证处理、受理及结果确认 | 受理后五分钟内拒绝该次登录及其续期凭证，不误伤其他独立登录 |
| IAM 或验证、状态服务故障 | CONF-GW-17 | CONF-IAM-09/15/16：可用验证信息、有效期限、故障与恢复的处理 | 明确可继续与必须拒绝的条件，满足停用、退出时限，不降为仅凭 Key 放行 |
| 应用责任及人员变动 | CONF-GW-12（关联 11/18） | CONF-IAM-10/19：稳定人员信息、停用或人员变动如何提供 | 应用开通与责任交接、停用记录；应用调用不依赖创建人保持登录 |
| 错误、记录与实际验证 | CONF-GW-19/20，分别记录错误处理及记录、投入结论 | CONF-IAM-07/16/17/18/21：IAM 错误与记录查询、产品侧联调条件 | 说明网关对应结果；同一组联调用例和证据引用一次即可 |

IAM 本机登录、客户端登记和日常续用等独立事项仍归原 CONF-IAM 编号；DSH 用途、应用开通、IP、额度及应用凭证有效期归网关对应编号。DSH 平台组负责客户端接入、本地退出及状态、错误展示；服务端撤销、身份验证及调用拦截由相应产品落实。行内实施团队负责协调依赖、行内政策、环境和模型服务配置，并组织验收，不能以客户端清理代替服务端失效验证。
