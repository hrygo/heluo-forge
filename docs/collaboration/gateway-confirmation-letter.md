## 1. 拟发正文：背景与需求

**主题：关于 AI 网关实施中 DSH 和应用 Agent 调用需求的补充确认**

AI 网关团队：

结合当前正在开展的 AI 网关实施，现补充 DSH 和应用 Agent 的模型调用需求。请对照下述场景，确认网关支持情况、实施安排和需要补充的能力。

这里的 **DSH 是我们面向企业研发场景定制化的 DeepSeek Harness**，员工使用公司 IAM 账号登录，用它辅助编码、代码评审和研发问答。统一使用 DSH，是为了形成一致的研发方法，减少多套工具带来的维护工作；同时，也要支持应用中的 Agent 自动调用模型。

前期材料已介绍用户通过 IAM 登录网关控制台、创建 API Key（下文简称 Key）的方式。以下在此基础上说明两类场景的具体需求，不预先指定实现方式。涉及 IAM 配合的，请说明网关需要哪些身份信息、状态或接入条件，由实施团队协调确认。

### 1.1 场景一：员工通过 DSH 使用模型

员工在自己的电脑上登录 DSH，进行日常研发。具体需求如下：

1. **个人只能使用自己的 Key。** 例如，张三登录 DSH 后，只能使用张三的 Key；即使填入李四的 Key，也应被网关拒绝。不能只在创建 Key 时登记归属，还需要在调用时确认使用人。
2. **这类访问只允许通过 DSH。** 不能把个人 Key 直接配置到其他编程助手中使用。识别 DSH 采用简单、可维护的方式即可；首期不要求防范有权限的人刻意复制全部凭据、仿冒 DSH。
3. **网络要求以企业基线为准。** 个人访问遵守企业统一的网络要求；个人自选加严来源限制属可选能力，本期不作为要求。
4. **登录与模型开通分开管理。** 能登录 DSH，不代表已经获准使用模型；模型权限和个人、团队额度仍由网关管理。一个人使用多台电脑或更换 Key，不能重新获得一份个人额度。

以上按目前已有的 Key 使用方式描述需求。如现有产品有更简便的方式，能够确认使用人并达到同样效果，请一并提出，不要求必须保留个人静态 Key。

### 1.2 场景二：应用中的 Agent 自动调用模型

例如，一个后台应用需要持续调用模型，此时没有员工在 DSH 中操作。这类调用与员工日常研发分开管理，具体需求如下：

1. **为指定应用单独开通。** 每个应用使用自己的凭证，不与其他应用共用；本期只对接一个环境，测试与生产分别开通不作为要求。
2. **开通需要审批或由获授权的管理员办理。** 普通用户不能自行开通一个不受限制的应用 Key，再拿去其他编程助手使用。
3. **记录创建人及使用责任。** 保留最初创建人并明确责任团队，不能留下无人负责的应用凭证。
4. **调用时不要求创建人在线。** 运行时按已批准的应用使用要求判断，不要求创建人保持 IAM 或 DSH 登录。创建人退出 DSH，不应直接中断独立应用的正常调用；创建人离职或停用时，由责任团队决定是否停用该应用凭证。
5. **默认设置 IP 白名单。** 只允许指定的应用出口 IP 访问；确需不设白名单或放宽限制时，由有权限的人审批。
6. **默认有效期为 90 天。** 更长时间需审批；支持人工更换与主动撤销。

员工在 DSH 中交互使用的 Agent，仍按场景一管理，不能因为叫“Agent”就改用不受个人研发限制的凭证。

### 1.3 两类调用还需满足的使用与管理要求

- **停用后及时阻止新调用。** 个人账号在 IAM 中实际停用，或网关管理员实际封禁个人、应用访问后，最迟五分钟内拒绝受影响的新模型请求，不能通过继续续期延长使用。这是从上述起点到各网关节点拒绝新请求的总时限，各环节不能分别再加五分钟。HR 等人员系统到 IAM 的同步时间另计。创建人账号停用本身不直接等于应用停用；创建人离职或停用时由责任团队决定是否停用该应用凭证。应用被实际封禁后适用上述时限。
- **退出 DSH 默认只结束当前电脑的这次登录。** 本地立即停止企业调用、清理登录状态及运行时凭据副本，并取消本地正在进行的请求。服务端受理这次登录的撤销请求后，最迟五分钟内，这次登录已取得的、以及利用旧登录状态继续续期得到的全部访问凭证，都不能再发起新请求；即使凭证被复制到别处使用，也适用同一时限。其他电脑的独立登录、浏览器中的其他企业系统和独立应用 Agent 不受影响，不默认撤销长期个人 Key。
- **离线退出要如实提示。** 本地可以立即退出，但应提示服务端处理尚未确认。上述五分钟从服务端受理时开始计算，不能从离线点击退出时开始承诺。
- **已经接收的请求与后续请求分开处理。** 服务端已经接收、正在逐步返回内容的请求，可以按现有最长执行时间结束；后续每次新的模型请求都应重新检查。用户本地取消连接，不代表后台一定已停止生成，也不要求已发生的调用免费。
- **故障时不能省略必要检查。** IAM 或相关服务故障时，只有仍能确认访问有效、并保证上述停用和退出时限的请求才可继续；否则应拒绝，不能改成只检查 Key 就放行。
- **统一在网关控制台管理。** Key、应用开通、审批、IP 白名单与更换都在网关侧管理。DSH 展示状态、错误提示及控制台入口，不再建设一套管理后台。已有到期提醒等功能可以直接复用，不要求另建自动更换系统。
- **保留必要的用量和操作记录。** 能查到谁或哪个应用调用了什么模型、用了多少额度，以及谁办理了开通、变更或吊销。模型请求只转到机构内的模型服务；网关和模型服务均关闭请求、响应正文的日志记录，不记录 Key 等秘密信息。

## 2. 请逐项确认是否支持

请网关团队按以下编号回复。已支持的说明配置和适用版本；不能完全支持的说明网关侧差距、处理建议和实施安排。需要 IAM、模型服务或其他相关系统配合的，请列明所需条件，由实施团队协调核实。本版为回函 v1.2 后的第二轮确认，编号不变，已闭合的事项不再重复询问。

### CONF-GW-09｜能否限制个人只能使用自己的 Key？

是否支持场景一的“张三登录后不能使用李四的 Key”？请分别回答三点：一是当前版本能否在调用时确认使用人并与 Key 归属核对，若尚不能，请给出“Agent 和 IAM 认证完成后携带 `id_token`＋Key”这一规划的版本号与预计时间，并说明在此之前个人 Key 访问按什么边界开放；二是不保留个人静态 Key、只凭面向网关的令牌完成身份、计量与审计的方式是否存在——这是我方首选，请说明现状与差距；三是 IAM 主体与 Key 归属人如何对应，账号改名、删除后重建时旧 Key 是否失效或需重新绑定。

### CONF-GW-10｜能否让个人研发访问只用于 DSH？

我方拟保留 DSH 默认 `User-Agent`，不修改 DSH 核心，也不由插件改写 UA；请网关评估按 UA 中的子串关键词匹配，候选关键词为 `deepseek-harness`，具体字面值及大小写、重复头和边界处理均待网关确认。请确认五点：一是是否支持上述关键词匹配、具体匹配规则及配置入口，按凭证还是按团队配置；缺失、被剥离或不匹配的 UA 如何处理；二是拒绝时返回什么状态码与原因码，能否与“Key 无效”区分，且不扣额度、不转发上游；三是校验是否在鉴权之后、模型权限与额度扣减之前执行；四是除模型协议入口与 Coding Plan 外，后续新增入口是否自动纳入同一规则，客户端直连上游是否在网关侧被禁止；五是经企业代理或转发后，网关看到的 `User-Agent` 是否可能被改写或剥离。可选的 `X-` 请求头尚未实现，本方案不依赖它们。UA 可被复制或仿冒，只能作为降低误用的线索，不证明身份或作为撤权依据，也不替代 CONF-GW-09 的独立身份归属校验；相关能力、风险处置及准入均待确认。

### CONF-GW-11｜应用凭证的调用是否依赖创建人在线？

我方只对接一个环境，测试与生产分别开通不再作为要求。请确认一点：应用凭证调用模型时不校验创建人的 `id_token`、不要求创建人保持登录，即 09 所述 `id_token`＋Key 只作用于个人凭据，不扩张到应用凭据。若该点尚不能保证，请说明应用凭证的鉴权依据，以及创建人离职、停用后应用调用是否受影响。

### CONF-GW-12｜能否控制应用开通与个人 Key 申领？

按答复理解：应用凭证由团队负责人直接创建；普通用户只能申领个人 Key，经团队负责人审批后可使用或吊销，不能改作其他用途；审批有日志。请确认该理解准确，并补充一点：应用凭证的创建、吊销是否同样留痕、可否查询（查询口径并入 CONF-GW-20）。

### CONF-GW-13｜能否分别管理模型权限和额度？

请按四点回答，能取数的请给出字段名或接口：一是模型权限——登录后是否仍需单独分配、能否授权到单个模型、权限变更后已存在的 Key 是否立即生效、最迟多久生效；二是额度层级——团队额度、个人总额度、单个 Key 额度能否分别配置、分别由谁配置，同一员工多个 Key 是否共用一份个人总额度，换 Key 或换设备是否重置；三是超额与查询——额度耗尽返回什么状态码与响应字段、是否带 `reset_at` 或 `Retry-After`，是否有查询当前额度的接口或可深链的控制台页面；四是统计口径——能否按人去重得到“首次调用时间”和“日活跃用户数”，数据从控制台报表、API 还是日志取得，去重依据是哪个字段（`owner_user_id`、`sub` 或其他），保留多久、能否导出。

### CONF-GW-14｜IP 限制的范围如何界定？

我方按现行答复将限制记录为：仅平台管理员可为应用或智能体配置出口 IP 限制，支持单个 IP 与地址段；个人凭据不支持自选加严来源限制；网关不把转发头中自报的地址作为来源依据。请确认上述表述准确，并说明两处边界：一是该配置由谁修改、变更是否有记录；二是经代理或转发时，网关判断的实际来源是什么（连接对端地址、受控代理链，还是其他），以及个人调用是否受同一来源判定影响。我方不再要求本期补齐个人自选 IP 能力，按受限制的答复设计方案。

### CONF-GW-15｜停用或封禁后，能否在五分钟内阻止新调用？

请给出可核算的答复，不再以“待与 IAM 确认”作为结论：一是人员停用或网关封禁后，各网关节点拒绝新请求的最坏总耗时是多少，同步、缓存、失效各环节如何分布；二是已知 Kong 凭据缓存最长约 300 秒，与五分钟要求如何相容，靠缓存失效、令牌过期还是其他机制兜底；三是继续续期是否会延长可用时间；四是应用凭证被封禁时五分钟如何保证——这一项须与人员停用分开回答，不能合并；五是列出所需 IAM 配合条件（状态传递方式与时效），由实施团队核实。

### CONF-GW-16｜退出 DSH 时，能否只结束当前电脑的这次登录？

答复只覆盖“`id_token` 过期时间小于五分钟、DSH 在过期前刷新、网关检查过期时间”，这解决的是令牌短命，不是撤销。请补充五点：一是撤销接口——DSH 发起退出后，网关或 IAM 是否有受理接口、受理回执与结果查询，五分钟从何时起算；二是续期后代——该次登录用刷新令牌续期得到的新访问凭证是否一并失效，只让访问令牌短期过期无法阻止持续续期；三是复制到别处——该次登录凭证被复制后是否同样失效，判定依据是什么，不能只按设备标识或 IP；四是影响范围——是否影响其他电脑的独立登录、浏览器中的其他企业系统与独立应用；五是离线退出——恢复网络后如何安全补办、网关如何反馈结果。同时请确认该方案要求 IAM 把 `id_token` 有效期压到五分钟内并承担更高刷新频率，这一条件由谁确认；网关侧是否还有其他失效手段，不依赖 IAM 降低令牌寿命。

### CONF-GW-17｜IAM 等服务故障时，能否仍守住使用限制？

请回答三点：一是 `id_token` 检查策略由谁开启，能否作为平台级默认强制，个人或团队负责人能否关闭；二是 IAM 或验证服务故障时，已开启该策略的个人请求是拒绝还是放行，能继续多久，依据是什么（缓存、时钟偏移、密钥轮换）；三是应用凭据在同等故障下如何处理，什么条件下必须拒绝，是否会出现只凭 Key 放行。

### CONF-GW-18｜Key 的到期与提醒如何管理？

换新已按“先建新 Key、再吊销旧 Key”理解，不再要求说明并存。请补充两点：一是到期提醒——是否有提醒（邮件、控制台、接口）、提前多久、发给 Key 归属人还是团队负责人；二是默认策略——能否在平台级设定“默认 90 天、超过需审批”的统一规则，而不是逐个 Key 手工填写过期时间；若只能逐 Key 配置，请说明由谁填写、填错或留空的后果。

### CONF-GW-19｜正在返回内容的请求，取消或报错后如何处理？

请按五点回答：一是最长执行时间——600 秒是全局还是按凭证可配，超时返回什么状态码；二是断开后的计量——开始返回前断开记 499、不重试，是否计费、按什么计量，流式过程中断开上游是否停止生成、已生成部分是否计费、能否按请求查账单；三是错误分类——未登录或令牌过期、Key 无效或吊销、无该模型权限、来源限制（IP/UA）拒绝、额度耗尽、上游或网关故障这六类，目前分别返回什么状态码与响应体字段，能否互相区分；四是自动重试——网关的自动重试开关默认开还是关、对哪些状态码重试几次、重试是否可能导致重复计费、调用方能否从响应头或 trace 识别重试；五是防重复——是否支持请求唯一标识（request id 或 idempotency key），避免超时重发导致重复计费。

### CONF-GW-20｜能否满足记录要求，需要多少改动和投入？

请按五点回答：一是记录——能否查到“谁或哪个应用、调用了哪个模型、用了多少额度”，以及“谁开通、谁审批、谁吊销”，字段名与查询方式（控制台、API、导出）是什么，保留多久；二是正文日志——网关与模型两侧能否关闭请求、响应正文记录，UAG 现状是默认记录、按凭证开启 `privacy_mode`，能否在平台级或团队级默认关闭且个人不能自行打开，抽样排障如何授权与到期删除；三是已有与待建——上述能力中哪些是现成开关、哪些需要配置或开发；四是管理入口——能否复用现有控制台完成开通、审批、IP、更换与查询，不需要另一套后台；五是代价——对并发、响应时间与可用性的影响，以及开发、许可、联调与后续维护的投入、负责人和预计时间。

每项回复请列明：**是否支持、适用版本、限制、配置说明或脱敏示例**。涉及其他系统的，请分别列出网关已具备的能力、所需配合条件及尚待核实的事项。需要补充配置、联调或开发的，请明确负责人、预计时间和额外费用。对尚不能确定的事项，请列出待核实内容及反馈安排。
