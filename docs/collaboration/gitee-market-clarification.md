## 1. 结论（平台内部，不随函转发）

企业私有 npm 是唯一插件制品源，同时承载同步的公网包和内部定制包；固定 Gitee group 只约束内部定制插件的源码 repo，不要求所有 npm 包都在该 group 建库。企业 registry 地址与插件包名采用双层白名单，入名单包自动收录 DSH 兼容稳定版本，不逐版本人工审批；同步不等于收录全部 npm 包。本函仅问 Gitee 侧源码实体、只读权限、完整 commit、维护人、可选 star、审计及构建来源证据/联调条件，不请 Gitee 团队继续批准或设计中心取包。

npm 分发、公网同步、npm 下载统计、registry 凭据、制品保留与撤回由企业 npm 维护/IT 团队负责；内部构建与发布由 CI/npm 发布方负责。安装 npm 包的使用授权不能自动等同源码阅读权限；内部构建/发布须绑定 repo + 完整 commit + package version + integrity 证据，Gitee 只回答其侧可取得的证据，不能替 CI/npm 发布方证明包体来源。本函不重编号、不替代原 `CONF-GITEE-01..05` 的员工用户级 CLI 查询基线；回函不等于联调通过、实施授权或开放批准。

## 2. 范围与非目标（平台内部，不随函转发）

- 范围：实际私有版本及源码 API/CLI、固定 group 与 repo 的稳定身份和生命周期、只读自动化授权、源码阅读与制品使用授权分界、tag 到完整 commit、仓库维护人核验、可选内部 repo star、Gitee 侧审计/事件/CI 触发记录及测试联调。
- 非目标：把 Gitee 源码归档、release 附件或镜像作为默认插件制品源；询问 Gitee 下载统计或全部 npm 包的 Gitee star；代发函、创建账号/真实凭据、收集人员名单或业务源码正文，或要求 Gitee 团队批准 npm 分发、实现客户端及开发新功能。
- 证据分责：Gitee 团队提供其侧仓库身份、完整 commit、权限及现有触发/投递记录（如有）；CI/npm 发布方另提供构建执行、包名/版本、integrity 与发布记录的关联证据。不得仅凭 tag、服务账号可读或 npm 安装成功推定完整证据链或源码授权成立。

## 4. 可独立转发正文

**主题：** 请确认私有化 Gitee 内部插件源码仓库、只读权限及联调条件

**主送：** 私有化 Gitee 平台管理/运维团队；请协调贵方应用编程接口（API）、命令行工具（CLI）、仓库权限及现有持续集成（CI）触发记录相关责任岗位答复。授权答复岗位/联系人：[发函人填写]

**发函日期 / 回函期限：** [发函人填写] / [双方协商后填写]

**背景与本次请求**

我们拟为研发助手提供企业内部插件目录；插件是扩展软件。企业已确定以企业私有 npm 包仓库作为唯一插件制品源，由该仓库同步公网包并承载内部定制包；内部定制插件的源码在固定 Gitee 群组（group）下按仓库（repo）维护。本函只询问这些内部源码 repo 的身份、完整提交标识（commit）、读取权限、维护人及贵方现有运行能力，不将 Gitee group 当作全部 npm 包的目录或安装入口，也不从 Gitee 归档或附件分发插件包体。

npm 分发、公网同步、npm 下载统计、registry（包仓库）凭据、制品保留与撤回属于企业 npm 维护/IT 团队职责，不请贵团队批准 npm 权限或设计中心取包。安装 npm 包的使用授权不能自动等同源码阅读权限；是否可读仓库列表、元数据或源码，仍由 Gitee 侧按相应身份和资源权限判断。

内部构建/发布需要绑定 repo + 完整 commit + package version（包版本）+ integrity（npm 包体完整性校验值）的关联证据。请贵团队仅说明 Gitee 侧能够取得的仓库/commit 核验及现有 CI 触发或投递记录；构建执行、包版本、integrity 和 npm 发布记录由 CI/npm 发布方另负责，不要求贵方为其他系统的结果背书，也不要求另建复杂发布审批服务。

我们负责目录、终端适配与集成实现。请贵团队只确认现有接口、权限、使用规则与运行约束，不要求开发新功能或改造现有 CLI。本函不替代员工按本人权限查询仓库、问题（Issue）与合并请求（PR）的既有 CLI 接入问询，不申请写入、管理员或代员工点赞权限。

请各项选择“支持 / 有条件支持 / 不支持 / 待验证”，并说明适用产品版本、限制及证据。不支持是有效结论；待验证请列验证条件、责任岗位与计划，尚未排定可写“待定”，无需承诺新功能或虚构日期。请先答复第一组适用阻塞项；无法一次答全，可先认领并逐项补答。

**材料安全要求：** 请勿在本函、公开仓库或邮件回函中填写真实环境域名/内网地址、令牌或密钥、用户/成员名单及业务源码正文。示例请用 `corp.example`、`repo-demo` 等占位值；敏感环境地址、认证细节及原始证据走双方批准的受控附件或工单，回函仅填脱敏摘要及证据编号。凭据本体另走受控签发，不作为回函附件。

### 第一组：优先答复——源码接口联调前的阻塞项

#### GITEE-MKT-01｜实际产品版本及源码 API / CLI 差异

- **具体问题：** 实际私有化产品名称、版本/补丁和已启用的源码相关功能是什么？group/repo 枚举、tag 与完整 commit 解析、仓库角色核验及可选 star 分别能通过哪些只读 API 或现有 CLI 获取？与公有 Gitee API 文档及现有 `gh` 兼容 CLI 有哪些差异、缺失或版本约束？请按实际能力说明，不预设公有接口在私有部署可用。
- **期望证据：** 脱敏产品版本信息、适用的源码接口文档/CLI 帮助版本，以及操作到 API/CLI 的能力对照和结构化输出字段示例；未覆盖项标明“不支持/待验证”。

#### GITEE-MKT-02｜固定 group、稳定仓库身份及生命周期

- **具体问题：** 已指定的固定 group 在贵方产品中实际对应企业、组织、群组、项目还是命名空间？能否取得该 group 及内部源码 repo 的稳定 ID，分页列出授权可见的仓库并核对真实归属？重命名、跨 group 迁移、归档、删除/恢复后，ID、归属、可见性和查询结果如何变化，是否可能复用旧 ID？
- **期望证据：** 实际实体关系及 ID 字段说明、脱敏分页响应与生命周期文档或测试样例。请明确是否含子 group/归档库，以及因权限未返回的范围，避免把 URL 前缀当作归属证明；列出源码 repo 不代表对应 npm 包自动进入插件目录。

#### GITEE-MKT-03｜源码只读自动化凭据与最小权限

- **具体问题：** 读取指定 group/repo 的源码元数据、tag/commit 及确需的仓库权限核验信息，可使用何种受支持的自动化身份/凭据，能否按 group/repo 限定只读能力？如内部构建确需读取源码，与目录元数据读取应如何区分现有权限？凭据有效期、续期、轮换、双凭据过渡、撤销及其生效延迟如何？无法细分时请说明最小可行权限与不可隔离的能力，不要求管理员 token。
- **期望证据：** Gitee 权限—源码操作对照、受控申请/注入方式、有效期与轮换撤销规则、过期/撤销后的脱敏拒绝样例；只需字段与流程，不提供真实凭据，不包含 npm registry 凭据。

#### GITEE-MKT-04｜源码权限与制品使用授权分界

- **具体问题：** 对已获准安装内部 npm 包但未获准阅读其源码的使用者，Gitee 侧如何继续独立限制 repo 列表、元数据及源码的可见性？贵方现有权限或受控核验流程能否区分目录只读身份、构建读取身份和员工源码阅读身份，并在权限变更/撤销后拒绝相应读取？自动化身份“能读”不等于所有用户都可看源码；请仅确认 Gitee 权限边界，不决定 npm 制品使用或分发授权。
- **期望证据：** 不含真实名单的源码资源—身份角色访问矩阵、授权继承与撤销规则，以及“可使用制品但无源码权限”这一场景下的 Gitee 拒绝样例或待验证流程。无需提供 npm 授权名单，也不要求设计中心取包。

#### GITEE-MKT-05｜tag 到完整 commit 与可变更规则

- **具体问题：** 如何在指定内部源码 repo 中将 tag 可靠解析为完整 commit 标识，区分轻量/附注 tag 并取得最终指向？tag 能否移动、覆盖或删除，已有何种保护与修改权限限制？发生移动/删除时如何发现，旧 commit 在何种条件下仍可读取、核验并关联稳定 repo 身份？
- **期望证据：** 脱敏解析命令/API、完整 commit 字段、repo 关联字段、tag 保护与修改权限说明，以及移动/删除前后的响应或待验证用例。tag 或 commit 只证明源码指向，不单独证明 npm 包版本和包体 integrity；无需新增保护功能。

#### GITEE-MKT-09｜源码 API / CLI 认证与网络要求

- **具体问题：** 源码 API、现有 CLI，以及构建方确需的 Git 只读访问分别支持何种认证/传输方式？是否存在跨主机重定向或额外服务入口，认证信息如何限定发送范围？Gitee 侧要求的证书链/企业 CA、代理或网关条件及超时限制有哪些，是否已有防止令牌、认证头或敏感参数进入日志的规则？请勿建议关闭证书校验。
- **期望证据：** 脱敏认证方式/响应或 CLI 示例、相关主机角色和重定向行为（真实地址走受控材料）、证书与代理接入说明及 Gitee 侧日志脱敏规则。仅回答源码访问；终端网络放行由 IT/安全负责，npm 下载和 registry 认证另由其维护方答复。

#### GITEE-MKT-10｜源码查询分页、限流和拒绝语义

- **具体问题：** group/repo、tag 等列表的分页参数、最大页长、稳定排序/游标、末页及扫描期间变动语义是什么？限流按账号、token、IP、接口还是其他维度计算，有哪些限额与退避提示？API 的 401/403/404/429、对应 CLI 退出码/错误字段如何区分过期、权限不足、不存在或限流；隐藏存在性而返回 404 的情况如何表达？不要求高权限探测隐藏仓库。
- **期望证据：** 源码查询的分页/限流说明、跨页/末页及错误样例，适用时含限流头、重试时间和请求关联标识；请明确哪些失败无法判断资源是否存在。

#### GITEE-MKT-11｜内部源码仓库维护人及权限核验

- **具体问题：** 对指定的某位候选维护人，能否按稳定身份标识核验其对某个内部源码 repo 的当前角色/维护权限，或提供现有受控核验流程？仓库维护权限从哪里继承、多久生效，撤权如何核验？group 成员不自动等于 repo owner 或维护人；若核验需过高权限或暴露成员名单，有无不扩大权限的确认方式？
- **期望证据：** 仓库角色/继承规则、单人单仓核验的最小权限和脱敏字段/流程、撤权样例。只需核验结果或责任岗位确认，不索取全量成员/维护人名单；源码维护权限不能自动推定为 npm 发布权限。

#### GITEE-MKT-12｜测试联调资源与构建来源证据流程

- **具体问题：** 能否按现有流程提供非敏感测试 group/repo、至少两种权限不同的测试身份，并安排 tag 到完整 commit、凭据过期/撤销、无源码权限拒绝及获准的仓库迁移/归档/恢复测试？在 CI/npm 发布方配合的一次内部包测试中，贵方能提供哪些 repo/commit 核验、现有 CI 触发/投递记录及关联标识，以供他方绑定 package version + integrity？贵方不能取得的证据请指明边界，由 CI/npm 发布方另补。联调牵头、API/CLI 与权限责任岗位、窗口及缺少条件是什么？
- **期望证据：** 合成测试资源与身份角色矩阵、受控申请方式、Gitee 可交付证据样例及与 CI/npm 交接的字段/记录编号、尚缺材料的责任方和计划。构建执行与 npm 包体/发布证据由对应方提供；测试数据准备或生命周期变更由测试资源管理方另行授权，集成身份保持只读，不在回函内发凭据或真实包体。

### 第二组：开放前确认——Gitee 侧运行责任

#### GITEE-MKT-13｜源码审计、证据关联及恢复

- **具体问题：** 哪些源码查询/读取、鉴权拒绝及 group/repo、tag/commit、权限变更可在 Gitee 侧审计，能否取得 trace ID / request ID 等关联标识供贵方定位？如已有 CI 触发或事件投递记录，其可关联范围是什么？源码及其权限、审计证据的访问、保留、脱敏调阅和恢复规则如何，恢复后如何核对 repo/commit 关系与权限？
- **期望证据：** 脱敏审计/关联字段、现行保留与受控调阅规则、源码及权限恢复覆盖和已有演练摘要/证据编号。仅回答 Gitee 自有记录，不要求承诺 npm 制品、外部 CI 或其他系统的审计/恢复指标。

#### GITEE-MKT-14｜源码接口升级兼容、通知及支持

- **具体问题：** 私有版本升级时，源码 API/CLI 字段、分页、认证、group/repo 稳定 ID、完整 commit 解析及事件行为有哪些现行兼容约定或已知变化？升级/停机/接口弃用如何通知，能否先做非生产验证？源码查询故障、权限异常或 repo/commit 关联丢失由贵方哪些岗位受理，支持时间和升级路径有哪些现行约定？

#### GITEE-MKT-15｜内部源码 repo star（选答）

- **期望证据：** star 字段/类型/空值与错误语义、脱敏 0 和未知样例、下降/刷新说明或待验证条件。只问内部源码 repo，不要求所有 npm 包都映射到 Gitee，不索取点赞名单、不代员工点赞，也不将客户端收藏当作 star；不支持可不展示，不阻塞基本 npm 取包路径。

#### GITEE-MKT-17｜源码变更事件与 CI 触发证据（选答）

- **期望证据：** 现有事件/触发表、脱敏载荷与 Gitee 侧触发/投递记录、签名验证与重试限制，以及现有配置申请流程；密钥不入回函。投递/触发成功不能等同外部 CI 构建成功或 npm 发布成功，后两者的证据由对应方提供。
