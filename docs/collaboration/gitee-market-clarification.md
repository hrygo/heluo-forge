## 1. 结论（平台内部）

企业内部定制插件的源码托管在私有 Gitee 的固定群组（Group）下，经 CI 构建后发布到私有 npm。
本函专用于向 Gitee 运维团队确认**源码仓库的只读访问能力、自动化凭据与防篡改规则**。

## 2. 确认范围（平台内部）

- **确认范围**：Gitee 私有化版本与只读 API/CLI、自研插件专属 Group、只读 Token 与最小权限、Tag 到 Commit 映射（防篡改）、限流与错误码、审计与测试环境。
- **职责边界**：插件打包分发走企业私有 npm（由 IT/npm 团队负责），Gitee 仅负责源码托管与只读读取支持。

## 3. 使用说明（平台内部）

1. 仅复制 §4 中从“主题”到署名的正文发送给 Gitee 运维团队。
2. 涉及敏感内网地址或凭据时请走受控工单，回函中请使用脱敏示例。
3. 历史问题中与 npm 制品库相关的 5 项问题（原编号 06、07、08、16、18）已移交企业 npm 团队，本函保留现行 13 项源码专用问题。

**背景与目的**

我们计划在企业内网落地 DSH 编程助手的插件市场。其中，企业内部自研定制插件的源码托管在企业私有 Gitee 的指定群组（Group）下。
平台构建系统需要自动化读取自研插件的源码元数据与代码进行打包构建。为了确保接入顺畅、安全可控且不影响现有系统，需要 Gitee 管理/运维团队协助确认以下现有技术能力与只读接入要求。
本函仅申请只读权限，不申请写入或管理员权限。

**材料安全要求：** 请勿在本函中填写真实密码、个人名单或业务代码。示例请用 `corp.example`、`repo-demo` 等占位；敏感信息请通过企业受控工单传递，回函正文仅保留脱敏示例。

### 第一组：优先答复——源码接口联调前的阻塞项

#### GITEE-MKT-01｜实际产品版本及源码 API / CLI 差异

- **真实问题：** 企业私有部署的 Gitee 具体产品版本是什么？支持哪些只读 API 或 CLI 工具？
- **请确认事项：** 支持通过哪些接口或 CLI 查询 Group、Repo、Tag 和 Commit？与公网 Gitee API 是否存在功能差异？
- **期望提供：** 产品版本号、适用的 API/CLI 文档链接或帮助输出示例。

#### GITEE-MKT-02｜固定 group、稳定仓库身份及生命周期

- **真实问题：** 能否为自研插件统一划定一个专用的 Group（群组）进行集中管理？
- **请确认事项：** 该 Group 及名下仓库是否有唯一且不可变的 ID？如何分页列出名下所有仓库？若仓库改名、归档或删除，查询行为如何表现？
- **期望提供：** Group/Repo 列表查询的脱敏接口响应或 CLI 命令示例。

#### GITEE-MKT-03｜源码只读自动化凭据与最小权限

- **真实问题：** 自动化构建系统需要拉取代码，如何申请只读 Token 并做到最小权限？
- **请确认事项：** 能否仅为指定 Group/Repo 颁发只读 Token？凭据的有效期、轮换与撤销流程是怎样的？
- **期望提供：** 只读凭据的申请流程说明与脱敏权限配置示例。

#### GITEE-MKT-04｜源码权限与制品使用授权分界

- **真实问题：** 员工能安装自研插件，不代表有权看插件源码。Gitee 能否保障源码权限的独立性？
- **请确认事项：** 对于无该仓库阅读权限的员工，即使身处内网，Gitee 能否严格拦截其拉取源码的请求？
- **期望提供：** 权限继承规则及越权拉取被拒绝的脱敏报错示例。

#### GITEE-MKT-05｜tag 到完整 commit 与可变更规则

- **真实问题：** 插件发布依赖 Git Tag，如何防范 Tag 被恶意篡改或移动？
- **请确认事项：** Tag 如何解析为唯一的完整 Commit SHA？Gitee 是否支持保护 Tag（禁止覆盖、移动或删除）？
- **期望提供：** Tag 解析为 Commit 的命令/API 示例，以及 Tag 保护规则说明。

#### GITEE-MKT-09｜源码 API / CLI 认证与网络要求

- **真实问题：** 调用 Gitee API 和 Git 源码拉取需要经过哪些网络环境？
- **请确认事项：** 内网调用是否需要特定的企业自签 CA 证书或代理？是否存在跨主机重定向？
- **期望提供：** 证书、代理与网络访问要求说明。

#### GITEE-MKT-10｜源码查询分页、限流和拒绝语义

- **真实问题：** 批量拉取仓库列表时，如何处理分页和防限流？
- **请确认事项：** 列表单页最大条数是多少？API 限流阈值是多少？未授权（401/403）、不存在（404）和限流（429）的状态码与返回格式如何？
- **期望提供：** 分页参数说明、限流策略及典型错误响应示例。

#### GITEE-MKT-11｜内部源码仓库维护人及权限核验

- **真实问题：** 如何核实某个插件仓库的实际负责人（出现问题时需联系对应人员）？
- **请确认事项：** 能否通过接口或管理流程查询指定仓库的 Owner 或维护人？
- **期望提供：** 仓库角色查询方法或责任人确认流程说明。

#### GITEE-MKT-12｜测试联调资源与构建来源证据流程

- **真实问题：** 平台开发需要进行接口联调与权限验证。
- **请确认事项：** 能否提供一个用于测试的非敏感 Group/Repo 及测试凭据？
- **期望提供：** 测试环境申请方式与联调窗口对接人。

## 5. 失败模式与处理（平台内部，不随函转发）

| 情况 | 平台侧处理 |
|---|---|
| 实际版本、固定 group/repo 身份或源码读取权限未明确 | 不开放对应源码读取/展示；npm 制品使用授权不替代源码权限，不扩权或改用管理员身份探测 |
| repo/完整 commit 与内部构建/发布记录无法关联 | 不宣称来源证据完整；Gitee 仅补其侧证据，CI/npm 发布方补构建、package version 与 integrity，不用 tag、文件名或安装成功代替关联 |
| 401/403/404 隐藏存在性、429 或暂时失败 | 按已确认语义拒绝/退避/标未知，不提权探测；失败不解释为仓库删除、无权限者可读或 star 为 0 |
| 内部 repo star 不可用，源码 webhook/CI 触发记录不支持 | star 标未知/不展示，事件可用获准轮询；不伪造全部 npm 包的 Gitee repo/star，也不因选答缺失增设制品安装审批服务 |
| npm 同步、取包、统计、凭据、保留或撤回能力不明确 | 转企业 npm 维护/IT 团队在既有 CONF-IT-04 中确认；不转请 Gitee 批准，不回落 Gitee 归档、附件或镜像 |
| 回函仍是待验证，或 Gitee 运行/证据交接责任未落实 | 保留未关闭状态并安排验证；无回函不视为同意，回函不替代实测与本域签署 |
