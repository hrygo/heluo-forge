## 1. 适用范围

本文供开发 DSH 插件和仓库内工具的人员选择本地存储、使用现有凭据接口，以及设计新的 SQLite 数据持久化能力。第 2 节描述现有凭据实现，第 3—7 节规定存储扩展的评审准则；这些准则不代表通用业务数据库服务已经实现。

| 需要保存或读取的内容 | 使用入口 | 边界 |
|---|---|---|
| 当前登录人和 IAM 访问令牌 | `ctx.iam.getSession()`、`ctx.iam.getAccessToken()` | IAM 管理会话和刷新；业务模块不直接读写 grant 或 refresh token。独立进程入口见凭据接入指南。 |
| 插件自己的 API Key 等凭据 | 宿主 `ctx.credentials` | 引用由插件负责命名和使用；不要直接操作凭据库文件或其他模块的引用。 |
| 普通业务数据 | 优先使用已核验的宿主持久化接口；确需 SQLite 时先完成所属模块的存储设计 | 当前仓库的 SQLite 是凭据后端，不提供已接线的通用 SQL 服务。业务数据不能写入凭据数据库。 |
| 临时状态或可重新获取的缓存 | 进程内状态或已有缓存接口 | 先判断是否需要持久化，不因可能扩展而预建数据库。 |

本规范不修改 DSH 本体，不建立新的通用存储服务，也不授权迁移、清除或覆盖现有用户数据。业务共享数据库、加密需求与迁移方案按实际功能设计；本文不将单机助手设计成多用户数据库服务。

## 2. 已有凭据存储

### 2.1 宿主插件接入

企业组合通过 `@heluo/forge-credentials-keychain` 提供 `ctx.credentials`。插件为自己的凭据使用独立引用名；引用在共享命名空间中须避免与其他插件冲突，只能包含字母、数字和下划线，且以字母或下划线开头。值必须是非空字符串。引用名以明文保存，不放真实凭据或个人信息。

引用名只用于避免命名冲突，不是访问控制。获得同一 `ctx.credentials` 服务的同权插件可按引用名读写；该接口不按插件身份隔离凭据。

业务插件通过 `set()`、`resolve()` 和 `unset()` 管理自己的引用，完整示例见[凭据接入指南 §3.4](../../packages/forge-iam/docs/credential-access.md#34-保存业务插件自己的凭据)。凭据值由用户界面或其他受控输入提供。引用未配置时 `resolve()` 返回 `undefined`；存储或解密失败会抛错，调用方不得把异常当成“未配置”，更不能自动清空、覆盖或退回明文。凭据、令牌及包含这些值的对象不进入日志、命令参数、提示词或错误输出。单引用操作不构成多条记录的联合事务。

内置凭据提供器的常见结果如下；业务接口可能将其映射为自己的错误码：

| 结果 | 调用方处理 |
|---|---|
| `resolve()` 返回 `undefined` | 按未配置处理，提示用户通过受控入口提供凭据。 |
| `KEYCHAIN_REF_INVALID`、`KEYCHAIN_VALUE_EMPTY` | 修正引用名或输入，不持久化无效值。 |
| `CRED_LOCK_TIMEOUT`、`CRED_LOCK_RECOVERY_FAILED` | 提示存储暂不可用；写结果未确认时先核对，不盲目重放。 |
| `CRED_KEY_UNAVAILABLE`、`CRED_DECRYPT_FAILED` | 保留数据库与密钥原物，按凭据包说明排查，不自动重建或覆盖。 |

IAM access token、refresh token 和 IAM 会话记录由 IAM 管理；插件按需调用 `ctx.iam.getAccessToken()`，不把令牌复制到自己的引用。个人网关 Key 使用企业账号页面或 `ctx.iam.saveGatewayCredential()`，不直接修改 IAM 的内部记录。完整示例和令牌读取边界见[凭据接入指南](../../packages/forge-iam/docs/credential-access.md)。

### 2.2 实现与安全边界

现有组合把每个凭据值经 AES-256-GCM 独立加密后保存到 SQLite。数据库键、类型、属主、密钥版本、修订号与更新时间不是密文；记录中的 `subject` 或 `ownerSubject` 可作为明文属主，因此这些字段不能包含秘密，身份标识按实际数据分类和环境规则保护。密钥文件自身未加密，同一操作系统账户下的进程可读取或修改文件；分目录不提供按应用隔离，也不能防止删除和回滚。

提供器对更新事件失败的日志处理见[凭据包说明](../../packages/forge-credentials-keychain/README.md#装配与读取)；监听器自身的日志和错误输出仍须遵循本节的敏感信息要求。

Host 和 CLI 要读取同一存储时，目录与命名空间必须一致。该后端只支持同机、同 PID namespace 的本地文件系统，存储目录必须在 Git 工作区外。数据库与 keyring 的布局、平台默认目录、权限要求、旧格式处理行为和错误细节以[凭据包说明](../../packages/forge-credentials-keychain/README.md)为准。

写入通过凭据后端的逻辑锁串行化，实际数据库写事务保持短暂。默认 `lockTimeoutMs` 是每个等待阶段的上限，不是整次操作的总时限。`modifyRecord()` 的回调即使是异步的，也不能在回调内再次调用同一后端的写接口；远程请求和用户交互应移出锁与写事务。回调返回 `undefined` 表示不写入；删除使用 `deleteRecord()`。更新时返回新记录，不原地修改输入后返回 `undefined`。单记录更新不能代替网关凭据与元数据的联合条件提交；IAM 的受信组合能力不对外扩展成任意业务表事务。

包根导出的 `createCredentialStore()`、`createKeychainProvider()` 等构造器用于凭据组合与测试；它们的导出不等于宿主提供通用 SQL 接口。普通业务插件使用 `ctx.credentials`，不导入其他包的内部源码，不直接修改 `secret`、`meta`、密钥文件或内部锁记录。

### 2.3 备份与密钥

备份或恢复凭据前，关闭使用该存储的 Host、CLI 和其他进程；数据库目录与密钥目录须成对备份并按密钥保护，恢复时不得覆盖已有存储。没有配套密钥时密文无法恢复，恢复后的令牌仍受服务端过期和撤销状态约束。

目录布局、恢复条件、权限和旧密钥处理以[凭据包说明](../../packages/forge-credentials-keychain/README.md#密钥生命周期与备份)为准。当前没有内置备份、恢复或迁移命令；实际启用前须在目标平台验证恢复流程。

## 3. 新业务数据的设计与所有权

新增 SQLite 数据库前，所属模块的设计应写清数据用途、持久化必要性、数据库所有者、访问入口、存储位置、数据分类、生命周期和删除方式；存储位置使用平台用户目录或受控配置，不能放在仓库或安装目录内。可重建缓存要明确重建来源；不可重建数据要明确备份与恢复责任。敏感配置、密钥和真实用户数据不进入示例、测试夹具或日志。

凭据数据库只服务凭据后端，业务表使用独立的业务数据库；多个模块确需共享业务数据库时，在设计中明确唯一 schema／迁移所有者、各模块访问接口及事务边界。不要直接访问其他模块私有表，也不要仅凭同一个文件推断跨模块授权或数据隔离。SQLite 文件由本机进程访问时，按单用户应用的实际并发设计，不以网络共享目录或多台主机直接访问同一个文件。

插件自己的凭据通过第 2 节的 `ctx.credentials` 保存；IAM 令牌由 IAM 管理。业务数据库涉及凭据时只保存必要的非秘密标识或引用，其他业务数据按数据分类和实际需要存储。确需持久化敏感业务内容时，先确定加密、密钥、权限与恢复方案，不能假定 SQLite 文件本身加密，也不能借用凭据包私有密钥或密码实现。

## 4. 连接、SQL 与事务

- 工具链按仓库 [`.node-version`](../../.node-version) 和 `package.json`；当前凭据实现使用 `node:sqlite` 的 `DatabaseSync`。业务模块选用接口前须核对目标 Node、DSH／Electron 运行时和平台能力，不能只凭开发机可用推断交付环境可用。
- `DatabaseSync` 在调用线程同步执行；保持查询和事务简短，按实际数据量评估耗时，必要时将耗时工作移出交互线程。连接由创建者关闭，关闭期间不再接收新操作。
- 用户输入作为参数绑定到预编译语句；动态表名或排序字段不能作为值参数，须从代码中的允许列表选择。禁止拼接未受信输入形成 SQL。
- 同一项业务变更需要原子提交时，在所属数据库内使用事务；失败回滚并传播可处理的错误。数据库写事务内不等待网络、用户输入或长时间任务。跨数据库、文件和远端服务的操作不能仅靠一个 SQLite 事务宣称原子完成。
- 竞争、磁盘满、权限不足、损坏和提交结果未知须分别处理。重试有界且仅用于确认可安全重试的操作；结果未知时先按业务标识核对，不盲目重放非幂等写入或宣称成功。
- 显式选择并验证连接的外键、锁等待、journal 和同步策略；不依赖 SQLite 编译默认值，也不随意改写其他模块数据库的 PRAGMA。现有凭据后端没有对外承诺统一使用 WAL；测试主动启用 WAL 不等于默认启用。

下面的例子仅使用内存数据库，展示参数绑定和短事务，不创建项目业务库，也不访问凭据；文件数据库的连接与恢复策略须按上面的要求另行设计和验证：

```js
import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync(':memory:');
try {
  db.exec('CREATE TABLE preference (name TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT');
  const save = db.prepare('INSERT INTO preference (name, value) VALUES (?, ?)');
  db.exec('BEGIN IMMEDIATE');
  try {
    save.run('theme', 'system');
    db.exec('COMMIT');
  } catch (error) {
    try { db.exec('ROLLBACK'); } catch { /* 保留原始错误 */ }
    throw error;
  }
  const read = db.prepare('SELECT value FROM preference WHERE name = ?');
  console.log(read.get('theme').value); // system；仅为合成示例
} finally {
  db.close();
}
```

若业务库采用 WAL，须验证同机本地文件系统、运行时所带 SQLite 版本与恢复流程；WAL 仍只有一个写者，并存在 `-wal` 和 `-shm` 文件，不能在运行中只复制主文件当作完整备份。具体限制和版本注意事项见 [SQLite WAL 文档](https://www.sqlite.org/wal.html)。业务库的备份接口按其实现验证；SQLite 在线备份能力不等于本仓库已提供凭据在线备份，参考 [SQLite Backup API](https://www.sqlite.org/backup.html)。

SQLite 官方记录过特定版本在 WAL 并发写入和 checkpoint 交错时可能损坏数据库；启用 WAL 的实现须核对目标运行时是否包含相应修复。下面的命令只显示执行该命令的 Node 进程所带版本，目标 DSH／Electron 的 SQLite 版本须在其实际运行时另行核验：

```sh
node --input-type=module -e "import { DatabaseSync } from 'node:sqlite'; const db = new DatabaseSync(':memory:'); console.log(db.prepare('SELECT sqlite_version() AS version, sqlite_source_id() AS source_id').get()); db.close();"
```

## 5. 格式、升级与恢复

每个业务数据库由所有者定义可识别的 schema 版本、初始化与升级规则，记录支持的旧版、失败后的状态和回退方案。新旧程序可能同时访问时，升级前明确兼容窗口和串行机制；版本未知或高于当前程序支持范围时停止写入，保留文件并给出可处理的错误。不得通过删除旧库、自动重建或静默降级解决格式不兼容。

迁移应使用受控脚本或模块代码、可验证的版本判断与必要事务；先验证旧数据、升级中断、重复执行和回退。涉及真实数据的破坏性变更须经明确授权，并先验证备份和恢复路径。不要改写 SQLite 的内部 `schema_version`；可由业务数据库所有者选择 `user_version` 或自己的版本表，确保只有一个真源。

备份设计须覆盖一致性、文件及其关联密钥、权限、恢复到独立位置和恢复结果核验。不得在线直接复制正在写入的数据库及其伴随文件并假定一致，也不得将其他数据库的备份规则套用到凭据库。凭据库仍按第 2.3 节的停机配对规则操作。

## 6. 凭据后端扩展

新增或替换凭据后端时，先定义单记录读写、删除、枚举、事务、关闭、失败与并发语义；不存在的记录、不可用与损坏必须能区分。现有默认后端由组合根的静态注册表创建并绑定能力；注入对象自报 `durable`、锁或原子能力不能获得 IAM 信任。内存后端只用于显式允许的隔离测试，不能作为生产故障回退。

需要多记录联合提交时，单独验证预期值比较、同步 guard、事务回滚、并发修改和生命周期失效；网络请求仍在数据库事务和锁外，未知结果不能自动当作失败后重试。新的后端、密钥来源或信任边界必须先有设计、独立证据和测试，不能通过改配置绕过现有门禁。

## 7. 验证要求

| 场景 | 最低验证内容 |
|---|---|
| 接口与数据 | 合成数据读写、更新、删除、缺失、无效输入；令牌和 Key 等秘密不出现在数据库明文、日志或错误输出，身份等数据按其分类验证保护措施。 |
| 并发与故障 | 同一数据库的并发写、竞争超时、写入失败或中断后状态；检查回调是否会重复执行。 |
| 版本与迁移 | 空库初始化、支持的旧版、未知新版、重复迁移与中断；验证旧数据保留和失败后的可恢复性。 |
| 备份与恢复 | 在隔离目录用合成数据验证一致备份和恢复；涉及密钥时覆盖缺钥、错配及历史密钥。 |
| 平台与宿主 | 记录 Node／SQLite、DSH／Electron、操作系统、文件系统及测试结果；模拟或托管 runner 结果不代替目标环境证据。 |

凭据实现的现有回归入口：

```sh
node --test packages/forge-credentials-keychain/test/*.test.mjs
pnpm check
```

测试只使用隔离目录与合成值。具体实现及验证状态以[设计索引](../design/README.md#22-实现与验证入口)为准；未验证的环境单独记录，不以 SQLite 或单元测试通过推定企业联调完成。

## 8. 待确认事项

| 事项 | 责任方 | 截止门禁 |
|---|---|---|
| 某项业务是否确需 SQLite、使用独立或共享业务库，以及数据分类、备份和迁移要求 | 该功能负责人 | 对应业务存储设计与实现前 |
| 新凭据后端或密钥来源的可信能力、权限与失效行为 | 该实现负责人 | 后端装配与启用前 |
| 目标宿主运行时、平台权限、备份恢复与企业接入证据 | 对应功能负责人 | 目标环境启用前 |
