# forge-devops 变更全流程交付 · PRD

基线依赖：无

> 本需求是 heluo-forge 产品线的首个 TeamFlow 需求，没有前置任务夹。仓库既有资产（`packages/forge-devops` 只读骨架、`@heluo/forge-policy` 门禁、`@heluo/forge-enterprise` 组合与自包含 tarball 构建链路）作为**现状输入**写入背景，不作为基线依赖项。

## 1. 背景与目标

### 1.1 现在的样子（已核验的仓库与本机事实）

### 1.2 要变成的样子

开发者安装插件后，在 DSH 里给出**一个系统变更号**，DSH 自己取平台事实、识别歧义、把必须由人决定的问题连选项一起交上来、组织交付、维护平台记录、做一次交叉审查、最后用验收证据说明"是否完成"。开发者只做两件事：决定关键取舍、确认审查结果。

衡量标准不是"流程跑通了"，而是开发者从"持续指挥 AI、维护平台记录的人"变成"提任务、定取舍、确认结果的人"，同时仍然掌握真实进展。

### 1.3 目标（本需求要达成的可检验结果）

1. 插件**以 profile 包形态真实安装并加载**（不是 `file://` 手工挂载），可用、可回滚；装载证据以本机已装 `0.2.1-rc.2` 实测为准，`0.2.1-rc.3` 标 `NOT RUN`。
2. 一个变更号 → 一张**来源可核对的上下文卡**：业务事实来自 dop（`change view -j` 字段契约），仓库/Issue/PR 事实来自 gh；每项带来源与时间。
3. 歧义分流：**只有会改变验收结论或承建范围的歧义**才硬门禁停下来问（2—3 个选项 + 利弊 + 推荐）；其余记为「已记录假设」并在上下文卡中可见。
4. 交付按真实边界组织（1 个或多个 Issue），提交、PR、Issue 关系**自动且可追溯**，同一变更的提交以 `[变更号]` 开头。
5. 写动作**按门禁已覆盖的范围默认开放**（建 Issue、回写澄清、PR 关联、审查评论）；未覆盖或拒绝时状态可见为 `denied`，绝不静默跳过；平台动作状态只允许 `done` / `failed` / `denied` / `unknown`（扩展 `skipped` / `blocked` / `stale`）。
6. 完成报告逐条给验收证据（**mock 实测与企业实测必须分开标注**）；合并 PR、关闭 Issue 仍须人工确认；不早于既有流程把系统变更/用户故事标成完成。

## 2. 用户故事与验收标准

> AC 编号仅限本任务夹。判据均可在本地离线复现（mock dop 夹具 + gh 只读 + 探针 + `node --test`）；涉及真实宿主安装/加载的条目（AC-7/AC-8/AC-9）由主 agent 执行，以宿主日志与 `--dump-config` 为证。

### S1｜安装即用：让 DSH 真正能用企业研发平台（P0）

**AC-1 包根加载入口声明**
安装单元（`@heluo/forge-devops` 或承载它的伞包）的 `package.json` 含 `dsh.bundle.patch`，指向仓库内 `cordis.patch.yml`；该补丁 `insert:` 行 `name` 使用**包根名**（不得写 `@heluo/forge-devops/xxx` 这类子路径）；若声明 `dsh.client`，注入项同样用包根名。
判据：`node -e` 读清单断言上述三点（退出码 0）；`dsh --profile web --patch <patch 文件> --dump-config` 输出含 `id: forge-devops`。对照样本：已装 `dsh-plugin-teamflow@0.3.2` 的 `dsh` 块与其 `cordis.patch.yml` 注释（"name 必须用包根名"）。

**AC-2 分发白名单**
`files` 至少包含 `cordis.patch.yml`、入口实现目录（`src` 或构建产物目录）、`README.md`。
判据：`npm pack --dry-run --json` 的文件列表包含上述路径（可复用 `scripts/check-bundle-tarballs.mjs` 的审计）。

**AC-3 依赖协议可被 profile 解析**
最终待安装清单（源码清单若用 `workspace:*`，以构建期闭包后的 tarball 清单为准）**不含** `workspace:` 等本地协议。
判据：`node -e "const s=require('fs').readFileSync('<清单路径>','utf8');process.exit(/workspace:/.test(s)?1:0)"` 退出码 0；源码用 `workspace:` 时，tarball 内 `dependencies` 为精确版本（ADR-12 构建器产出）。

**AC-4 宿主运行期依赖按宿主模块表声明**
宿主提供的包（`@deepseek-ai/*`，若用 React 则含 `react`）只出现在 `peerDependencies`，并在 `peerDependenciesMeta` 标 `optional: true`；不得出现在 `dependencies`。
判据：`node -e` 断言集合关系（退出码 0）。

**AC-5 产物与源码同步**
安装与提交前必须重新产出安装物：若分发构建产物，产物内必须能找到只存在于当前源码的特征串（如 `forge_devops_` 工具名或动作 id 常量），且产物 mtime 晚于全部 `src/**`；若直接分发 `src`，tarball 内入口文件与仓库源码 sha256 逐字节一致。
判据：脚本断言（退出码 0）；`git status` 不出现"产物落后于源码"的未提交漂移。

**AC-6 装载安全**
模块顶层不得抛错、不得访问尚未注入的服务（`ctx.*`）或必需环境变量。
判据：`node --input-type=module -e "await import('<入口绝对路径>')"` 退出码 0；对入口文件 grep 断言顶层无 `ctx.` 访问（在 `export default`/`export const apply` 之外的顶层作用域）。

**AC-7 能被 profile 真实装入（本机入口，不写死路径）**
按本机探测到的入口安装：`dsh plugin --profile web add <tarball 绝对路径>`（`dsh` 在 PATH 上，转发到 `$DSH_HOME/profiles/web` 执行 pnpm）。
判据：安装后 `$DSH_HOME/profiles/web/package.json` 的 `dependencies` 出现安装单元，`dsh.profile.bundles` 含其包名；profile `cordis.patch.yml` 里 2026-10-28 的 `file://` 手工 UAT 段**已移除**（避免重复挂载）。

**AC-8 装载后宿主真实加载（端到端）**
重启宿主后，启动日志/插件列表出现该插件；模型可见工具面出现四个只读工具与新的聚合读取工具；`dsh --profile web --dump-config` 含 `id: forge-devops` 且不再是 `file://` 行。
判据：宿主启动日志片段 + 工具列表文本 + `--dump-config` 输出，三者齐备才算通过；仅有源码或 tarball 不算。证据必须写明实测宿主版本（本机 `0.2.1-rc.2`），`0.2.1-rc.3` 记为 `NOT RUN`。

**AC-9 安装必须带回滚**
安装动作开始前，回复中必须写明卸载步骤：`dsh plugin --profile web remove <包名>`、确认 `dsh.profile.bundles` 已摘除、按原样恢复被删除的手工 UAT 段；包名从产物 `package.json` 读取，不写死。
判据：装后验证（AC-7/AC-8）任一失败 → 立即执行卸载；回滚后 `dependencies`/`bundles`/`--dump-config` 回到安装前状态且宿主可启动，并在回复中报告失败原因与已回滚。

### S2｜只给一个系统变更号（P0）

**AC-10 唯一入口，只要变更号**
用户可通过显式入口（skill/command，名称 `devops-change`）启动，只需提供变更号（形如 `ARD123456`，mock 夹具 id）；不要求用户同时给仓库、分支、Issue 或验收标准。入口不按 id 前缀/文本推断任何含义。
判据：入口存在且用户可触发（`modelInvocable: false` 不自动冒用）；缺参、空值或含空白/非法字符时输出"期望格式 + 缺什么"，不进入后续流程、不猜测。

**AC-11 上下文卡：一次聚合，来源可核对**
一次启动聚合两类事实并输出上下文卡：

- 业务侧（dop `change view <id> -j`，字段契约 2026-07-06 校准）：`id`、`title`、`status`、`type`、`owner`、`description`、`acceptance_criteria[]`（**逐条编号展示**）、`created_at`、`sub_systems[{code,name}]`、`user_stories[{id,code,title,type,state,stage,team,assignee,business_owner,release_info{release_num,release_name,release_date,release_stage}}]`。
- 仓库侧（gh 只读）：承建仓库、开放 Issue 与 PR 及其当前状态、与变更的关联；仓库侧取不到时标 `unknown`，不阻塞业务侧展示。

规则：`release_info` 在多个用户故事间取**首个非空**（夹具 `ARD222222`：首个 story 的 `release_info` 为空，必须取到第二个非空值；`ARD123456`：单 story、`release_info` 全非空）；每类事实带**来源（dop/gh）+ 来源版本或时间戳**；任一类为 `unknown` 时在卡上标 `unknown` 与原因（如 `OMS_MOCK_DOP_FAIL_GET=1` 时 `change view/list` 退出码 1），不静默省略、不当作"无数据"。
判据：以 `ARD123456` / `ARD222222` 两个夹具跑出固定输出，人工核对字段齐全与首个非空规则；失败注入分支有独立用例。

**AC-12 承建系统不猜**
候选仓库/系统**只能**来自 dop `sub_systems` 与 gh 可见仓库集合；当变更为多系统、仓库不唯一或无法与候选对上时，结果标 `blocked`，输出候选清单与各候选依据（哪条字段/哪次查询），请用户确认。
判据：不得依据变更号文本推断仓库或承建系统；不得在信息不足时自行选定后继续；`blocked` 状态下不产生任何写动作。

### S3｜把真正需要我决定的问题交上来（P0）

**AC-13 澄清单：有依据、有选项、有推荐，且只问该问的**
每条待澄清项包含：编号、依据（dop 字段或原文引用）、2—3 个**有实质区别**的选项及各自影响与利弊、推荐项与理由；能自行查证的先查证并附查证结果（结论注明来源）。
分流规则（本轮拍板）：**只有会改变验收结论或承建范围的歧义**进入硬门禁（必须由人确认后才推进）；其余歧义写入「已记录假设」段（编号 `H-1…`，含假设内容、依据与若不成立的影响），并在上下文卡中可见，完成报告逐条复核这些假设。
判据：一条"怎么办"式问题（无选项）即判不通过；改变验收结论/承建范围的歧义若未进入门禁、或非关键歧义未进入假设段，均判不通过；用户确认后生成带版本标识的澄清规格，后续环节只引用该版本。

**AC-14 澄清回写：门禁内、结果诚实、无命令即拒绝可见**
澄清规格回写必须经策略门禁，且只使用白名单内动作：dop 命令面当前只有 `change create|list|view|done`，**没有澄清/评论写命令**，因此 dop 侧回写只能落 `denied`（原因：动作未白名单/未覆盖）并可见说明；可追溯副本可落到已关联 Issue 的评论（`gh issue comment`，须在白名单内且被门禁覆盖，否则同样 `denied`）。
判据：写通道未开放、无权限或结果不可确认时状态只能是 `denied`/`skipped`/`unknown` 并给出原因与影响；产物与回复中不得出现"已回写/已同步"等未确认成功的表述；成功时返回可核对的对象标识（变更号 + 对象 id/链接）；门禁拒绝路径有独立用例（拒绝时适配器零调用）。

### S4｜自主组织交付，不要我逐步指挥（P0）

**AC-15 交付计划：验收条件 → 实现 → 验证**
输出计划，逐条把验收条件映射到实现项与验证方式；简单变更对应 1 个 Issue/PR，复杂变更按真实交付边界拆分；不引入与本次变更无关的固定阶段、模板或文档。
判据：除变更号、澄清规格与平台事实外不需要追问即可成计划；每条验收条件在计划中有对应行；无对应验证方式的条目判不通过。

**AC-16 平台动作状态、幂等与真实远端保护**
每个平台动作用四种状态之一记：`done` / `failed` / `denied` / `unknown`，并带目标对象标识与失败原因；同一变更重复执行不重复创建对象（幂等键 = 变更号 + 对象类型 + 标题归一化哈希；创建前先用 gh 查询同名 open Issue / 同分支 open PR，命中即复用）；`unknown` 时转人工核对，不自动重放。
由于 gh 写动作指向**真实远端仓库**：任何写动作执行前必须显示目标仓库与对象，并只通过白名单动作执行；执行后回读一次确认，回读不一致记 `unknown`。
判据：离线用例覆盖四种状态与重复执行（重复执行不新增对象）；`unknown` 后无自动重放；写动作执行前后均有目标对象与回读记录。

**AC-17 提交信息带变更号**
同一系统变更下的提交信息以 `[变更号]` 开头（原文约束）。提交前校验，不合规即拒绝并给出期望格式。
判据：违规样例被拒绝（退出码非 0 + 提示格式），合规样例通过。

### S5｜交付前先交叉审查，再由我确认（P0）

**AC-18 交叉审查与版本绑定**
研发完成后产生 `review.md`：问题清单、风险、审查意见与结论；记录**实际使用的模型名**（从 profile 可用更强档位中选，如 `deepseek-v4-pro`/`gpt-6.1-sol`/`gpt-6-astra`/`muse-spark-1.3-contributor`；若不可用则用同模型二次独立审查并明示"未使用更强模型"）与**被审代码的 commit sha**；AI 审查意见与人工确认**分栏记录**（谁、何时、针对哪个 sha、结论）；sha 变化后旧确认标记 `stale`，不得沿用。
审查评论发到对应 PR 属门禁已覆盖动作（`gh pr comment` 等白名单动作），发前须人确认文案与目标 PR。
判据：人工改动一个字符使 sha 变化 → 旧确认失效且流程要求重新确认；产物中两栏可区分；`review.md` 头部有模型名与 sha。

**AC-19 不合并、不越权结项**
动作白名单**不含** `dop change done`、`pr.merge`、CI 触发/重跑、生产部署/回滚/审批；插件不执行 PR 合并、不关闭 Issue（即使写动作默认开放，合并与关闭仍须人工确认后由人或经人工确认的单次动作完成）；不因代码完成、PR 合入、Issue 关闭或 UAT 部署成功而把系统变更或用户故事标记为完成；其最终完成状态与结束时间随所属用户故事既有流程联动。
判据：任何路径下无合并/关闭/`change done` 调用；产物与回复中不出现"系统变更已完成/用户故事已完成"。

### S6｜用平台事实与验收证据说明是否完成（P0）

**AC-20 完成报告：逐条证据，缺项可见，来源标注**
`report.md` 逐条列验收条件、证据（命令、输出摘要、链接）、结论（通过/未通过/未验证）；证据必须标注来源类型：**mock 实测**（mock dop / 本地夹具）与**企业实测**（真实企业平台/联调）分开写，不得用 mock 结果冒充企业证据；分列"已提交/待审查/已合入"；关联 Issue 仅当"对应验收通过 + 交付 PR 已合入 + 无未完成交付"三者同时成立才进入关闭流程（且关闭动作需人工确认），否则保持打开并写明缺项；取不到的 CI/CD 与 UAT 信息标 `unknown`；失败与阻塞单列；`H-*` 假设逐条复核结论。
判据：以固定事实跑出报告，逐条核对；缺任一验收条件证据、未标注来源类型、把未合入 PR 写成已交付，任一出现即判不通过。

**AC-21 UAT 与部署边界**
UAT 部署由企业既有 CI/CD 完成，本插件只读核对结果、不建设第二套部署流程、不发起部署。
判据：白名单与代码中无部署/发布/CI 触发动作；仅存在读取与核对路径；无结果时报告 `unknown`。

### S7｜命令面、配置注入与证据纪律（P0）

**AC-22 固定命令白名单 + 配置注入（不落凭据、不硬编码路径）**
不提供通用 `run(command)`。白名单固定且可审计：

| 来源 | 允许 | 明确禁止 |
|---|---|---|
| dop | `change view`、`change list`（均带 `-j`） | `change done`、`change create`、任何写命令 |
| gh | `repo view`、`issue list/view/create/comment`、`pr list/view/create/comment` | `pr merge`、`pr close`、`issue close`、`release`、`workflow`（CI 触发/重跑） |

配置：dop 可执行路径与 endpoint **经环境变量注入**（不写配置文件、不入库、不落日志）；`dop` 不在 PATH 且 mock 脚本位于仓库外的另一工程，因此实现**不得硬编码本机绝对路径、不得在运行期依赖该外部仓库**（夹具可在测试中指向 mock，生产路径由环境提供）；未配置时 fail closed 并给出可见原因（`denied`，不猜默认值）。
判据：白名单单元测试枚举允许/拒绝动作（未列命令一律拒绝且适配器零调用）；grep 断言源码与文档中无内网地址、无本机绝对路径、无凭据；未配置环境时可见 `denied` 而非崩溃。

**AC-23 证据纪律：mock 与真实分开记账**
任何"已实测/已验证"的结论必须写明：命令、时间、宿主版本、目标仓库/变更号以及**来源类型（mock 实测 / 企业实测）**；仓库侧写动作必须写明目标仓库全名与对象链接。
判据：抽查 `report.md`、`review.md` 与回复中的通过结论，缺来源类型即判不通过；把 mock 结论写成"企业已联调/已验证"判不通过。

### 状态词表（全流程统一）

| 词 | 含义 | 禁止用法 |
|---|---|---|
| `done` | 动作已执行且平台给出可核对对象，并已回读确认 | 只有退出码 0 时使用 |
| `failed` | 明确失败，带原因 | — |
| `denied` | 门禁/权限/白名单拒绝，适配器未被调用 | 当成"暂时不可用"悄悄跳过 |
| `unknown` | 结果不可确认（超时、断流、只有退出码、回读不一致） | 当成成功 |
| `skipped` | 用户或门禁决定不做，带原因 | 用于掩盖失败 |
| `blocked` | 缺关键信息，等待人工输入 | 自行补默认值继续 |
| `stale` | 结论对应的代码版本已变化 | 沿用旧确认 |

## 3. 范围与非目标

**范围内**：可安装/可加载的 DevOps 插件（宿主半）、变更号入口、dop 业务事实与 gh 仓库事实的聚合、上下文卡、澄清单与澄清规格（含「已记录假设」分流）、交付计划、平台动作白名单/状态模型/幂等、门禁内写动作（建 Issue、审查评论、PR 关联；澄清回写按命令面现状落 `denied` 可见）、提交信息校验、交叉审查产物与确认失效规则、完成报告与证据纪律、UAT 只读核对。

**非目标（本需求不做）**
- 不做 Web UI / 客户端半（`plugin-host` 形态，只有宿主半）。
- 不建设 DevOps MCP 服务、不修改上游 DSH、不做核心补丁（沿用仓库既有边界）。
- 不建设第二套部署/发布流水线；不做业务验收、上线审批与回滚；不触发或重跑 CI。
- 不做度量看板、成本统计与团队排名（后续观察项，不进本需求）。
- 不接管用户故事整体：任务对象以系统变更为主。
- 不使用 `dop change done`、不合并 PR、不自动关闭 Issue。

## 4. anti-goals / 反面目标

> 以下每一条都是"测试全绿但仍然会被用户拒绝"的具体失败形态，验收时逐条核对。

1. **装上之后"在列表里但用不了"**：插件出现在插件列表、启动日志无报错，但模型可见面没有工具、用户调不出入口，而安装报告写着"安装成功、验证通过"。用户此后的每一步都无从下手——这比装不上更糟。
2. **多个候选仓库时自己挑一个往下做**：变更号对应两个以上候选系统/仓库，DSH 选了其中一个继续研发并开 PR；用户直到看 PR 才发现承建系统错了，之前的工作全部作废。
3. **把"怎么办"原样抛回给我**：澄清环节列出"这里需要你决定"，没有选项、没有影响、没有推荐，用户仍然要自己想方案——那不如不要这一步；反过来，事无巨细都停下来问，也等于把决策成本原样退回。
4. **平台记录与实际不符**：写动作无权限或超时，报告里写"已创建 Issue / 已回写澄清"，用户到平台找不到；或同一变更反复执行就在真实仓库刷出多个重复 Issue/PR，用户还得逐个清理。
5. **把"代码写完"说成"变更完成"**：完成报告只有一句"研发已完成"，没有逐条验收条件证据，或把 mock 结果当成企业已联调，或把"PR 已提交"当成"已交付"，甚至把系统变更/用户故事标成完成。

## 5. 交互流程摘要

```
用户: devops-change ARD123456
  │
  ├─① 聚合读取（dop change view -j → 业务事实；gh 只读 → 仓库/Issue/PR；全部经白名单+门禁）
  │     → 上下文卡：需求 · 逐条验收 · 系统+仓库 · 故事背景（release_info 取首个非空）· 已有关联
  │        └─ 多系统/仓库不唯一/对不上 → blocked + 候选清单（不猜，不写）
  │        └─ dop 失败注入/超时 → 该项 unknown（不当作无数据）
  ├─② 理解与歧义分流
  │     ├─ 改变验收结论或承建范围 → 硬门禁：依据 + 2—3 选项 + 利弊 + 推荐 → 用户确认
  │     └─ 其余 → 已记录假设 H-n（上下文卡可见，报告逐条复核）
  │     → 澄清规格 vN → 门禁内回写（dop 无写命令 ⇒ denied 可见；副本可选 gh Issue 评论）
  ├─③ 交付计划（验收条件 → 实现项 → 验证方式；1 个或多个 Issue/PR）
  ├─④ 研发推进 + 平台记录（幂等创建 + 回读确认 + 四状态；提交以 [变更号] 开头）
  ├─⑤ 交叉审查 review.md（更强档位模型，记录实际模型名；绑定 commit sha）
  │     → AI 意见 / 人工确认 分栏 → sha 变化 → stale
  ├─⑥ 完成报告 report.md（逐条证据 + 来源类型 mock/企业；已提交/待审/已合入；Issue 关闭条件；CI/CD 与 UAT：读或 unknown）
  └─⑦ 边界：不合并 PR、不关闭 Issue、不 change done、不标系统变更/用户故事完成（随既有流程联动）
```

产物落盘：`<目标仓库>/.dsh-devops/<变更号>/` 下的 `context.md`、`clarify.md`、`plan.md`、`review.md`、`report.md`，每个文件头部含 `change` / `generatedAt` / `sourceType`（mock / 企业）/ `sourceRevision`（平台来源版本）/ `commit`（涉及代码时）。该目录由开发阶段加入 `.gitignore`（运行期产物不入库）。

## 6. 优先级

| 优先级 | 内容 | 理由 |
|---|---|---|
| P0 | S1 安装契约（AC-1～AC-9）、S2 变更号与上下文卡（AC-10～AC-12）、S3 歧义分流与回写诚实（AC-13～AC-14）、S4 计划/记录/白名单与幂等（AC-15～AC-17）、S5 交叉审查与确认（AC-18～AC-19）、S6 完成报告与边界（AC-20～AC-21）、S7 白名单与证据纪律（AC-22～AC-23） | 用户明确要求的端到端闭环；本地可用 mock dop 夹具 + gh 只读 + 探针验证 |

## 7. 依赖与风险

| 项 | 影响 | 应对 |
|---|---|---|
| 企业 dop 未联调，只有 2026-07-06 校准的 mock | 字段与行为差异可能在上真接口时暴露；mock 通过不等于企业通过 | 字段映射以 mock 契约为准并集中在一层；报告与 review 强制标注来源类型（AC-23）；上真接口只改适配层 |
| `dop` 不在 PATH，脚本在仓库外另一工程（oh-my-sdd） | 硬编码路径会让插件换机即坏，或反向依赖外部工程 | 路径与 endpoint 经环境变量注入；实现不硬编码本机绝对路径、运行期不依赖该外部仓库；mock 只作测试夹具 |
| dop 默认 endpoint 是内网桩地址 | 写进文档/日志/制品会泄露内网信息 | 只在运行时注入；grep 断言源码与文档中无内网地址、无凭据、无本机绝对路径（AC-22） |
| gh 写动作指向真实远端仓库 | 可能产生真实 Issue/PR 噪音或误关对象 | 白名单 + 幂等（创建前查询复用）+ 回读确认 + 合并/关闭须人工确认；真实写只在人工确认下执行 |
| 宿主版本双轨：仓库目标 `0.2.1-rc.3`，已装 CLI `0.2.1-rc.2` | 装载结论可能被当成 rc.3 已验 | 本轮已定：`engines.dsh` 声明兼容区间，rc.2 实测为证，证据里对 rc.3 标 `NOT RUN` |
| 交叉审查的模型档位 | 强模型不可用时可能悄悄降级 | 记录实际模型名；降级时在 `review.md` 明示"未使用更强模型"（AC-18） |
| 「有关仓库的都按 gh 实现」的解释 | 若用户本意不同（如仓库事实也走 dop 或其他端点），来源映射需调整 | 当前解释：业务事实（变更/用户故事/验收）走 dop，仓库/Issue/PR 事实与动作走 gh；改动只影响适配层与 AC-11 取数来源 |
| profile 里仍有 2026-10-28 的手工 `file://` UAT 段 | 若不清除会与新安装重复挂载，工具注册冲突/行为不确定 | 安装步骤包含"删除该段"；回滚步骤包含"原样恢复" |
| `pnpm check` 为全仓门禁（文档/仓库/tarball/单测） | 新增包若清单或产物不合规则整体失败 | 新增包必须带离线测试进入 `node --test` 自动发现；tarball 审计复用现有脚本 |

## 9. 工程约束

**分支（照录状态核对）**：当前在 `feat/devops-change-flow`，不新建分支；如需重建，从最新 `main` 拉出后再实现。工作区未提交改动 1 处：`?? docs/teamflow/`（本需求产物夹）。

**未提交改动处理**：`docs/teamflow/` 是本需求产物夹，保留原样；不得 `git stash`、丢弃、覆盖或回退他人改动；提交时只纳入本需求产物与实现改动，不把未知改动混入同一提交。

**提交信息（原文约束）**：让同一系统变更下的提交信息以 `[变更号]` 开头。

**安装执行者（工作区外写权限）**：流水线子代理写不了工作区之外，AC-7/8/9 的安装、重启验证与回滚**必须**写成给主 agent 执行的步骤（主 agent 可申请一次性升级授权，由用户批准），不得写成"请用户手动测试"。本机命令：

```sh
# 构建/取得 tarball 后（包名从产物 package.json 读取，不写死）
dsh plugin --profile web add <tarball 绝对路径>
# 之后把包名加入 $DSH_HOME/profiles/web/package.json 的 dsh.profile.bundles
# 并删除 cordis.patch.yml 中 2026-10-28 的 file:// UAT 段
# 回滚
dsh plugin --profile web remove <包名>
# 从 dsh.profile.bundles 摘除该包名，恢复被删除的 UAT 段
```

**运行时配置注入（不在文档/配置里落值）**：dop 可执行路径与 endpoint 由环境变量提供（变量名在实现里集中声明，文档只写变量名与用途，不写值、不写内网地址、不写本机绝对路径）；未配置时 fail closed 并可见 `denied`。

**版本控制卫生（开发阶段动作，本阶段不执行）**：审计并扩展 `.gitignore`——加入 `.agents/`（本地 worktree/探针工作区，根目录当前未忽略，会被整树暂存）、`logs/teamflow/`（运行期瞬态暂存，由宿主归档后删除）与 `.dsh-devops/`（运行期产物）；确认 `lib/`、`cordis.patch.yml`、`package.json` 不被忽略（`dist/`、`output/`、`*.tgz`、`*.log` 已有规则；安装用 tarball 在临时目录构建、不入库）。

**验证基线**：仓库根 `pnpm check` 与 `git diff --check`；新增/修改包必须有离线测试并进入 `node --test` 自动发现范围；核对受影响的相对链接、锚点与文档登记。真实远端（gh）写动作只在人工确认下执行一次取证，其余用 mock/离线夹具与幂等预演。

**文档边界**：TeamFlow 契约文档只写本任务夹；不写宿主 `docs/<role>/`、不在项目根散落日志；凭据、内网地址与本机绝对路径不得进入文档、日志或制品；`docs/teamflow/memory.md` 只在本需求引入团队约定时更新同主题行（幂等，不追加变更日志）。

## 10. 假设与待澄清

- **（口味）取证期的真实远端写**：AC-16/AC-20 需要验证 gh 上的"创建 Issue/评论"链路，而 gh 指向真实仓库。是允许在真实仓库创建对象取证（证据最硬，但仓库会留下测试对象），还是把真实写收敛为人工确认的一次取证、其余用 mock/离线夹具 + 幂等预演（仓库干净，但真实远端覆盖只靠那一次人工确认）？默认（推荐）：后者——真实写仅在人工确认下执行一次（执行前先展示目标仓库与对象），其余全部离线；这是"写动作按门禁开放"与"不污染真实仓库"之间的折中。
