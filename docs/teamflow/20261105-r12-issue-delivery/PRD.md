# 单 Issue 可信待验收交付 PRD

> 编制：产品经理（代拟）。本轮用户已确认首批目标与工作区选择；本文将已确认方向转为验收条件，不代表技术接口已验证、实现已完成或用户已验收。

## 1. 背景与目标

产品语义：**一个 Issue 对应一份可追溯到实际代码版本的待验收交付；Skill 补企业语义，原生 Teamflow 唯一执行，用户决定接受，交付不等于可关闭。**

本需求是既有 DevOps/Gitee 插件及企业组合的迭代，不是新项目。上位范围遵循[需求基线 §2.3](<../../requirements/requirements-baseline.md#23-issue-交付模型与受控研发目标需求已确认>)，本轮仅落实其首批切片，不另立企业需求真源、不取代历史任务夹的验收口径。

### 1.1 已知事实与证据边界

- 2026-11-05 在当前隔离工作树实跑 `pwd`、`git rev-parse --show-toplevel`、`git branch --show-current`、`git status --short`：执行目录与授权 worktree 一致，分支为 `feat/plugin-workflow-new`，起始工作树干净，HEAD 为 `55e964c`。任务旧快照的主目录分支及两处未提交项不作为本工作树事实。
- 已读[企业组合清单](<../../../packages/forge-enterprise/package.json>)、[组合入口](<../../../packages/forge-enterprise/src/index.mjs>)及 [Skill 装配源码](<../../../packages/forge-enterprise/src/skills.mjs>)：存在装配辅助能力；当前组合依赖仅凭据、策略、IAM 三包。辅助函数存在不等于正式企业研发 Skill 已进入发行制品或被宿主自动发现。
- [设计索引](<../../design/README.md#22-实现与验证入口>)与[阶段交接](<../../plans/2026-11-04-devops-plugin-stage-handoff.md>)提供历史实现和实测索引。后者记载 dop 企业只读及一次同值写回，不证明本轮关联、续跑、提交或交付链路；企业 Gitee CLI 仍缺真实联调证据。

### 1.2 本轮成功标准

1. 从可交付制品安装后，企业研发入口及必需工具可发现；缺依赖可定位、可行动，不能“装上却静默无入口”。
2. 用户明确选定 Issue 后，核实唯一变更、唯一仓库、需求来源和已有 run，再交给原生 Teamflow；支持中断续跑，不重复开工。
3. 候选交付包含实际版本、本地验证、独立只读 AI 审查及逐项证据；代码或要求变化后旧证据不能自动沿用。
4. 缺企业条件、可信来源或宿主能力时如实报告阻塞／未验。可以交付本地机制演示，但不能把演示写成真实 Issue 已完成、生产可用或可关闭。

## 2. 范围与非目标

### 2.1 本轮范围

- 企业研发 Skill 的正式资源分发、发现说明、依赖诊断与停用清理；基于现有企业组合及构建链路补齐所需能力。
- 变更／Issue 双入口的最小业务上下文核实；从变更进入须先选本次 Issue，一个 Issue 只关联一个变更和一个仓库。
- 对原生 Teamflow 的任务关联、启动、结果读取、中断续跑、提交约束做真实接口核验及最小适配。
- 交付版本与本地验证、独立 AI 审查、证据摘要的绑定和过期判定；用户按实际版本验收的交接约定。
- 关联冲突、版本变化、已有 run 与中断续跑的正反向测试，以及制品、文档、安全回归。

### 2.2 非目标

不新建流程引擎、任务数据库、状态面板或跨系统调度器；不修改／fork DSH，不恢复 SDD 冻结流程。指标、完整 CI/UAT、更多界面、产物目录统一后置。企业 CLI 全能力取证、可信确认机制和受控远端协作属于后续优先项，不以本轮顺手扩建；本轮仅核验必需读能力并暴露缺口。自动合并、关闭 Issue、结束业务变更、发布、部署、流水线触发不在授权内。

本轮不增加统一的“必须 CI 通过／PR 已合并才可人工验收”规则；目标仓库已存在的必要 CI、分支保护和企业强制要求仍必须遵守。没有 PR 时如实标未创建，不为凑证据自动开 PR。

## 3. 用户故事与验收条件

AC 编号只属于本任务夹。下表均为目标，未代表已实测。P0 为首批可信交付成立的必要条件，P1 为正式交付完整性条件；二者均须验收，不能以优先级省略。

### US-1：开发者安装企业组合后，能找到正确入口并知道缺什么

| 编号 | 优先级 | 可测试验收条件 |
|---|---|---|
| AC-1 | P0 | 以最终发行 tarball 而非源码目录或个人 Skill 副本验证：包体包含企业研发 Skill 正文及全部被引用的必需资源；在隔离宿主装配中能枚举入口名称、用途、触发方式和权限边界，按需读取正文成功。删除个人试点 Skill 后结果不变；不得要求安装者手抄提示词或手工拼接未声明资源。 |
| AC-2 | P0 | 企业组合补齐本链路实际需要的 DevOps、Gitee、Policy 与 Skill 发现／原生 Teamflow 依赖，区分随包成员和宿主前置能力。装配后读工具与入口可见、同一能力无重复注册；现有策略共享目录、官方行禁用、IAM／凭据 fail-closed 不被削弱，停用研发入口不删除用户配置或企业对象。 |
| AC-3 | P0 | 分别移除必需插件、Skill 服务、Teamflow 能力、CLI 入口各测一次：输出缺失项、受影响步骤和可执行下一步，不输出秘密或底层路径；关联尚未核实或执行依赖不足时启动／续跑／远端写调用均为 0。诊断复用现有入口，不以新增通用 doctor 工具或新面板为前提。 |

### US-2：开发者选择一个 Issue，系统核实真实关联后才开始工作

| 编号 | 优先级 | 可测试验收条件 |
|---|---|---|
| AC-4 | P0 | 支持 Issue 入口和变更入口；后者先选定一个 Issue。启动前核实 Issue 恰一所属变更、恰一代码仓库，读取范围、验收、依赖及来源修订／可复核版本标识；每个关联标明真实读取来源。调用参数、标题相似度、模型推断和人工提供的关联只能标为声明，不能标成独立核验结果。 |
| AC-5 | P0 | 对无关联、多变更、多仓库、入口与读取结果冲突、无法读取各有负测。均展示冲突对象／缺失信息，只进行只读澄清；Teamflow 新启动、续跑、提交和远端写调用均为 0，不自行选第一个对象、不写回“修正”关联。用户补充线索后须重新读取核验。 |
| AC-6 | P0 | 技术阶段先提交目标宿主接口核验表，覆盖任务关联、启动、查询、续跑、提交要求和完成结果：每项列实际宿主版本、真实工具／Service 名、参数与返回依据、作用域、能力缺口及证据。只读发现／源码可证明接口存在，实际调用才证明行为；不把工具说明或自造字段当运行证据。必需接口无支持时阻断对应承诺，不修改／fork DSH。 |

### US-3：开发者把任务交给原生 Teamflow，中断后继续同一工作

| 编号 | 优先级 | 可测试验收条件 |
|---|---|---|
| AC-7 | P0 | 对关联已核实、Issue 信息充分的首次请求，通过真实宿主接口最多启动 1 次 Teamflow，并保留可读取的 run 标识和 Issue／仓库关联证据。传入既有范围及验收，不要求用户再手填一份规格；原生内部 PRD／技术材料可保留，但不得成为第二业务真源。接口要求的澄清、分支决策和 PRD 确认照实处理，不声称跳过未支持的阶段。 |
| AC-8 | P0 | 相同 Issue、仓库及要求版本再次进入时，先查询并核对已有 run。运行中仅展示／跟踪原 run，新增启动 0 次；可续跑的中断 run 使用原生续跑一次，新增启动 0 次；已完成 run 先核对当前版本及证据，不自动重开。多个候选、映射不可信、查询失败或不可续跑时暂停并说明；确需新 run 须用户明确决定，保留前序关系，不建立第二任务库。 |
| AC-9 | P0 | 启动、续跑、提交及最终交付前核对真实 cwd、仓库根和用户授权 worktree。工作区错位、任务仓库不符或分支未经授权改变时停止；自动切主目录、stash、提交或清理其他工作树的调用均为 0。为三个错位场景提供负测，并报告冲突而不覆盖现有改动。 |
| AC-10 | P0 | 用真实宿主交接路径和隔离 Git 仓库验证本任务相关实际提交首行保留 `[变更号]`，关联来自 AC-4；读取真实提交信息及 SHA，不仅校验拟议消息。核验原生最终提交是否支持该要求；不支持则列明确阻塞，不能只改 Skill 文案后宣称满足，不能通过跳钩子、改签名或重写历史补救。 |

### US-4：接手人能判断验证和独立审查是否覆盖手里的代码

| 编号 | 优先级 | 可测试验收条件 |
|---|---|---|
| AC-11 | P0 | 验证、审查与交付记录均能定位仓库、Issue 要求版本、实际提交 SHA 和被检代码内容；如检查时有未提交改动，还须保留可复核的差异标识，不把 HEAD 当成全部被检代码。交付前核对最终代码与记录一致，交付范围无遗漏的暂存／未跟踪代码；只有分支名、runId 或不可复核文本不合格。具体绑定方式由技术方案验证，不要求用户手填专有 manifest。 |
| AC-12 | P0 | 对已绑定版本执行本地验证，逐条记录命令、时间、宿主／工具版本、目标版本、退出／断言结果与证据位置。必要验证失败、未运行或无法定位版本时不得宣称验证通过；本需求新增验收用例 0 失败、0 跳过；既有跳过项须单列来源，不计入通过，不以缩小覆盖或删除用例凑绿。 |
| AC-13 | P0 | 独立 AI 审查发生在与实现分离且可证明只读的上下文，记录实际审查者／模型、上下文标识、审查版本、发现及结论；提供只读权限／写入被拒的验证证据。实现者自报、调用方传入 `pass` 或实现上下文自审不算独立审查。修复回实现上下文，修改后复审；无可用隔离能力时明确未审查，不伪造第二审查者。是否额外强制异模型见“假设与待澄清”。 |
| AC-14 | P0 | 验证后修改代码、审查后修改代码、切换提交、变更测试／依赖／验收要求分别测试。旧证据保留为历史，但不得自动用于新候选；重新核对关联与覆盖，并为受影响的最终版本取得新验证及独立审查证据。续跑和交付前均检查版本；未知差异按未覆盖处理，不自动迁移用户旧验收结论。 |
| AC-15 | P1 | 一份交付摘要串联变更、Issue、仓库、相关 run、实际 SHA／已有 PR、验证、独立审查、依赖及未验项。每条结论可定位到证据，写明时间、实际宿主版本、目标对象、来源类型；区分本地真实执行、宿主实测、夹具／mock、企业实测和调用方声明。缺字段标未知，不以调用方声明包装独立取证；命令输出经脱敏且不制造整段日志副本。 |

### US-5：用户能接受当前版本，而不会误以为系统已替自己关闭业务

| 编号 | 优先级 | 可测试验收条件 |
|---|---|---|
| AC-16 | P0 | “待验收交付”须同时满足真实关联已核实、实际版本一致、必需本地验证通过、独立只读 AI 审查通过，并披露依赖及必要仓库规则的满足情况。原生 `completed` 仅证明执行状态，不直接证明这些条件。缺任一必需证据只报告未完成／未验；仅夹具跑通须标“本地机制演示，企业链路未验”，不得计为真实 Issue 交付成功。 |
| AC-17 | P0 | 报告分别列执行结果、候选交付、用户验收、CI、合入、Issue 状态和业务结束状态；未知保持未知。AI 仅提出“待用户验收”，用户对实际版本的明确结论才可记录为人工意见；没有可信取证只保留声明来源，不代写确认。“待验收”不映射为关闭四项全通过，不新增关闭／合并动作，不自动调用关闭、合并、发版或 `change done`。 |
| AC-18 | P0 | 真实企业 CLI、凭据／授权、IAM、受保护仓库规则、Windows／麒麟实机未验证时逐项标 `NOT RUN`／未知及影响；本地宿主链路通过不能改写为企业生产可用。错误、权限拒绝、远端结果 unknown 不自动重放；原有受控写开关、审批、回读、秘密保护及失败脱敏行为不回归，Skill 不承担硬门禁。 |
| AC-19 | P1 | 提供可复跑矩阵，至少包含正常首次交接、相同任务重复进入、运行中进入、中断续跑、已完成再进入、关联冲突、版本变化、缺依赖、伪造通过声明 9 类场景。每例断言启动／续跑／写调用次数、关联及版本、候选资格与失败提示；夹具测试与真实宿主测试分列，必需宿主行为未验不得由 mock 结果替代。 |
| AC-20 | P1 | 同步正式 Skill 使用说明、企业组合／相关包 README、受影响设计索引与契约引用；清楚区分首批交付与后续能力。开发阶段完成本项目 `.gitignore` 审计与必要补齐，证明 tarball／dist／日志／缓存／本地秘密不入库。最终提供 `pnpm check`、`git diff --check` 的实际结果及剩余未验范围；不以文档自检代替代码和宿主行为验收。 |

## 4. anti-goals / 反面目标

1. 安装成功后入口仍只存在于作者的个人 Skill 目录，接手人只能复制聊天里的提示词才能使用；包体测试全绿也拒绝交付（AC-1～3）。
2. 关联缺失或出现两个仓库时，系统悄悄挑一个开始研发；用户重复请求或中断续跑后出现第二个未获确认的 run（AC-4～9）。
3. 用户改过代码，页面／报告仍展示旧验证和旧审查“通过”；或者实现者在同一可写上下文自称已完成独立审查（AC-11～14）。
4. 用户看到“可信交付／可关闭”，打开证据却只有调用参数、模型自述或 mock；本地跑通同时被写成企业授权、IAM 或真实 Gitee 已就绪（AC-15～18）。
5. 用户给出信息充分的 Issue 后被迫重填另一份规格；或只是提交待验收候选，系统便替用户合并／关闭业务（AC-7、AC-17）。

以上都是已确认要求可客观判定的失败，不另设主观速度、风格或界面阈值。独立审查是否必须异模型是额外强度取舍，单列为口味问题，不能据此放松上下文独立与只读要求。

## 5. 交互流程摘要

1. **显式进入**：用户从可发现的企业研发 Skill 选择 Issue；从变更进入时选定本次 Issue，不默认批量启动。
2. **就绪诊断与只读核实**：确认所需工具、原生 Teamflow、CLI 和授权工作区；读取对象及来源。缺验收仅问具体缺口，可提出标明“待确认”的草案，不将草案当已批准平台事实、不擅自写回。
3. **识别既有执行**：按真实 Issue／仓库／要求版本核对 run。已有运行则跟踪、中断则按原生状态续跑；无法唯一定位先澄清，不先启动再去重。
4. **最小交接**：沿用已授权 worktree，把已核实范围、验收、提交要求、企业约束交给原生 Teamflow，保留必要宿主决策关卡；Skill 不接管排程和任务状态。
5. **按版本收口**：读取真实执行结果与 Git 状态，取得该版本本地验证及独立只读审查；修复后更新证据。交付前再核对关联、代码版本及依赖变化。
6. **交给用户**：展示短摘要及可打开的完整证据材料。满足 AC-16 才称待验收候选；用户按该版本决定接受／退回，CI、合入、关闭及业务结束各自保留真实状态。后续写动作需另行具体授权。

摘要使用现有会话／原生工作台，不建设新界面；证据复用已存在载体并给引用，不以统一搬迁所有产物目录为前置条件。

## 6. 优先级与里程碑建议

| 里程碑 | 优先级 | 内容与退出条件 |
|---|---|---|
| M1：先证实可接 | P0 | 核对实际 worktree；形成 AC-6 接口证据表、关联来源和宿主提交可行性结论。任何必需能力无法满足时，先列具体阻塞与可行切片，不能边写边假定上游能力存在。 |
| M2：可安装可发现 | P0 | 完成正式 Skill 资源、组合闭包和依赖诊断，最终 tarball 在隔离宿主可发现，相关能力关闭／缺失不越权。 |
| M3：可交接可续跑 | P0 | 正常交接、重复进入和中断续跑均有真实宿主证据；关联冲突零启动；实际提交满足前缀且仅操作授权 worktree。 |
| M4：可核对待验收 | P0 | 绑定实际代码版本，独立只读审查及本地验证可复核；过期和伪造证据负测通过；不满足企业取证条件则只交本地演示与缺口，不冒称真实 Issue 已交付。 |
