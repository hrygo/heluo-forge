# memory.md — heluo-forge 团队约定与待办（TeamFlow）

> 只记跨需求长期有效的团队约定与待办；需求过程产物留在各自任务夹，不在此追加变更日志。

## 约定

- **插件交付形态**：交付物必须能被宿主以 profile 包形态安装——`package.json` 声明 `dsh.bundle.patch`，补丁 `insert:` 行 `name` 用**包根名**（子路径会被判"无 client 声明"而静默跳过）；声明文件进 `files` 白名单；安装清单不含 `workspace:` 等本地协议（源码引用由构建期闭包，见 ADR-12/#37）；`@deepseek-ai/*` 与 `react` 只走 `peerDependencies` + `peerDependenciesMeta.optional`；策略依赖型插件（如 devops）的补丁层还须自带非空 `config.catalog`（覆盖其只读动作）与显式 `config.audit`（内存舱须 `allowNonDurable`，生产换持久 sink），否则装上也不激活；策略依赖型插件共存时，两个补丁层插入**同一个 `heluo-policy` 行**并写入逐字相同的并集目录（不写 `isolate`、不存在第二个策略实例），同 id 覆盖靠「目录逐字一致」保证，由 `tests/plugin-patch-layers.test.mjs` 守。UI 半的挂载点 `ctx.slots.inject('<slot>', () => ctx.slots.register({ name: '<同一 slot 字串>', id: '<插件标识>' }))`：`inject` 参数与 `register.name` 必须逐字等于宿主槽位名（如 `settings.section`），插件自身标识只放 `id`；写错会静默不挂载而单测全绿。UI 交付的验收以「装进独立 profile、宿主启动日志出现该插件、设置页真实可见该分区」为准，不以步骤文档或静态检查代替。
- **企业交付形态（issue #222 收窄，2026-11-10）**：面向员工的企业交付是「官方 DSH 宿主原样 + 企业私版插件 `.tgz` + 一次初始化脚本」，不制作、不重签、不公证完整 DSH 安装包，也不随包再分发宿主；宿主由员工/管理员从官方渠道取得。初始化脚本 `scripts/init-enterprise-plugin.mjs` 的唯一写入面是 `dsh plugin --profile <p> add <tgz>`（execFile、`shell:false`、固定 argv），幂等（同版本零写入、异版本停止不自动升级），核验只到 `--dump-config` 能证明的注册层并输出 `mounted=unknown`，不得把「包内有文件」或「安装命令退出 0」写成已挂载；不创建 profile、不改 `plugin_manager` 权限、不覆盖用户数据。完整安装包装配器（assemble/verify-full-installer、full-installer 库、installer-inputs）随本次收窄删除。
- **安装入口以本机探测为准**，不写死 profile 名/路径：`dsh` 在 PATH 时用 `dsh plugin --profile <p> add|remove <pkg>`（转发到 profile 目录执行 pnpm），`dsh.profile.bundles` 条目由包自身的 `dsh.bundle.patch` 推导；安装发生在工作区之外，由**主 agent** 执行并预先写明回滚步骤。**卸载不等于 `remove`**：上游 `remove_bundle` 只做依赖移除与重载，不清理 profile 补丁层，配置页写进去的 `- id: forge-devops` 行会残留并在每次冷启动打印「entry not found」；卸载一律走本仓库的卸载命令 `pnpm uninstall:devops --profile <名>`（`--keep-plugin` 只清理补丁层并打印下一步）——按精确条目 id/name 只删本插件写入的那一条、其它条目逐字不动、回显删除区间，再移除插件，不得只跑 `dsh plugin remove`。
- **CLI 入口与配置面**：路径类配置以插件配置页（Web UI 表单；经 `dsh-settings` 表单面 + `dsh-config-editor` 落到活动 profile 补丁）为主路径，环境变量只在 CI / 无 UI 场景兜底；缺省由装配期自动发现自身位置。Windows 上路径类入口只判「存在且是普通文件」，不按扩展名拦截：npm 生成的 `.cmd`/`.ps1`/无后缀 shim 都能保存、也能被自动发现（同一位置有原生 `.exe` 时 `.exe` 优先），`.cmd`/`.bat`/`.ps1`/`.com`/`.vbs` 词表只用于运行期失败提示。`shell:false` 启动不了这些脚本，提示须把原因归到运行时能力并指向原生可执行文件，绝不为此引入 shell 或改启动方式。契约键是四个 camelCase `dopBin`/`dopEndpoint`/`sourceType`/`timeoutMs`，配置页只暴露普通用户能判断的两项 `dopBin`/`timeoutMs`；`dopEndpoint` 只经环境变量或配置文件设置，页面保存不得清空；`sourceType` 由后端按 dop 单侧推导（显式配置 > 环境变量 > 推导：dop 入口已解析时 `enterprise`，否则 `mock`），普通用户在页面上既看不到也不需要判断。Gitee 包的五个键（`cliPath`/`host`/`timeoutMs`/`authEnv`/`persistentToken`）不进配置页：`authEnv` 与 `host` 均可选，默认直接用 CLI 全局凭据（不再要求单独配 `GH_TOKEN`），`persistentToken` 默认 `warn` 只告警。配置页显示名与指引句统一为「设置 → 企业 DevOps」（页面 `nav`/`title`、`CLI_PAGE_HINT`、README 同源），用户可见文案不写 `.exe` 后缀。路径与 endpoint 只在配置页内可见，工具输出、日志、报告一律不回显。
- **平台来源分工**：业务事实（系统变更、用户故事、验收条件、发布信息）走企业 dop CLI（`change view <id> --json`、`change list --json`；真机无 `-j` 短名，字段契约按 2026-07-06 校准；本机为 mock，位于外部工程 oh-my-sdd 的 `scripts/dop`，不在 PATH、非常驻服务，可执行路径与 endpoint 按「插件配置页 > 环境变量 > 装配期自动发现」三层解析，不硬编码、不写入文档、不落版本库）；仓库/Issue/PR/评审/交付判定走企业内**唯一的 Gitee**——`gh` 是给它写的兼容 CLI（语法与 GitHub 版完全相同），全局命令、前提是本地已配好 SSH/凭据，不另配 `GH_TOKEN`，不存在「GitHub 面 vs Gitee 面」两个 provider；本地 `git commit`（首行必须 `[变更号]`）与 `git push`（远端写，须登记 + `confirm`）也归 Gitee 侧执行，PR 合并/Issue 关闭/发版/流水线触发仍不做。mock 结果不算企业证据。
- **契约兼容只在适配层吸收**：平台原生命名与输出封装差异——dop 原生 `code`/`state`/`summary`/`userStory`、Gitee `gh` 的 `data.list` 信封与 `path_with_namespace`、`org/group/repo` 三段仓库引用——只在 `packages/forge-devops/src/` 适配层单点归一（字段别名表一处、仓库引用解析一处，不得在多处复制正则），归一结果仍是契约里的 snake_case 形状；平台未给的字段进 `missingFields` 并在卡片上显示「平台未提供」，不猜字段、不伪造，同样不得因此放松任何写门禁或 fail-closed 语义。
- **平台写动作按门禁已覆盖范围默认开放**（建 Issue、审查评论、PR 关联；变更内容回写自 2026-11-04 起由 `change update --summary/--description/--ai-ac` 实现，默认不登记即拒绝、登记 enabled 需审批台账，写前须先读该变更、写后回读），未覆盖或无权限时状态可见为 `denied`，绝不静默跳过；状态只允许 `done` / `failed` / `denied` / `unknown`（扩展 `skipped` / `blocked` / `stale`），只用退出码 0 不算成功，`unknown` 不自动重放；同一变更重复执行幂等。合并 PR、关闭 Issue、`dop change done`、CI 触发、部署/回滚与审批永不在动作白名单内。
- **平台写回只有一个入口**：`forge_devops_change_update`（`change.clarification.write`）固定 argv `change update <code> [--summary|--description|--ai-ac]`，不做 argv 透传；`confirm{object}` 与目标逐字一致、目标必须是会话已读到的变更；结果以 `change view` 回读为准（done/failed/unknown），退出码 0 不算成功、未知不重放；默认关闭，登记 enabled 还须有效审批台账。
- **只读面是枚举式薄 runner**（D 方案，2026-11-03 用户确认）：一个只读工具按枚举动作（`change.read` / `change.list`）分发，每个动作有自己的参数 schema；新增只读子命令走"取证真实 flag → 加枚举与 schema"，绝不引入自由 argv / 通用 `run`。清单 `target` 固定 `@me`（策略要求非空 target）；`facts.raw` 只进当前受权会话，不落指标/审计/产物。产物落盘的 `clarify` / `plan` 只接受结构化 `data`、由纯函数机检并生成正文，手写 `body` 不能绕过。
- **证据纪律**：任何"已实测/已验证"的结论必须写明命令、时间、宿主版本、目标对象与**来源类型（mock 实测 / 企业实测）**；mock 结论不得写成企业已联调。Teamflow run 的归属只看宿主 journal 的 `workspacePath` 是否落在授权 worktree 内（真实路径比较）：归属由 `agent.session.header.cwd` 决定、`productRoot` 不改变归属；`stateRoot`/`commitRoot` 在 0.3.2/0.3.3 宿主不提供，记 `unknown`、**不得作为失败项或阻断项**（2026-11-06 判据，取代 r13 AC-9/G0 口径，见 `docs/teamflow/20261106-r1-journal-root-alignment/TECH-CHANGE.md`）。
- **验证基线**：仓库根 `pnpm check` + `git diff --check`；新增或修改包必须带离线测试并进入 `node --test` 自动发现范围，tarball 清单复用 `scripts/check-bundle-tarballs.mjs`；发布产物以 `node scripts/build-enterprise-bundle.mjs <dir>` 生成 tarball + `bundle-manifest.json` + `SHA256SUMS`（`/artifacts/` 已忽略），再以 `pnpm verify:bundle <tarball>` 离线核验（exit 0/1/2、首个差异即失败、结构规则与 manifest 逐项比对）；`tests/host-probe.test.mjs` 按 `.dsh-version` 做宿主版本门控——`dsh --version` 不等于目标时两例 skip 并在文案中写明实际版本、目标版本与 K-1 原因，`DSH_BIN` 仍可指定、`DSH_HOST_PROBE_FORCE=1` 强制复跑，断言不得删除或弱化。
