# r9 · 失败面脱敏 / 刷新重建读面 / 卸载清理补丁条目

## 1. 背景与目标

三项问题都已在本机真实使用中暴露，且都在「用户已经按提示做完动作、问题仍然存在」的位置上：

1. **spawn 失败把本机路径吐给用户。** 唯一子进程出口在命令**未启动**时，把底层 Node 错误（形如 `spawn <本机绝对路径>/dop ENOENT`）当证据行透传进失败面，读信封、写动作结果与变更卡片都会带出本机绝对路径；现有的路径脱敏只对绝对路径与 URI 生效，且**故意保留 errno**，相对路径入口（如 `bin/dop`）连脱敏都不触发。
2. **刷新只换卡面、不换读面。** 配置页的「重新自动发现」走 `GET /api/forge-devops/cli?refresh=1`，只重扫发现结果并重合并配置层，**不重建流程/适配器**；工具调用仍按旧路径启动。于是二进制改名或移动后，页面显示「未找到」，工具却继续按旧路径 spawn，出现互相打脸的一致性窗口。
3. **卸载留下悬空补丁条目。** 配置页保存会把本插件条目写进活动 profile 的补丁层；卸载插件（`remove_bundle`）只做依赖移除与重载，**不清理补丁层**，残留的 `- id: forge-devops` 行在宿主下次启动时触发「entry not found」警告，且每次启动都重复。

**目标**：三项各自收敛到「用户看到的就是事实」——失败提示只说类别与下一步（零路径、零 errno、零原始报错）；点一次刷新，卡面与读面同时是新状态；卸载之后，本插件写过的补丁条目一条不剩、别人的一条不少。

**非目标中的底线**：不修改上游 DSH（不建 fork、不打 `@deepseek-ai/*` 补丁）；`remove_bundle` 保持上游行为，清理能力由本仓库提供。

## 2. 用户故事

1. **入口配错的企业用户**：保存成功、调用工具失败。我看到的是「入口是包装脚本 / 原生入口未能启动」这一类**类别**加一句「去设置 → 企业 DevOps 重新选择」的**下一步**，而不是一段带本机路径的 Node 报错，也不是一个我需要去搜的 errno（AC-1、AC-3）。
2. **同一用户的第二诉求：能自查但不能被泄漏**：提示里没有任何路径、endpoint、errno、退出码或原始报错片段——把提示整段贴给同事或贴进工单，不会带出我的机器目录结构（AC-2）。
3. **换了 CLI 安装位置的运维**：我把 `dop` 改名/挪走后点「重新自动发现」，页面说「已找到（新路径）」时，下一次工具调用用的就是新路径；页面说「未找到」时，下一次调用明确报未找到，绝不会按旧路径偷偷启动（AC-6、AC-7、AC-8）。
4. **卸载后不再被警告骚扰的用户**：我卸载本插件后，宿主冷启动不再打印这个插件的「entry not found」；我的其它插件条目、我手写的注释和顺序一字未变，并且卸载输出明确告诉我删了哪一条、删在哪几行（AC-11、AC-12、AC-13、AC-14、AC-15）。

## 3. 范围与非目标

**范围（本轮三项全修）**

- 失败面脱敏：命令未启动（spawn 失败）时的只读信封、写动作结果、变更卡片，统一为 NO_READER 同口径的「reason + 失败类别 + 下一步」，零路径、零 errno、零原始报错。
- 刷新重建读面：「重新自动发现」与「内容变化后保存」走同一套完整重建逻辑，刷新响应返回前读面已就绪。
- 卸载清理补丁条目：本仓库提供卸载命令，先精确删除本插件写入 profile 补丁层的那一条、回显删除内容，再（可探测到 CLI 时）执行插件移除；其它条目逐字不动。

**非目标**

- 不改上游 DSH 任何包，不新增 `@deepseek-ai/*` 补丁、不建 fork；`dsh plugin remove` / `remove_bundle` 单独使用时仍是上游行为（文档说明，不承诺自动清理）。
- 不改变配置页可编辑字段集（仍是 dop 可执行文件 / gh 可执行文件 / 超时三项），不新增页面控件。
- 不改发现算法本身（候选目录、tier 优先级、200 目录/300ms 预算）、不改工具清单与写动作默认 denied 口径。
- 不引入凭据、真实企业地址或本机路径进文档、日志与报告。

## 4. 反面目标 / anti-goals

以下任一条发生，即使测试全绿、AC 逐条打勾，也应判定本次交付失败：

1. **脱敏后提示变成一句「命令失败」。** 用户把包装脚本入口配上后调用，提示里既没有「入口形态」也没有「下一步」，用户看完不知道该换原生二进制还是该重装 CLI——提示存在，但与用户下一步动作无关。
2. **刷新看起来生效了但没生效。** 改名二进制后点刷新，卡面显示「已找到（新路径）」，下一次工具调用仍按旧路径 spawn 并报旧路径未找到；或卡面显示「未找到」而工具照旧跑通。卡面与工具结果互相打脸。
3. **清理误伤：删掉的不是自己的那条。** 卸载一次，兄弟插件（如 forge-gitee 的策略行）、官方行或用户手写注释一并消失或被重排——补丁层「干净了」，但用户丢的是别人的配置。
4. **「说了删了、其实没删」。** 卸载命令 exit 0 并回显「已清理」，宿主冷启动仍打印同一警告；或命令只打印计划、需要第二次确认才真正写入，用户以为已完成。
5. **只对开发机这一次有效。** 清理靠硬编码 profile 路径、硬编码 tarball 名或只认 `id:` 一种写法；换 profile 名、或条目写成 `name:`、或补丁层不存在时，命令静默 exit 0 却什么都没删——看起来通用，实际只在自己机器上工作过。

## 5. 交互流程摘要

**A. 工具调用命中 spawn 失败**

工具调用 → 门禁 → 适配器 → `execFile` 未启动（`exitCode === null`）→ 单点脱敏渲染 → 三出口：只读信封（`message` 为无路径指引句，`detail = { reason, category, next }`）、写动作结果（`status: unknown` + 同类 detail，语义不变）、变更卡片失败行 → 用户看到类别与下一步，看不到任何路径与 errno。

**B. 配置页「重新自动发现」**

点刷新 → `GET /api/forge-devops/cli?refresh=1` → 服务端：一次发现 → 重合并配置层 → **重建流程/读面/适配器** → 组装响应 → 页面渲染新卡面 → 下一次工具调用使用新读面（同一状态，无中间态）。失败则返回结构化失败（reason + 指引），不返回空白 500、不留半重建状态。

**C. 卸载**

从仓库根执行卸载命令（`--profile <名>`，缺省探测活动 profile）→ 读该 profile 补丁层 → 定位本插件写入的条目（按精确条目 id/name）→ 删除该条目及其配置子树 → 回显 profile 名、条目 id、删除行区间、前后行数 → 探测到 `dsh` CLI 时执行插件移除（探测不到则只清理并打印下一步命令）→ 宿主下次启动无该条目警告。

## 7. 依赖与风险

**依赖**

- 本机 DSH 的插件管理入口（`dsh plugin --profile <p> add|remove`）与 profile 补丁层文件位置，以本机探测为准；上游实现不在本仓库、不得修改。
- 现有只读解析能力（`scripts/lib/bundle-rules.mjs` 的 `parsePatchLayer`）可复用于补丁层结构识别。
- 既有静态门禁 `tests/plugin-patch-layers.test.mjs`（补丁行 id 唯一、策略行至多一行、isolate label 对齐）不得被新逻辑破坏。

**风险与缓解**

- *脱敏降低可诊断性*：缓解 = 类别枚举固定且互斥（包装脚本 / 原生入口未启动）+ 固定下一步指引 + 文档给出「现象 → 类别 → 动作」对照；不在提示里塞路径作为补偿。
- *刷新变慢或触发企业侧命令*：缓解 = 刷新只做「发现 + 重建」，不试跑目标命令（见 T2 默认），发现预算沿用 r3 的 200 目录 / 300ms。
- *补丁层写法多样（`id:` / `name:`、注释、空行、缩进块）*：缓解 = 结构化解析 + 按行区间删除，禁止正则前缀模糊匹配；正反 fixture 覆盖。
- *上游 `remove_bundle` 未来行为变化*：缓解 = 清理命令不依赖其内部实现，只依赖「依赖清单 + profile 补丁层文件」两个事实；文档标注口径来源。
- *真实冷启动验证需宿主重启*：本轮以 fixture + 单测验证「补丁层无残留」，真实安装→卸载→冷启动由主 agent 在验收阶段执行，本轮相关项标 NOT RUN。

## 11. 假设与待澄清

- **F1（事实）卸载入口归属**：`remove_bundle` 属上游 DSH 插件管理器，本仓库 AGENTS.md §1 明确不分发 DSH 本体、不创建 fork 或修改上游，因此「卸载时自动清理补丁条目」只能由本仓库提供一条卸载命令承担，`dsh plugin remove` 单独使用仍是上游行为。若用户要求必须由 `remove_bundle` 自身完成，则需修改上游包（越界，需单独授权）。默认：本仓库提供卸载命令。
- **F2（事实）真实冷启动验证归属**：本轮可在 fixture 级证明「补丁层零残留」，但「卸载 → 冷启动无警告」需在真实 profile 安装并重启宿主，属主 agent 验收动作；本轮相关项标 NOT RUN，不写成已验证。默认：主 agent 在验收阶段执行真实安装/卸载/重启并复核。
- **T1（口味）脱敏文案是否保留「入口形态」类别**：一种做法是保留类别（来自**配置**而非错误文本，仍不含路径/errno），用户能据此决定「换原生二进制」还是「重装 CLI」；另一种是彻底一句话（最安全但可诊断性最低）。默认：保留类别，因为它是唯一不依赖底层报错的可行动线索。
- **T2（口味）刷新是否顺带做一次可用性自检**：可在刷新时试跑目标命令（如 `--version`）以「刷新即知能不能跑」，代价是刷新触发企业侧进程与额外耗时，且与「刷新零副作用」的直觉冲突。默认：不试跑，刷新只做发现 + 重建。
- **T3（口味）清理范围**：只删本插件登记的那一条条目，还是连带清理所有 `heluo-` 前缀条目（例如配置页曾写过的策略行）。默认：只删本插件登记条目（精确 id/name 匹配），用户手写与兄弟插件条目一律不动。
- **T4（口味）卸载命令形态**：一条命令完成「清理 + 移除插件」，还是分两步（先清理、再由用户执行 `dsh plugin remove`）。默认：一条命令完成（提供 `--keep-plugin` 只清理），因为「卸载」应一步到位且输出可回显。
