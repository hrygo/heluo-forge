# PRD · r20 受控写最小门禁 P1 安全基线

## 1. 背景与目标

### 1.1 现状

- 受控写最小门禁按 `docs/plans/2026-11-19-policy-minimal-gates.md`（CORP-DSH-PLAN-024）分四阶段实施；P0 骨架已完成（`docs/teamflow/20261119-r19-policy-minimal-gates/`，HEAD `8c68d41`）：八开关默认全关、配置装载期校验、恒开审计、gate 只装配 resolve/identity/audit/receipt，未实现开关置 `true` 会在装载期报错。
- P0 已删除 approval 通道，但确认卡尚未接入 `ctx.userQuestions`；`denyDelegatedWrites`、`confirmPush`、`confirmDopWrite` 三个开关仍不可开启；子代理写与决策复用没有独立行为与用例。
- P0 的身份校验实际已对登记写动作生效，但没有「常开且无开关」的显式契约与三态用例，失败文案与复验边界未形成可回归基线。

### 1.2 本阶段目标

1. **身份校验常开**：6 条登记受控写必须解析出 IAM 身份，解析失败即拒，不提供关闭开关，不缓存身份。
2. **子代理写拒绝且不弹卡**：`denyDelegatedWrites` 开启时，子代理发起的受控写一律拒绝；子代理永远不会收到确认卡，无法借卡片获得人工授权。
3. **确认卡片通道**：`confirmPush` 只作用于 `gitee.git.push`，`confirmDopWrite` 只作用于 `change.clarification.write`（DOP 流转）；一次判定最多一次 `ask`，多原因合并、分步呈现、默认 120s 超时、固定错误码、询问与结论均入审计。
4. **决策复用**：用户已允许过的同一调用重试时按 `toolName + callId + action + 参数摘要` 复用上次允许，不再弹卡；会话内 32 条 LRU，命中只记一条 `rule=reused-decision` 审计。
5. **不回退**：八开关全关时行为与 P0 等价；其余五个未实现开关继续 fail-closed；审计恒开、失败中止、失败面零泄漏的口径不变。

### 1.3 成功判据

- 单元用例覆盖三个已实现开关的关/开/依赖缺失三态、卡片错误码矩阵、决策复用与 LRU 上限、子代理拒绝、身份缺失。
- pinned Node 24.21.0 下 `pnpm check` 全绿、`git diff --check` 干净；独立 PR（base `feat/policy-p0-skeleton`）。
- 隔离 profile 实测由用户亲自执行，执行前一律标 `NOT RUN`，不写成本地已通过。

## 3. 范围与非目标

### 3.1 范围

- `packages/forge-policy` 内实现身份常开、子代理拒绝、`ctx.userQuestions` 确认通道、决策复用及其审计。
- 只放开 `denyDelegatedWrites`、`confirmPush`、`confirmDopWrite` 三个开关；`IMPLEMENTED_RULES` 追加这三项，其余五个保持未实现。
- 单测覆盖 §7 全部 AC；包内文档补最小使用说明；独立 PR 交付。
- 与 `forge-devops`/`forge-gitee` 的消费面只做必要适配：动作名与卡片所需的目标定位信息取自既有工具调用参数，不改变业务写实现。

### 3.2 非目标

- 不做 P2 内容闸：`contentGate` 保持未实现，置 `true` 仍应在装载期报错；9 条内容规则、内容软命中的分步卡片本阶段不实现。
- 不做 P3 的 `denyUnknownAction`、`denyHumanRecord`、`protectPaths`、`enforceProcessRules` 与 `/policy-audit`。
- 不调用宿主 approval，不覆写宿主 `permission`，不接管沙箱与会话审批策略。
- 不自建确认 UI；卡片由宿主 `ui-user-questions` 渲染，插件只负责请求与判定。
- 不做跨会话、跨 profile 的决策复用，不把决策缓存落盘。
- 不做按动作超时配置、自定义确认文案、用户输入确认短语等扩展。
- 不改 catalog 的 6 条写动作构成，不改 bundle 补丁层（补丁层继续不写 `rules`）。
- 不修改 DSH 本体，不改动 PR #400 的内容与历史。

## 4. 反面目标 / anti-goals

> 即使测试全绿、开关可配，只要出现以下任一结果，本阶段就应被判定为产品失败。

1. **用户拒绝或超时后仍然写成功。** 在隔离 profile 对同一目标重跑，点了「取消」或等到超时，远端仍出现新提交或新变更内容；或卡片弹出前就已经执行，卡片只是事后通知。要求：拒绝/超时后执行体与远端写均为 0 次，卡片必须先于执行。
2. **子代理换个工具名、拆参数或换个受控动作就能写。** `denyDelegatedWrites` 开启时，子代理对 6 条受控写逐条尝试，任一动作发生执行或收到卡片即失败；拒绝文案不得暗示「改用别的工具/参数重试」。
3. **卡片把正文、令牌或路径摊在用户面前。** 卡片字段里能搜到提交正文、变更描述、令牌、绝对路径或文件名；用户截一张图就能泄露内容。卡片只允许出现动作可读名、repo/branch/changeId 定位与原因类别。
4. **复用把一次允许套到另一次写入上。** 同一 callId 但目标、分支或正文已变化时不再询问而直接放行；或把 A 动作的允许用于 B 动作。要求：键中 action 与参数摘要必须同时命中，执行前再复验一次。
5. **没有应答端或用户走开时调用挂死。** 在 CLI/无卡片环境调用受控写，进程等待远超 120 秒仍不返回；或超时后没有任何可读原因，用户不知道是否执行过。要求：最迟 120 秒给出拒绝结论，并说明未执行。

## 5. 交互流程摘要

### 5.1 判定顺序

```
工具调用
└─ resolve：工具名 → action；未登记 → out-of-scope 直接放行（不读身份、不写审计）
   └─ delegation（denyDelegatedWrites）：子代理 + 受控写 → 拒绝，不弹卡
      └─ identity（常开）：未解析到 IAM actor → 拒绝
         └─ 是否需要确认：confirmPush && gitee.git.push，或 confirmDopWrite && change.clarification.write
            ├─ 否 → 放行
            └─ 是 → 复用命中（键完全一致）？
               ├─ 是 → 放行（只记 1 条 rule=reused-decision 审计）
               └─ 否 → 审计 asked → ask(questions…) [默认 120s]
                        ├─ 应答恰为允许标签 → 审计 answered=allow → 放行
                        └─ 拒绝/超时/无应答端/非法应答 → 审计 answered=deny → 拒绝
         └─ 放行 → 审计 begin → 执行恰 1 次 → 身份/参数复验 → 审计 settle
```

关闭的规则不生成阶段，不进入对应分支，只保留 P0 已有的放行审计；八开关全关时与 P0 行为逐项等价。

### 5.2 卡片契约

- 一次判定至多调用 `ask` 一次；`questions` 数组长度等于合并后的原因数，客户端按「下一步/提交」分步呈现，提交时合并结果。
- 每个问题包含：可读标题、说明、允许标签、拒绝标签。固定标签：允许「允许本次写入」，拒绝「取消本次写入」；判定用常量精确匹配，不做包含、大小写或前缀匹配。
- 展示内容只含：动作可读名、目标定位（`repo`/`branch` 或 `changeId`）、原因类别（动作确认 / 内容风险）。正文、参数原文、令牌、绝对路径、文件名一律不出现。
- P1 生产路径只有「动作确认」一个原因；合并函数必须可承载两类原因（动作确认在前、内容风险在后），用 2 个合成原因做单测，P2 接入内容闸时不改卡片契约。
- 默认超时 `confirmation.timeoutMs = 120000`，覆盖整次询问（含多个问题）；超时、无应答端、`ask` 异常、应答形状非法全部 fail-closed 为拒绝。
- 插件卸载/重载时，挂起询问按拒绝收尾并留审计；不跨会话恢复。

**卡片错误码矩阵**

| 代码 | 触发 | 判定 | 用户可见要点 | 可重试 |
|---|---|---|---|---|
| `POLICY_CONFIRM_DENIED` | 用户选拒绝标签，或应答含拒绝标签 | deny | 已取消本次写入，未执行；可调整后重试 | 是 |
| `POLICY_CONFIRM_TIMEOUT` | 超过 `confirmation.timeoutMs`（默认 120s） | deny | 等待确认超时，未执行；请重试 | 是 |
| `POLICY_CONFIRM_UNAVAILABLE` | `ctx.userQuestions` 缺失、无应答端、服务不可用 | deny | 当前环境无法发起确认，未执行；请在桌面端重试 | 是 |
| `POLICY_CONFIRM_INVALID_ANSWER` | 应答缺失、结构非法、空/非数组 `selected`、未知标签 | deny | 确认结果无法识别，已按未确认处理 | 是 |
| `POLICY_CONFIRM_DELEGATED` | 子代理来源命中需要卡片的动作（防御性兜底） | deny | 受控写必须在主会话发起 | 否（换主会话） |
| `POLICY_CONFIRM_ERROR` | `ask` 抛错或确认流程内部异常 | deny | 确认流程异常，未执行；请重试或联系管理员 | 是 |

代码写入结构化判定结果与审计；用户可见文案不拼接代码，不用超时冒充拒绝，也不用通道缺失冒充超时。

### 5.3 决策复用

- 键 = `toolName + callId + action + 参数摘要`；参数摘要沿用审计 `contentDigest` 的归一化摘要，不落参数原文。
- 只有卡片判定为「允许」的决策进入缓存；拒绝、超时、无应答、非法应答与执行失败都不入缓存。
- 命中后跳过 `ask`，不写 asked/answered，只写 1 条 `rule=reused-decision` 审计；写动作本身的 begin/settle、一次性收据与身份/参数复验照常执行。
- 会话内 LRU，上限 32 条；同键重复命中刷新为最新且不增条目；第 33 个不同键淘汰最久未使用项；插件卸载/重载即清空，不落盘、不跨会话。

### 5.4 开关行为矩阵

| 配置 | `gitee.git.push` | `change.clarification.write` | 其余 4 条受控写 | 子代理受控写 |
|---|---|---|---|---|
| 全关（默认） | 直接放行 + 审计 | 直接放行 + 审计 | 直接放行 + 审计 | 与 P0 同路径（delegation 阶段不生成） |
| `confirmPush` | 弹卡 1 次 | 直接放行 | 直接放行 | 需要卡片的写拒绝且不弹卡 |
| `confirmDopWrite` | 直接放行 | 弹卡 1 次 | 直接放行 | 同上 |
| `denyDelegatedWrites` | — | — | — | 一律拒绝，先于身份与卡片 |

## 7. 验收标准

**AC-1 身份校验常开，无开关。** 在三个已实现开关的任意组合（含全关）下，6 条登记受控写缺少 IAM actor（`undefined`、空串、无 `principal`/`subject`）一律拒绝；执行体调用 0 次；文案含动作名与「设置 → 账号」。配置层不存在可关闭身份校验的键，`rules.identityCheck` 之类未知键装载期报错并拒绝挂载。验证：单测覆盖每个开关组合 + 配置校验用例。

**AC-2 身份每次实时解析，前后复验。** 准入前、执行前/后各解析一次身份；期间 actor 变化或变为空，本次写拒绝或按失败处理，执行 0 次；同一会话内两次调用各自解析，不复用上次结果。验证：假 `getActor` 按调用次数返回不同值。

**AC-3 子代理拒绝（开关开）。** `denyDelegatedWrites=true` 时，子代理来源（`agent.kind=child`）发起的 6 条受控写全部拒绝；`userQuestions.ask` 调用 0 次；执行体 0 次；审计恰 1 条 deny，`agent.kind=child`，summary 含「子代理」；文案含「主会话」且不提示改用其他工具或参数规避。验证：6 动作 × 单测。

**AC-4 子代理规则关闭时的语义。** `denyDelegatedWrites=false` 时不生成 delegation 阶段，该规则不拦截；但子代理永远不会收到确认卡：命中 `confirmPush`/`confirmDopWrite` 的写一律拒绝（`POLICY_CONFIRM_DELEGATED`），`ask` 0 次；不需要卡片的受控写与主会话同路径处理，审计保留 `agent.kind=child`。验证：子代理 × 开关组合矩阵。

**AC-5 弹卡范围精确。** `confirmPush=true` 时仅 `gitee.git.push` 弹卡 1 次；`confirmDopWrite=true` 时仅 `change.clarification.write` 弹卡 1 次；其余 4 条（`gitee.issue.write`、`gitee.pr.write`、`gitee.review.publish`、`gitee.review.record`）在任何开关组合下 `ask` 0 次并直接放行；两个确认开关全关时 6 条写 `ask` 全部 0 次，行为与 P0 一致。验证：6 动作 × 4 开关组合。

**AC-6 一次询问承载全部原因。** 一次判定至多 1 次 `ask`；`questions` 数量等于合并原因数；每项含标题、说明、固定允许标签与固定拒绝标签；卡片字段只含动作可读名、目标定位与原因类别，正文/参数原文/令牌/绝对路径/文件名 0 命中；P1 生产路径 1 个原因，合并函数用 2 个合成原因验证顺序（动作确认在前、内容风险在后）与单次提交。验证：假 `userQuestions` 捕获请求 + 全文正则扫描。

**AC-7 应答判定 fail-closed。** 仅当每个问题的 `selected` 恰为允许标签、且不含拒绝标签、无未知标签时判允许；拒绝标签、空/缺失/非数组 `selected`、未知标签、多余应答任一出现即拒绝；「未选择」绝不等于允许；禁止包含、大小写或前缀模糊匹配。验证：应答矩阵（≥8 种畸形输入）。

**AC-8 超时边界。** 默认 `confirmation.timeoutMs=120000`，取值必须为正整数（0、负数、非数在装载期拒绝）；从发起 `ask` 起计时，覆盖整次询问；超时即拒绝（`POLICY_CONFIRM_TIMEOUT`），文案说明超时与可重试；假 `userQuestions` 永不返回时，进程在超时后结束等待，不挂死。验证：注入短超时/假时钟，不真等 120 秒。

**AC-9 无应答端与通道异常 fail-closed。** `ctx.userQuestions` 缺失、`ask` 抛错或返回不可用 → 拒绝（`UNAVAILABLE`/`ERROR`）；执行 0 次、不重试弹卡、不降级调用 approval；文案可读，不含堆栈、路径、errno、spawn 前缀。验证：3 类异常注入。

**AC-10 错误码矩阵唯一。** 六类结论对应 §5.2 的唯一代码；代码同时写入结构化判定结果与审计；用户可见文案不拼接代码；同一场景不出现两个代码。验证：每个代码至少 1 条正例，跨场景不串码。

**AC-11 询问与结论可追溯。** 弹卡前写 1 条 `asked` 审计（动作、目标、原因类别、`agent.kind`、`operationId`），结论后写 1 条 `answered`（decision、代码、耗时）；拒绝与超时也各 1 条；正文、参数原文、令牌、绝对路径、文件名原文 0 出现；`asked` 写失败则中止，不弹卡、不执行，文案不含「审计」二字；允许后的写仍按 P0 记 begin/settle。验证：假审计 sink 记录条数与字段 + 泄漏正则。

**AC-12 复用命中。** 键 = `toolName + callId + action + 参数摘要`；卡片允许后，同键重试不再调用 `ask`，直接进入审计与执行；不写 asked/answered，只写 1 条 `rule=reused-decision` 审计；不同 callId、action、参数摘要任一变化必须重新弹卡；拒绝、超时、无应答、非法应答与执行失败均不入缓存。验证：键的 4 个分量逐一变异。

**AC-13 LRU 上限与会话边界。** 缓存最多 32 条；写入第 33 个不同键时淘汰最久未使用的一条；同键重复命中刷新到最新且不增加条目；被淘汰键重试重新弹卡；插件卸载/重载后缓存为空，不落盘、不跨会话。验证：33 键序列 + 命中顺序断言。

**AC-14 复用不越界。** 命中复用后、执行前重新校验参数摘要与准入时逐字一致；target、正文、分支等任一变化即拒绝并重新弹卡；仅凭 callId 不得放行；复用不得跳过身份校验、一次性收据与执行后复验。验证：同 callId 改参数 + 身份变化组合。

**AC-15 允许前零执行、允许后恰一次。** 卡片允许前执行体 0 次；拒绝/超时/无应答后 0 次；允许后恰 1 次；同一次执行对象只准入一次（并发 prepare 不重复发卡、不重复收据）；不伪造 allowed-once、不绕过 guard。验证：执行计数器 + 并发准入用例。

**AC-16 三态与依赖缺失。** `denyDelegatedWrites`、`confirmPush`、`confirmDopWrite` 各有关/开/依赖缺失三态用例；关 = 不生成阶段、行为与 P0 等价（仅原有审计）；开 = 装载成功且 pipeline 出现对应阶段；开关开但依赖缺失（无 `userQuestions` 或无 IAM）时判定拒绝而不是放行；其余五个未实现开关置 `true` 仍在装载期报 `rules.<key>` 且不挂载。验证：参数化用例 + 装载期错误断言。

**AC-17 失败面不掺假。** 身份缺失、子代理、拒绝、超时、无应答、非法应答六类文案与审计 summary 不含绝对路径、盘符、UNC、`~/`、URI、spawn 前缀、errno、退出码、堆栈、令牌；每类文案与真实原因一致（超时不得写成用户拒绝，通道缺失不得写成超时）。验证：六类输出全文正则 + 语义断言。

**AC-18 文档口径。** 包 README 或既有 policy 使用文档补最小说明：三个开关已实现、其余五个未实现；只有 push 与 DOP 流转弹卡；默认 120s；复用范围与命中规则；不得出现「八开关全部可用」「所有受控写都会弹卡」的表述。验证：文档关键词断言 + 人工复核。

**AC-19 工程门禁。** pinned Node 24.21.0 下 `pnpm check` exit 0、0 fail、新增用例 0 skip；policy 包用例数只增不减；`git diff --check` 干净；无新增运行时依赖；未修改 DSH 本体；未改动 PR #400 内容与历史；`git status` 无 `dist/`、`logs/`、`*.tgz` 等产物。验证：命令输出与变更清单。

**AC-20 交付形态。** 独立 PR，base=`feat/policy-p0-skeleton`，标题 `feat(policy): P1 安全基线（身份/子代理/确认卡片/决策复用）`；提交说明不以 `#` 开头；PR 描述列出四项能力的证据清单与 `NOT RUN` 项。验证：PR 元数据与提交历史检查。

**AC-21 隔离 profile 实机（用户执行）。** 在隔离 profile 的 `never` 会话开启 `confirmPush`：真实 `gitee.git.push` 弹卡；允许后执行 1 次并落审计；拒绝后远端零改动；子代理发起同一写被拒且不弹卡；身份缺失被拒。记录命令、时间、宿主版本与来源类型（用户实测）；未执行前标 `NOT RUN`，不计入 CI 通过。验证：用户执行记录。

## 11. 假设与待澄清

- **(a) 事实｜宿主 `ctx.userQuestions` 契约。** 本 PRD 按 ADR-29 假设宿主提供 `userQuestions.ask`，可一次携带多条 question 并按顺序返回 `selected`；超时由插件计时，无应答端表现为不可用或超时。若目标宿主（仓库 `.dsh-version` 0.2.1-rc.3）实际只支持单条询问、返回结构不同或没有该服务，合并卡片与超时实现需调整，缺服务时该动作一律拒绝。**默认：按 ADR-29 契约实现，TECH 阶段先用真实宿主契约锚定并补一条适配用例。**
- **(a) 事实｜子代理识别字段。** P0 的 `agentKindOf(exec)` 已读取 `exec.agent.kind`，但 root/child 的具体取值、父子会话是否都携带 `agent` 需在 TECH 阶段用宿主契约与真实 exec 锚定。若无法可靠识别，则「需要卡片的写」一律拒绝（无法证明主会话人工在场）。**默认：`agent.kind === 'child'`（归一常见同义取值），并在真实 exec 上补一条锚定用例。**
- **(b) 口味｜`denyDelegatedWrites` 关闭时，子代理发起「需要卡片」的写怎么办？** 默认仍拒绝且不弹卡（子代理无法获得人工确认，卡只对主会话有意义）；此时开关只决定是否「一律拒绝所有受控写」，关闭时非确认写与主会话同路径。若用户希望关闭即完全不拦（子代理的确认写也可无卡执行），则 AC-4 改为放行，安全面明显收窄。
- **(b) 口味｜决策复用是否缓存「拒绝/超时」？** 默认只缓存允许：拒绝、超时、错误都不入缓存，同键重试重新弹卡，避免一次误点或走开在会话内堵死重试。若希望拒绝也复用（重试直接沿用上次拒绝、不再打扰），AC-12 需扩展 deny 缓存并改变重试体验。
