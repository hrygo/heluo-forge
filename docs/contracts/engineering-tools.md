## 1. 结论

相同业务动作在人类 CLI 与 Agent 面共享资源、身份、结果和审计语义。优先直接使用现有 CLI；以下字段只描述必须取得的事实，可映射原有 JSON，不因命名不同而新建包装层。只有必要缺口经确认后才做薄适配。

查询可用不代表写可用。任务入口不是任意 Shell 的授权；写必须满足动作开关、当前用户服务端权限、任务范围、必要人工确认与审计。不能证明控制或结果时关闭相关能力，不用模型生成的 `approved`、`readOnly` 等标志作证明。

## 2. 范围与对象真源

正文“变更号”及 `change-id` 泛指 DevOps 的正式系统变更标识；工程字段 `change_id` 承载原平台正式变更号，`change_ref` 是获准的不透明关联引用，两者由提供方明确映射，不能直接互换或自行推导。commit message 的 `[变更号]` 使用正式变更号；指标使用 `change_ref`，不因字段名称相似而复制 `change_id`。字段名以对应契约为准，任何标识或编号前缀都不能代替系统/仓库的显式映射。

| 目标事实 | 规范化候选字段 | 真源及缺失行为 |
|---|---|---|
| 上层目标与总体约束 | `change_id`, `change_ref` | DevOps 系统变更；一变更 1:N Issue；标识有效不等于已证明 Issue 关联 |
| 本项要求与验收 | `description`, `acceptance_criteria`, `requirement_revision` | 本 Issue 为独立交付要求，结合变更总体约束；正文仅业务通道使用；无版本时声明不能保证并发覆盖 |
| 上层背景 | `story_refs` | DevOps；故事作背景，不推断一故事只含一变更，业务要求冲突由用户决定 |
| 工作边界 | `system_id`, `repository_ref`, `target_branch` | Gitee 仓库事实与真实系统关联；每 Issue 恰一变更及一仓库，跨仓库拆独立交付验收 Issue；前缀及入参不证明关联 |
| 独立交付与工程对象 | `issue_ref`, `pr_ref`, `commit_ref`, `pr_revision`, `merge_state` | Git/Gitee；Issue 为独立交付单元，PR 关联 Issue，提交保留 `[变更号]`；不强制新分支语法，PR 创建／关闭不等于已合入 |
| 按需设计与兼容旧清单 | `spec_ref`, `spec_fingerprint`, `requirement_revision` | 充分 Issue 不另写独立规格，Agent 按需设计；旧 SDD 字段仅兼容盘点，不是默认必填或冻结要求，指纹不证明业务正确 |
| 测试证据 | `test_evidence_refs`, `tested_revision`, `test_state` | 实际测试运行/CI；NOT RUN、超时、缺证据不算通过 |
| 可选发布关联 | `release_ref`, `released_revision` | 已获准查询的 DevOps/变更平台；不为指标新增生产访问，缺失不推断上线或结项 |
| 交付就绪 | `build_ref`, `artifact_ref`, `deployment_ref`, `environment`, `deployment_state`, `included_change_refs` | DevOps 关联的 CI/CD 事实；无法证明包含本变更则为 unknown |
| 评审确认 | `review_ref`, `review_kind`, `reviewed_revision` | Gitee 正式记录；AI/人工分开、确认只覆盖对应版本 |

评审来源属性须由平台或既有可信执行/审计机制生成并关联正式记录，不能仅凭模型可编辑的正文前缀或自报 `review_kind` 判定。AI 来源与人工确认者、目标版本分别可核对；具体机制由 Gitee/平台验证，不强制另建独立账号或证明服务。无法证明时关闭相应自动评审写，保留原平台人工入口。

引用包括来源系统与不透明标识，不要求统一编号数据库；正式 URL 必须由原平台返回并在企业目标范围内。可人工访问的业务正文不能据此进入审计/指标。字段空、缺失、无权限、不适用必须分开，不能全部折叠为空字符串或空数组。

## 3. 业务动作目录（不是命令名）

| 动作标识 | 输入/前置事实 | 预期结果 | 属性/目标状态 |
|---|---|---|---|
| `change.read` | 明确变更号、当前用户 | 要求、验收、归属与版本 | 读；只读基线 |
| `change.list` | 当前用户（`@me`）、可选状态过滤（真实 flag 待核验） | 本用户可见的变更清单（编号/标题/状态/类型）与总数 | 读；只读基线；CLI 的 `change list` 天然是当前登录人范围，不另建权限判断 |
| `change.clarification.write` | 用户已采纳且属于变更层的澄清、目标及原版本 | 原平台新版本及关联确认 | 研发写；需求已确认，当前禁用及接口缺口不变 |
| `change.progress.write` | 平台确认的开始/进展字段及语义 | 实际记录值与版本 | 研发写；不得改最终完成/结束时间 |
| `gitee.repository.read`, `gitee.issue.read`, `gitee.pr.read` | 明确仓库/对象 | 状态与可核对引用 | 读；只读基线；由 `@heluo/forge-gitee` 唯一实现 |
| `issue.create_or_update` | 当前变更、本仓库交付项、验收及真实关联 | 已创建／更新对象引用；本项澄清写回 Issue | 研发写；需求已确认，能力与门禁待验证 |
| `branch.create`, `commit.record`, `pr.create_or_update` | 本 Issue／目标仓库、变更号、受控差异范围 | 按需分支、提交或关联 Issue 的 PR 引用 | 本地／远端写分开；需求已确认，能力与门禁待验证；保留 `[变更号]`，不强制新分支语法 |
| `review.ai.publish` | 真实审查结果、对应 PR 版本及可信来源依据 | 可验证为 AI 来源的意见记录 | 评审写；不是人工批准 |
| `review.human.record` | 宿主可信人工确认及其确切动作/意见/PR 版本 | 以实际确认者身份形成的正式 review | 评审写；不能以模型勾选代替，也不授权合并 |
| `issue.close` | 独立于用户验收记录，核对平台关闭规则、未完成交付及真实确认 | 平台关闭事实，与 CI／合入／验收／业务结束分记 | 目标语义，当前没有执行接口；不自动关闭；既有关闭判定仍检查已合入，不将其套作所有验收的前提，取消／废弃需用户另定 |
| `delivery.read` | 当前变更及交付引用 | 构建、制品、UAT 状态 | 条件读；接口/必要性待验 |

能力地图中的测试用例/缺陷查询及生产发布信息查询为条件需求，不在当前最小动作目录；本稿尚不定义 `test.read` / `release.read` 的可执行映射。若需启用，须由提供方先冻结对象、动作、权限与结果语义；不得通过 `delivery.read` 扩大测试/生产访问范围。

### 3.1 平台归属与实现映射（r10 收敛）

动作目录是业务语义，落到两个 bundle 的分工时只有一条轴——**按平台切**：dop 只讲变更流程，Gitee 只讲代码托管。

| 动作族 | 归属 | 实现动作标识 | 登记状态 |
|---|---|---|---|
| 变更读取与澄清回写 | `@heluo/forge-devops` | `change.read`、`change.list`；`change.clarification.write` | 两条读随包登记；澄清回写默认不登记即拒绝，且当前工具面不提供该动作（dop 无澄清写命令，不保留恒失败入口） |
| 仓库 / Issue / PR 读取 | `@heluo/forge-gitee` | `gitee.repository.read`、`gitee.issue.read`、`gitee.pr.read` | 随包登记（只读） |
| 交付就绪判定 | `@heluo/forge-gitee` | `gitee.delivery.judge` | 随包登记为只读判定（`target: change`、`egress: allow`），只判定不执行 |
| Issue / PR / 评审写 | `@heluo/forge-gitee` | `gitee.issue.write`、`gitee.pr.write`、`gitee.review.publish`、`gitee.review.record` | 默认不登记即拒绝；开闸需审批台账条目与 `confirm{repo,object}` |
| 本地提交与推送 | `@heluo/forge-gitee` | `git commit` 是**本地动作**（不进策略目录，首行 `[变更号]` 由 `git-message.mjs` 强校验）；`git push` 是远端写，动作 `gitee.git.push` | push 默认不登记即拒绝，登记后仍需确认与审批 |

r10 起 devops 不再持有仓库/Issue/PR 的读写实现（gh 侧模块已删除），`change_context` 的承建仓库段降级为外部指引（`REPO_FACTS_EXTERNAL` → `forge_gitee_repository_read` / `forge_gitee_issue_read`）。`git commit` 不进策略目录不是放宽：策略对任何 `enabled` 的非读动作恒要求审批台账，而提交必须发生，因此改为本地动作 + 提交信息单源校验。

2026-11-03（用户确认 D 方案）：只读面改为枚举式薄 runner——一个只读工具按 `change.read` / `change.list` 两个动作分发，每个动作有自己的参数 schema（不是自由 argv）；新增清单读取是因为 CLI 已有 `change list` 而原工具面没有入口。产物落盘的 `clarify` / `plan` 两类改由纯函数机检后生成正文（硬门禁/假设/修订标识、验收条件→实现→验证逐条映射），手写正文不再绕过检查。工具面因此从 4 个降为 3 个：恒 `denied` 的澄清写工具删除，澄清单改为本地产物 + 待人工确认。以上是工具面与校验口径调整，不代表企业 CLI 已联调；`--status` 等扩展参数的真实 flag 仍待核验。

不提供 `pr.merge`、CI 触发/重跑、生产部署/回滚/审批、故事/变更最终完成动作；旧项目中的 `dop change done` 不进入本清单。不提供通用 `run(command)` 型企业代理，也不允许通过别名或改用 Shell 绕过被拒绝的业务动作。

本表的 `属性/目标状态` 是各动作 `kind` 与开关的真源；运行时登记形态、判定顺序与 command/tool 统一门禁见[策略与审计详细设计 §5.1](../design/plugins/forge-policy.md#51-受控动作目录与统一门禁)。

## 4. 调用、授权和结果语义

### 4.1 有限任务委托

入口由用户明确触发，可提供变更号或 Issue；先读取真实变更—Issue—仓库关系，必要信息缺失时补足，不从编号前缀或调用参数推导。宿主可校验的上下文绑定当前用户、变更、Issue、单仓库与已开放动作；这是既有会话／权限机制的语义要求，不新建令牌服务或权限库。run 是执行记录，不增为业务对象。Skill 负责企业语义，Teamflow 唯一执行；内部 PRD／技术蓝图仅为运行材料，不是第二需求真源，不重复要求用户填写。服务端仍独立鉴权，本机规则不能代理用户权限。

当前用户已确认有限委托目标，不需平台／安全／PMO 再批准需求；Agent 仍须核验 C3 动作分类、既有审批台账、可信确认、真实权限及必要审计。核验／实现不足时，相关动作按现行 ask 或关闭处理；入口确认不能绕过 C3。依据为[需求 §2.3](../requirements/requirements-baseline.md)及[能力设计](../design/plugins/forge-devops-lifecycle.md)。满足实际门禁的普通获准研发写才可沿有限委托推进，不反复逐步询问。以下不被入口吞并：业务取舍、采纳后的澄清内容、人工正式 review，以及 C3 外发等原有强制确认。确认必须对应实际动作、目标和要求/PR 版本，取消/过期/版本变化后不再生效；身份与确认来源不能由模型自行填参数证明。现有宿主不支持时停止相应写能力，列待核验，不用提示词伪造保证。

凭据按对应提供方确认方式注入，业务凭据不进模型上下文。命令行参数、Shell 历史、错误输出、配置目录和子进程继承是否泄漏均需两端验证；未验证不开放。安全清单是策略维护者登记，不信任工具自报读写属性。只读、普通研发写、人工确认动作分别开关，默认空清单拒绝。

### 4.2 规范化结果

| 字段 | 候选要求 |
|---|---|
| `operation_id` | 同一逻辑动作的关联标识；重试不生成新的业务动作，用于核对与观察去重；不是服务端幂等保证 |
| `action`, `target_ref` | 明确动作与资源；不能只返回退出码 |
| `status` | `succeeded` / `failed` / `partial` / `unknown` |
| `execution_state` | `not_started` / `started` / `confirmed` / `unknown`，区分拒绝与可能已发生副作用 |
| `result_refs` | 已证实产生的对象和版本；没有证据不得合成 URL/对象编号 |
| `completed_effects`, `pending_effects` | 仅在复合调用确有部分成功时使用；不得以总退出码覆盖 |
| `error_code`, `retry_policy` | 结构化原因；`none` / `read_recheck` / `safe_retry`；安全重试必须有提供方依据 |
| `command` | 实际执行的逻辑命令标签（不含 endpoint、盘符与绝对路径），供复核与来源记录；不是可执行字符串 |
| `truncated` | 输出是否被长度上限截断；为 `true` 时只能作诊断线索，不得据此判定事实完整 |
| `facts` | 平台原始事实（仅当前受权会话）：单条读取携带平台记录与归一结果，清单读取携带 `user`/`total`/`count`/`items`/`filter`。不得进入指标、审计或产物；原始记录中的契约外字段不落盘 |
| `observed_at`, `source_revision` | 原始观察时间和来源版本；来源版本取该对象在提供方输出里**实际存在**的时间事实（Gitee 实测：Issue/PR 为 `updated_at`，仓库只有 `last_activity_at`，见 [Gitee 接入详细设计](../design/plugins/forge-gitee.md) §5.2）；取不到时才标缺失，不伪造冻结事实，也不拿不相干的时间字段冒充 |

字段名以提供方输出与 CLI 的**实测结果**为准，不按其他平台的命名习惯改写（例如 Gitee 的 PR 编号是 `iid`、Issue 是 `id`，仓库链接是 `web_url`）；实测不存在的字段按缺失处理，不用同名近似字段替代。读取侧不假设 CLI 具备字段过滤能力：字段子集只是本地投影，取不到的键走 `missing_fields`，不因此伪造字段或降级成猜测值。

业务内容与结果引用可以进入当前受权会话，但不得原样进入指标或审计。非 JSON/截断结果可提示人类诊断，不可作为可自动决策的成功结构。

### 4.3 未知、幂等与并发

读操作在明确无副作用前提下可有限退避；写超时、断流、取消或认证刷新后不能直接重放。先通过原平台按目标、已有返回引用或提供方支持的关联键查询效果。

提供方支持幂等键时使用其约定；不支持时，只在可确切回查和去重的动作上恢复。检索标题“看起来一样”不能证明同一对象；若无法唯一判定，保留 unknown、交人核对并关闭自动重试。不新建本地写任务数据库冒充平台恰好一次保证。

澄清或评审等依赖版本的写采用原平台支持的条件更新；不支持时不能声称并发安全，需改为提供方认可的串行确认方案并重新评审。部分成功先保留真实对象，不自动删 Issue、撤 review 或做破坏性“回滚”。

## 5. 失败模式

| 场景 | 业务结果 | 客户端行为 |
|---|---|---|
| 未安装/版本未知/必要字段缺失 | 不具备动作契约 | 明确关闭该动作，不发明子命令 |
| 401/403、主体/资源不符 | 未授权或执行状态待判定 | 不借其他用户/服务账号；有副作用可能则先回查 |
| policy/必要审计/可信确认不可用 | 拒绝动作 | 不以关闭安全组件兜底 |
| 退出 0 但缺对象/版本 | 未能确认成功 | unknown；不宣称已回写/建单 |
| 建单已成、后续 PR 失败 | 部分成功 | 展示真实引用，核对后只继续剩余动作 |
| 必要检查未运行／超时或版本不符 | 不具备对应通过证据 | 保留 NOT RUN／unknown，不宣称待验收条件已满足 |
| PR 未合入或远端 CI 尚无结果 | 合入／CI 状态独立，未必阻塞用户验收 | 守必要 CI／保护；本地验证与独立 AI 审查通过可待用户验收实际版本，不自动合并或关闭 |
| UAT 无版本关联 | 无法确认本变更就绪 | unknown，不用最近一次成功部署替代 |
| DevOps 故事/变更仍未结束 | 可能正常等待验收上线 | 不视为同步错误，不调用最终完成 |

## 6. 验收目标

1. 同一用户从 CLI 和 Agent 执行同一业务动作时，权限、目标资源和结果语义一致。
2. 无效变更、错仓库、无权限、写开关关闭、缺必要审计均不产生未授权副作用。
3. 安全批准相关 C3 动作分类前，有限委托内自动写规则不生效，按现行 ask 或关闭处理（见需求 §2.3、设计 D-13）；批准后普通获准研发写可在有限委托内执行；业务澄清与正式 review 缺真实确认时拒绝，模型自填确认不能通过。
4. 超时后回查已创建的 Issue 不重复创建；不能唯一回查时保持 unknown。
5. 已变化的需求/PR 版本不能复用旧确认；未合入/未验收的 Issue 不能交付关闭。
6. 任何任务路径都不调用 merge、CI 触发、生产变更或故事/系统变更最终完成。
7. 以上仅为未来企业/DSH 验收目标，本次 **NOT RUN：无企业内网与目标运行环境**。
