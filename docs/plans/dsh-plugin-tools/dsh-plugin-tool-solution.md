## 摘要

本方案回答一个具体问题：在 IAM 6.0.3 厂商口径不支持公共客户端/PKCE（内部回函未确认公共客户端）、AI 网关 2.2.1 只支持 Key 认证、AIGS 要到 2027Q2 才引入的条件下，DSH 的插件与工具如何先可用，并在 2027 年收敛到终版。

结论是三条。第一，V1 用机密客户端 + 系统浏览器 + 本机回环 + 系统钥匙串完成登录，不再把 PKCE 作为前置。第二，模型访问用一人一 Key + UA/IP + privacy_mode，不把 Key-only 说成身份绑定。第三，工具先只读、再受控写；AIGS 只进 V2 工具面，不补 V1 的身份缺口。

> 能力口径：以厂商 6.0.3/6.3 版本矩阵为主；内部校验回函 §02 的 PKCE 观察未确认公共客户端，冲突处按保守口径。

2027 终版不是另一套系统，而是在同一组接口上替换实现：身份从 IAM 机密客户端扩到 IAM 6.3 + AIGS 智能体身份；令牌从静态 Key 扩到 Key+Token 或委派令牌；授权从本地策略扩到 AIGS PDP；审计从本地事件扩到 SIEM/AIGS。V1 的插件、工具元数据与审计字段保留。

**表 0　关键决策**

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | V1 采用 IAM 机密客户端，PKCE 推迟 | 厂商 6.0.3 与 6.3.0 的 08 项均为“不支持”；内部 §08 未答；等 PKCE 会阻塞 800 人上线。 |
| D2 | 按部门/批次注册多个 client，不做全组织单一 secret | 把单点泄露的爆炸半径从 800 人压到一个批次；代价是登记与轮换工作量。 |
| D3 | 网关先用一人一 Key，不伪造“当前人校验” | AI 网关 2.2.1 模型路由只有 key-auth；UA/IP 只能降低误用，不能替代身份绑定。 |
| D4 | AIGS 只进 V2 工具面，不进 V1 登录 | AIGS 未部署、未许可；且其 SCIM 依赖 IAM 出站，当前不成立。 |
| D5 | 工具先只读，写操作放到 P1 且必须人工确认 | 先把查询、日志、Issue/PR 只读跑通；写操作需要审批台账与回查。 |
| D6 | 用稳定接口留演进缝，不做一次性适配 | 身份、令牌、策略、审计、工具描述都定义可替换接口；2027 换实现不换契约。 |

## 1　结论与范围

本方案不是 IAM 问询的延续，而是对现有版本能力的工程裁决。它把“能做什么、先做什么、什么不做、什么时候切换”写成可执行的计划，避免继续等待单点能力而阻塞整体上线。

### 1.1　三条结论

- **先可用**：2026Q4 用 IAM 6.0.3 的机密客户端完成登录，用 AI 网关个人 Key 完成模型调用，用本地策略完成工具管控；30 人试点，100 人复制。
- **再补齐**：2027Q1 升级 IAM 6.3，补 nonce/auth_time、RP 登出、SCIM 的部分能力；网关若具备令牌+Key 能力再切换，否则保持 Key-only 并书面接受残余风险。
- **后智能体**：2027Q2 AIGS 只做单场景 POC，先一个只读 MCP 工具；通过后再扩工具、再谈三重交权。AIGS 不进入 V1 登录链路。

### 1.2　范围

**表 1　方案范围**

| 维度 | 本期范围 | 不在本期 |
| --- | --- | --- |
| 用户 | 3 个部门 800 人；Windows 约 50%，银河麒麟 aarch64 约 50% | macOS、多人共享单实例、白标发行 |
| DSH | 0.2.1-rc.3；每人一套；银河麒麟用本机 Web | 修改 DSH 核心；自建多租户 |
| 身份 | IAM 6.0.3 机密客户端；2027Q1 升 6.3 | 等待 IAM 公共客户端/PKCE 再上线 |
| 模型 | AI 网关个人 Key + UA/IP + privacy_mode | 客户端直连上游；共享 Key；自建推理 |
| 工具 | DevOps/Gitee 只读；SDD 本地；P1 受控写 | V1 启用 MCP；自动合并/发布 |
| 智能体 | 2027Q2 AIGS 单场景 POC | 2026 年引入 AIGS；用 AIGS 补 IAM 缺口 |

### 1.3　成功标准

本方案的成功不是“装上了插件”，而是四件事同时成立：用户能登录、模型能调用、工具能管控、故障能回滚。四项分别对应身份、凭据、策略、运维四条验收线，缺一不进入下一阶段。

> **一句话**　V1 的目标是“可用的受控版本”，不是“安全的终版”；终版目标在 2027 年，通过同一组接口演进，不重写。

### 2.3　三个硬约束

**约束一：厂商口径下 IAM 6.3 仍不解决公共客户端/PKCE。** 厂商回函对 08 项的 6.3.0 结论仍是“不支持”；内部校验回函 §02 称 PKCE 能力、§08 未答，不能推出公共客户端。桌面端不能在 2027Q1 切到公共客户端/PKCE；谁把它写进 Q1 验收，谁就会在 3 月阻塞 800 人上线。

**约束二：网关不能证明“当前人”。** AI 网关 2.2.1 的模型路由只认 API Key；UA 识别、IP 限制、privacy_mode 是降低误用与泄露的手段，不是身份绑定。V1 的准确表述是“本人 Key 模式”，不是“当前人校验已通过”。

**约束三：AIGS 不是 IAM 的补丁。** AIGS 的 SCIM 端点需要上游推送；IAM 6.0.3 没有 SCIM 出站，6.3 也只是部分支持。AIGS 的三重交权还需要业务系统权限数据；当前 IAM 只有应用/菜单级授权。AIGS 只能解决它自己的问题，不能拿来关闭 IAM 的 08/19。

> **口径**　本文所有“已支持”均指有书面依据或可复现实测；“待验证”不作为放行依据；“不支持”不写成“后续版本会支持”，除非有版本号与时间。

## 3　总体架构

架构按“身份、凭据、模型、策略、工具、审计”六层拆分。V1 与 2027 终版使用同一分层，只替换每层的实现；这样 2027 年不需要重写插件，也不需要把 V1 的工具下架。

### 3.1　分层

**表 4　六层与稳定接口**

| 层 | V1（2026Q4） | 2027 终版 | 稳定接口 |
| --- | --- | --- | --- |
| 身份 | IAM 6.0.3 机密客户端；系统浏览器 + 回环 | IAM 6.3 + AIGS 智能体身份 | IdentityProvider |
| 凭据 | OS 钥匙串；AI 网关个人 Key | 钥匙串 + AIGS 凭证保险箱 | CredentialProvider |
| 模型 | DSH 原生 llm-pi-ai + AI 网关 Key | AI 网关 Key+Token（若支持）/ AIGS MCP | ModelAccess |
| 策略 | forge-policy 本地硬拒绝 + 人工确认 | 本地 + AIGS PDP（按工具） | PolicyDecisionPoint |
| 工具 | DevOps/Gitee 只读；SDD 本地 | 只读 + 受控写 + MCP 工具 | ToolDescriptor |
| 审计 | 本地事件 + OTel | SIEM + AIGS jti 全链 | AuditSink |

### 3.2　V1 调用链

**登录链**：DSH 打开系统浏览器 → IAM 授权端点（client_id + redirect_uri + state + nonce）→ 用户认证 → 回环回调 → DSH 用 client_secret 换 token → ID Token 校验 → 写钥匙串。client_secret 不进入配置、日志、上下文；回调只接受 state/nonce 匹配的 GET。

**模型链**：DSH 从钥匙串取本人 AI 网关 Key → `apikey` 头 + 固定 UA + 请求模型 → AI 网关 校验 Key/模型/预算/IP → 私有模型。请求失败按 401/429/5xx 分类；已输出或结果未知不自动重放。

**工具链**：模型发起工具调用 → forge-policy 校验动作/目标/风险 → 只读放行或转人工确认 → DevOps/Gitee CLI 执行 → 审计事件。策略拒绝时适配器零调用；子 Agent 继承同一策略。

### 3.3　2027 终版调用链

**人的登录**仍由 IAM 6.3 承担；AIGS 不改变员工登录路径。**智能体**在 AIGS 注册，绑定责任人、工具集与调用范围；工具调用经 AIGS STS 换发“人 + 智能体”双标识短时效令牌，MCP 网关做 PEP，PDP 做能力上限 ∩ 人的权限 ∩ 策略范围的求交。**审计**用同一 jti 贯穿 IAM、AIGS、MCP 与业务系统；本地策略保留为第二道闸，不作为唯一授权。

终版不假设所有能力都可用：PKCE、SCIM、网关令牌+Key、三重交权都设“条件门”。条件不成立时保留 V1 实现与开关，不把未验证能力写成已交付。

### 3.4　演进缝

**表 5　演进缝与兼容规则**

| 演进缝 | V1 实现 | 2027 实现 | 兼容规则 |
| --- | --- | --- | --- |

### 4.2　为什么网关不单独建包

V1 的模型访问是“配置 + 凭据 + 错误映射”，DSH 原生 `llm-pi-ai` 已能指向 OpenAI 兼容网关，凭据 seam 已能按请求解析。再建一个 `@heluo/forge-gateway` 包，会把 provider、凭据、重试三件事重复一遍，增加版本耦合。

因此 P0 不建 gateway 包；把网关差异收敛到三处配置：`baseUrl`、`apiKey` 引用、模型白名单。若 P1 证明原生配置无法表达 UA 头、错误映射或令牌+Key，再建一个**薄配置包**，不复制 provider。

| --- | --- | --- | --- |

### 4.4　凭据与密钥

IAM 的 client_secret、AI 网关 的个人 Key、未来的 AIGS 委派令牌，全部只进 OS 钥匙串；配置里只保留引用名。钥匙串不可用时 fail closed；仅试点允许显式 0600 文件，且由 `forge-policy` 硬拒绝 Agent 读取 `$DSH_HOME/**`。

AI 网关 Key 由本人在网关控制台创建，DSH 只录入、清除、显示状态，不代创建、不代轮换。默认 90 天提醒更换；到期前 14 天提示，不自动续期。

## 5　分阶段路线

路线按“可用—补齐—智能体—终版”四段推进。每段都有退出条件与停止规则；退出条件不满足，不进入下一段，不用“先上线再说”掩盖。

| P2 智能体 | 2027-04—06 | AIGS 单场景 POC | forge-aigs、MCP 工具、智能体身份、委派令牌、CIBA | 一个只读工具全链可回放，100% jti，未通过不进生产 |
| P3 终版 | 2027-07—12 | 2027 终版收敛 | 读写工具、AIGS 扩展、SIEM、容量与运营 | 所有开放能力有证据；未开放能力有开关与替代 |

### 5.2　P0：先可用（2026Q4）

P0 只做四件事：登录、模型、只读工具、回滚。目标不是把 800 人全部迁完，而是证明“一个普通研发人员在一台 Windows 和一台银河麒麟上，能登录、能调模型、能查流水线，且不泄露密钥”。

- **身份**：注册部门级机密客户端；确认回环回调与动态端口规则；client_secret 入钥匙串；AT TTL 争取 300—900 秒。
- **模型**：30 个 AI 网关个人 Key；UA 固定；IP 白名单；privacy_mode 全开；模型白名单与 Key 权限取交集。
- **工具**：DevOps 只读四工具；Gitee CLI 只读查询（若 CLI 鉴权通过）；SDD 本地可用。
- **策略**：`$DSH_HOME/**` 硬拒绝；C3 外发确认；工具白名单；审计事件落本地并可导出。
- **验证**：30 人两周；记录登录成功率、刷新失败、模型错误、撤销时长、回滚耗时。

P0 的停止规则：登录成功率低于 95%、出现密钥进入日志/上下文、钥匙串不可用且未走试点例外、回滚超过 30 分钟——任一条触发，暂停扩量，先修。

### 5.3　P1：补齐（2027Q1）

IAM 6.3 升级后先做回归，不直接扩到 800。回归清单是：nonce/auth_time 是否回传、RP 登出是否可用、SCIM 是否能向目标出站、AT TTL 是否可配、管理台强制下线是否即时。每项有书面/实测结论后再改插件。

如果 6.3 的 08 项仍是“不支持”，P1 继续用机密客户端；如果 6.3 的 14 项只到“部分支持”，保留浏览器 SSO 登出兜底；如果 19 项只到“部分支持”，不把 SCIM 设为 800 人上线前置，改为“JIT + 管理台强制下线 + 90 天 Key 轮换”。

网关侧只做一件事：如果 AI 网关 生产版本提供 `id_token`+Key 的当前人校验，切到“令牌+Key”；否则保持 Key-only，把 5 分钟停用写成“待实测”，不写成“已满足”。

### 5.4　P2：智能体（2027Q2）

AIGS 引入只做单场景：选一个低风险、只读、单工具的场景（代码检索或日志查询），验证注册、双标识令牌、audience、PDP 求交、CIBA、审计回放六项。六项全过，才扩第二个工具；不过，AIGS 停在 POC，不影响 V1。

P2 不解决 IAM 的 08/19，也不把 AIGS 当作 V1 的兜底。AIGS 的 SCIM 依赖 IAM 出站；如果 6.3 的 SCIM 仍不成立，P2 只做“工具调用治理”，不做“人员/组织联动”，并把目录同步列为 P3 的前置。

### 5.5　P3：终版（2027H2）

P3 把 P0—P2 的能力收敛成可运营的终版：800 人、双端、读写工具、AIGS 扩展、SIEM、容量基线、演练与回滚。终版不是“所有能力都开”，而是“开的能力有证据，没开的能力有开关和替代”。

## 6　2027 终版方案

本章定义 2027-12-31 的目标状态。它是“终版”，但不是“所有条件都成立”；凡依赖 IAM/网关/AIGS 版本的能力，都写成条件能力，并给出不成立时的保留路径。

### 6.1　终版定义

终版由五个“已开放”与五个“未开放”共同定义。已开放：人的登录、模型调用、只读工具、受控写、智能体单场景。未开放：无数据支撑的三重交权、未许可的 AIGS 生产、未证实的五分钟、未支持的 PKCE、未通过的写操作。

### 6.2　目标能力

**表 9　2027 终版能力**

| 能力 | 2027 终版目标 | 成立条件 | 不成立时 |
| --- | --- | --- | --- |
| 人的登录 | IAM 6.3；机密客户端为主；PKCE 若可用则灰度 | IAM 6.3 升级完成；回调/claims 回归通过 | 保持机密客户端；不写 PKCE |
| 会话退出 | RP 登出可用则调用；否则本地清空 + 浏览器 SSO 登出 | 6.3 的 14 项实测 | 保留兜底；不宣称全局登出 |

| 工具 | 只读 + L1/L2 受控写；审批台账与回查 | 策略/审批/审计通过 | 仅只读；写操作关闭 |
| 智能体 | AIGS 单场景扩到 2—3 个工具；双标识/委派/CIBA | AIGS 许可/部署；SCIM 或目录桥接 | 停在 POC；V1 不受影响 |

| 凭据 | 钥匙串（人/客户端）+ AIGS 凭证保险箱（智能体） | 同一 CredentialProvider 接口，新增后端 |

### 6.4　终版不承诺

终版不承诺“三重交权全量落地”。三重交权需要业务系统的实时权限数据；如果取不到，最终权限退化为“智能体能力上限 ∩ 策略范围”，并在审计中标注 `degraded=true`。终版不承诺“五分钟停用”在所有网关节点成立；如果实测超过五分钟，就把该能力标为未达标，限制高风险用途，而不是改口径。

终版不承诺“AIGS 生产全覆盖”。AIGS 只覆盖工具调用；人的登录、模型 Key、DevOps/Gitee 仍由 IAM/网关/各自服务端负责。终版不承诺“PKCE 已支持”；只有 IAM 书面确认并通过回归，才把 `authMode=pkce` 打开。

### 6.5　终版的可运营性

终版必须能运营，不只是能演示：版本可锁、配置可回滚、密钥可轮换、审计可查询、故障可降级、容量有基线。运营指标至少包括：登录成功率、刷新失败率、模型 401/429/5xx、工具拒绝率、审批时长、Key 轮换到期数、AIGS 决策拒绝率、jti 缺失率。

## 8　交叉审查

本章记录四轮审查的方法、发现与处置。审查对象不是文字，而是“主张是否有证据、架构是否自洽、路线是否可行、边界是否会被绕过”。

### 8.1　审查方法

- **证据对齐**：每条能力主张对应一条证据（回函、分析稿、代码/测试、设计文档）；无证据的主张降级为“待验证”。
- **架构自洽**：检查登录、模型、工具、审计四条链路是否互相矛盾；检查 V1 与 2027 终版是否共用同一组接口。
- **对抗审查**：假设用户提取 secret、伪造 UA、绕过策略、断网、银河麒麟无钥匙串、AIGS 未部署，逐项看方案是否仍成立。
- **一致性复核**：版本、日期、人数、阶段、指标、术语全文对齐；同一能力不出现两种结论。

### 8.2　第一轮：证据一致性

第一轮把上一版方案与 2026-10-26 回函逐条对照，发现 6 处直接冲突：PKCE、网关当前人、AIGS 补 SCIM、五分钟、单 secret、6.3 能力。处置如下。

| --- | --- | --- | --- | --- |
| F01 | V1 用授权码 + PKCE | 厂商 08：6.0.3/6.3 均不支持；内部 §08 未答 | 不成立 | 改机密客户端；PKCE 留开关 |
| F02 | 网关校验当前人 | AI 网关 2.2.1 只有 key-auth | 不成立 | 改 Key-only；UA/IP 只降误用 |

### 8.4　第三轮：对抗与安全

第三轮按攻击者视角审查：secret 被提取、UA 被伪造、策略被绕过、Key 被共享、断网重放、AIGS 匿名注册。结论是 V1 不能声称“身份绑定”，但可以把风险限制在“本人 Key 被本人滥用/泄露”，并通过钥匙串、审计、轮换、策略硬拒绝降低。
