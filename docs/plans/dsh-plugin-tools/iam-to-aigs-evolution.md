## 摘要

回函在 21 项 IAM 答复之外，用专页提出“智能体域独立治理、由 AIGS 承接”的演进主张，并在 15 项“AIGS 演进视角”中延伸。本文将其整理为“一个判断、五项能力、三条边界、两期路径”，并做批判性评估。

判断：把智能体身份与人的 IAM 分开，方向正确。身份模型、凭据策略、授权时机、审计主体四类差异，能够解释为什么不宜把智能体直接塞进 IAM 账号模型。但“独立成域”是设计选择，不是唯一解；回函没有比较“网关单点治理”和“扩展 IAM”两条路线的成本。

风险：回函把 AIGS 当作 IAM 缺口的兜底，存在四个未闭环：① IAM 无 SCIM 2.0 出站，AIGS 却称“接收 IAM SCIM 推送”；② AIGS 未部署、未许可、未验证；③ 三重交权依赖业务系统的实时权限数据，而 IAM 只有应用/菜单级授权；④ 透明代理“零代码纳管”对共享 Key 场景的归因较弱。

建议：V1 不以 AIGS 为前置；V2 先以单场景 POC 验证六项能力；把“AIGS 承接”改写为“带日期的能力承诺 + 验收标准”；在架构上明确 IAM、AI 网关、AIGS 三个策略执行点的边界。

**要点**

- AIGS 的方向正确，但不是 V1 的答案；V1 的登录与撤权仍靠 IAM + AI 网关。
- 五项能力成熟度不同：统一认证、调用链身份传递较成熟；三重交权最依赖外部数据；全链路审计与人在回路是有效补充。
- 采用顺序：制度 → 通道 → POC → 许可 → 规模化；POC 以六项能力为退出标准。
- 三个不要：不要把 AIGS 当 IAM 缺口的兜底；不要把“标准名称”当“标准实现”；不要把“零代码”当“零治理”。

## 1　背景与范围

### 1.1　回函的结构

回函由两部分组成：第一张表是 21 项 IAM 逐项答复，第二张表是 AIGS 演进建议。AIGS 专页分三节：演进定位与分期、五项能力、与 IAM 的分工；逐项表的“AIGS 演进视角”列在 15 项中延伸。AIGS 不是第 22 项 IAM 问题，而是对 V2 的架构主张；它不改变 V1 的 IAM 结论。

这 15 项延伸大致覆盖四类议题：智能体身份与令牌（01/02/03/08/09/10/15）、调用链与资源绑定（03/11）、生命周期与撤权（04/05/06/07/12/13/14/15/19/20）、审计与高风险操作（21/20）。它们共同指向一个判断：人的登录治理与智能体的调用治理，不是同一套模型。

### 1.2　本文的依据与边界

本文只基于回函文本，不引用厂商未提供的白皮书、接口文档或测试报告，不评价厂商其他产品，不构成选型、采购或批准结论。文中对 AIGS 能力均标注“回函自述”，并以“待验证”处理。涉及 IAM 21 项的内容，以《IAM 回函分析与第二轮问询函》为准，本文不重复。

需要特别说明：回函把 AIGS 描述为“对外统一口径”的五项能力，但没有给出产品版本、部署形态、许可方式与已交付客户证据。因此，本文讨论的是“这套治理思路是否成立、缺什么、如何验证”，不是“AIGS 是否已经可用”。

## 2　问题：人的 IAM 为什么不够

### 2.1　研发助手的双重身份

研发助手的特殊性在于它同时承载两种身份：屏幕前的人，和替人执行任务的智能体。V1 只要求回答“谁在登录”：员工经 IAM 完成认证，DSH 持有会话，模型调用由 AI 网关按个人凭据放行。V2 启用工程服务或 MCP 后，问题变成“谁让哪个智能体、用什么工具、对哪个资源、做了什么”，而且要在每次调用时回答，不是登录时回答一次。

这两种问题对应两套治理对象。人的身份相对稳定、数量有限、生命周期由人力资源权威源驱动；智能体数量随场景增长、行为高频、权限随调用上下文变化。把两者放进同一账号模型，短期可行，长期会同时拖累身份目录与令牌引擎：目录被大量非人主体稀释，令牌引擎被人与机器的不同时效策略拉扯。

### 2.2　四类差异与评价

**表 2  人的 IAM 与智能体治理的四类差异**

| 维度 | 人的 IAM | 智能体治理 | 评价 |
| --- | --- | --- | --- |
| 身份模型 | 实名、组织树、人力资源权威源 | 非人主体，绑定责任人、工具集、调用范围，数量级增长 | 成立；但“数字员工”是否进 IAM 需单独定义 |
| 凭据策略 | 小时到天，追求稳定续期 | 分钟级、逐跳交换、按上下文降权 | 成立；短 TTL 的刷新、时钟与可用性成本需量化 |
| 授权时机 | 登录时预配置，应用/菜单级 | 运行时单次调用，工具/参数/数据范围 | 成立；但依赖业务权限数据，落地难度常被低估 |
| 审计主体 | 人，低频随机 | 机器，高频规律 | 成立；分管道不等于分系统，关联键必须统一 |

这四点是回函论证中最有说服力的部分。但它们支持的是“智能体治理需要独立的策略与凭据机制”，不直接等于“必须采购一个独立平台”。独立平台是组织与产品选择；在规模较小时，网关单点治理同样可以满足。回函没有比较这两条路线。

### 2.3　三种可选架构

**表 3  三种架构路线**

| 方案 | 做法 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- | --- |
| A 扩展 IAM | 智能体作为特殊账号或“数字员工”进目录 | 统一目录、统一登录 | 账号膨胀、凭据策略冲突、运行时授权不足 | 少量数字员工 |
| B 网关单点 | AI/MCP 网关做认证、授权、审计 | 轻量、贴近调用、上线快 | 缺身份生命周期、跨网关策略、归因弱 | V1/V2 早期 |
| C 独立控制面 | AIGS + 现有 PEP | 能力完整、可扩展、职责清晰 | 多平台、集成成本、策略碎片 | 规模化、多工具/多智能体 |

回函主张 C，但没有给出 A/B 的成本对比，也没有定义“规模阈值”。建议在 V2 立项时用三个问题决策：智能体数量是否超过人工可管理阈值？是否存在跨系统工具调用？是否要求工具级审计？三者任一为“是”，C 的价值上升；否则 B 足够。把 C 作为唯一目标态，容易在 V2 早期引入不必要的平台复杂度。

## 3　AIGS 的目标架构

### 3.1　分层与组件

把回函的描述还原成架构，可以分成四层：人的身份层（IAM、DSH 会话）、智能体控制面（注册、STS、PDP、凭证保险箱、工作负载身份）、执行面（AI 网关、MCP 网关、业务系统/模型服务）、审计面（审计、UEBA、SIEM）。控制面与数据面分离，是这套架构最重要的设计选择：策略与凭据集中管理，执行点贴近调用。

架构上最关键的断点是 IAM 到 AIGS 的人员/组织同步。回函称 AIGS 只读消费 IAM 目录，但 IAM 部署版没有 SCIM 2.0 出站；没有这条通道，AIGS 的注册、责任人、生命周期联动都缺少数据基础。这一点在 §5 展开。

**表 4  AIGS 组件与前提**

| 组件 | 职责 | 关键前提 |
| --- | --- | --- |
| 智能体注册 | 实名、责任人、工具集、调用范围、版本与环境 | 智能体清单与责任人制度 |
| 安全令牌服务 STS | RFC 8693 交换；主体=人、代理=智能体；绑定 audience；短 TTL；按上下文降权 | 人的令牌可交换、资源注册表 |
| 策略引擎 PDP | 能力上限 ∩ 人的权限 ∩ 策略范围；工具/参数；行列过滤 | 权限数据、策略作者、低延迟 |
| 策略执行点 PEP | AI 网关、MCP 网关、SDK 拦截器 | 所有调用经过 PEP |
| 凭证保险箱 | 静态密钥、自动轮换、运行时注入、不落盘 | 密钥生命周期与审计 |
| 工作负载身份 | SPIFFE/SPIRE 颁发身份与双向 TLS 证书 | 容器/云原生；传统环境成本高 |
| 审计 / UEBA | 双画像、哈希链、分级保留、SIEM 对接 | 全量日志、隐私合规 |
| 人在回路 | CIBA + 企业 IM；一次性短令牌放行 | 责任人可达、IM 集成 |

### 3.3　与 IAM、AI 网关的边界

回函说“IAM 管人、AIGS 管智能体”，方向正确，但边界只画到“对象”，没有画到“请求”。一次模型调用可能同时经过 AI 网关和 AIGS：模型权限、额度归谁判？工具调用中的模型请求归谁审计？如果两个平台都判，策略会重复；如果都不判，会出现空档。

**表 5  按资源类型划分的策略权威源（建议）**

| 资源类型 | 认证 | 授权 | 额度 | 审计 |
| --- | --- | --- | --- | --- |
| 模型 | IAM（人） | AI 网关 | AI 网关 | AI 网关 + IAM |
| MCP 工具 | IAM + AIGS | AIGS / MCP 网关 | AIGS | AIGS |
| 业务 API | IAM 或应用 | 业务系统 | 业务系统 | 业务系统 + AIGS |

建议坚持三条原则：一个请求只经过必要的 PEP；一个决策只有一个权威源；审计用同一 jti 关联。否则，“独立治理”会退化为“多一套策略要维护”。

## 4　五项能力逐项评估

回函把 AIGS 的能力归纳为五项，称“对外统一口径”。以下逐项拆解机制、价值、前提与待验证点。评价的标准不是“听起来是否先进”，而是“在企业的现有系统与组织条件下，能否落地、能否验收”。

### 4.1　智能体统一认证

机制：智能体实名注册并强制绑定人类责任人，拒绝匿名与共享账户；数字员工以独立工号挂组织树；基于 RFC 8693 的令牌交换换发“主体=人 + 代理=智能体”的双标识短时效令牌；静态密钥收口凭证保险箱；智能体间通信用 SPIFFE/SPIRE 颁发数字身份与双向 TLS 证书。

价值：把“谁负责这个智能体”变成可登记、可审计的一等属性；短时效与逐跳交换降低令牌泄露的爆炸半径；工作负载身份减少长期密钥。对研发助手这类“替人调用工具”的场景，双标识令牌是后续逐跳授权与归因的基础。

前提：智能体清单与责任人制度；IAM 目录同步；STS 高可用；SPIFFE 运维能力；SDK/代理的引导凭据管理。任何一项缺失，统一认证都会退化为“登记表 + 静态密钥”。

待验证：① “数字员工独立工号”与“智能体不进 IAM 账号模型”存在张力，需要区分数字员工、智能体实例、工具型 agent 三类；② SPIFFE 是工作负载身份，不是业务智能体身份，两层映射必须定义；③ SDK 首次接入仍需引导凭据，不能宣称“完全无静态密钥”；④ 分钟级 TTL 的刷新频率、时钟偏差、离线场景需要压测。

### 4.2　智能体调用链的身份传递

机制：调用链每一跳实名，jti 贯穿全链；每次跨智能体调用强制令牌交换；委派令牌绑定目标资源域（audience），跨域重放即拒；下游解析“人 + 智能体”双重身份，把每次调用归因到发起的自然人。

价值：解决“单一长令牌权限扩散”的根因；比“全网一张大令牌”更符合最小特权；为跨系统审计提供统一关联键。对多跳工具调用，逐跳收缩是比“一次授权、全程通行”更可靠的安全模型。

前提：所有跳都支持交换；目标服务注册 audience；令牌格式与签名统一；下游愿意改造解析双身份。任何一跳不支持，链路就会出现“降级跳”，归因与授权都会断。

待验证：非 MCP、非改造系统无法参与，实际覆盖率可能远低于“全链路”；audience 注册表由谁维护；多跳令牌膨胀与延迟；jti 的全局唯一与存储；重放窗口与时钟。回函没有给出覆盖率数据，这是 POC 必须测的指标。

### 4.3　三重交权的细粒度权限控制

机制：最终权限 = 智能体能力上限 ∩ 调用者（人）实际权限 ∩ 策略绑定范围；默认拒绝；MCP 网关作为 PEP，判定到单个工具与参数取值域；数据库类工具支持行/列过滤与 SQL 改写；策略由独立 PDP 承载。

价值：这是 AIGS 最有价值的能力，也是最接近“运行时最小特权”的模型。它能防住三类问题：智能体被赋予过大能力；人越权指使智能体；参数级注入或越界查询。对“批量导出、跨库查询、对外发送”这类高危工具，参数级判定比应用级授权更有意义。

前提：业务系统的权限可被实时查询或表达；工具 schema 与参数约束完整；有策略作者与治理流程；PDP 低延迟、高可用；PEP 覆盖所有调用路径。

待验证：最大难点是“人的实际权限”数据源。IAM 只有应用/菜单级授权，业务系统各自自治；如果取不到，三重交集会退化为“能力上限”或“全拒”。SQL 改写是高风险能力，需防语义错误、性能退化与注入；策略数量增长会带来可维护性问题；PDP 故障时 fail-open 还是 fail-closed 必须明确，不能留给实施阶段即兴决定。

### 4.4　智能体全链路可视化监控

机制：一次调用可回放到人；人与智能体两张画像同源；UEBA 为人与智能体分别建基线、分别计算风险分；决策日志哈希链防篡改；分级保留最长 7 年；与 SIEM 协同输出。

价值：人机分管道审计，避免基线互相污染；jti 关联支持并案稽查；哈希链提升取证可信度。对监管检查与内部审计，这种“可回放到自然人”的能力比单纯的日志聚合更有说服力。

前提：全量调用日志；隐私合规评估；存储成本；UEBA 训练数据；SIEM 对接。审计不是“打开开关”，而是数据治理工程。

待验证：7 年保留的成本与法律依据；员工行为监控的告知、同意与最小化；哈希链只能防篡改，不能防删除；UEBA 误报与处置流程；跨系统时钟与事件排序。回函称“与 SIEM 协同输出”，但没有给出格式、吞吐、断链补传，这些是运维落地项。

### 4.5　智能体高危操作人在回路

机制：高危操作（交易参数修改、批量导出、对外发送等）挂起，经 CIBA 异步推送责任人，在企业 IM 卡片确认后发放一次性短时效令牌放行；超时或拒绝即阻断。

价值：把“登录时的身份强度”扩展到“运行中的操作强度”；对批量导出、对外发送等不可逆操作尤其有价值。它补的是 MFA 与静态授权之间的空档。

前提：责任人可达；IM 集成；CIBA 能力；操作分类与策略；审计。任何一项缺失，确认会变成“找不到人”或“默认放行”。

待验证：责任人离线、离职或代理；审批疲劳；IM 作为安全通道的可用性与被攻破风险；超时策略；不能替代事前授权与最小权限。评价：这是对“MFA 只管登录”的有效补充；但“所有高危操作都推送”会造成疲劳，应按风险分级，并允许“预授权 + 抽检”的混合模式。

## 5　与 IAM 的分工

### 5.1　边界表

**表 6  与 IAM 的职责边界**

| 治理对象 / 能力 | 权威源 | AIGS 的角色 | 备注 |
| --- | --- | --- | --- |
| 身份与组织 | IAM | 只读消费（SCIM 同步） | 不回写、不迁移、不替换 |
| 人的认证与单点登录 | IAM | 不改变登录路径 | V1 唯一入口仍是 IAM |
| 业务应用权限（菜单/按钮/数据） | 各业务系统 | 不取授权结论；按人的身份走应用既有授权 | OBO 模式 |
| AI 资源（模型、MCP 工具、智能体、AI API） | AIGS | 令牌服务 + AI/MCP 网关 + 权限包 | 判定到工具/参数 |
| 审计 | IAM 管人的登录/授权；AIGS 管调用链 | jti 关联 | 同一实名口径 |
| 生命周期 | IAM 管人；AIGS 管人名下智能体 | SCIM 联动 | 回收凭据与权限 |

### 5.2　同一实名口径的三条实现

回函用“只读对接、不回写、不替换”描述 AIGS 与 IAM 的关系。这个原则是对的：一个治理对象只能有一个权威源；AIGS 不应成为第二套身份目录。但要落地，需要三条通道：人员/组织同步、人员状态事件、认证结果。

- 只读目录：SCIM 同步人与组织。当前部署 6.0.3 无 SCIM 出站，6.3 仅部分支持，链路仍是断点；这是本文最关注的缺口。
- jti 关联：调用链与人的审计用同一 jti/sub 关联；需要 IAM 与 AIGS 的时钟、字段、保留期对齐。
- 不回写：AIGS 不修正 IAM 数据；IAM 数据质量会传导到 AIGS，需要在 IAM 侧治理，而不是在 AIGS 侧打补丁。

评价：原则正确，但“只读”不是“自动”。没有通道，只读只是口号。回函一方面称 AIGS 接收 IAM 的 SCIM 推送，另一方面称 IAM 部署版没有 SCIM 出站；这两个表述不能同时成立。需要明确：是升级 IAM、加中间件，还是由 AIGS 反向拉取其他目录。

### 5.3　三个必须写清的接口

**表 7  IAM 与 AIGS 的三个接口**

| 接口（含方向） | 内容 | 时延要求 | 失败处理 | 当前状态 |
| --- | --- | --- | --- | --- |
| 人员/组织同步（IAM→AIGS） | 用户、组织、组、active | 分钟级 | 重试/对账/死信 | 6.0.3 无 SCIM 出站；6.3 部分支持（缺口） |

### 5.4　与 AI 网关的边界

AI 网关是模型访问的 PEP，AIGS 是工具调用的 PEP；两者都可能出现在同一次请求链上。回函没有说明模型权限、额度、审计归谁。建议用表 5 的资源类型矩阵明确权威源，避免策略重复或空档。原则是：一个请求只经过必要的 PEP；一个决策只有一个权威源；审计用同一 jti 关联。

## 6　演进路径

### 6.1　V1：人的登录

V1 的目标不是“上 AIGS”，而是“让人安全地登录、稳定地调用模型、可撤权地退出”。IAM 提供唯一 IdP；客户端按公共/机密客户端登记；AI 网关按个人凭据放行；短期 AT + 网关回查 + 本地清理构成撤权链。AIGS 不进入 V1 关键路径。

这条路径的缺口已经在 IAM 回函中暴露：厂商口径下公共客户端/PKCE 不支持、已发 AT 无法服务端阻断，6.0.3 无 SCIM 出站、6.3 仅部分支持。内部校验回函对 PKCE 与账号禁用后的即时作废另有不同观察，但未确认公共客户端，也与厂商版本矩阵冲突；两种口径均不能直接当作已交付能力。这些缺口需要用替代方案与补偿控制解决，不能用“V2 上 AIGS”来遮盖。

### 6.2　V2 的触发条件

V2 的触发条件建议写成可判定的：① 启用工程服务或 MCP；② 智能体/工具数量超过人工可管理阈值（例如 20 个智能体或 50 个工具）；③ 出现跨系统工具调用；④ 监管或审计要求工具级授权/留痕。四项任一为“是”，启动 AIGS 评估；否则继续用网关单点。

### 6.3　两条接入路径

**表 8  两条接入路径**

| 路径 | 适用 | 做法 | 优点 / 代价 | 风险 |
| --- | --- | --- | --- | --- |
| 透明代理 + 网关 | 第三方/不可改造客户端 | 代理拦截流量，网关做认证/授权/审计 | 零代码、上线快；但需代理部署、证书与性能 | 身份绑定依赖 Key/流量，归因弱 |
| SDK | 自研客户端 | 嵌入 SDK，5 接口：登录、换执行令牌、权限校验、换业务令牌、审计上报 | 细粒度、可拦截、可离线；但需改造、升级、多语言与 SDK 安全 | 引导凭据、完整性、版本碎片 |

评价：两条路径的安全强度不同。透明代理在共享 Key 场景下只能证明“某个 Key 被使用”，不能证明“某个人在使用”；SDK 可以拿到人的令牌并做逐跳交换。不能在同一合规口径下宣称“同等”。如果审计要归因到人，优先 SDK；如果只是存量第三方客户端纳管，透明代理是过渡。

### 6.4　“无返工”评估

回函称“两期之间无废弃、无返工：V1 登记的 Client ID、会话与审计事件在 V2 全部沿用”。这句话在登录入口层面成立，在调用治理层面不成立。

**表 9  两期兼容性清单**

| 可沿用 | 可能返工 / 新增 |
| --- | --- |
| IAM 登录入口、Client ID、会话、审计事件 | 公共客户端/PKCE 改造（V1 若按机密客户端过渡） |
| 人的实名与组织数据 | 令牌 audience 与资源注册 |
| AI 网关的个人凭据与模型权限 | 智能体注册、责任人、工具集 |
| — | SDK 集成/代理部署、网关路由 |
| — | 业务权限数据对接、策略模型 |

建议在合同中写“兼容性清单”，不写口号。兼容性不是“同一套系统”，而是“哪些资产、哪些标识、哪些审计记录可以延续”。把清单列清楚，比承诺“无返工”更有价值。

## 7　标准与合规

回函使用了 RFC 8693、RFC 8707、OIDC CIBA、SCIM 2.0、SPIFFE/SPIRE、TC260 框架等标准与框架。使用标准是好事，但要注意三点：标准版本、标准角色、标准实现。标准名称不等于标准实现，支持某标准也不等于通过验收。

**表 11  标准与合规映射**

| 标准 / 框架 | 回函用法 | 评价 | 待验证 |
| --- | --- | --- | --- |
| RFC 8693 | STS 令牌交换 | 成熟；适合“人 + 代理”双标识 | actor/subject 语义、audience、令牌类型 |
| RFC 8707 | AIGS 称 audience 绑定 | IAM 不支持 resource；AIGS 需自有注册表 | 是否实现 resource 参数 |
| OIDC CIBA | 人在回路 | 成熟；适合异步确认 | auth_req_id 生命周期、binding message、IM 依赖 |
| SCIM 2.0 | IAM→AIGS 同步 | 标准；但 IAM 无出站 | 通道、中间件、时延 |
| SPIFFE/SPIRE | 工作负载身份 | 云原生适用；传统环境成本高 | 与业务 agent 身份的映射 |
| TC260 框架 | 分工论证 | 方向一致；非认证 | 不能作为合规证明 |
| 等保/密评/PIPL | 审计/UEBA | 需隐私评估 | 告知、同意、最小化、保留期 |

RFC 8693 的 actor_token 与 subject_token 语义、RFC 8707 的 resource 参数、SCIM 的 PATCH 语义、CIBA 的 auth_req_id 生命周期，都需要在 POC 中逐项验证；不能以“支持某标准”作为验收结论。特别是 RFC 8707：AIGS 声称“委派令牌绑定目标资源域”，但 IAM 明确不支持 resource 参数；如果 AIGS 没有自己的资源注册与 audience 校验，所谓“标准绑定”就只是产品内部字段。

TC260 框架是风险治理框架，不是产品认证。回函称“与 TC260 对智能体身份与访问管理独立成域的要求一致”，方向可以认同，但不能据此证明合规。等保、密评、数据安全法与个人信息保护法对员工画像、审计保留、访问控制有具体要求；UEBA 与 7 年审计涉及员工数据，需要告知、最小化、保留期与访问控制，不能只用“安全”作为合法性基础。

## 8　适用性评估与建议

### 8.1　对本项目的价值

对本项目，AIGS 的价值在 V2：当研发助手从“模型问答”扩展到“调用工程服务/MCP 工具”时，需要工具级授权、逐跳身份、调用链审计。AIGS 的五项能力与这些需求高度对应。但 AIGS 不解决 V1 的登录、会话、撤权；也不能用来填补厂商口径下 IAM 的 08（公共客户端/PKCE）与 19（SCIM 出站）缺口。把 AIGS 放进 V1，会让一个尚未验证的平台成为登录链路的依赖，风险和进度都不可控。

### 8.2　采用建议

### 8.3　五条设计原则

- 默认拒绝：没有明确策略即拒绝，不做“先放行后补策略”。
- 人可问责：每个智能体必须有责任人；责任人变更、离职要转移或注销，不能留下孤儿。
- 逐跳收缩：令牌每跳换发、绑定 audience，不携带全局长令牌。
- 证据可回放：每次决策可回放到人、工具、参数、策略版本。
- 故障 fail-closed：PDP/STS 故障时拒绝高危操作；低危可降级但需记录，不能静默放行。

### 8.5　决策建议

- 如果 V2 仅模型 API：不引入 AIGS；用 IAM + AI 网关，先把登录、撤权、审计闭环。
- 如果 V2 有 MCP/工具调用：先 POC AIGS，不直接生产；POC 以六项能力为退出标准。
- 如果监管要求工具级审计：AIGS 的价值上升；但先解决权限数据与 SCIM 通道，否则审计只能看到“允许/拒绝”，看不到“为什么”。
- 如果组织没有智能体责任人制度：先建制度；否则 AIGS 的注册、责任人、生命周期能力无法发挥作用。

## 10　结论

- 方向正确：智能体治理需要独立于人的 IAM 的策略与凭据机制；四类差异成立。
- 但 AIGS 不是 V1 的答案：V1 的登录与撤权仍靠 IAM + AI 网关；AIGS 不能填补 08/19 的缺口。
- 五项能力成熟度不同：统一认证、调用链身份传递较成熟；三重交权最依赖外部数据；审计与人在回路是有效补充。
- 采用顺序：制度 → 通道 → POC → 许可 → 规模化；POC 以注册、双标识、audience、PDP、CIBA、审计六项为退出标准。
- 三个不要：不要把 AIGS 当 IAM 缺口的兜底；不要把“标准名称”当“标准实现”；不要把“零代码”当“零治理”。

AIGS 不是“更高级的 IAM”，而是“智能体调用治理”的另一套问题域。把它放在正确的位置，它能解决 V2 的真实问题；把它当成 V1 的万能补丁，它会掩盖当前版本的缺口，并推迟真正需要的改造。
