## 1. 背景与目标

结论：方案在文档设计层面具备可实施路径，且大部分工作不需要从零开始；企业接口与双端实测通过门禁前，不代表已经可上线。企业侧已具备标准 OAuth IAM、自研 Kong AI 网关（对接企业内私有化模型）和带 API/CLI 的自研 DevOps 平台，拟用 DSH 的凭据 seam、LLM 路由和插件机制承接；真正的约束来自三处——**DSH 是单用户产品**、**官方桌面端不构建 Linux**、**银河麒麟 aarch64（占试点终端 50%，约 400 台）的沙箱与原生模块需要实机先验**。

因此一期面向 3 个部门共 800 人，按“每人一套 DSH”落地，不做多租户：Windows（约 400 人）用桌面 App，银河麒麟（约 400 台）用 `dsh --profile web` + 浏览器（仅本机自用），macOS 不纳入一期。IAM 插件承担企业登录、身份与工具授权；模型网关凭据由 UAG 个人凭证单独承担，不承担“打开 DSH 的准入”。

### 1.1 已确认的决策输入

| # | 决策 | 影响 |
|---|---|---|
| 1 | 企业自研 IAM，遵循 OAuth 标准，支持跳转登录与回调 | 走 Authorization Code + PKCE；需确认 OIDC 还是纯 OAuth2 |
| 2 | 基于 Kong 的自研 AI 网关 + 企业内私有化模型，具备详细额度管理 | 个人走当前身份＋DSH 用途，A/B 待评估；应用 Agent 受控开通，不以控制台 OIDC 证明数据面能力 直通；客户端不持上游模型密钥，持有网关个人凭据；团队/成员预算与限额在网关侧 |
| 3 | 每人使用自己的 DSH；共享 Web 后续再议 | 多租户整块移出一期，省略 connection/session 的核心改造 |
| 4 | 自研 DevOps 平台，提供 API 与 CLI | 复用现有 CLI，以系统变更及独立验收为主；查询基线 + 受控写目标（待批/默认禁用），不自建 MCP 服务 |

### 1.2 不在本期范围

一期不做事项以 [需求与场景基线](../requirements/requirements-baseline.md) §2.2（`N1–N8`）为唯一真源，涵盖：多人共享单实例（多租户）、macOS 客户端、白标发行、自建模型推理服务、公网访问或跨网段暴露本机 Web、替换 DevOps/Gitee 平台、修改 DSH 核心（DevOps/Gitee CLI 不需要核心补丁；其他 MCP 补丁须单独评审）、客户端二次计量。默认采用官方 App，不白标；§9 的询问不能直接翻转非目标，确需白标须先走范围变更并单独立项。

## 2. 目标架构

```text
员工终端（每人一套 DSH，3 部门 800 人）
├─ Windows（50%）：DSH Desktop（MSI 自助安装 / MDM 可选）
└─ 银河麒麟 aarch64（50%）：dsh --profile web（绑定 127.0.0.1）+ dsh-web-open + 浏览器

  ├─ IAM 插件（@heluo/forge-iam；可选参考 dsh-oidc）
  │    系统浏览器 → 企业 IAM：Code + PKCE
  │    回调 127.0.0.1:<port>/iam/callback
  │    登录/刷新维护 IAM 会话；网关目标授权的取用方式待确认
  │    账户/首启展示授权状态，B 路线另录入本人 Key（探测待验证）
  │    为未来获批的 MCP 集成预留按 resource 取 token；不是 CLI 接入前提
  │
  ├─ 策略插件（@heluo/forge-policy，tools/pre-execute + tools.guard）
  │    ├─ $DSH_HOME/** 硬拒绝（防 Agent 读取 .credentials.yaml）
  │    ├─ 客户数据外发（C3）转本机 ask 二次确认
  │    ├─ SDD 阶段路径保护规则
  │    └─ 决策审计上报 OTel Collector
  │
  ├─ LLM 路由（目标凭据承载待 DSH seam 核验）
  │    A 目标令牌 / B 目标令牌＋本人 Key → 网关身份/用途/策略 → 私有模型
  │      ├─ 当前人员＋DSH 用途；B 另校验本人 Key 归属
  │      ├─ 模型白名单 + 团队/成员预算 + RPM/TPM
  │      └─ 有 Key 开 privacy_mode；A 无 Key 有等效 C4 策略
  │
  ├─ DevOps CLI（查询基线 + 受控写目标，未批写禁用）→ 企业 DevOps API
  └─ Gitee gh 兼容 CLI（查询基线 + 受控写目标，未批写禁用）→ Gitee API
```

### 2.1 令牌与身份传递

个人 A 纯令牌或 B Key＋令牌均需要可信当前人员、网关目标授权及单授权生命周期。B 两种凭据同时验证并比较归属，不允许二选一；A 必须有无 Key 的等效预算、IP 及 C4 策略。具体传输头、配置和 DSH 适配尚待 G1 冻结，不能把旧 `apiKeyEnv=ENTERPRISE_STATIC_KEY` 视为完整目标实现。

按请求重新解析凭据，刷新/换 Key 后无需重启为目标；不能仅凭 seam 判断已可行。身份续期与模型请求重发分开，已执行、已输出或未知请求不自动重放。DevOps/Gitee 仍按各自 CLI 用户凭据接入，不自动纳入本轮网关取令牌改造。

当前授权退出、五分钟停用/撤销、离线及故障边界严格按[评审稿 §4](../architecture/gateway-identity-review.md#4-撤权退出与故障的时间语义)验收；本轮没有修改实际实现或配置。

### 2.2 认证与调用链路

| 链路 | 做法 | 备注 |
|---|---|---|
| IAM 登录 | Authorization Code + PKCE（S256），public client，loopback 回调 | 桌面走系统浏览器，不把 IAM 登录页嵌进 WebView |
| 模型请求 | A 网关目标令牌或 B 令牌＋本人 Key，验证身份、用途、来源、模型及预算 | 具体承载待核验；不持上游密钥，未知结果不重放；不回落裸 Key |
| DevOps CLI | 本机受控调用，经 bash seam 与策略执行；查询与受控写分别列清单 | 系统变更及独立验收为主、故事作背景；核验输出/凭据/权限，研发写待范围与 C3 分类批准后另验 |
| Gitee CLI | 本机受控调用 `gh` 兼容 CLI；查询基线 + 受控写目标 | 核验仓库/Issue/PR 查询、JSON/凭据/双端；常规研发与评审写待范围/C3批准、真实确认及回查验证，不自动合并 |

> 本节为历史目标链路，保留以说明设计初衷；V1 现状见 §10.2：厂商 6.0.3/6.3 不支持公共客户端/PKCE，实际采用机密客户端 + 系统钥匙串。

现有 UAG key-auth 是历史能力证据，不证明新路线已支持。按[网关契约](../contracts/gateway-contract.md)与网关新函验证身份、用途、五分钟及策略等效，错误/重试、流式取消与预算仍需真实联调。应用 Agent 仅复用网关受控开通，不在本项目建设管理后台。

企业授权由 IAM、网关、DevOps / Gitee 服务端校验身份、scope 与资源授权兜底。用户有本机管理员权限，preset、本机配置与插件开关只是客户端治理措施，不是不可绕过的企业授权边界；`approval=never` 也不代表 C3 风险动作已经完成人工确认。

## 3. 关键技术事实与依据

以下表格保留原文于 2026-10-20 记载的 DSH `0.2.1-rc.2` 源码、官方文档与公开仓库历史核验结论，引用路径指向上游资料，并非本项目已有代码或本次重新核验结果。企业部署适用性仍须门禁实测；“硬拒绝”“纯配置打通”等是待验证方案目标，50–80 行补丁、约 30 行适配层为规模估算，5 秒刷新/锁行为为测试目标，不是已证实能力或工期保证。

| # | 事实 | 证据 | 对方案的影响 |
|---|---|---|---|
| 1 | 浏览器连接共享单一 owner Peer，cookie 负载只有 authority，没有用户主体 | `packages/client/connection/src/rpc-host.ts`（`browserPeer`）、`browser-auth.ts`（cookie payload v1/v2） | 共享实例等于共享身份；一期按每人一套规避 |
| 2 | 凭据 seam 分 `CredentialRef` 与 `CredentialKey` 两个空间，消费者按操作重新解析 | `packages/credentials/credentials`、`docs/subsystems/credentials.md` | 令牌轮换即时生效，不需要重启 |
| 3 | `llm-pi-ai` 支持自定义 OpenAI 兼容网关，`apiKeyEnv` 按请求解析 | `packages/llm/llm-pi-ai/README.md` | 模型链路纯配置即可打通 |
| 4 | MCP client 的 `env` / `headers` 在加载时求值，没有按请求解析或 OAuth 客户端 | `packages/mcp/mcp-client/README.md` | 仅在后续有获批 MCP 集成且无法由现有机制满足身份生命周期时评估补丁；不阻塞 DevOps/Gitee CLI |
| 5 | 官方桌面端只构建 macOS 与 Windows，发布 feed 目标为 `mac-arm64`、`mac-x64`、`win-x64` | `apps/desktop/scripts/electron-builder-config.mjs`、`apps/desktop/publishing/README.md` | 银河麒麟没有官方 Electron 客户端，只能走本机 Web |
| 6 | Linux 沙箱链为 `bwrap → Landlock → fail closed`，无可用后端时拒绝执行而非降级 | `packages/sandbox/sandbox-local/README.md` | 约 400 台麒麟的首要准入验证项；加固内核可能直接不可用 |
| 7 | Web 前端构建目标为 `es2022` | `apps/web/vite.config.ts` | 浏览器版本已确认达标，不再作为风险 |
| 8 | 插件市场为 AIHUB 托管的 format-1 index，私有 registry 优先且不回落公网 | [DESIGN-012](../design/services/market-index.md)、[issue #12](https://github.com/hrygo/heluo-forge/issues/12) | 仍需 AIHUB 索引、终端 npm 认证与三目标实机验证 |
| 9 | 目标 DSH 只随附 0600 的 `$DSH_HOME/.credentials.yaml`，agent 以同一 OS 用户运行，可读取 | `packages/credentials/credentials-local/README.md` | 生产前由独立 keychain provider 保护；不可用 fail closed；仅 dev/pilot 显式接受 0600，并用 `@heluo/forge-policy` 硬拒绝访问 `$DSH_HOME/**` + 沙箱遮蔽挂载 + 短 TTL |
| 10 | 公开部署的 launch URL 即进程凭据，文档要求只分享给预期用户 | `docs/user/guide/public-deployments.md` | 麒麟本机 Web 强制绑定 `127.0.0.1`，由 `dsh-web-open` 脚本读取本机 launch URL 拉起 |
| 11 | npm 上 `@deepseek-ai/dsh` 共 36 个版本，全部为预发布，最近 30 天 14 个版本，最新 `0.2.1-rc.2` | npm registry 实测 | 必须锁版本、内部镜像、兼容性门禁 |
| 12 | `sharp`、`koffi`、`node-addon-system` 均有 linux-arm64 预编译；`node-pty` 无预编译，安装时回退 `node-gyp rebuild` | npm registry 元数据、`packages/subprocess/subprocess-local/package.json` | 麒麟需在 arm64 构建机预构建 profile，避免用户端编译 |
| 13 | 旧方案所选 `mcp-gitee` 发布资产没有 `linux-arm64`；当前已改为复用 Gitee 现有 CLI | GitHub Releases API（旧方案核验，v1.0.0）；CLI 可用性待 Gitee 团队核验 | 该资产缺口不再触发交叉编译；新形态依赖 CLI 的麒麟可用性与稳定 JSON 输出 |

## 4. 工作分解

工期为推断，按 2–3 名 DSH 工程师计，不含企业 IAM / 网关 / DevOps 等团队的排期等待。以下是同一项目的条件基准，不是四份可独立承诺的日程；完整范围、优先级与指标以 [需求与场景基线](../requirements/requirements-baseline.md) 为真源。全周期分为四个阶段与四道门禁：
- **P0 前置验证（1 周，过 G0 门禁）**
- **P1 概念验证（4 周，过 G1 门禁）**
- **P2 试点工程与运行（工程准备 4 周过 G2 门禁 + 3 部门 800 人试点运行 6 周过 G3 门禁）**
- **P3 持续推广（G3 后持续）**

本轮 A/B 需提供方分别评估配置、开发、许可、联调、上线等待与持续维护成本。旧“无需网关改造”及历史“加两周”均不能沿用；路线未冻结前不承诺固定增量或总日期。

> **P0 启动条件（2026-10-28 复核）**：共享 `client_secret` 的威胁模型、客户端实现与 secret 生命周期、平台 keychain 适配器三项未关闭前，只做离线设计与契约验证，不占用 30 人试点名额；详见 DESIGN-002 §4.5 与 §10.6。

### 4.5 项目级关键路径与资源假设

结论：**15 周 = 1 周前置验证 + 4 周概念验证 + 4 周工程准备 + 6 周试点观察**，仅为依赖按时到位、资源无冲突且门禁一次通过时的工作周基准，不是开工或上线日期承诺。阶段、需求优先级与 WBS 的 `P0/P1/P2` 含义不同，映射仍以 [需求与场景基线](../requirements/requirements-baseline.md) §5 为准。

| 基准窗口 | 关键依赖与合流点 | 未满足时的处置 |
|---|---|---|
| 第 1 周，G0 | P0-1 双端验证计划及麒麟候选环境；P0-2 / P0-4 IAM 协议、刷新；P0-3 / P0-5 网关候选路线及专用访问、预算、日志边界；责任团队认领接口和排期 | 阻断相关前置结论，不以回函、脚本输出或日历到期代替实测 |
| 第 2–5 周，G1 | Windows 登录适配与 DevOps/Gitee CLI 双端验证可并行；以两项只读闭环、凭据注入和 10 人内测合流 | CLI 命令、结构化输出、身份授权或目标终端可用性未通过时，关闭对应工具并提交替代形态评审 |
| 第 6–9 周，G2 | 经验证的 CLI 只读查询与未知结果处置；策略与最小审计；双端安装、私有市场；C1–C4 与安全负向用例合流 | 任何准入安全缺口先关闭相关能力、暂停相关批次；不得关沙箱、放宽令牌或绕过授权赶进场 |
| 第 10–15 周，G3 | G2 签署后试点运行；按基线第 4 / 6 周观察与 M1–M3、M5–M6 复核，完成 A10–A13 的推广完整性验收 | 观察不足、数据不可判定或指标未通过则延期 / 复测，不视为已获扩量批准 |

资源与估算口径：

- **资源假设**：2–3 名 DSH 工程师承担客户端、插件、集成、打包与支持；IAM、网关、DevOps、Gitee、安全、IT、PMO 各自指定接口人与评审人（均待确认）。开发与 800 人试点支持争用同一人力，约 1:300 只是既有粗估，不代表已具备值班或响应承诺；支持占用增加时须重排工程任务。
- **依赖等待**：企业团队的受理、环境开通、接口确认、审批与修复等待未计入 15 周。PMO 按责任方记录“请求 / 承诺 / 实到 / 阻塞门禁”；只把阻塞关键路径且不能并行消化的净等待计入重排，不能把所有团队等待机械相加。
- **条件增量**：本轮 A/B 的新增配置、开发、许可及联调等待重新估算；旧零改造或固定两周不沿用。取得负责人和计划后更新里程碑，不先承诺日期。
- **容量与性能**：800 是一期试点人数，不是 800 并发承诺。P1 测量模型调用时延（含 P95）、错误率、令牌刷新、并发连接与限流等基线；负载模型、峰值假设及 G2 通过阈值由 `CONF-GW-*` / `CONF-PMO-*` 回函确认，未拍板前不编造吞吐、并发或时延数值。阈值未定或测试未通过，不能以“容量 800”替代准入证据。

### 4.7 试点运行、止损、退出与恢复

结论：一期仍为 3 部门 800 人；分两批各 400 人只是资源建议，不改变总范围、五项指标数值或既定分母。完整需求与判定以 [需求与场景基线](../requirements/requirements-baseline.md) §6 / §8 为准，PMO 未批准前不另立计量口径。

**计时与批次（待 PMO 在 G0 批准并回写基线）**：记录每批实际进场时点 `T_b`、名单版本、终端与角色构成；M1 / M2 仍按基线的 24 小时窗口，第 4 / 6 周仍按基线口径采集。建议另附各批相对 `T_b` 的第 4 / 6 周结果检查可比性，不能把第二批观察不足冒充完整 6 周，也不能混用“已进场”与“全量 800”分母美化结果。若错峰、暂停或数据缺失导致观察窗口不足，G3 延后；末批覆盖窗口超出第 15 周属于条件基准延长，不自动压缩观察期。各批独立观察是否作为正式口径，须经 `CONF-PMO-*` 确认，不能由本计划自行生效。

恢复不仅是“进程启动”：还须检查错误 / 过期令牌仍拒绝、权限未放大、C1/C4 未改变、审计可归因。变更版本、策略或接口后须重测受影响门禁，不能复用失效证据；退出、恢复和事件留存的具体步骤及保留期由对应 L3 运行手册与 `CONF-IT-*` / `CONF-SEC-*` / 服务方回函确认。

### 6.3 三条不变量与结束边界

1. **一致性**：canonical spec 与代码不漂移，保留 freeze / 指纹 / stale / archive。
2. **原子性**：交付 PR 同时包含实现、spec 与归档。
3. **可追溯**：系统变更号贯穿 Issue、提交、PR 与验收证据。

Issue 在相应验收通过且交付 PR 已合入后关闭；DSH 不自动合并。业务验收、生产上线、用户故事及系统变更最终结束由既有流程负责，不能照搬旧 `change done`。CI/CD 已有制品与 UAT 部署关联只查询，不接管执行。

| A14 | 标准符合性 | 授权码 + loopback IP（V1 为机密客户端；PKCE 仅在厂商书面确认且可用时纳入验证），错误 `state` / 回调 / 身份校验失败拒绝；DevOps/Gitee CLI 按确认的用户授权范围执行只读命令；若后续另有获批 HTTP MCP，按资源校验 `aud` 并暴露 PRM；错误资源/scope 拒绝；未来 MCP 的 401 刷新仅对可安全重试的只读请求验证，无法确认未执行时不自动重放；本轮验证网关目标 Access Token、拒绝 ID Token 冒用、B 身份归属 AND、用途全入口、五分钟和当前授权/刷新后代隔离；未知结果不重放；UAG 标准部署的 MCP 使用同一 `apikey`、不按 `resource` 换令牌，不能据此宣称 A14 已满足 |

**A14 补充判据（2026-10-28）**：机密客户端必须验证 token、refresh、revoke 三处均携带 client authentication；错误/缺失 secret 被拒；secret 不出现在日志、argv 或错误消息；不同 client 不能互换 secret；轮换/吊销后旧 secret 失效。回调必须取得书面精确匹配规则并做相似路径/额外后缀/未登记端口负向测试；无法取得时，不得仅凭 loopback 判定通过。

验收记录须包含至少一个拒绝反例及其可观察结果；仅存在规则、配置键或 `mutating` 标记不构成通过。当前会话若出现 `approval changed` 仅表示 runtime 状态变化，不是企业需求变更或本机确认完成证据；企业风险确认要求只能按正式范围 / 策略变更流程调整。

| 白标发行与官方更新策略冲突 | 中 | 一期用官方 App；确需白标时单独立项 |
| MCP 工具过多挤占上下文 | 中 | 按 7 类角色 preset 裁剪、只读优先、Skill 承载流程 |
| 依赖等待 / 试点支持挤占关键路径 | 高 | PMO 按净关键路径重排；条件增量不机械相加，15 周不作为日期承诺；支持资源与升级时限由团队确认 |
| 工具标签失真、查询越权或结果未知 | 高 | 不信任工具自报 `mutating` 作为授权；只读清单外的工具拒绝；服务端独立授权；超时或无法确认未执行时不盲目重放 |
| 800 人被误作 800 并发且性能阈值未定 | 高 | P1 先测基线，`CONF-GW-*` / `CONF-PMO-*` 在 G2 确认负载与通过阈值；未测 / 未批准不能视为容量通过 |

## 10. 2026Q4—2027 插件与工具落地（2026-10-28 更新）

> 本节替代第 2—9 章中与 IAM 6.0.3 / AI 网关 2.2.1 现状冲突的 PKCE 与 A/B 假设；第 1—9 章保留为历史方案与背景，不再作为本期插件与工具排期依据。本节所有“支持/不支持”以 2026-10-26 厂商 21 项回函的版本矩阵为主口径；内部校验回函的不同观察不升级为厂商承诺，冲突见 §10.2 注；未实测能力一律标注“待验证”，不作为放行依据。
>
> 本节保留的 V1 Key-only 路径及令牌延期安排只是历史候选，不能覆盖 ADR-16 与[网关契约 §4.1](../contracts/gateway-contract.md#41-身份用途与凭据)的当前人归属、撤权等准入条件；条件未满足时不开放个人模型访问。ADR-18 采用默认 UA 的关键词匹配也不改变上述身份门禁。

### 10.1 结论

V1 按当前版本的真实能力落地，不把 PKCE 或 SCIM 作为唯一实现路径；个人模型访问仍须满足当前人归属校验、撤权等既定放行条件，能力不足时不开放该路径。三条结论：

1. **登录**：IAM 6.0.3 用机密客户端 + 系统浏览器 + 本机回环 + 系统钥匙串，`client_secret` 只进钥匙串；不宣称公共客户端/PKCE。
2. **模型**：AI 网关 2.2.1 的历史接入候选为一人一 Key + `apikey` + DSH 默认 UA + IP + `privacy_mode`；网关按 UA 关键字匹配为目标、能力待确认，UA/IP 只降低误用，不是身份绑定，也不替代人员归属等放行条件。详见[网关契约](../contracts/gateway-contract.md#41-身份用途与凭据)与 ADR-18。
3. **工具**：先只读、再受控写；AIGS 只进 V2 工具面，不补 V1 的 08/19 缺口。

2026Q4 先做 30 人、再复制到 100 人；2027Q1 随 IAM 6.3 扩到 800 人；2027Q2 AIGS 单场景 POC；2027H2 收敛到终版。终版不是另一套系统，而是在同一组接口上替换实现。

### 10.2 能力边界

| 能力 | IAM 6.0.3 | IAM 6.3 | AI 网关 2.2.1 | AIGS 2027Q2 | 方案应对 |
|---|---|---|---|---|---|
| OIDC 登录 | 支持 | 支持 | — | — | 系统浏览器 + 回环 |
| 公共客户端/PKCE | 不支持（厂商口径） | 不支持（08 项，厂商口径） | — | 智能体侧支持 | V1 机密客户端；PKCE 留开关（代码待实现）；内部回函未确认公共客户端 |
| AT 形态/TTL | 不透明；默认 7200s，可配 | 同左 | 不验 IAM AT | 委派令牌分钟级 | AT 尽量 300—900s；模型走 Key |
| RP 登出 | 不支持 | 部分支持 | — | — | 本地清空 + 浏览器 SSO 登出；6.3 后接 RP 登出 |
| SCIM 出站 | 不支持 | 部分支持 | — | 有 SCIM 端点 | V1 不做目录同步；P2 前验证 6.3 或桥接 |
| 网关当前人校验 | — | — | 不支持 | MCP 侧支持 | V1 明确 Key-only；UA/IP 只降误用 |
| 五分钟停用 | 管理台可强制下线 | 待测 | 未证实；缓存约 300s | 智能体 5 秒清退 | V1 不宣称 5 分钟；实测后定边界 |
| MCP/工具治理 | — | — | 无 | 五项能力 | V1 只读本地工具；P2 接 AIGS |
| 工具授权 | — | — | — | PDP/PEP | V1 本地策略；P2 接 AIGS PDP |

> 08 项存在来源冲突：厂商 6.0.3/6.3 书面回函均不支持公共客户端/PKCE；内部 2026-10-26 校验回函 §02 称授权码 PKCE 能力（允许 plain），但 §08 未答，未确认免 Secret 公共客户端。V1 按较保守的厂商口径执行，不把 PKCE 作为门禁。
>
> 表中 04/14/15 也有来源差异：厂商把已发 AT 实时阻断列为“按不具备规划”、6.0.3 不支持 RP 登出、未确认自定义有效性接口；内部校验回函对停用即时作废、登出端点、有效性回查另有观察。V1 均按较保守口径处理，详见 IAM 台账 §4.5.5。

三个硬约束：

- **6.3 的厂商口径仍不解决公共客户端/PKCE**：厂商 6.3.0 对 08 项结论仍是“不支持”；内部校验回函 §02 仅称 PKCE 能力、§08 未答，不能推出公共客户端。谁把公共客户端/PKCE 写进 Q1 验收，谁就会在 3 月阻塞 800 人上线。
- **网关不能证明当前人**：模型路由只认 API Key；准确表述是“本人 Key 模式”，不是“当前人校验已通过”。
- **AIGS 不是 IAM 的补丁**：AIGS 的 SCIM 端点需要上游推送；IAM 6.0.3 没有 SCIM 出站，6.3 也只是部分支持；三重交权还需要业务权限数据。

| 阶段 | 时间 | 目标 | 关键交付 | 退出条件 |
|---|---|---|---|---|

P0 只做四件事：登录、模型、只读工具、回滚。停止规则：登录成功率低于 95%、密钥进入日志/上下文、钥匙串不可用且未走试点例外、回滚超过 30 分钟——任一条触发，暂停扩量。

P1 升级 IAM 6.3 后先做五项回归：nonce/auth_time、RP 登出、SCIM 出站、AT TTL、管理台强制下线。每项有书面/实测结论后再改插件；08 仍不支持则继续机密客户端，19 只部分支持则不把 SCIM 设为 800 人前置。

P2 只选一个低风险、只读、单工具场景（代码检索或日志查询），验证注册、双标识令牌、audience、PDP 求交、CIBA、审计回放六项。六项全过才扩第二个工具；不过，AIGS 停在 POC，不影响 V1。

### 10.5 关键决策

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | V1 用机密客户端，不硬等 PKCE | 厂商 6.0.3/6.3 的 08 项均不支持；内部 §02 的 PKCE 观察未确认公共客户端；等 PKCE 会阻塞 800 人 |
| D2 | 按部门/批次注册多个 client；单 client 覆盖人数与轮换周期由 P0-6 定，未定前不扩量 | 把单一 secret 泄露的爆炸半径压到批次；不把“多 client”当成已足够 |
| D3 | 网关先用 Key-only，明确标注 | 当前无当前人校验；UA/IP 不能替代 |
| D4 | AIGS 不进 V1 | 未部署/未许可；SCIM 依赖不成立 |
| D5 | 工具先只读 | 写操作需要审批/回查；先把查询跑通 |
| D6 | 不新建 gateway 包 | 原生 provider + 凭据 seam 已够；避免重复实现 |
| D7 | 用稳定接口留演进缝 | 2027 换实现不换契约 |
| D8 | 五分钟不达标就不宣称 | 当前无书面证据；缓存约 300s |

### 10.6 书面接受的残余风险

| 国产 Linux 钥匙串/沙箱不确定 | P0 小范围 | P0/P1 实机门禁；不可用则 0600 仅试点 + 策略硬拒绝；生产无适配器不扩量 | 进入 800 人前 |
| AIGS 三重交权缺数据 | P2 POC | 退化为能力上限 ∩ 策略范围，审计标注 `degraded` | 业务权限接口可用 |
| AIGS SCIM 不成立 | P2 工具场景 | 不做目录联动；JIT + 管理台下线 | IAM 6.3 SCIM 实测通过 |

## 11. 2027 终版方案

### 11.1 终版定义

终版是 2027-12-31 可复现的运行状态，不是“所有能力都开”。已开放：人的登录、模型调用、只读工具、受控写、智能体单场景。未开放：无数据支撑的三重交权、未许可的 AIGS 生产、未证实的五分钟、未支持的 PKCE、未通过的写操作。

### 11.2 目标能力

| 能力 | 终版目标 | 成立条件 | 不成立时 |
|---|---|---|---|
| 人的登录 | IAM 6.3；机密客户端为主；PKCE 若可用则灰度 | 6.3 升级完成；回调/claims 回归通过 | 保持机密客户端；不写 PKCE |
| 会话退出 | RP 登出可用则调用；否则本地清空 + 浏览器 SSO 登出 | 6.3 的 14 项实测 | 保留兜底；不宣称全局登出 |
| 模型访问 | 网关 Key+Token 或 Key-only；一人一凭据 | 网关生产版本确认 | Key-only + UA/IP + 90 天轮换 |
| 工具 | 只读 + L1/L2 受控写；审批台账与回查 | 策略/审批/审计通过 | 仅只读；写操作关闭 |
| 智能体 | AIGS 单场景扩到 2—3 个工具；双标识/委派/CIBA | AIGS 许可/部署；SCIM 或目录桥接 | 停在 POC；V1 不受影响 |
| 审计 | jti 全链；本地 + SIEM | 字段对齐；保留期批准 | 本地审计 + 导出 |

终版不承诺“三重交权全量落地”。三重交权需要业务系统实时权限数据；取不到时，最终权限退化为“智能体能力上限 ∩ 策略范围”，审计标注 `degraded=true`。终版不承诺“五分钟停用”在所有网关节点成立；实测超过五分钟，就把该能力标为未达标，限制高风险用途，而不是改口径。终版不承诺“AIGS 生产全覆盖”；AIGS 只覆盖工具调用，人的登录、模型 Key、DevOps/Gitee 仍由各自服务端负责。终版不承诺“PKCE 已支持”；只有 IAM 书面确认并通过回归，才把 `authMode=pkce`（当前未实现）打开。

### 11.3 演进缝

| 演进缝 | V1 实现 | 2027 实现 | 兼容规则 |
|---|---|---|---|
| 认证模式 | `confidential` | `confidential` / `pkce` / `aigs` | `authMode` 为 V1 目标接口，当前配置校验拒绝；同一回调路径 |
| 令牌来源 | `staticKey` | `key+token` / `delegated` | `TokenSource` 接口；不改变调用方 |
| 策略 | 本地 policy | 本地 + AIGS PDP | decision 结构 allow/deny/approval + obligations |
| 工具描述 | risk/resource/action | 同左 + `agentScope` | 字段只增不减；旧字段保留 |
| 审计 | actor/jti/decision_id | 同左 + `agent_id`/`on_behalf_of` | V1 写空值，2027 填值；查询兼容 |
| 分发 | enterprise bundle | bundle + 原生市场 | 包名与配置 schema 不变；只升版本 |

### 11.4 可运营性

终版必须能运营：版本可锁、配置可回滚、密钥可轮换、审计可查询、故障可降级、容量有基线。运营指标至少包括：登录成功率、刷新失败率、模型 401/429/5xx、工具拒绝率、审批时长、Key 轮换到期数、AIGS 决策拒绝率、jti 缺失率。

## 12. 交叉审查摘要

### 12.1 方法

## 附录 A 银河麒麟兼容性验证脚本

以下为历史只读候选探针，不安装组件或改变系统配置；本次未执行。由获准人员在目标麒麟机器执行并保留脱敏输出，仅用于环境初筛，不能代替 A4 / A6 的真实隔离测试或证明命令 / 子进程已受保护。

```sh
uname -a
uname -m
getconf GNU_LIBC_VERSION
node -v 2>/dev/null || echo "node missing"
command -v bwrap && bwrap --version
bwrap --unshare-user --dev-bind / / true && echo bwrap-ok || echo bwrap-fail
cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null || echo "userns knob absent"
cat /sys/kernel/security/lsm 2>/dev/null || echo "lsm unavailable"
```

判读：

- `aarch64` + glibc ≥ 2.28 + Node 24 可运行：仅形成基础环境候选结论，还需验证原生模块与实际安装包。
- `bwrap-ok`：只说明该最小命令成功，未证明 DSH runner 配置下凭据遮蔽、文件 / 命令 / 链接 / 子进程隔离成立；须完成 A4 / A6 正反例后才能判定可用。
- `bwrap-fail` 且 `lsm` 含 `landlock`：仅列 Landlock 为候选，仍需核验内核实际支持、权限与 runner 行为，不能凭字符串决定已可用。
- 两者都不可用：由 IT / 安全确认装 bwrap / 开 userns / 自定义 runner 的处置路径并验证后再推进相应能力；不得用关闭沙箱代替通过。
- Windows 不适用上述 Linux 探针，必须另按 A4 建立实机负向回归；本附录不提供 Windows 安全隔离已经成立的结论。
