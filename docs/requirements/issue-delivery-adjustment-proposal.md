## 1. 结论与效力

1. 建议以“系统变更组织业务目标，Issue 承载单仓库、可独立交付与验收的工作”替代以系统变更直接绑定唯一仓库的执行模型。
2. Issue 信息充分时不另行编写需求规格；Agent 按复杂度、风险及接口影响决定设计材料，不以固定规格、冻结清单或 Skill 序列作为默认开工条件。
3. 研发执行复用 Teamflow，企业语义通过 Skill 指引；动作门禁归 `forge-policy`，对象与授权归既有业务平台，交付证据优先复用 Git、PR 和 CI，不建立第二套流程、授权或业务状态库。
4. 当前需求不足以证明必须保留独立 SDD 产品或默认启用专有冻结 CLI。建议先收缩默认交付要求，再按实际缺口决定是否保留特定校验；本轮不删除、停用或迁移现有实现。

**本文不是第二份范围基线。**项目范围仍以[基线 §2](requirements-baseline.md#2-范围边界唯一真源)为唯一真源。§3 记录需求方已确认的澄清，§4—§8 是拟议调整、证据与后续评审安排；本次仅新增方案及导航登记，不修改现行基线、架构、组件契约或批准记录，不表示建议已部署。

## 2. 本轮产出边界

本轮交付一份可供评审的需求差异、职责分配与验证方案，不实施接口或行为变化。代码、插件配置、企业权限、默认团队和现有 SDD 包保持原状；不运行真实需求、不合并、不推送、不发布、不关闭 Issue 或系统变更。

方案采纳后，必须先将批准的差异合入基线，再同步架构、设计、契约、计划与验收；未经相应审核，不以本方案绕过当前安全门禁。真实字段及平台能力不足时先提交缺口，不凭设计文字宣称已支持。

## 3. 需求方已确认的交付模型

### 3.1 对象与执行单元

| 对象或关系 | 已确认要求 | 执行含义 |
|---|---|---|
| 系统变更 | 业务管理对象；一个变更对应一个或多个 Issue | 保存共同业务目标、总体范围和约束，不把新会话默认扩展为全部 Issue |
| Issue 与变更 | 每个 Issue 必须关联一个系统变更 | 从 Issue 开始时核实所属变更；不从标题相似度猜关联 |
| Issue 与仓库 | 每个 Issue 仅对应一个代码仓库 | 本次实施只在已确认的该仓库执行；跨仓库工作拆成多个 Issue |
| Issue 拆分 | 每个 Issue 必须能够独立交付与验收 | 按结果拆分，不以只完成一部分文件修改代替可验收交付 |
| 日常入口 | 可以从系统变更或 Issue 开始 | 从变更进入时选择本次 Issue；从 Issue 进入时反查并核实变更 |
| 需求材料 | Issue 信息充分时，不另行编写需求规格 | 缺失信息先澄清；不生成重复、独立维护的需求真源 |
| 设计材料 | Agent 按复杂度和风险决定是否需要 | 简单工作可直接使用 Issue；跨接口、复杂约束或高风险时补必要设计 |

一个 Issue 可以对应续跑、返工等多次执行记录。Teamflow run 不是新的业务对象；恢复同一工作应保留既有 Issue、变更、仓库和执行证据，不强制 Issue 与 run 永久一对一。

### 3.2 信息职责与冲突处理

- 系统变更承载共同业务目标和总体约束；Issue 承载具体范围、验收条件、依赖及已确认补充。两者按职责组合读取，不将完整变更正文复制到每个 Issue。
- 业务澄清需要更新权威对象时，按该信息的归属写回；写回仍需真实动作、目标、授权和版本检查。本文不裁定尚未核验的平台字段或写接口。
- 变更与 Issue 有实质冲突、缺失关联、关联多个变更、仓库不唯一或源版本不可核实时，允许只读核查和澄清，不猜测后进入实施。
- 信息充分性至少覆盖目标、范围与非目标、必要约束和可执行验收条件；存在依赖时还需说明依赖交付及版本。Agent 的设计裁量不等于改变业务范围或批准高风险操作。
- 需求版本、代码版本或验收条件变化后，重新判断受影响的方案、验证与人工确认；不得沿用针对旧版本的通过结论。

### 3.3 独立交付与验收

独立不等于没有依赖。每个 Issue 应有本仓库可识别的交付结果、验证方法以及必要前置条件；依赖其他 Issue 时明确依赖交付和版本。尚未满足的前置条件如实列为未验或阻塞，不能用模拟结果代替真实联调通过。

不能形成独立验收结果时，调整 Issue 边界、交付顺序或约定的接口前置条件，不以“其他仓库以后补齐”宣布当前 Issue 完成。跨 Issue 的集成或业务验收属于变更层面的另行验证，不要求跨仓库原子提交，也不因单个 Issue 完成而自动通过。

### 3.4 可核对交付的最小结果

利用现有记录串联：系统变更、Issue、唯一仓库、相关 run、实际提交 SHA／PR 和对应版本的验证证据。报告区分“已执行且通过”“失败”“未执行或未知”，并注明证据来源与对象版本，不增加必须手填的专有 manifest。

本地检查通过、远端 CI 通过、PR 合并、Issue 验收和系统变更业务验收是不同结论。远端 CI 不可用时可报告已验证的本地候选交付，但不得写成已通过 CI 或已完成业务验收。Agent 不代写人工确认，也不因证据齐备自动执行合并、发布或关闭。

## 4. 对现行要求的调整建议

以下是待并入基线的差异，不是对当前规则的静默覆盖。沿用已有需求编号，不创建另一套需求 ID。

| 现行位置 | 处理 | 拟议调整 | 保留边界 |
|---|---|---|---|
| [基线 §2.3、REQ-09／REQ-10](requirements-baseline.md)；全流程设计 §2—§3 | 调整 | 支持变更与 Issue 双入口；将执行仓库约束下移到 Issue，先核实关联再实施 | 变更仍是业务对象；真实只读证据、唯一仓库与授权匹配不放宽 |
| [基线 §2.3、REQ-22](requirements-baseline.md)；全流程设计 §6 | 调整 | 一次工作聚焦一个已确认 Issue；业务澄清按变更／Issue 职责归属，不能将执行记录变为新真源 | 版本冲突、未知结果不重放、受控写与人工业务验收边界保留 |
| [基线 S8、REQ-18](requirements-baseline.md)；SDD 设计 §4—§6 | 收缩 | 从默认规格冻结、专有清单和实现＋spec＋archive 齐套，转为 Issue 充分性、按需设计和版本对应证据 | 必需文档与实现不矛盾、实际验证可追溯；不以文件摘要代替业务正确性 |
| [基线 REQ-20](requirements-baseline.md)；[策略设计](../design/plugins/forge-policy.md) | 保留并澄清归属 | 动作、路径、风险确认和审计继续归 Policy；不在 SDD 或 Skill 中复制硬门禁 | 不以收缩 SDD 放宽 HARD 规则；阶段保护是否保留及如何映射执行阶段需另行评审，不能声称已实现 |
| 基线 §2.3；[全流程设计 §5／§8](../design/plugins/forge-devops-lifecycle.md) | 保留 | 独立审查、人工确认、版本变化失效、真实结果回查 | 工程验收不冒充业务验收；不自动合并、部署或最终关闭 |
| [架构 §7.4、ADR-6](../architecture/platform-architecture.md)；[SDD 设计](../design/plugins/forge-sdd.md) | 收缩组件要求 | 不将独立 SDD 产品、冻结 CLI 或固定 Skill 链列为默认交付；按 §6 评估具体校验需求 | 不新建流程引擎，不将所有交付检查塞入 Policy；现有实现不在本轮删除 |
| [推广方案 P2-7、A11、企业交付清单](../plans/rollout-plan.md) | 调整验收与交付目标 | 用 §7 的 Issue 执行、关联与证据场景替换强制 spec／freeze／archive 齐套验收；复核企业交付清单中默认 SDD CLI 的必要性 | 必要安全与人工审查验收保留；测试与门禁要有实际正反例证据，本地通过不替代企业或双端验证 |
| [跨模块冲突 C4](../design/conflict-resolution.md)；[设计索引](../design/README.md) | 提请复核适用范围 | 按调整后的需求确定仍需执行的校验并同步登记；C4 不要求每次交付必跑本地与 CI 两端，不将其解释为默认交付 SDD CLI 的依据 | 同项检查在本地和 CI 执行时仍用同一规则／版本，本地不替代 CI、不维护第二套规则；既有 2026-10-24 决定及历史实测记录保留，适用范围变化需新的责任方结论 |

提交前缀 `[变更号]` 等现行追溯约束不因本方案自动取消。是否同时规定 Issue 标识的具体语法、分支和 PR 校验位置，须随接口与仓库规则评审确定，不在本轮编造新格式。

## 5. 职责收敛与方案取舍

### 5.1 推荐职责

| 能力 | 首选承载 | 不应承担 |
|---|---|---|
| 双入口、Issue 拆分与信息充分性、按需设计、交付整理 | 企业 Skill 指引 | 第二套研发调度、权限系统或业务状态库；以提示词冒充硬门禁 |
| 分诊、开发、测试、工程验收、恢复与 run 证据 | Teamflow | 取代变更／Issue 真源、人工业务验收或自动企业闭环 |
| 变更读取与必要受控更新 | 现有 DevOps 能力及其平台 | 复制代码平台能力；以本地数据猜企业字段 |
| Issue／仓库／PR／提交读取及获准操作 | 现有代码平台能力 | 自行授予写权限，绕过服务端授权或未知写自动重试 |
| 动作、路径、风险确认与审计 | `forge-policy` 与服务端已有控制 | 重建研发状态机；宣称所有 shell／Git／UI 入口已被覆盖 |
| 版本、评审、测试与关联证据 | Git、PR、CI 等现有记录 | 单凭文件 hash、手填 revision 或 Agent 口头结论证明正确性 |
| 确有不足的读取、输出转换或交接 | 经证据确认后再评估薄适配 | 预设新增插件、通用引擎、数据面或控制面 |

职责归属是方案，不代表所有链路已接通。当前工作区 DevOps／Gitee 的收敛实现与个人 Skill 试点不能替代企业服务端权限、字段和双端证明。

### 5.2 备选路径

| 路径 | 评价 | 结论 |
|---|---|---|
| Skill＋Teamflow＋现有业务工具／Policy／Git／CI，必要时薄适配 | 与当前需求匹配，复用执行与证据；仍需核实 §6 缺口 | 推荐先验证，不预设新增组件 |
| 将冻结、manifest 和 SDD CLI 保留为默认流程 | 现有代码可做部分文件一致性检查，但已确认需求没有提出普遍冻结要求，会增加重复产物 | 不作为默认交付；专门场景另有需求时再评估 |
| 将全部流程和交付检查并入 Policy | 混合动作授权与事后证据判断，扩大安全组件职责 | 不推荐；门禁保留，交付核对复用业务平台与 CI |

## 7. 拟议验收场景

下列断言用于后续方案采纳后的验证设计，本轮未执行这些业务场景。

| 场景 | 通过判据 | 负向判据或禁止行为 |
|---|---|---|
| 从 Issue 开始新会话 | 读到唯一有效变更关联、唯一仓库和可执行验收条件，范围只含本 Issue | 关联缺失／冲突／越权／版本未知时只读澄清，不猜测实施 |
| 从系统变更开始 | 展示关联 Issue 并确定本次执行对象 | 不自动启动全部 Issue 或把变更强绑唯一仓库 |
| 跨仓库需求拆分 | 每个 Issue 只有一个仓库，分别有交付结果、验收方法和显式依赖 | 不创建一个跨仓库执行 Issue；依赖未满足不伪称已验收 |
| Issue 信息充分 | 不要求独立需求规格才能开工；必要设计可定位回 Issue | 不强制生成 spec／freeze／archive 齐套，不自动宣称 Teamflow 已可裁剪阶段 |
| 需求不足或实质冲突 | 询问缺口并保留实际确认、来源与版本 | 不用默认假设代替范围／验收决定，不擅自写回 |
| 中断、返工及版本变化 | 可追溯同一 Issue 的 run 与代码版本，旧证据只适用于原版本 | 不重复启动掩盖已有 run，不沿用过期人工确认 |
| 可核对候选交付 | 定位变更、Issue、仓库、实际 SHA／PR 及对应版本的实际验证；缺项明确未知 | 不以 hash 或手填 testedRevision 证明测试，不把本地成功写成 CI／业务验收 |
| 独立审查与人工结论 | 审查和人工确认指向实际对象版本，区分来源 | Agent 不代写人工结论，版本变化后不自动沿用 |
| 其他 Issue 未完成 | 如实报告本 Issue 可证实的交付，列出剩余业务工作 | 不把本 Issue 或全部 run 完成当作系统变更关闭依据 |
| 未获准写入与安全保护 | 现有授权、HARD 规则、风险确认与审计继续生效 | 不因使用 Skill／Teamflow 绕过门禁；不自动合并、发布、部署或关闭 |

## 8. 采纳与后续文档顺序

1. **本轮方案产出**：新增本文，登记版本及导航；不更改现行规则，不删除 SDD 实现，不执行真实业务场景。
2. **需求调整评审**：需求、平台与受影响安全／业务团队核对 §4 差异及 §9 事项，保留真实确认；批准后先更新基线 §2、S8 与相关 REQ 条目，范围真源仍只有一处。
3. **设计与验收同步**：依次更新总体架构及相关 ADR、全流程／SDD／Policy 设计、工具字段契约、冲突 C4、推广 P2-7／A11、组件与组合包说明、索引和登记。历史决定和测试记录保留，不将其改写为新方案已验。
4. **缺口验证再立实施任务**：先取得真实只读关联样本和现有 Git／PR／CI 证据，再确认 Teamflow 内部产物、提交格式、隔离与交接限制。由这些结果决定 Skill、CI 配置或薄适配的具体任务；不得由本文自动派生新产品或放宽权限。
5. **现有 SDD 处置另行批准**：若确认不再使用某项校验，先盘点调用、包分发、组合包与 CI 依赖，再制定兼容、下线及回退方案。没有该证据和授权，不删除文件、不撤包、不更改已安装 profile。
