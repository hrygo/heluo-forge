## 1. 结论与效力

**本方案的需求和四项取舍已由项目负责人（当前用户）于 2026-11-03 最终确认，不再等待平台、安全或 PMO 替本项目批准。** Agent 负责第三方开发者建议、技术核验及实施。企业目标角色与外部维护方是使用场景、事实来源或权限提供方，不是本项目的需求审批链；真实服务端权限、企业强制规则及安全控制仍必须遵守。

决定以系统变更组织业务目标，以 Issue 承载单仓库、可独立交付验收的工作；支持变更／Issue 双入口。充分 Issue 不另写需求规格，Agent 按需设计。研发执行只复用 Teamflow，Skill 提供企业语义，Policy 执行动作门禁，Git／PR／CI 保留版本及验证证据，不建立第二套流程或业务状态库。

**本文不是第二份范围基线。** [需求基线 §2](requirements-baseline.md#2-范围边界唯一真源)为唯一范围真源；本文记录已确认的决定、落实顺序与技术验证任务。生效的是本方案决定，不表示相关实现、安装或企业联调完成，也不把基线及架构中其余未核验章节一并标成已批准。

## 2. 本轮产出边界

本轮同步文档（需求、治理、架构、设计、契约工作语义、计划验收和导航登记）及仓库文档检查器与用例；产品源码、包清单、组合配置、企业权限、已安装 profile 及现有 SDD 包不修改。不删除、卸载或停用组件，不启动 Teamflow 或真实业务，不提交、推送、合并、发布、部署或关闭对象。

已确认产品要求直接作为设计依据。实际字段、平台能力与安全映射不足时，由 Agent 取得证据并报告具体缺口；不重复询问同一需求，不将技术未验变成虚构的组织审批。后续代码改造、安装迁移和真实试跑须在相应已明确授权的实施范围内执行。

## 3. 已确认交付模型

### 3.1 对象与执行单元

| 对象或关系 | 已确认要求 | 执行含义 |
|---|---|---|
| 系统变更 | 业务管理对象；一个变更对应一个或多个 Issue | 保存共同目标、总体范围和约束，不强绑唯一仓库，不默认启动全部 Issue |
| Issue 与变更 | 每个 Issue 恰好关联一个系统变更 | 从 Issue 进入时核实所属变更，不凭标题猜关联 |
| Issue 与仓库 | 每个 Issue 恰好对应一个代码仓库 | 本次只在该仓库实施；跨仓库工作拆成独立交付验收 Issue |
| Issue 拆分 | 按可验收结果拆分 | 每项有交付、验证方法和显式依赖，不以局部文件修改冒充完成 |
| 日常入口 | 变更或 Issue 均可进入 | 变更入口先选定本次 Issue，Issue 入口反查并核实变更及仓库 |
| 需求材料 | Issue 信息充分时不另写规格 | 不维护重复需求真源；不足时只澄清缺口 |
| 设计材料 | Agent 按复杂度、风险和接口影响决定 | 必要设计可定位回 Issue，不固定 Skill 或文档序列 |

一个 Issue 可对应续跑、返工等多次 run。run 是执行记录，不是业务对象，不要求与 Issue 永久一对一。

### 3.2 信息职责与版本

- 变更承载共同业务目标和总体约束，Issue 承载具体范围、非目标、验收、依赖及已确认补充，按职责组合读取。
- 澄清按归属写回权威变更或 Issue，仍需真实动作授权、目标、源版本和回查；不在聊天或内部 PRD 中另立业务真源。
- 关联缺失、多变更、多仓库、实质冲突、无权限或源版本不可核实时，只读核查及澄清，不猜测后实施。
- 信息充分性覆盖目标、范围、非目标、约束、可执行验收及必要依赖版本。Agent 的设计裁量不授予范围或高风险动作决定权。
- 需求、代码或验收版本改变后，重新判断旧方案、验证及人工确认的覆盖，不沿用旧版本通过结论。

### 3.3 独立交付与验收

独立不等于没有依赖。每个 Issue 应有本仓库可识别的结果、验证方法和前置条件；依赖未满足时列为未验或阻塞，不能用模拟结果替代真实联调。不能形成独立验收结果时调整 Issue 边界或交付顺序；变更层集成及业务验收另行核对，不要求跨仓库原子提交。

本地验证与独立 AI 审查通过后形成待验收交付，用户对实际代码版本决定是否接受。远端 CI 通过、PR 合并不是所有人工验收的统一前提；已有必要 CI、分支保护及仓库强制规则仍须遵守。本地验证、CI、合入、Issue 状态、用户验收与业务结束分别记录，不互相替代。

### 3.4 最小追溯结果

复用现有记录串联变更、Issue、唯一仓库、相关 run、实际 SHA／PR 与版本对应验证；区分通过、失败、未执行或未知，注明来源，不增加必须手填的专有 manifest。相关提交保留 `[变更号]` 前缀，PR 关联本次 Issue，不新增强制分支命名语法。

Agent 不代写人工结论。用户验收不自动授权合并、发布、部署或关闭；单个 Issue 或全部 run 完成不导致变更最终结束，不调用旧 `dop change done` 代替业务判断。

## 4. 四项已确认决定

| 决定 | 2026-11-03 最终确认 | 落实与验证边界 |
|---|---|---|
| SDD 退出默认并以独立组件退役为目标 | 不把规格、冻结清单、spec／freeze／archive 齐套作为默认开工或验收前提 | 先盘 CLI、bundle、tests、callers，再处理未使用部分；只留明确用途的最小能力，不为旧代码创造冻结需求；本轮不删源码、撤包或改 profile |
| 接受 Teamflow 内部运行材料 | 内部 PRD、技术蓝图等可以保留，不作为第二需求真源，不要求用户重复填写 | 实际重复确认或阻塞按证据最小解决，不新建流程引擎，不宣称当前已跳过 PRD |
| 保留现有提交追溯 | 提交保留 `[变更号]`，PR 关联 Issue，不强制新分支语法 | 核实 Teamflow 最终提交模板、现有仓库规则及证据，不承诺开工 commitMessage 已控制最终模板 |
| 验证、独立 AI 审查后待用户验收 | 用户针对实际代码版本验收，不一刀切以 CI／已合并为前置 | 必要 CI、分支保护必须守；CI／merge／Issue close／验收／业务结束分开，不自动 merge、部署、关闭或代人工结论 |

## 7. 后续验证场景

| 场景 | 通过判据 | 负向判据或禁止行为 |
|---|---|---|
| 从 Issue 开始 | 读到唯一变更、唯一仓库与可执行验收，范围只含本 Issue | 关联缺失／冲突／越权／版本未知时不猜测实施 |
| 从变更开始 | 展示关联 Issue，确定本次对象 | 不自动启动全部 Issue，不强绑唯一仓库 |
| 跨仓库拆分 | 各 Issue 独立交付验收且依赖版本明确 | 不用一个跨仓库 Issue，不把未满足依赖写成已验 |
| Issue 充分 | 不要求用户重复规格，必要设计可追溯；内部 PRD 不成为新真源 | 不强制 spec／freeze／archive，不声称当前阶段已裁剪 |
| 缺口及版本变化 | 只问缺口并记录真实确认，重判旧证据覆盖 | 不用默认假设代业务决定，不沿用过期确认 |
| 候选交付 | 本地验证与独立 AI 审查对应实际代码版本，待用户验收 | 不以 hash 或自报 testedRevision 证明测试，不把本地成功写成 CI 成功 |
| 用户验收与状态分离 | 用户明确接受对应版本，CI／合入／Issue 状态／业务结束分别记录 | 不以统一已合并门槛阻塞人工验收，不绕过必要 CI 或保护，不自动关闭 |
| 未获准写及强制控制 | 动作授权、HARD 规则、风险确认及审计继续有效 | Skill／Teamflow 不绕过门禁，不代写人工结论，不自动合并／发布／部署 |

## 8. 落实顺序与完成边界

1. **本轮文档同步**：先保留基线 §2.3 的已确认决定，统一 S8、相关 REQ 与治理；同步架构、全流程、SDD 兼容退役、冲突 C4、工具工作语义、推广 P2-7／A11、组件说明、导航与登记。保留原编号、路径、历史依据和未验状态，不改产品源码与组合配置；文档检查器及用例如实随规则同步。
2. **文档交付核对**：检查范围唯一真源、确认日期及边界、版本登记、链接、表格和语义冲突；独立 AI 审查指出具体问题，由用户验收文档。检查通过不等于企业联调。
3. **真实只读取证**：后续在获准环境核实变更↔Issue↔仓库关联、源版本和现有 Git／PR／CI 证据；未取到证据保持未知，不编造 API。
4. **执行兼容验证**：核对 Teamflow 输入、内部 PRD、最终前缀、PR 关联、工作区暂存与交接限制。以实际缺口确定 Skill 或薄适配任务；不修改已安装依赖凑验收，不建流程引擎。
5. **SDD 盘点与退出实施准备**：在 CLI／bin、bundle dependency、构建／安装／回退、测试和所有调用者中定位实际使用；区分未使用部分与有清晰用途的最小能力。形成兼容、移除顺序、回归及回退方案，再按授权实施源码／配置变更；不把本轮文档写成已删包、已卸载或已退役。
6. **后续代码与环境实证**：本地验证、独立 AI 审查后形成候选，用户对实际版本验收；必要 CI 与分支保护按真规则执行，企业及双端未验项分别留证，合并／发布／关闭单独授权。

以上是执行顺序，不新增日历承诺或需求编号。本轮只完成文档目标，未执行后续业务验证或实际退役。
