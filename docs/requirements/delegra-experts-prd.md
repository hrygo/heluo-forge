## 1. 产品结论与文档效力

**Forge 专家**是 DSH 中面向企业各类工作的云端专家智能体入口。员工可以发现自己有权查看的专家，在聊天框中选择并 `@` 一位专家；DSH 主助手根据员工指定的目标调用专家，结合专家结果综合回复，并支持员工追问和使用成果。Delegra 负责专家配置与实际执行；DSH 插件负责员工的发现、委派和结果体验。

Paperclip 部署在云端，与员工运行 DSH 的终端分离；插件通过经授权的网络连接访问云端服务。云端的机构边界、网络路径、服务部署版本和身份授权以目标环境核验为准，不能据此推定使用公有云或机构外服务，也不以本机部署作为产品前提。

专家的职责定位与其获授工具权限集合共同界定它适合处理的工作；产品不预设专家只服务研发，也不内置固定的专家类型或工具清单。专家的实际执行还受服务端授权、工具可用性、目标系统规则和具体任务约束。用户选择专家时，目录展示可理解的能力与权限摘要，不以专家名称推断其真实权限。

产品定位、专家信息展示、主助手调用与结果呈现方式、跨会话上下文和记录可见规则以及部署拓扑已按文档信息中的确认事项确定；本文中的首期优先级、其他交互细节及验收指标是**建议**，供项目负责人完善，不表示已全部确认。示例专家、系统和数据均为说明，不表示企业已部署对应能力。

本文是产品需求草案，不是第二份项目范围基线。[需求基线 §2](requirements-baseline.md#2-范围边界唯一真源)是项目范围唯一真源，其中当前暂不做跨系统 Agent 调度。本产品涉及从 DSH 发起 Delegra 云端执行，是否及如何纳入项目范围由项目负责人决定；确认后同步基线及受影响的架构、契约、设计、实施和验收。本文不授权建设新包、改动 DSH 核心或开放企业环境。

## 2. 问题、目标与用户

### 2.1 要解决的问题

企业可以在 Delegra 配置覆盖不同岗位和业务领域的专家，但员工需要知道去哪找专家、判断哪个专家适合当前工作、了解它获准使用哪些能力、转交所需资料并带回结果。缺少统一入口时，发现、任务上下文和结果容易分散，用户也难以判断专家正在做什么、结果是否可靠以及操作由谁授权。

产品的价值是让员工在当前工作中找到合适的专家，明确把一项工作交给它，并能够追踪和继续使用结果。专家的专业能力、资源访问和执行可靠性由实际平台与企业规则决定，插件界面不创造这些能力。

### 2.2 目标与角色

| 角色 | 要完成的事 | 产品应提供的帮助 |
|---|---|---|
| 企业员工：研发、运营、财务、人力及其他岗位人员 | 找到能处理当前工作的专家，把任务及必要资料交给它 | 权限内目录、可理解的能力与权限摘要、`@` 委派、状态与结果 |
| 专家提供者 | 在企业已有平台配置专家职责定位、知识、工具与授权范围 | 插件准确展示实际发布且允许员工了解的信息；专家配置仍由 Delegra 及企业平台负责 |
| 企业管理员或运维人员 | 管理身份、授权、可用性和运行支持 | 复用现有管理入口和审计；员工能看到可采取的故障处理提示 |

首期目标建议为：完成“发现 → 选择 → 主助手调用专家 → 跟踪 → 主助手综合回复 → 追问”的可验收闭环，并在整个闭环中保留当前员工身份、权限边界、专家来源和任务归属。员工无需知道专家内部标识或先打开 Delegra 控制台。

不以专家数量、消息数量或接口返回成功单独证明产品成功；也不把调用专家等同于结果正确、企业动作已完成或业务验收通过。

### 2.3 产品边界

| 范围 | 产品要求 |
|---|---|
| DSH 插件 | 提供专家目录、选择、任务交互和结果呈现；接入真实身份和已验证的服务能力 |
| Delegra / Paperclip | 以独立云端服务维护专家及其可用信息，承载实际会话、任务、工具执行和产物；按其真实规则执行服务端授权 |
| 企业 IAM、策略与目标系统 | 分别负责身份、授权策略和目标资源的实际访问控制；具体接入以契约与实测为准 |
| 企业聊天产品 | [Forge Chat 草案](enterprise-collaboration-chat-proposal.md)关注人与人的聊天及个人总结；本文面向个人 DSH 工作流中的云端专家，两者不互相假定已实现 |

本文不建设专家创建平台、独立推理服务、企业 IAM 或新的权限管理后台，也不把专家目录当作插件市场。多人在企业群聊中共同 `@` 专家、自动选择多个专家、主动推荐、定时或无人值守任务不是本草案已确认的首期要求。

## 3. 场景与协作方式

### 3.1 代表性用户旅程

1. 员工登录企业身份，在 DSH 打开“专家”入口，浏览和搜索当前可见专家，查看专家名称、职责以及实际可得的能力与权限摘要。
2. 员工在聊天框输入 `@`，从“专家”候选中选择目标，并输入任务，例如“`@经营分析专家 请分析我提供的业务资料`”。
3. 发送前，员工可以辨认指定专家和本次交付的任务文字、已选择的资料，以及已确认的远端会话共享与可见规则；主助手按当前员工指定的专家发起调用。普通请求不额外确认，但触发[需求基线 §4.4](requirements-baseline.md#44-数据与合规约束)的客户数据导出、外发或批量复制时，必须先在本机取得人工确认。
4. DSH 呈现服务端能证明的接收、排队、执行、等待用户和终态；需要澄清时，员工通过主助手继续与同一专家关联的任务交互。
5. 专家返回可用结果后，主助手结合结果综合回复，显示专家状态与来源；原始结果默认折叠，员工可按当前权限展开查看。保留可访问产物的关联，区分专家建议、主助手的综合判断与目标系统实际完成的动作。

示例中的专家、任务和资料只是说明。是否需要上传文件、调用哪个业务系统以及首期必须支持哪些实际写操作，需结合真实场景确定。

| 领域示例 | 专家职责定位与工作 | 获授工具权限示例 |
|---|---|---|
| 运营 | 经营分析专家整理和解释业务数据 | 读取获准访问的业务报表 |
| 人力 | 制度问答专家解答员工提出的制度问题 | 检索获准使用的制度资料 |
| 研发 | 代码审查专家分析员工指定的变更 | 读取获准访问的代码与变更信息 |

这些示例用于说明同一发现和委派流程可以服务不同领域；具体专家、工具和访问范围由实际提供方配置，不能据此推断任何企业能力已存在。

### 3.2 主助手与专家的协作

员工显式选择一位专家；DSH 主助手是当次交互的协调者和综合回复者，Delegra 专家承担获授范围内的实际工作。主助手取得专家本次结果后进行综合，默认显示专家身份、可证实的任务状态与结果来源；专家原始结果默认折叠，员工可在有权访问且结果可得时展开核对。原始结果不可得、不完整或无权查看时如实提示，不将主助手的综合内容冒充专家原文。不能把专家建议、主助手判断或任务已受理说成目标系统操作已完成。

用户的每次新委派必须能明确辨认目标；对同一任务的追问保留专家与会话关联。默认不因文本中出现专家名称就推断授权，也不把上一次选择的专家默认为所有未来消息的接收方。主助手未能调用指定专家或未取得有效结果时，必须如实说明，不冒称专家已参与、不自动替换专家。

## 4. 功能需求与优先级

P0 是建议的首期最小闭环，P1 是有价值但须结合实际能力和场景确定的扩展；优先级不是已批准的项目范围。权限、数据和失败处理是各功能的组成部分。

| 编号 | 优先级 | 功能要求 | 通过条件 |
|---|---|---|---|
| FE-FR-01 | P0 | 专家目录：跨业务领域列出当前员工在已确认组织范围内**全部有权查看**的专家 | 不按研发领域或预置类型过滤；有权查看的条目可见；无权查看的专家不通过列表、搜索或缓存泄露；范围或结果不完整时明确提示 |
| FE-FR-02 | P0 | 搜索与详情：按实际可得的名称、职责等信息查找，展示可理解的能力与权限摘要 | 使用稳定身份区分同名专家；摘要依据提供方可披露的信息，说明可处理的工作和可访问资源或动作；信息不可得时如实提示，不虚构权限、能力、排名或在线状态 |
| FE-FR-03 | P0 | 查看与调用分离：展示允许查看但不能调用的专家及其状态 | 无调用权时不能提交任务；服务端对真实身份、专家和动作重新授权 |
| FE-FR-04 | P0 | `@` 选择：在聊天框的候选中区分专家与文件、会话等引用 | 用户能识别并选择唯一专家；普通 `@` 文本不隐式触发调用；已选目标因编辑或恢复丢失时保留草稿，不静默改为普通消息或调用其他专家 |
| FE-FR-05 | P0 | 主助手委派：根据用户选定的专家发起调用，向该专家发送明确填写的任务文字和明确选择的资料 | 界面可辨认目标、发送范围与已确认的远端可见规则；远端执行前核对本次员工身份、选定专家和允许发送的资料，模型生成参数不构成授权；适用基线 C3 时本机确认先于发送或执行 |
| FE-FR-06 | P0 | 任务反馈：显示可证实的接收、排队、运行、等待用户和终态 | 无精确进度时只显示已知阶段；接受、已回复及实际任务完成不混为一谈；耗时任务的结果保持正确会话关联并供主助手综合 |
| FE-FR-07 | P0 | 综合回复与追问：主助手根据所选专家的有效结果回复，并保留专家、任务与产物的关联 | 默认显示专家状态和来源，原始结果默认折叠，可按当前权限展开；不可得或无权查看时如实提示；重开或切换会话后仍可恢复经授权的记录或可靠访问其来源；主助手的综合判断、专家结果与实际外部动作可区分；追问保持正确任务关联 |
| FE-FR-08 | P0 | 身份与权限变化：登录、退出、切换账号或撤权后重新判断访问 | 新身份不继承旧身份的目录、草稿目标或可执行权限；历史专家结果的恢复及再次进入模型上下文遵循已确认的数据保留和授权规则；不可证明授权时拒绝受影响的路径 |
| FE-FR-09 | P0 | 故障与恢复：区分未发送、服务端已接收、执行中、失败、取消和结果未知 | 超时或失联不显示成功；结果未知时先查询，不盲目重放可能有副作用的工作 |
| FE-FR-10 | P0 | 会话关系：不同 DSH 会话的专家上下文默认隔离，用户可明确选择复用获准使用的既有上下文 | 未选择复用时，其他 DSH 会话此前交给专家的消息与资料不得进入本次专家上下文；选择复用时说明来源与范围并核验权限；隔离无法保证时不开放该隔离路径，不静默改为共享或重置既有会话 |
| FE-FR-11 | P0 | 结果使用：区分专家建议、生成的产物和外部系统实际动作 | 只有能够按当前授权打开的产物提供入口；外部动作有目标系统或可信回执证据才显示已完成 |
| FE-FR-12 | P1 | 附件：由用户选择并上传文件，供专家读取或处理 | 上传前可识别文件及接收方；大小、格式、权限和实际可读性均以已验证能力为准；未读取时如实提示 |
| FE-FR-13 | P1／待定 | 业务操作：专家使用其获准工具查询或改变外部系统 | 是否需要外部操作及具体系统、动作和授权方式由负责人确认；服务端和目标系统独立执行授权与必要审计；当前基线不允许执行生产环境变更 |
| FE-FR-14 | P1 | 便利能力：收藏、排序、多专家协作和主动推荐 | 仅在目录、权限与基本委派闭环验证后按产品价值决定；不作为本版现有能力 |
| FE-FR-15 | P0 | 结果交接：将指定专家本次实际返回的结果交给主助手综合 | 主助手接收到的内容与专家、任务和来源对应且可追溯；无有效专家结果时不虚构专家观点或声称已完成；交接遵循当前权限和数据策略 |
| FE-FR-16 | P0 | 记录可见性：专家委派的会话、历史、结果和产物默认仅发起员工及按企业规则获权的管理、审计人员可见 | 服务端对会话、任务、结果及附件等入口执行实际授权；其他组织成员不得仅因同属组织而查看；无法证明该范围时不开放受影响路径 |

P0 的“全部”指真实服务可判定的当前员工授权范围，不等于某个管理员账号、某一个公司或缓存中的全部条目。若企业身份对应多个组织，聚合范围、去重与完整性由真实目录和身份契约决定；接口不支持时不得显示为已覆盖。

## 5. 交互状态与异常

| 场景 | 员工看到的状态或处理 |
|---|---|
| 未登录或身份已失效 | 展示登录入口或身份失效提示；不展示旧身份的受限目录，不发起新任务 |
| 目录为空、无搜索结果 | 分别说明没有可见专家或没有匹配项；不将接口失败伪装为空目录 |
| 目录加载失败或范围不完整 | 明确提示不可用或不完整；不把旧缓存作为当前授权事实 |
| 专家可见但不可调用 | 标明不可调用及服务允许披露的原因；不提供共享账号或其他绕过路径 |
| 草稿中目标失效、同名或未选中 | 保留已输入内容，要求重新确定目标；不以名称相似度投递，不静默把专家委派改为普通消息或派给其他专家 |
| 等待接收、排队或执行 | 按已知事实显示对应状态；允许查看专家身份与已提交内容 |
| 主助手未调用或专家未返回有效结果 | 清楚说明尚未完成专家调用或结果不可用；不冒称已获取专家意见，不自动改派其他专家 |
| 专家需要澄清或用户操作 | 显示需要用户处理的事项；提交补充信息前不伪称任务完成 |
| 连接中断、超时或结果不明 | 明确标示未知，恢复后按服务端支持的状态和事件查询；不自动重复外部写入 |
| 无法保证跨会话隔离 | 说明默认隔离路径不可用并阻止该路径；不静默共享既有上下文，也不以隐藏历史或重置其他会话代替隔离 |
| 无法保证记录可见范围 | 说明相关路径不可用并阻止受影响的提交和读取；不以界面隐藏或事先提示代替服务端授权 |
| 取消 | 显示“取消请求中”，仅在可靠终态确认后显示已取消；已发生的外部动作不承诺自动撤销 |
| 权限变化或账号切换 | 停止新的受保护读取与调用；已发送的数据、正在运行的任务和历史记录按实际服务规则处理 |
| 附件不支持或部分失败 | 标明没有成功发送或专家未能读取的内容；不声称分析覆盖了全部资料 |

界面不因一个提供方、目录或网络暂时不可用而静默切换专家、账号或模型。重试、恢复和取消的可用条件由接口契约与真实结果决定；已确认失败与结果未知应提供不同处置。

## 6. 上下文、权限与数据

### 6.1 上下文和可见范围

建议本次发送给专家的请求只包含用户输入和用户明确选定、允许发送的资料；不自动发送全部 DSH 历史、当前工作区或其他会话。主助手可按 DSH 当前会话规则结合上下文综合回复，但不能因此扩大向远端专家发送的数据范围。员工应能识别专家、资料类型和任务关联。此前交给同一远端会话的内容仍可能存在于该服务的上下文中，不能因本次输入最小化就声称远端没有历史。

不同 DSH 会话调用同一专家时，默认隔离此前分别交给该专家的消息、任务和资料；只有用户明确选择且当前权限允许时，才复用所选既有上下文，并向用户说明其来源和范围。这一规则不自动改变专家通用配置、企业知识或工具权限，相关访问仍须遵循实际授权。

Delegra 当前工作区的 Agent Chat 以人员、专家和企业为粒度组织持久会话；多条 DSH 会话复用同一远端会话时可能共享上下文。目标云端须核验远端会话、运行器及工具是否满足所需隔离和选择复用语义；分别创建任务本身不能证明专家不会读取跨任务历史。若不能保证默认隔离，必须说明并停止该隔离路径，不能靠客户端隐藏历史、静默 `/new` 或未经用户选择复用既有上下文声称隔离。用户明确选择复用时，同样需要实际服务能力和当前授权支持。

专家委派产生的会话、任务历史、结果及产物（含附件）默认仅发起员工及按企业规则获权的管理、审计人员可见；其他人员不能仅因属于同一组织而读取。管理或审计角色的实际访问仍受具体授权范围约束，界面应说明适用的可见规则；专家运行器及获授权的工具按执行所需权限处理资料，不因此赋予其他人员查看权限。

个人 DSH 中显示专家结果，不代表云端记录已符合该可见范围。Delegra 当前工作区源码中的 Agent Chat 依托普通任务及其权限，默认可见性不保证满足本产品规则；目标云端须在会话、任务、结果和产物的服务端入口分别核验。无法证明默认可见范围时，不开放受影响的提交和读取路径，不能以客户端隐藏或提前告知其他可见者代替授权。

### 7.1 技术路线的产品约束

产品目标是让员工在 DSH 中指定专家，由主助手调用并基于真实结果综合回复。可研究“专家引用进入普通用户消息 + 主助手调用插件工具 + 专家结果返回主助手”的路径；接口接缝只是可行性线索，不证明完整链路已经可用。模型可能不调用工具、选择错误目标、附带未经选择的资料或生成没有依据的内容，因此必须在真实接入中核验员工、专家和资料的本次选择绑定，确保不匹配时在发送资料或触发远端执行前拒绝；还须核验服务端授权、结果来源、失败提示和会话可追溯性，不能把提示词、模型参数或模型自述当作授权与调用证据。

候选路径还必须验证重开会话、追问、错误、取消、附件和日志边界。若当前扩展点不能满足这些要求，应作为详细设计准入的待解决问题，交项目负责人决定，不静默改变产品承诺或修改 DSH 核心。

远端调用是否需要 Delegra 侧补齐企业身份、逐专家授权或会话隔离，以双方真实契约验证为准。不能把 DSH 会话 ID、专家名称、客户端过滤或 Agent 自报当成用户身份与授权。

### 7.2 Paperclip 用户连接：按任务交办

Delegra 工作区的 `server/src/services/public-mcp/capabilities.ts` 提供以人员身份访问 Paperclip 的公共 MCP 工具。2026-11-11 使用本机客户端的现有连接只读调用 `paperclip_connection` 和 `paperclip_list_agents` 成功：前者返回当前人员、一个授权企业和连接范围，后者返回该企业内当前连接可见的专家。该探针未创建任务、发送评论或运行专家；它不证明服务与客户端同机、DSH 已接通，也不证明覆盖员工在其他企业中的授权范围。

| 顺序 | 工具和主要输入 | 实际语义与边界 |
|---|---|---|
| 1 | `paperclip_connection` | 获取已连接人员、授权企业 `companyId` 和连接范围；身份由连接提供，不能让模型自行冒充 |
| 2 | `paperclip_list_agents({ companyId })` | 读取该连接授权企业的专家，返回 `id`、`name`、`role`、`title`、`status`、`capabilities`；这些字段不包含完整工具权限策略 |
| 3 | `paperclip_create_task({ companyId, requestId, title, description, assigneeAgentId, projectId? })` | 成功返回 `task` 才表示已创建并交由正常调度，不等于已开始执行或已完成；也可能返回 `outcome: rejected` 或 `outcome: unknown`。同一次请求保持相同 `requestId` 和参数；结果未知时先查询，不换新 ID 盲目重试 |
| 4 | `paperclip_read_task({ companyId, taskId })` 与 `paperclip_list_deliverables({ companyId, taskId })` | 读取任务状态、最近评论与活动，以及文档、附件和产物引用；`read_task` 只取最近 30 条评论和活动，不能视为完整运行轨迹或保证最终答复都在最后一条评论中 |
| 5 | `paperclip_add_comment({ companyId, taskId, requestId, body })` | 以当前人员身份对同一任务补充信息；成功后可能唤醒专家或排队，不等于自动开启新的私人聊天；拒绝或结果未知时不得显示已提交成功 |

公共 MCP 的人员 OAuth 连接限定一个企业并按作用域开放操作；写入需 `paperclip:write` 和服务端有效权限。目录 `capabilities` 是已发布的能力描述，不是经证明的工具权限清单。任务同样受普通 issue 可见性规则约束，不能直接声称只有发起人能看到。具体任务的专家输出可能以评论、运行结果、交互或产物形式出现，须按实际运行器和接口确认如何取得主助手可用的完整结果。任务式交办适合研究员工要求专家实际完成工作的场景，但追问、等待和结果回传不能仅靠工具名称推定。

rc.3 的 `dsh-mcp-client` 可通过 Streamable HTTP 把 MCP 工具暴露给模型；其配置提供 URL 和请求头，当前 transport 源码未配置 OAuth `authProvider`，因此现有 Codex 连接成功不等于 DSH 已具备同一人员的授权获取、续期与撤销能力。该客户端会注册服务端公开的工具，产品还须验证最小授权和工具范围，避免把无关管理操作开放给主助手。是否启用 MCP 属现有基线的条件项，本文只记录候选路线。

| 7 | `GET /api/heartbeat-runs/{runId}/events?afterSeq={seq}&limit={limit}`；`POST /api/heartbeat-runs/{runId}/cancel` | 分 run 按序补读持久事件，或提交针对 run 的取消；须重新查询终态，取消不保证撤销已发生的外部动作 |

对同一次消息重试应复用相同 `clientRequestId` 和完整请求；超时或断线可能处于结果未知状态，不应生成新的标识盲目重发。上传附件需要先通过任务附件接口上传，再在评论中引用返回的附件 ID；附件读取仍须核验实际运行器能力和权限。

聊天路由要求 board 用户身份；工作区支持与真实用户绑定的 board API key 或适用的浏览器会话，Agent API key 不能直接代替 board 用户身份。`local_trusted` 无凭据时使用固定的本机身份，不能证明多员工身份隔离。同一企业、人员和专家复用持久会话，普通任务可见规则仍适用，不保证仅发起人可见。REST 使用的 board bearer 不能假设也可用于实时 WebSocket；当前源码的 WS bearer 分支查询 Agent key，是否支持用户身份实时订阅须在实际部署核验。

当前公共 MCP 工具清单没有发现 Agent Chat 专用操作，`paperclip_call_api` 也不能调用任意 REST 路径。上游 Paperclip 的[实现说明](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC-implementation.md)可能随版本演进，不能替代对实际 Delegra 部署版本的核验。

### 7.4 待验证的异步与身份衔接

任务式 MCP 与 Agent Chat 均可能先返回接收回执，再排队、运行和产出结果；界面和主助手不能把接收回执综合成专家结论。DSH rc.3 的 MCP 工具请求默认超时为 60 秒；长任务的状态查询、结果取得及主助手继续回复需要单独设计。外部 subagent provider 可作为另一种研究方向：它能在运行结束后向仍在线的父会话送回完成通知，但现成 DSH 不含 Delegra provider，也不保证跨进程恢复、后续追问或远端取消。

rc.3 的模型接口没有 `tool_choice`；工具注册或提示词不能保证模型一定调用指定专家。选定专家、当前员工和允许发送的资料需由可信的宿主侧上下文绑定并在远端执行前核验；若目标或资料不匹配则拒绝。应以真实调用回执和结果作为专家已参与的证据，模型直接作答不算完成委派。

建议优先验证人员 OAuth 公共 MCP 的任务式路径：现有只读探针证明一个人员连接可以读取其授权范围内的专家目录，任务工具有明确的提交、追问和结果查询入口。该建议不意味着已完成 DSH 身份打通、专家执行或结果回流；若产品需要复用 Paperclip 持久聊天语义，应另行验证 §7.3 的接口及其可见性，而不是把创建任务当成已建立专家聊天。无论采用哪条路径，DSH 专家目录、`@` 选择、可靠绑定和主助手综合回复仍需插件侧能力及目标宿主验证。

终端到云端的连接须核验实际网络可达性、传输保护、身份凭据生命周期和企业允许的数据路径。连接不可用、认证失败或撤权时应明确呈现状态并停止未授权调用；恢复后依实际回执查询，不能静默切换到本机服务、共享身份或其他专家，也不能假定提交中的任务未被云端接收。

## 8. 验收场景

下列是拟议验收断言；每个断言应在相应目标版本、真实或明确标注的隔离环境中分别留证。模拟通过不代替企业联调。

| 编号 | 场景 | 通过判据 |
|---|---|---|
| FE-AC-01 | 可见目录 | 在已确认的组织范围内，员工看到全部获准查看的专家；无权限专家不出现在目录和搜索；数据不完整时有提示 |
| FE-AC-02 | 权限分离 | 有查看权但无调用权的员工可见该专家但不能调用；直接 API 的聊天、读取、续跑、重试与取消均按真实员工、专家、会话和动作执行服务端授权，撤权后不绕过判定 |
| FE-AC-03 | `@` 目标 | 从候选选择的专家与实际接收方一致；同名专家可区分；普通未选中文字不会被误报为成功委派；已选目标意外丢失后，保留草稿，不静默改发普通消息或调用其他专家 |
| FE-AC-04 | 草稿与恢复 | 覆盖 `@` 前有文字、移动或删除选择、切换会话、重启和目录变化；目标不能恢复时保留文字并说明重新选择或明确改发的方式 |
| FE-AC-05 | 输入范围 | 本次从 DSH 新发送的资料限于员工明确提交、选定且有权发送的内容；缺失、失败或不支持的资料明确提示；远端历史和工具上下文按已确认规则另行说明 |
| FE-AC-06 | 委派与追问 | 主助手按员工选择调用正确专家，接收、执行、结果与追问关联到正确员工、专家和任务；专家已回复但关联任务仍在运行时，不显示整个工作已完成 |
| FE-AC-07 | 重开与结果 | 关闭或重开 DSH 后能按当前权限恢复专家身份、任务状态和结果，或以清晰的来源入口访问；没有权限时不能恢复受限内容 |
| FE-AC-08 | 多会话上下文 | 两个 DSH 会话调用同一专家时，默认不得使用另一会话此前交给专家的消息、任务和资料；用户明确选择且获权后可复用选定上下文，并能识别来源和范围；无法保证隔离时不开放该隔离路径，不静默共享或重置其他会话 |
| FE-AC-09 | 数据可见性 | 会话、任务历史、结果和附件等产物默认仅发起员工及按企业规则获权的管理、审计人员可见；同组织未获权人员通过界面和直接 API 均不能读取；发送前说明规则；无法证明时不开放受影响路径 |
| FE-AC-10 | 失败与未知 | 同一请求因重复点击、断网、超时或重启恢复而重试时不虚报成功或重复执行不可安全重放的任务；结果未知且无法查询时保持未知并停止盲目重放；用户明确发起的新任务与同一请求的重试可区分 |
| FE-AC-11 | 取消与外部动作 | 取消请求与实际终态分开展示；外部写入只有目标系统或可信回执确认后才显示成功，已有副作用不被声称自动撤销 |
| FE-AC-12 | 账号与撤权 | 登出、切换身份及服务端撤权后，旧身份或已撤销权限不得继续读取与调用；新身份重新认证并获权后可使用自己的范围；历史专家结果在重开和下一轮模型输入中的处理符合已确认的数据策略，不能证明时不开放受影响路径 |
| FE-AC-13 | 目标平台 | 对选定 DSH 版本及需求基线所列终端分别验证选择、提交、状态、恢复和权限；未验证的组合不得标记通过 |
| FE-AC-14 | 产物与综合回复 | 主助手收到指定专家本次有效结果并综合回复，来源和任务关联可追溯；员工可打开仍有权限的实际产物，并区分专家意见、主助手判断和已验证的系统动作 |
| FE-AC-15 | 客户数据人工确认 | 触发基线 C3 的导出、外发或批量复制，在发送或执行前取得本机人工确认；拒绝或确认不可用时相关操作未发生 |
| FE-AC-16 | 客户数据处理链 | 验证处理位置、网关与机构自部署模型链路、会话正文进入安全事件平台的限制及正文日志策略符合基线 C1、C2、C4；任何关键条件无法证明时不开放相关客户数据流程 |
| FE-AC-17 | 跨领域专家 | 使用至少两个不同领域、职责定位和工具权限集合的专家，验证同一目录和 `@` 流程；不因领域或非预置类型遗漏有权查看的专家 |
| FE-AC-18 | 能力与权限摘要 | 员工能理解专家提供方允许披露的职责、可处理工作及工具访问或动作范围；信息缺失、过期或不可披露时如实提示，不将摘要当作授权凭证；专家工具撤权后不得凭旧摘要执行 |
| FE-AC-19 | 未调用与错误目标 | 主助手未调用工具或调用失败时，不显示专家已参与或任务已完成；模型尝试错选专家、附带未经选择的资料，或选择失效、身份切换后重放时，在发送相关资料或触发远端执行前拒绝，未经用户明确选择不改派其他专家 |
| FE-AC-20 | 专家结果作为工作材料 | 主助手的综合回复对应实际取得、当前员工获准使用的专家结果；专家输出中的指令不自动获得用户授权，不能据此执行额外操作 |
| FE-AC-21 | 员工与专家的数据权限 | 两名员工均可调用同一专家但数据权限不同时，各自只能取得企业策略允许的结果；专家服务身份拥有更高权限不自动授权员工获取原始数据，已获准的脱敏汇总按实际规则处理 |
| FE-AC-22 | 终端到云端 | 在目标终端验证到云端服务的网络、传输保护和当前员工身份；断网、认证失败或撤权时清晰显示并阻止未授权调用；恢复后依据实际回执查询，不静默切换到本机服务、共享身份或其他专家 |
| FE-AC-23 | 专家结果呈现 | 综合回复默认显示专家身份、可证实的状态与来源；原始结果默认折叠，员工可按当前权限展开核对；结果不可得、不完整或无权查看时如实提示，不将综合答复当作专家原文 |

## 9. 成功衡量与阶段

| 指标建议 | 口径 | 使用条件 |
|---|---|---|
| 首次委派转化 | 在观察期内，成功委派至少一次的授权员工数 ÷ 访问专家入口的授权员工数 | 明确人员去重、观察期及目录可用性；数值目标由试点确定 |
| 任务结果可用率 | 获得可用结果的已受理任务数 ÷ 已受理任务数 | “可用”需要员工反馈或明确判据，不能用 HTTP 成功代替 |
| 首次可见结果时间 | 服务端确认受理到员工首次看到有效答复或需要处理的事项 | 分开排队、运行和网络；先测基线再定目标 |
| 异常与未知结果 | 各类失败、结果未知和无法恢复的任务数及原因 | 不收集任务正文或附件作为指标前提；按真实审计规则执行 |

建议先核验目标宿主的 `@`、提交和可恢复展示，以及 Delegra 的身份、授权、会话和事件契约；之后在隔离环境验证完整闭环，再在授权的企业环境按目标平台和真实场景验收。具体人数、排期、性能阈值、可用性目标及运营投入待试点信息和资源条件明确后确定，不把建议写成承诺。
