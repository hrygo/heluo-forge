## 摘要（一页纸）

**做什么**：让 3 个部门的 800 名研发同事在自己电脑上用上企业版 DSH——模型走企业网关，代码能读能写，研发平台以只读查询为现有基线，全程可追溯；系统变更驱动的受控写目标见 §2.3，尚待范围与安全准入。

**为什么做**：企业已有 IAM、AI 网关与自研 DevOps，但各自独立使用、没有统一入口；本方案把这些能力接进一个客户端，模型与代码都不出机构边界。

**不做什么**：多人共享实例、macOS 客户端、白标发行、自建模型、公网访问、执行生产变更。

**给谁用**：开发、评审、发布、测试、运维、PMO、外包共 7 类角色；Windows 与银河麒麟各占一半。

**要多久**：前置验证 1 周（过 G0）、概念验证 4 周（过 G1）、试点工程准备 4 周（过 G2）+ 试点运行评估 6 周（过 G3）。总周期取决于企业 IAM、网关、DevOps 三个团队的配合时间，这三段等待不在平台组控制内。

**要什么投入**：平台组 2–3 名工程师为工程粗估，各团队投入和试点支持待认领；模型与网关沿用现有，但不能据此宣称零成本。ARM构建、内部源、签名/分发、监控与支持资源是否可复用，须在G0确认。

**怎么算成功**（试点运行 6 周后判定）：

| 看什么 | 目标 |
|---|---|
| 第一次登录就成功的人 | ≥ 95% |
| 麒麟电脑装成功的比例 | ≥ 90% |
| 第 4 周还在用的人 | ≥ 60%（约 480 人） |
| 严重故障（连续 >2 小时不可用） | ≤ 2 起/月 |
| 试点结束仍愿意继续用的人 | ≥ 70% |

**最大的两个风险**：约 400 台银河麒麟的沙箱与安装；800 人对应 2–3 名工程师的支持比（约 1:300）。

**需要领导在 G0 拍板的 5 件事**：

1. 800 人一次进场，还是按人力复核结果拆两批各 400 人。
2. 客户与生产数据进入 DSH，是否按 §4.4 的四条约束执行。
3. 麒麟验证前置导致周期拉长，是否接受。
4. 是否白标；这决定 Windows 用官方 App 还是自建安装包。
5. 范围变更由谁批准。

## 1. 结论

DSH 的产品目标是替代 Comet 与 oh-my-sdd 成为企业新一代智能研发工具，不替代 DevOps/Gitee。企业业务模型及受控写增量依据 2026-10-22 需求方澄清整理；当前无企业内网访问，既有工具使用文档不等于接口实测或跨团队批准。

本文把一期范围、使用人群、必须跑通的场景、22 条有效需求（REQ-11 已取消）与 5 项试点指标收敛成一份可判定基线，作为项目范围的唯一真源。它影响四类人：领导据此决定投入与去留，开发据此排期与验收，用户据此知道能做什么，安全据此评审数据边界。

相对初版主文档的四项裁定（试点扩至 3 部门 800 人、银河麒麟占 50% 并前置为准入项、用户自助安装为主、角色细分为 7 类）已在 V0.4 中完成回写。本版另按 §5.5 / ADR-11/13 同步插件来源、AIHUB 原生索引、自包含三目标首版与轻量边界，并联动[总体架构设计](<../architecture/platform-architecture.md>)及[推广实施方案](<../plans/rollout-plan.md>)；上述人群、终端与角色输入不变。企业接口与终端能力仍待团队确认及实测，文档口径一致不等于技术验证完成。

仍缺三项输入：三个部门的名称、五项硬依赖的到位时间、试点签署人。

## 2. 范围边界（唯一真源）

一句话：一期只做 Windows 与银河麒麟两端、每人一套；模型与工具都走企业现有系统；共享实例、macOS、白标、自建模型一律不做。

本节为项目范围的唯一真源；其他文档直接引用本节，不另写独立清单。

### 2.3 系统变更驱动的受控写目标（范围调整草案）

需求方于 2026-10-22 确认以下目标；这是设计输入，不是安全、PMO 或提供方的批准。§2.1/§5.2 中只读里程碑和既有优先级暂保留，不能把下表当作已开放功能，也不能只在设计中写“自动回写”而不处理范围变化。完整能力地图见 [DESIGN-013](../design/plugins/forge-devops-lifecycle.md)，候选动作/字段见[工程工具契约](../contracts/engineering-tools.md)。

| 对应条目 | 拟调整的产品要求 | 现有基线与开放前条件 |
|---|---|---|
| REQ-09 / A7 / P1-5 | 显式 command/Skill 加明确系统变更号；取独立描述、验收、系统/仓库及所属故事；人确认后的澄清回写正确对象，按平台语义记录开始/研发进展 | 只读输入优先核验；回写范围、字段、版本冲突、权限与审计待 DevOps/安全/PMO 确认，写默认关闭 |
| REQ-10、REQ-22 / A8 / P1-4 扩展 | 系统变更关联一或多个 Issue；自动维护分支/PR及交付关联；相关 commit 均以 `[变更号]` 开头；Issue 只在本项验收通过且交付 PR 已合入后关闭 | 普通研发写拟沿有限任务委托执行；动作级开关、目标仓库、用户权限、幂等/回查、确认与审计需 Gitee/安全/PMO 批准 |
| REQ-18、REQ-20 / A11 / P2-7 | 保留产物/冻结/原子交付不变量；不固定 Skill 次序、不移植旧 Runtime；更强模型交叉审查后由人确认，正式 review 留在 Gitee | 模型选择、独立审查、原生确认和策略挂点需宿主实测；不得自建通用编排引擎补齐 |
| C3 / §5.3 | 对已确认本次变更/仓库内的常规研发写，提出可由有限任务委托覆盖的精确分类；业务澄清、人工 review、批量/跨边界数据外发仍需相应真实确认 | 现有 C3 对跨系统写要求 ask；分类调整须安全批准。批准前不得用入口确认直接绕过 C3，相关写保持关闭或执行原确认要求 |
| REQ-16 / A13 / P2-5 协同 | 在必要审计之外增加可独立降级的最小观察事件，平台计算研发过程指标 | 指标用途、分母、认证与保留期待批准；不改 M1–M6/G3，不新增指标平台 |

**企业责任边界**：用户故事可有多个系统变更；一个变更明确对应一个系统和仓库。一次 DSH 任务只承接一个变更，不自动接管其他系统。要求澄清回写 DevOps，不在聊天或仓库另立业务真源。业务验收由业务人员承担，功能上线后故事结束，系统变更状态/结束时间随故事变化；工程交付后不得提前设置最终完成，也不照搬旧项目 `dop change done`。Git Issue 与 DevOps 最终状态可以不同步结束。

**保持不做**：自动合并、代替业务验收、生产部署/回滚/审批、最终结项管理、跨系统 Agent 调度、通用修复循环引擎。CI 触发及生产状态读取若另有必要，分别走范围评审，不因六阶段地图出现就变成一期必做。DSH 可以读必要交付事实，但不承担上线过程。

## 3. 用户与终端画像

一句话：3 个部门共 800 人，Windows 与麒麟各半，从开发到 PMO 共 7 类角色，用户自己安装软件。

### 3.1 规模

| 部门 | 人数 | 说明 |
|---|---|---|
| 部门 1 | 200 | 待 PMO 提供 |
| 部门 2 | 500 | 待 PMO 提供 |
| 部门 3 | 100 | 待 PMO 提供 |
| 合计 | 800 | 800 人全部为一期试点（已裁定并回写 L1/L2） |

800 人为一期试点总人数。按 2–3 名 DSH 工程师的配置，支持比约 1:300；这是推断，需 PMO 与平台组在 G0 按实际人力复核，建议分两批（每批 400 人）有序进场。

### 3.2 角色与权限档位

| 角色 | 主要用途 | 建议档位 | 依据 |
|---|---|---|---|
| 开发者 | 写代码、调模型、调用工程系统工具 | 可安装 AIHUB 索引内、发布前策展的精确稳定版；禁直连公网源 | 架构 §7.5 |
| 评审人 | 看改动、按规范卡点 | 只读为主；禁装插件 | 架构 §7.4、§7.5 |
| 发布负责人 | 流水线、发布信息查询 | 只读；禁装插件 | 架构 §7.3、§7.5 |

| 运维 / SRE | 查研发信息与日志 | 只读；禁装插件 | 架构 §7.3、§7.5 |
| 项目经理 / PMO | 进度、指标、审计查看 | 只读 + 审计只读；禁装插件 | 架构 §7.6 |
| 外包 / 实习生 | 受限开发 | 最小权限：禁用 `plugin_manager` | 架构 §7.5 |

### 3.3 终端与前置条件

| 项 | 现状 | 影响 |
|---|---|---|
| Windows | 50%（约 400 人，推断） | 官方 App + MSI 自助安装；MDM 推送为可选路径 |
| 银河麒麟 | 50%（约 400 台，推断） | 安装包 + 内部软件源；沙箱与终端组件必须先验 |
| 终端权限 | 用户有本机管理员权限，可自助安装 | 不依赖 MDM；安装失败率与版本漂移由升级门禁兜住 |

用户可自助安装缩短了对 IT 的依赖，但把风险转到两处：安装成功率无法由 IT 统一兜底，版本可控更依赖升级门禁与版本检测。约 400 台麒麟是本方案最大的单点，麒麟验证不通过则一半用户无法上岗。

## 4. 核心场景

一句话：试点必须跑通 7 条场景；其中首次登录、额度与登录异常两条不能失败。生产环境变更不在一期范围（N9），工程系统现有只读基线与 §2.3 受控写目标分开验收。

### 4.1 场景总览

| # | 场景 | 什么时候发生 | 做到什么算成功 | 主要失败点 | 验收 |
|---|---|---|---|---|---|
| S1 | 首次登录与激活 | 第一次打开 | 完成登录与网关凭据配置后 30 秒内完成一次对话；未登录或凭据未配置时企业模型不可用 | 浏览器未拉起、回调端口不通、用户取消授权、凭据未创建/粘贴错误 | A1、A2、A3 |
| S2 | 日常编码与问答 | 每天 | 能对话、能调工具、能改代码；额度用完不自动重试 | 额度耗尽、上下文超限、模型未授权 | A3、A4 |
| S3 | 查用户故事与研发信息 | 生成 spec 或排查问题时 | 只读查询返回真实结果，用户故事可用于 spec 输入 | 工具未授权、令牌未绑定、工具过多挤占上下文 | A7、A14 |

### 4.2 用户会经历什么

**第一天。** 自己装好（或由 IT 推送），双击打开，浏览器跳出公司登录页，用现有账号登录；随后按提示到 UAG 控制台创建一把个人凭据（每台设备一把，建议 90 天），粘贴回 DSH 并完成探测，就能提问。登录与凭据配置完成后，目标是 30 秒内完成第一次对话；首次开通总时长取决于控制台操作，另行测量，不套用 30 秒。没登录或没配置凭据时不会给你任何替代模型，避免把公司代码发到外面。

**平时。** 像现在一样打开项目目录，让它读代码、改代码、跑测试；问它“上次构建为什么失败”；让它查研发平台里的用户故事与工程信息。它的能力清单在会话里可见，不用记命令。

**出问题时。** 额度用完，界面展示恢复时间；UAG 不细分个人/团队时提示到控制台查看具体额度，不会偷偷换成别的模型。网关 401 提示检查 Key 或到控制台核查，不把凭据失效冒充登录过期；登录过期才提示重新登录，不用重启。生产环境变更由既有平台和人工流程执行，助手不承担。

### 4.3 两条不能失败的路径

**S1 首次登录**：未登录时企业模型全部不可用（组合包不保留其他路由）→ 点登录拉起系统浏览器 → IAM 登录页 → 回调本机 `127.0.0.1:<port>` → 校验 `state` / `nonce` / `iss` / `aud` → 写入 IAM 会话 → 引导到 UAG 控制台创建个人凭证 → 粘贴 → 探测 → 首次对话。登录失败停在“待重新登录”；凭据未配置/无效停在“模型未就绪”，两者不得混同。任一步失败，不得降级到任何公网模型。

**S7 异常自助**：预算耗尽时展示 `reset_at`；无法区分个人/团队时提示到 UAG 控制台查看，不自动重试。RPM/TPM 429 按 `Retry-After` 退避。登录过期由客户端刷新并重试一次；网关 401 不刷新 IAM、不重放，提示检查或重建 UAG 凭据。不静默切换模型。

### 4.4 数据与合规约束

试点允许客户与生产数据进入 DSH 上下文，以下四条作为硬约束：

| # | 约束 | 通俗说 | 落点 |
|---|---|---|---|

### 5.3 追踪约定

- `REQ-*` 是唯一需求编号；验收项与工作分解项只在这里引用，不在其他文档另起编号。
- 需求删除不删编号，标“已取消”并写明替代项；REQ-11 按此处理。
- 一条需求对应多条验收时，全部通过才算达标。

### 5.5 插件制品来源决策

2026-10-21 用户已确认[ADR-11](<../architecture/plugin-registry-source-decision.md>)：企业私有 npm 统一承载公网同步包和内部定制包；固定 Gitee group 只约束内部定制源码，不要求公网包先迁入 Gitee。终端不直连公网，企业仓库缺包或上游不可达不能转向公网或 Gitee 归档；内部 scope 不得代理到公网同名包。

用户另确认首版只收自包含、Windows 10 amd64／统信 UOS 20 amd64／银河麒麟 aarch64 三目标通用的稳定版；普通带依赖或单平台包不是 DSH 非法，只是不进首版索引。2026-10-21 进一步决定采用原生索引轻量模式（ADR-13）：AIHUB 维护并托管 format-1 索引，用户通过原生「索引源」添加只读 URL，官方 manager 安装精确版本；不再建设生成器、`current/policy/evidence`、CI 单写发布、15 分钟租约或写前授权。正式技术方案仍保留审核/批准待定；企业接入与三目标安装必须通过 G1/G2，其他一期范围、人群、指标及 A/REQ 编号不变。

2026-10-21 用户进一步裁决平台边界：企业可用插件由外部“AI 开发者平台”（AIHUB）完成预创建、Gitee 指定 group 建仓、审查、发布 npm，并维护/托管 format-1 索引 JSON；本项目不承建其后台、生成器或审批系统，只定义索引契约、提供只读校验器并做三目标验收。客户端直接用原生「插件市场 → 索引源」添加 AIHUB 的只读 URL，不要求内置自定义市场插件。自研/内部插件的中英文名称、描述、图标及真实 tarball 由平台负责人验收。终端目标为 Win10 amd64、统信 UOS 20 amd64 与银河麒麟 aarch64 三目标并存，UOS 与麒麟不互相替代，试点人群与终端比例口径不变；企业私服入口仅存本地配置并在打包时内置，允许内网 HTTP（已批准例外）。

## 6. 成功指标

一句话：6 周试点运行后看 5 个数。登录成功率不过关就没得谈，其余可以修补。

### 6.1 指标定义

| # | 指标 | 怎么算 | 目标 | 数据来源 |
|---|---|---|---|---|
| M1 | 首次登录与激活成功率 | 触发登录的人里，24 小时内完成网关凭据配置并完成一次成功对话的比例 | ≥ 95% | IAM 登录日志 + UAG 凭据/首调用记录 |
| M2 | 麒麟安装成功率 | 执行安装的麒麟设备里，24 小时内完成一次成功对话的比例 | ≥ 90% | 安装脚本回执 + 首调用；失败样本注明原因 |
| M3 | 周活（第 4 周 / 第 6 周） | 单周内至少 1 次成功对话的人数 ÷ 已进场试点人数 | ≥ 60%（全量时 480 人） | 网关按人去重 |
| M5 | 严重故障次数 | 单次导致 ≥30% 试点用户连续 >2 小时不可用 | ≤ 2 起/月 | 工单系统 + 值班记录 |
| M6 | 愿意继续用 | 试点末问卷中“收回 DSH 会主动申请继续用”的同意比例 | ≥ 70% | 匿名问卷，有效回收率 ≥50% |

> M4（写操作审计覆盖率）随生产变更场景撤销；M5 / M6 编号保留，不重排。

M1 含网关凭据配置：登录成功但未创建/粘贴个人凭据不计激活；去重口径以 UAG 能否按 `owner_user_id` 提供统计为准（AS-3 待确认，见 §7.2）。M2 的“成功对话”同样要求凭据配置完成。

M3 是试点中期的检查点：第 4 周不达标即启动干预（增补指引、缩小部门、延长时间），最终判定沿用第 6 周最后一周的周活，目标同为 ≥60%。两个时点用同一口径，不重复计数。

分两批各400人仍是待PMO批准的组织建议，不改变总规模与上述目标值。G0须明确运行起点、各批进场时点、已进场分母和第4/6周观察的可比性；按批记录起点、分别展示批次结果是[实施方案](../plans/rollout-plan.md)提出的待批准方法，不是已新增指标规则。若末批观察不足，不能以先行批次结果代替全体证据，也不能宣称第15周必然通过G3；须补足经批准的观察窗口并回写排期。

| 有条件通过（尚未过 G3） | M1 有完整证据且达标，其余 1–2 项未达标 | 停止扩量，制定责任明确的整改计划；经 PMO/业务批准延长 2 周或缩至单部门复测，复测达标后再签署 G3 |
| 不通过 | M1 未达标，或 M1 达标但其余 3–4 项未达标 | 停止扩量，回到对应验证阶段修复；不得把未覆盖组合默认为通过 |
| 不予判定 | 观察窗口不足、任一指标数据缺失/口径未冻结，无法证明达标 | 暂停 G3，先补证据和窗口；缺数不记为达标，重排需留痕，不以问卷/口头反馈替代调用与审计证据 |

### 6.3 采集与隐私

最小必要审计与 C1–C4 的控制须在 G2 前验证；REQ-16/A13 的 P1 优先级表示 G3 完成全量完整性评估，**不是允许试点期无审计或保留正文**。普通模型问答按稳定主体与调用关联，有研发变更时才关联 change-id，不为普通问答伪造变更编号。

- 客户端只上报事件（登录成功 / 失败、安装成功 / 失败、调用成功 / 失败），**不上报内容**，与 §4.4 C2 一致。
- M1 的“成功对话”以网关侧收到并返回成功为准，不用客户端自报，避免两套账。
- M3 的“独立用户”按人去重；一人多设备只计一次。
- 故障次数以工单为唯一口径，口头反馈不计入。

### 6.4 不作为成功判据的观察项

调用总量、令牌总量、装机数、人均日用量只进周报观察，不参与试点成败判定。这些数只能证明“装了、跑了”，不能证明“有人用、值得用”。不另设项目成功指标中的成本阈值，**不等于取消网关团队/成员预算或业务预算**；异常消耗由网关控制与周报共同暴露，再按已确认预算责任人工处置。

### 6.5 企业研发过程观察指标

[全流程能力设计](../design/plugins/forge-devops-lifecycle.md) §9 定义观察目录，[事件契约](../contracts/metrics-events.md)定义客户端补充事件。DevOps 汇聚已有仓库、CI/CD 和客户端缺口数据，不另建指标平台；平台已有事实不由客户端重复采集。仅作改进观察，不用于个人排名、绩效评估或 G3 去留，不改变 M1–M6（M4 已取消）的口径、目标与责任。

字段采用允许清单，禁止需求正文、提示词、代码、diff、工具输出及其内容哈希。必要安全审计与可降级指标投影分别处理。缺失、重复、迟到、失败和离线均显式计量，未知不补零；保留期、采集主体与出口在安全/DevOps 批准前不启用。进入判定用途需 PMO 另批并冻结口径。

## 附录 C 试点用户须知

**你会得到什么**：一个能读你项目、改代码、查研发平台信息的助手；模型走公司网关，不需要你申请任何外部账号。

**怎么装**：Windows 双击安装包按提示完成；银河麒麟从内部软件源安装并点击桌面图标打开。装完打开，点登录，用公司账号登录；随后按提示到 UAG 控制台创建一把个人凭据（每台设备一把，建议 90 天），粘贴回 DSH 并完成探测。凭据由你自己创建，不需要管理员代建；控制台入口不可用时联系试点支持。全程约 5–10 分钟（估计，含一次控制台创建凭据）。

**能做什么**：读代码与文档、改代码并跑测试、查询研发平台的只读信息（用户故事、流水线与构建信息以接入工具为准）、按规范做评审、调用公司内部技能。

**不能做什么**：不能多人共用一个实例；不能从公网直接安装插件；经企业私有 npm 同步且获批的公网插件可按角色使用；不能把客户数据贴到公司以外的工具里；不能执行生产环境变更；不能替代人工代码评审的最终判断。

**出问题时找谁**：试点支持渠道在试点开始前公布。额度问题会显示恢复时间；凭据问题按提示到 UAG 控制台核查或重建；只有登录过期才点“重新登录”。

**关于数据**：审计记录的是“谁在什么时候调用了什么工具、做了什么决定”，不记录对话正文；对话内容默认不进安全事件平台；河洛使用的网关凭据会开启 `privacy_mode`，开通/更换时核对并抽验服务端不含对话正文。
