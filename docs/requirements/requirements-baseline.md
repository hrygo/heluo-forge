## 摘要（一页纸）

**做什么**：让 3 个部门的 800 名研发同事在自己电脑上用上企业版 DSH——模型走企业网关，代码能读能写，研发平台只读查询，全程可追溯。

**为什么做**：企业已有 IAM、AI 网关与自研 DevOps，但各自独立使用、没有统一入口；本方案把这些能力接进一个客户端，模型与代码都不出机构边界。

**不做什么**：多人共享实例、macOS 客户端、白标发行、自建模型、公网访问、执行生产变更。

**给谁用**：开发、评审、发布、测试、运维、PMO、外包共 7 类角色；Windows 与银河麒麟各占一半。

**要多久**：前置验证 1 周（过 G0）、概念验证 4 周（过 G1）、试点工程准备 4 周（过 G2）+ 试点运行评估 6 周（过 G3）。总周期取决于企业 IAM、网关、DevOps 三个团队的配合时间，这三段等待不在平台组控制内。

**要什么投入**：平台组 2–3 名工程师为工程粗估，各团队投入和试点支持待认领；模型与网关沿用现有，但不能据此宣称零成本。ARM构建、内部源、签名/分发、监控与支持资源是否可复用，须在G0确认。

**怎么算成功**（试点运行 6 周后判定）：

| 看什么 | 目标 |
|---|---|
| 第一次登录就成功的人 | ≥ 95% |
| 麒麟电脑装成功的比例 | ≥ 90% |
| 第 4 周还在用的人 | ≥ 60%（约 480 人） |
| 严重故障（连续 >2 小时不可用） | ≤ 2 起/月 |
| 试点结束仍愿意继续用的人 | ≥ 70% |

**最大的两个风险**：约 400 台银河麒麟的沙箱与安装；800 人对应 2–3 名工程师的支持比（约 1:300）。

**需要领导在 G0 拍板的 5 件事**：

1. 800 人一次进场，还是按人力复核结果拆两批各 400 人。
2. 客户与生产数据进入 DSH，是否按 §4.4 的四条约束执行。
3. 麒麟验证前置导致周期拉长，是否接受。
4. 是否白标；这决定 Windows 用官方 App 还是自建安装包。
5. 范围变更由谁批准。

## 1. 结论

本文把一期范围、使用人群、必须跑通的场景、22 条有效需求（REQ-11 已取消）与 5 项试点指标收敛成一份可判定基线，作为项目范围的唯一真源。它影响四类人：领导据此决定投入与去留，开发据此排期与验收，用户据此知道能做什么，安全据此评审数据边界。

相对初版主文档的四项裁定（试点扩至 3 部门 800 人、银河麒麟占 50% 并前置为准入项、用户自助安装为主、角色细分为 7 类）已在 V0.4 中完成回写；本版同步至 [总体架构设计](../architecture/platform-architecture.md)（V1.4）与 [推广实施方案](../plans/rollout-plan.md)（V1.3），不改变这些范围输入。企业接口与终端能力仍待团队确认及实测，文档口径一致不等于技术验证完成。

仍缺三项输入：三个部门的名称、五项硬依赖的到位时间、试点签署人。

## 3. 用户与终端画像

一句话：3 个部门共 800 人，Windows 与麒麟各半，从开发到 PMO 共 7 类角色，用户自己安装软件。

### 3.1 规模

| 部门 | 人数 | 说明 |
|---|---|---|
| 部门 1 | 200 | 待 PMO 提供 |
| 部门 2 | 500 | 待 PMO 提供 |
| 部门 3 | 100 | 待 PMO 提供 |
| 合计 | 800 | 800 人全部为一期试点（已裁定并回写 L1/L2） |

800 人为一期试点总人数。按 2–3 名 DSH 工程师的配置，支持比约 1:300；这是推断，需 PMO 与平台组在 G0 按实际人力复核，建议分两批（每批 400 人）有序进场。

| 评审人 | 看改动、按规范卡点 | 只读为主；禁装插件 | 架构 §7.4、§7.5 |

### 3.3 终端与前置条件

| 项 | 现状 | 影响 |
|---|---|---|
| Windows | 50%（约 400 人，推断） | 官方 App + MSI 自助安装；MDM 推送为可选路径 |
| 银河麒麟 | 50%（约 400 台，推断） | 安装包 + 内部软件源；沙箱与终端组件必须先验 |
| 终端权限 | 用户有本机管理员权限，可自助安装 | 不依赖 MDM；安装失败率与版本漂移由升级门禁兜住 |

用户可自助安装缩短了对 IT 的依赖，但把风险转到两处：安装成功率无法由 IT 统一兜底，版本可控更依赖升级门禁与版本检测。约 400 台麒麟是本方案最大的单点，麒麟验证不通过则一半用户无法上岗。

## 4. 核心场景

一句话：试点必须跑通 7 条场景；其中首次登录、额度与登录异常两条不能失败。生产环境变更不在一期范围（N9），工程系统工具全部为只读查询。

### 4.1 场景总览

| # | 场景 | 什么时候发生 | 做到什么算成功 | 主要失败点 | 验收 |
|---|---|---|---|---|---|
| S1 | 首次登录与激活 | 第一次打开 | 30 秒内完成一次对话；未登录时企业模型不可用 | 浏览器未拉起、回调端口不通、用户取消授权 | A1、A2 |
| S2 | 日常编码与问答 | 每天 | 能对话、能调工具、能改代码；额度用完不自动重试 | 额度耗尽、上下文超限、模型未授权 | A3、A4 |
| S3 | 查用户故事与研发信息 | 生成 spec 或排查问题时 | 只读查询返回真实结果，用户故事可用于 spec 输入 | 工具未授权、令牌未绑定、工具过多挤占上下文 | A7、A14 |
| S5 | 代码评审 | 提交前 | 按规范给出可执行意见；评审阶段不写源码 | 路径规则误拦、规范与代码漂移 | A11 |
| S6 | 装插件与技能 | 需要新能力 | 公网不可达时开发者仍能从内部源安装；受限与只读角色禁装 | 误用公网源、校验和不符、版本不匹配 | A9、A10 |
| S7 | 额度与登录异常自助 | 报错时 | 说清是个人额度还是团队额度、何时恢复；登录过期提示重登 | 静默换模型、无限重试 | A2、A3 |
| S8 | SDD 变更流程 | 有规格变更 | 变更编号贯穿分支、提交与 PR；PR 同时含实现、规格与归档 | 元数据缺失时误阻塞普通开发 | A11 |

> S4（部署与回滚）已撤销：生产环境变更由既有变更平台与人工流程承担，DSH 不执行生产写操作（N9）。S5–S8 编号保留，不重排。

### 4.2 用户会经历什么

**第一天。** 自己装好（或由 IT 推送），双击打开，浏览器跳出公司登录页，用现有账号登录，回到 DSH 就能直接提问。从装完到能用，目标是 30 秒内完成第一次对话。没登录时不会给你任何替代模型，避免把公司代码发到外面。

**平时。** 像现在一样打开项目目录，让它读代码、改代码、跑测试；问它“上次构建为什么失败”；让它查研发平台里的用户故事与工程信息。它的能力清单在会话里可见，不用记命令。

**出问题时。** 额度用完，界面会说清是个人额度还是团队额度、什么时候恢复，不会偷偷换成别的模型；登录过期，提示重新登录，不用重启。生产环境变更由既有平台和人工流程执行，助手不承担。

### 4.3 两条不能失败的路径

**S1 首次登录**：未登录时企业模型全部不可用（组合包不保留其他路由）→ 点登录拉起系统浏览器 → IAM 登录页 → 回调本机 `127.0.0.1:<port>` → 校验 `state` / `nonce` / `iss` / `aud` → 写入凭据 → 首次对话。任一步失败，用户停在“待重新登录”，不得降级到任何公网模型。

**S7 异常自助**：额度耗尽时展示“个人额度”或“团队额度”与恢复时间，不自动重试；登录过期由客户端自动刷新并重试一次，仍失败则提示重新登录，不静默切换模型。

### 4.4 数据与合规约束

试点允许客户与生产数据进入 DSH 上下文，以下四条作为硬约束：

| # | 约束 | 通俗说 | 落点 |
|---|---|---|---|
| C1 | 客户数据只经企业 AI 网关与机构自部署模型，不出机构边界 | 数据不出公司 | 架构 §7.2 / §10、[AI 网关契约](../contracts/gateway-contract.md) §4.5 |
| C2 | 会话正文默认不进安全事件平台，保留期单独评审 | 聊天内容不留档，要留先评审 | 架构 §7.6 |
| C3 | 客户数据的导出、外发、批量复制需本机人工确认（`ask`） | 往外搬数据要问你 | 架构 §7.6 / §9（`@heluo/forge-policy`） |
| C4 | 模型服务与网关的请求正文日志默认关闭，排障采样保留期单独定义 | 服务端也不默认存原文 | [AI 网关契约](../contracts/gateway-contract.md) §4.5 |

> 已确认（2026-10-20，用户书面确认）：网关与模型均为本机构私有化部署，没有第三方上游，因此“不留存正文 / 不用于训练”的供应商条款不适用，C1 收敛为“不出机构边界”。此前会话中的“优化部署”为口误，已由用户澄清。剩余风险在机构内部：模型服务与其日志的访问控制、请求正文保留期。若后续接入外部模型，C1 需重评。

### 4.5 未纳入的场景

- 多人协作同一会话（依赖多租户，见 N1）。
- 跨终端迁移会话与工作区（一期不做）。
- macOS 上的使用（见 N2）。
- 执行生产环境变更（部署、回滚与变更审批，见 N9）。

### 5.3 追踪约定

- `REQ-*` 是唯一需求编号；验收项与工作分解项只在这里引用，不在其他文档另起编号。
- 需求删除不删编号，标“已取消”并写明替代项；REQ-11 按此处理。
- 一条需求对应多条验收时，全部通过才算达标。
- 本机确认是 C3 风险动作的必要条件；approval policy为`never`、无确认UI、超时/异常均拒绝，不能把“不询问”解释为自动允许。
- 工具描述/preset不是服务端授权依据，本机管理员可修改客户端；企业服务端独立鉴权与撤权必须成立。对文件及命令子进程的秘密隔离，两端都要实测，未通过不开放相应工具。
- 可选插件可隔离不等于强制安全依赖可绕过；IAM/policy/必要审计缺失时拒绝相应操作。

### 5.4 只有一处核心补丁

REQ-12 是全部 22 条有效需求中唯一需要改 DSH 核心的项（`dsh-mcp-client` 的 HTTP 请求头回调取值与 `stdio` 凭据重连），约 50–80 行，独立成 PR 并向上游提案。其余需求全部落在插件、组合包、MCP 与配置上。即使上游暂未合入该 PR，企业内部也可通过私有 registry 发布带补丁的 `@heluo/forge-mcp-client`（或构建期补丁）维持短 TTL（≤60 分钟）与按请求取令牌，**无需延长令牌有效期，也不牺牲 A14 与安全边界**。若 DevOps 与 Gitee 的 CLI 方案成立，本条可能撤销，待核验；对应设计见 DESIGN-009、DESIGN-010，三项前提不成立时维持本条与 MCP 形态。

## 6. 成功指标

一句话：6 周试点运行后看 5 个数。登录成功率不过关就没得谈，其余可以修补。

### 6.1 指标定义

| # | 指标 | 怎么算 | 目标 | 数据来源 |
|---|---|---|---|---|
| M1 | 首次登录成功率 | 触发登录的人里，24 小时内完成一次成功对话的比例 | ≥ 95% | IAM 登录日志 + 网关首调用记录 |
| M2 | 麒麟安装成功率 | 执行安装的麒麟设备里，24 小时内完成一次成功对话的比例 | ≥ 90% | 安装脚本回执 + 首调用；失败样本注明原因 |
| M3 | 周活（第 4 周 / 第 6 周） | 单周内至少 1 次成功对话的人数 ÷ 已进场试点人数 | ≥ 60%（全量时 480 人） | 网关按人去重 |
| M5 | 严重故障次数 | 单次导致 ≥30% 试点用户连续 >2 小时不可用 | ≤ 2 起/月 | 工单系统 + 值班记录 |
| M6 | 愿意继续用 | 试点末问卷中“收回 DSH 会主动申请继续用”的同意比例 | ≥ 70% | 匿名问卷，有效回收率 ≥50% |

> M4（写操作审计覆盖率）随生产变更场景撤销；M5 / M6 编号保留，不重排。

M3 是试点中期的检查点：第 4 周不达标即启动干预（增补指引、缩小部门、延长时间），最终判定沿用第 6 周最后一周的周活，目标同为 ≥60%。两个时点用同一口径，不重复计数。

分两批各400人仍是待PMO批准的组织建议，不改变总规模与上述目标值。G0须明确运行起点、各批进场时点、已进场分母和第4/6周观察的可比性；按批记录起点、分别展示批次结果是[实施方案](../plans/rollout-plan.md)提出的待批准方法，不是已新增指标规则。若末批观察不足，不能以先行批次结果代替全体证据，也不能宣称第15周必然通过G3；须补足经批准的观察窗口并回写排期。

### 6.2 判定规则

| 结果 | 条件 | 处置 |
|---|---|---|
| 通过（过 G3） | 观察窗口与证据完整，5 项全达标 | 由有权签署人批准后进入 P3 持续推广 |
| 有条件通过（尚未过 G3） | M1 有完整证据且达标，其余 1–2 项未达标 | 停止扩量，制定责任明确的整改计划；经 PMO/业务批准延长 2 周或缩至单部门复测，复测达标后再签署 G3 |
| 不通过 | M1 未达标，或 M1 达标但其余 3–4 项未达标 | 停止扩量，回到对应验证阶段修复；不得把未覆盖组合默认为通过 |
| 不予判定 | 观察窗口不足、任一指标数据缺失/口径未冻结，无法证明达标 | 暂停 G3，先补证据和窗口；缺数不记为达标，重排需留痕，不以问卷/口头反馈替代调用与审计证据 |

### 6.3 采集与隐私

最小必要审计与 C1–C4 的控制须在 G2 前验证；REQ-16/A13 的 P1 优先级表示 G3 完成全量完整性评估，**不是允许试点期无审计或保留正文**。普通模型问答按稳定主体与调用关联，有研发变更时才关联 change-id，不为普通问答伪造变更编号。

- 客户端只上报事件（登录成功 / 失败、安装成功 / 失败、调用成功 / 失败），**不上报内容**，与 §4.4 C2 一致。
- M1 的“成功对话”以网关侧收到并返回成功为准，不用客户端自报，避免两套账。
- M3 的“独立用户”按人去重；一人多设备只计一次。
- 故障次数以工单为唯一口径，口头反馈不计入。

### 6.4 不作为成功判据的观察项

调用总量、令牌总量、装机数、人均日用量只进周报观察，不参与试点成败判定。这些数只能证明“装了、跑了”，不能证明“有人用、值得用”。不另设项目成功指标中的成本阈值，**不等于取消网关个人/consumer额度或业务预算**；异常消耗由网关控制与周报共同暴露，再按已确认预算责任人工处置。

## 附录 C 试点用户须知

**你会得到什么**：一个能读你项目、改代码、查研发平台信息的助手；模型走公司网关，不需要你申请任何外部账号。

**怎么装**：Windows 双击安装包按提示完成；银河麒麟从内部软件源安装并点击桌面图标打开。装完打开，点登录，用公司账号登录一次即可。全程约 5 分钟（估计），不需要管理员帮你做额外配置。

**能做什么**：读代码与文档、改代码并跑测试、查询研发平台的只读信息（用户故事、流水线与构建信息以接入工具为准）、按规范做评审、调用公司内部技能。

**不能做什么**：不能多人共用一个实例；不能安装公网插件；不能把客户数据贴到公司以外的工具里；不能执行生产环境变更；不能替代人工代码评审的最终判断。

**出问题时找谁**：试点支持渠道在试点开始前公布。额度问题会显示恢复时间，登录问题点“重新登录”即可。

**关于数据**：审计记录的是“谁在什么时候调用了什么工具、做了什么决定”，不记录对话正文；对话内容默认不进安全事件平台，网关与模型服务默认也不留存对话正文日志。
