## 1. 结论

DSH 侧不选边。用**一个凭据接口 + 两个提供者 + 一个镜像**支持两种网关凭据形态，切换只改配置，不改调用链。

关键事实：两种形态最终都落到同一个 seam——`llm-pi-ai` 只解析 `CredentialRef`，不关心值从哪来。因此"支持两种"的成本不在模型调用链，而在**谁负责把正确的值写进那个引用**。

## 2. 目标与非目标

**目标**

- 同一份安装包，通过配置在令牌直通与静态 Key 之间切换。
- 两种形态共享额度展示、错误提示、审计字段与设备标识上报。
- 静态 Key 模式下不启动令牌刷新链；令牌模式下不支持手动填 Key。
- 切换不要求重装、不要求清空用户数据。

**非目标**

- 不在客户端实现 Key 签发。静态 Key 由网关控制台签发。
- 不并行使用两种凭据调同一个请求。
- 不改变服务端鉴权与额度规则。

## 3. 统一凭据接口

```ts title="凭据提供者（示意）"
interface GatewayCredentialProvider {
  readonly id: 'token' | 'static-key';
  /** 取当前可用于 Authorization 的值；失败抛出可归因错误 */
  resolve(): Promise<{ value: string; expiresAt?: number }>;
  /** 是否允许在 401 后自动刷新并重试一次 */
  canRefresh(): boolean;
  /** 401 后的处置建议，驱动界面与重试策略 */
  onUnauthorized(): 'refresh-retry' | 'reissue' | 'relogin' | 'fatal';
  /** 启动或切换时的一次性可用性探测 */
  probe(): Promise<'ok' | 'missing' | 'invalid' | 'unreachable'>;
}
```

接口只有四个方法，足以覆盖两种形态的差异：静态 Key 返回 `canRefresh=false` 与 `reissue`，令牌返回 `canRefresh=true` 与 `refresh-retry` 或 `relogin`。

## 4. 两个提供者

| 能力 | 令牌提供者 | 静态 Key 提供者 |
|---|---|---|
| 取值来源 | IAM 插件的按资源令牌 | 凭据存储中的 `ENTERPRISE_STATIC_KEY` |
| 有效期 | 有，到期前 60 秒预刷新 | 有，但不主动刷新 |
| 401 处置 | 刷新后至多重试一次 | 提示重新签发 |
| 账号切换 | 清理镜像与按资源缓存 | 清理镜像，要求重新粘贴 |
| 探测方式 | 令牌有效性与到期时间 | 一次最小调用 |
| 存储位置 | `CredentialKey` 记录 | 凭据记录；生产使用 keychain provider，仅 dev/pilot 可显式接受 `dsh-credentials-local` 的 0600 YAML |

两者都不把值写进日志、配置明文或模型上下文。

## 5. 镜像：两种形态的唯一汇合点

`llm-pi-ai` 解析 `CredentialRef: ENTERPRISE_ACCESS_TOKEN`。双模式不改这个事实，而是让**镜像组件**按模式写入：

```text
令牌模式：IAM 刷新成功 → 写 CredentialRef（每次刷新更新一次）
静态模式：用户粘贴 Key → 写 CredentialRef（写入一次，直到更换）
```

镜像组件持有当前模式，禁止跨模式写入：静态模式下 IAM 的刷新结果不得覆盖用户填写的 Key，令牌模式下不允许手工写入。

## 6. 模式选择

| 配置值 | 行为 | 适用 |
|---|---|---|
| `token` | 只用令牌提供者；无令牌即未就绪 | 默认，G2 后目标形态 |
| `static-key` | 只用 Key 提供者；无 Key 即未就绪 | 试点或网关暂不支持验签时 |
| `auto` | 有 Key 用 Key，否则用令牌 | 灰度期、混合环境 |

`auto` 的判定必须在启动时完成并记录结论，避免同一会话内两种凭据交替。切换模式视为配置变更：清理旧镜像，重新探测，记录审计事件。

## 7. 状态机

```flow TB
(1 未配置) -> {2 模式与凭据齐备?}
{2 模式与凭据齐备?} -> [3 探测中]: 是
{2 模式与凭据齐备?} -> [4 引导配置]: 否
[3 探测中] -> {5 探测结果}
{5 探测结果} -> [6 就绪]: ok
{5 探测结果} -> [7 需重新签发]: invalid
{5 探测结果} -> [8 需重新登录]: missing
{5 探测结果} -> [9 网络不可达，退避重试]: unreachable
```

状态只影响界面提示与是否允许发起调用，不改变模型调用的结果语义。

## 8. 错误与用户动作

| 场景 | 令牌模式 | 静态 Key 模式 |
|---|---|---|
| 401 | 刷新后至多一次；仍失败则提示重新登录 | 提示重新签发，不重试 |
| 403 | 提示权限不足 | 同左 |
| 429 | 展示重置时间，不自动重试 | 同左 |
| 5xx 或超时 | 先查单，不盲重放 | 同左 |
| 凭据缺失 | 引导登录 | 引导粘贴 |

两种模式共享同一张错误表，差异只在 401 这一行。

## 9. 安全边界

- 凭据值只存在于凭据存储与该引用；生产必须由 keychain provider 保护，keychain 不可用时 fail closed；仅 dev/pilot 可显式接受 `dsh-credentials-local` 的 0600 明文 YAML，并配合 A4 的文件/子进程拒绝。旧 0600 记录在 keychain 可用后迁移，成功才删除明文。
- 静态 Key 不参与刷新，避免"用长期凭据兑换短期凭据"的混合路径。
- 退出时两种模式都清理镜像与缓存；令牌模式额外调用撤销，静态模式不代用户撤销（撤销在控制台）。
- 切换模式必须留下审计事件：时间、旧模式、新模式、操作者。

## 10. 测试矩阵

| 层级 | 用例 |
|---|---|
| 单元 | 模式选择；`auto` 判定；镜像写入方向；401 映射到四种动作 |
| 契约 | 两种模式的请求头一致；错误码映射一致 |
| 集成 | 令牌刷新期间切换模式；Key 粘贴后探测失败；控制台撤销后 401 提示 |
| 端到端 | 双端各跑一次令牌模式与 Key 模式 |

## 11. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `llm-pi-ai` 只在启动时解析引用 | 令牌刷新后仍用旧值 | P0 实测；必要时以镜像更新触发重载 |
| 两种模式共用引用名 | 切换后残留旧值 | 切换即清理并重新探测 |
| `auto` 判定不稳定 | 同一用户两种凭据交替 | 启动时定案并记录 |
