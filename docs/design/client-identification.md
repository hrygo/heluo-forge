## 1. 结论

本方案采用 DSH 默认 `User-Agent`，要求网关对其执行关键词匹配，作为个人研发用途隔离的轻量环节；不修改 DSH 核心，也不由插件改写 UA。我方根据局部实测观察建议关键词 `deepseek-harness`，但该具体值及匹配规则须由网关团队确认，不代表网关已经支持或接受。

UA 只能降低误用：任何拿到凭据的人都可照抄该头部，无法区分伪造，不能替代 CONF-GW-09 的当前人归属校验或 Key 归属，也不能单独作为放行依据。网关匹配能力、实际链路头部传递和身份前提均须成立；UA 缺失、不匹配或前提不满足时访问失败，不回退为仅做人员归属校验或无标识放行。

## 2. 目标与非目标

- 目标：降低个人研发凭据被普通编程助手误用的风险；要求关键词规则在企业实际存在的全部模型入口（协议入口、流式、Coding Plan）一致生效。可选诊断实例标识可探索用于审计关联与排障，但不作为前提。
- 非目标：不防伪造、不抵抗有权限者复制凭据与头部；不识别具体员工；不做硬件绑定或设备指纹；不以 UA 决定模型权限、额度或撤权；不新增网关侧管理后台；不改 DSH 核心。

## 3. 需求与依赖

| 需求/验收 | 关系 | 说明 |
|---|---|---|
| REQ-03 | 支撑 | 个人研发只经 DSH；UA 可减少误用，但不能阻止复制凭据并仿冒头部 |
| A3 / A14 | 支撑 | 用途隔离与专用凭证的验收项；UA 只是其中一环，不能单独成立 |

| 依赖 | 类型 | 版本约束 | 缺失时的行为 |
|---|---|---|---|
| 网关按凭证配置 UA 关键词规则 | 服务 | 匹配能力与配置待确认（CONF-GW-10） | 规则不可配则方案不成立，相关访问失败 |
| DSH 默认 UA 可被规则识别 | 运行时及协议 | 仅局部实测，其他协议与版本待核验 | 不满足匹配规则时访问失败；不改核心或由插件改写 UA |
| 企业代理保留可匹配的 `User-Agent` | 网络 | 待核验 | 被剥离或改写至不匹配则访问失败，不据此判定用户违规 |
| 人员及 Key 归属校验 | 身份 | CONF-GW-09，待核验 | 前提不满足时访问失败；UA 不可替代归属校验 |

## 4. 标识结构与传输位置

| 组成 | 取值 | 变更条件 | 用途 |
|---|---|---|---|
| 默认 UA | 由 DSH 及其请求路径生成 | 版本或请求路径变化时可能改变 | 网关关键词匹配；不保证所有提供方、协议或版本相同 |
| 实例标识 | 可选提案：`X-DSH-Instance: <32 位小写十六进制>` | 若未来实现，拟首次启动随机生成且允许重置 | 可选排障关联；非认证、非必需，尚未实现 |
| 产品版本 | 可选提案：`X-DSH-Version: <semver>` | 若未来实现，拟随产品发布变化 | 可选诊断；非认证、非必需，尚未实现 |

2026-10-28 既有探针 [issue100-user-agent-probe.mjs](../../scripts/probe/issue100-user-agent-probe.mjs) 在 Node 24 与已安装 DSH `0.2.1-rc.3` 的合成 loopback、pi-ai OpenAI-completions SSE 路径中观察到默认 UA：`deepseek-harness/0.2.1-rc.3 (+https://github.com/deepseek-ai/deepseek-harness)`。profile 尝试设置的自定义 UA 被覆盖；两个合成 X 头通过，stream hook 调用一次。这不证明提议的诊断头已实现，也不证明真实网关或代理、Windows/Kylin、其他协议或提供方的行为。

- 要求所有发往网关的模型请求，包括流式、非流式和重试，均满足经网关确认的匹配规则；这是验收目标而非现状保证。
- 可选诊断头的格式、实现和网关记录能力均待确认；缺失不构成 UA 或身份校验的替代，也不应成为必需的放行条件。
- 若未来实施诊断头，不应包含用户名、工号、令牌、Key、主机名、设备序列号或任何秘密；随机实例标识不用于认证。

## 5. 网关校验规则（待提供方确认）

| 项 | 目标规则 |
|---|---|
| 配置粒度 | 按凭证配置允许的 UA 规则：个人研发凭据必须携带本方案 UA；应用凭据可选配 |
| 匹配方式 | 要求关键词包含匹配；建议候选 `deepseek-harness`，具体字面值、大小写敏感性、子串及边界语义、配置方式与能力均待网关确认 |
| 执行位置 | 鉴权与凭据状态检查之后、模型权限与额度扣减之前；不匹配不转发上游、不扣额度 |
| 入口覆盖 | 全部模型协议入口与 Coding Plan 入口统一执行；禁止绕过网关直连上游 |
| 拒绝结果 | 返回可与“Key 无效”区分的错误（如 403，原因码标识客户端标识不被接受），供客户端给出明确提示 |
| 代理改写 | 明确网关看到的 `User-Agent` 是否可能被中间代理替换；若无法可靠匹配，该链路访问失败，不绕过此机制 |

## 6. 流程

```text
DSH 请求：默认 UA + 凭据（诊断头仅为可选提案）
        │
        ▼
网关：鉴权 → 凭据状态 → UA 规则 → 模型权限 → 额度 → 转发上游
        │                                   │
        ├── UA 缺失或不匹配 → 拒绝（错误形式待确认）
        └── UA 匹配且其他校验通过 → 转发（可选诊断记录待确认）
```

客户端目标行为：正常路径不做任何分支；被拒绝时不自动重试、不改写 UA 重试、不退化为无标识请求，并提示“当前客户端的接入标识不被接受”及网关控制台的凭据检查入口。错误分类与提示尚待实现和验证。

## 7. 失败模式

| 场景 | 行为 | 用户可见结果 | 是否可重试 |
|---|---|---|---|
| UA 缺失或不匹配 | 网关应拒绝 | 提示客户端标识不被接受，附排查入口 | 否 |
| 代理剥离 UA 或改写至不匹配 | 受影响请求应被拒 | 提示可能是网络代理导致，转人工核实 | 否 |
| 网关不支持所需关键词匹配或身份前提缺失 | 方案不成立，访问失败 | 提示接入前提未满足，转人工核实 | — |
| 可选实例头缺失或未来被重置 | 不影响 UA 与身份校验；诊断关联可能缺失 | 视诊断实现而定 | — |
| 有权限者仿冒 UA | UA 检查无法区分伪造 | 属已接受残余风险；归属校验与审计不能保证识别伪造 | — |

## 8. 变更与兼容

- DSH 默认 UA 可能随版本、提供方或协议变化；升级及新增入口前须核验实际 UA 与已确认规则是否仍匹配，不承诺版本变化无需调整网关。
- 可选诊断头与默认 UA 分开讨论；它们尚未实现，其变化不得替代 UA 或身份校验。
- 网关侧变更匹配规则须提前协调并验证，不以“客户端会跟随”为由单方面收紧。
