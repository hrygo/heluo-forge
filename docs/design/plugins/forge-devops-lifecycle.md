## 1. 结论

DSH 将取代 Comet 与 oh-my-sdd，作为企业新一代智能研发工具；参考旧项目**使用企业工具的方式**，不要求复用其代码、Runtime、安装器或阶段体系。优先让模型与 Harness 承担通用分析、规划、实现、验证和修复；本项目补充企业事实、规范、工具入口、授权约束和工程追溯。

六阶段地图表示各阶段可提供的帮助，不表示 DSH 接管六阶段，更不以用户故事上线结束作为一次 DSH 任务必须负责到底的目标。业务验收、生产发布与最终结项继续由已有平台和人员负责。工程交付可以处于待评审、待合入、待 UAT 等状态，不能被统一包装成完成。

本稿同时描述只读基线与已确认的受控研发目标；写能力默认关闭，按真实开关、服务端权限、Policy 与接口证据逐项启用，不把产品确认等同技术验证。具体边界只在需求基线 §2.3 维护；本稿不发布接口已可用或企业联调已通过的结论。

Issue 信息充分时不另写规格，Agent 按复杂度、风险和接口影响决定必要设计；Teamflow 是唯一研发执行者，Skill 只补企业语义。Teamflow 内部 PRD、技术蓝图等可作为运行材料，但不要求用户重复填写，不另立需求真源。实际存在的重复确认或阻塞先核验，再做最小修正，不建设第二执行引擎，也不声称已能跳过现有阶段。

## 2. 目标、边界与证据

### 2.1 企业任务模型

| 对象 | 含义和真源 | DSH 责任 |
|---|---|---|
| 用户故事 | DevOps；业务价值、故事级范围与验收；可由多个系统承建 | 读取背景；改变故事级要求必须有相应人的决策，不能只改子变更 |
| 系统变更 | DevOps；业务目标、总体范围与约束；组织一个或多个 Issue，不强绑唯一仓库 | 读真实要求和 Issue 关联，选定本次交付单元 |
| Issue | Gitee；具体范围、非目标、约束、依赖和可执行验收；每项唯一变更、唯一仓库 | 跨仓库拆独立交付验收的 Issue；支持续跑、返工等多个 run，run 不作业务真源 |
| PR 与提交 | Git/Gitee；实际代码、评审和合入事实 | 维护 Issue 关联；相关 commit message 均以 `[变更号]` 开头；最终合入记录也不丢失该标识 |
| 构建、制品、UAT 部署 | 需求方确认 DevOps 已关联展示；实际记录仍由原 CI/CD 负责 | 优先读 DevOps；不另建追溯系统、不接管部署；部署成功不等于验收通过 |
| 业务验收、上线与结束 | 用户按实际代码版本验收；上线与业务结束依既有平台事实及流程 | 不代理人工判断；Issue 或 run 完成不推导变更最终结束 |

故事与系统变更的最终结束时间不可由工程交付时间代填。开始时间及研发进展仅在平台字段语义、可写权限明确后记录；不假定两个对象的时间自动联动。本地验证与独立 AI 审查通过后形成待验收交付，用户按实际代码版本决定是否接受；不统一强制远端 CI 通过或 PR 已合并才可验收，但已有必要 CI、分支保护及仓库规则必须遵守。CI、合入、人工验收、Issue 关闭与业务结束分别记录；用户验收不自动授权合并、部署或关闭。关闭须另有授权并核对真实平台条件，Issue 已关也不等于系统变更结束。

### 2.2 入口与交付约定

支持变更／Issue 双入口：从变更进入时选定本次 Issue；从 Issue 进入时核实其唯一变更、唯一仓库与验收。具体 command/Skill 命名及关联字段待核验，不把变更号设为唯一入口。关联缺失、冲突、多变更或多仓库时只读澄清，不用自然语言相似度猜测。用户输入只确定意图，不证明服务端权限；本次委托只覆盖选定 Issue 与已授权动作。

目标清楚后允许模型自主组织方法；模糊且需人取舍时给出 2–3 个有区别的方案、影响和建议。确认后的业务澄清回写相应 DevOps 对象；普通技术方案不全部回灌为业务规范。回写冲突不覆盖他人修改。

独立 AI 审查上下文只读；修复回实现上下文，修复后复审。审查意见与本地验证绑定实际 SHA／PR，形成待验收交付；用户的验收结论由用户本人确认，AI 不代写。获准发布时，审查与人工结论分别保留在 Gitee 正式记录。人工验收不等于合并授权，DSH 不自动合并。复用 Teamflow 及现有模型选择、独立审查与交互能力；若不能证明隔离或模型可用，记录缺口，不自建调度引擎或伪称交叉审查已通过。

### 2.3 非目标

不实现源码、包清单、生产工具、通用 Agent 流程引擎、跨系统 Agent 调度、知识平台、部署引擎、审批系统、指标后台或新看板；不 fork DSH，不搬运五环、Hook Router、状态快照/receipt 链；不自动安装旧项目或执行其命令。只有本次范围内的必要缺口才提出最小补充。

### 3.2 企业规范消费

以条款而非整 Skill 为筛选单位：区分通用知识、企业差异、强制要求，并标适用系统/版本、维护责任与依据。模型可建议精简，规范维护者确认有效性；DSH 按任务选择，不自行豁免。即使模型知道某安全知识，企业仍需声明适用约束。过粗的条款补清判据，过细的方法偏好降为建议；规则冲突提交维护者，不让每个会话自创优先级。既有检查器能验证的要求优先复用，未实测的宿主拦截不宣称硬保证。

## 5. 形态判定与人机双面

### 5.1 判定顺序

形态是职责组合，不是“命中一个就排除其他”。先定义必要业务能力和权限，再依次判断：

1. 已有企业 CLI 能满足双端运行、用户鉴权和稳定可判定输出时，**CLI 为默认执行面**；不要因模型会反复调用就先写插件工具。
2. 仅涉及企业业务语义、适用规则、产物与调用指引时用 **Skill**；不把授权、权威状态或真实副作用交给提示词保证。
3. CLI 存在必要的结果/交互适配缺口时，才评估 **薄插件工具**；其底层仍调用同一 CLI，不能形成另一套鉴权与数据账。策略/凭据接线优先使用既有宿主插件，不臆造 SDK 挂点。
4. 只有 CLI 三项前提失败或已确认的必要远程共享能力无法满足，才评审 **MCP**；失败先关闭动作，不自动部署服务。
5. 必须在仓库流水线验证的不变量交 **既有 CI job**，不让客户端复制流水线引擎。
6. 人需要可见信息时先用 **DSH 原生会话/确认、CLI 或原平台页面**；只有明确不可替代的需求才另评 Client 面板，不默认新增。

### 5.2 套用与反例

| 新能力 | 判定结果 | 反例及原因 |
|---|---|---|
| 查询变更及验收条件 | CLI 读取 + Skill 解释业务关系 | 常驻 MCP 包装同一个查询，只增加维护面 |
| 读取变更清单与批量事实 | 薄 runner：枚举只读动作 + 每动作参数 schema，底层仍是同一 CLI | 通用 `run` / 自由 `action` 参数把 argv 交给模型；每加一条子命令就新增一个工具 |
| 回写确认后的澄清 | 同一用户 CLI 受控写 + 原生确认 | Skill 写“已确认”不能替代真实人的决定与服务端权限 |
| PR 人工评审记录 | 原生确认 + 同一 CLI 写正式 review；绑定当前 PR 版本 | 另建面板/审批库会形成两套批准记录 |
| 查询 UAT 部署 | 优先读 DevOps 已有关联 | 为查询而新建部署引擎或直接连全部 CI/CD |
| 提交标识与必要校验 | Git/CLI 与已有必要 CI；不强制 spec/freeze/archive 齐套 | 用工具描述解释规则，却没有可验证结果 |

### 5.3 同一能力的两张使用面

人和 Agent 使用同一业务动作、目标资源、结果语义和审计；可读展示不同，不能把原始 CLI 全部暴露给模型，也不能以“人能运行任意命令”绕过企业服务端权限。人类原平台操作仍按原平台审计，本项目不声称控制 DSH 外的所有行为。

变更／Issue 双入口只表达有限委托：选定 Issue、其唯一变更/仓库和已启用动作。普通 Issue/PR 维护不逐步询问；业务歧义、澄清采纳和人工 review 必须真实确认。委托不能覆盖 N9、自动合并、越权或数据外发 C3。宿主/策略必须能绑定并校验确认事实，不能只凭模型生成的参数；不能证明时关闭相关写动作，不新增一套二次授权后台。

## 6. 追溯与最小工具契约

```text
DevOps 用户故事 → 一个或多个系统变更
单个系统变更 → 一个或多个 Issue（每项唯一变更 + 唯一仓库）
Issue → 一个或多个续跑/返工 run（运行记录，非业务真源）
Issue ↔ PR → Git 实际 SHA → 版本对应的验证、审查与用户验收
CI / 合入 / Issue 关闭 / 业务结束分别记录，不互相推导
```

| 追溯段 | 真源与读写责任 | 缺失处置 |
|---|---|---|
| 故事 → 系统变更 → Issue → 唯一仓库 | DevOps/Gitee 的真实关联；澄清按信息归属受控写回 | 关联缺失或冲突只读澄清，不新造业务主数据 |
| Issue 要求版本 → 必要设计与运行材料 | Issue 承载工作要求；Agent 按需设计；Teamflow 内部 PRD/蓝图只用于运行 | 无需求版本证据列缺口，不强制补规格/冻结，不伪造版本 |
| Issue → run / 提交 / PR | Teamflow 执行记录与 Git/Gitee；提交保留 `[变更号]`，PR 明确关联 Issue | 多 run 保留续跑/返工关系，不要求手填专有 manifest，不强制新分支语法 |
| 实际 SHA／PR → 本地验证 / 独立 AI 审查 / 用户验收 | 测试与只读审查结果分别绑定版本，用户本人确认实际代码版本 | 代码、要求或验收版本改变后重新判断覆盖，不复用失效确认 |
| 交付版本 → CI / 合入 / 构建 / 制品 / UAT | 既有 Git/Gitee/CI/CD 事实 | 只具本地证据可交付待验收候选；必要 CI/仓库规则未满足不得越过，无关联记 unknown |
| Issue 交付 → 关闭 / 发布 / 业务结束 | 具体动作另行授权，遵守真实平台条件 | 不因验收、PR 创建、run 完成或所有 Issue 完成而自动关闭、合并、部署或最终结项 |

动作及结果字段唯一真源为[工程工具契约](../../contracts/engineering-tools.md)。报告串联变更、Issue、仓库、相关 run、实际 SHA／PR 与版本对应验证，不建立第二需求真源。既有冻结指纹如有明确用途可作辅助证据，不作为开工/验收前提，不证明业务正确、已合入或 UAT 就绪。现有 Teamflow 提交/交付模板是否完整保留前缀及关联仍待核验，不把目标写成已具备。

不重复建立全生命周期数据库。关联优先写回现有 DevOps/Gitee 支持的关联字段；若只有受控描述区/链接，需提供方确认维护规则；两者都不支持时将自动闭环标为阻塞，不宣称双向强一致。目标变更并发修改或未知写入结果只允许查询核对，禁止无脑重放。

### 6.1 只读查询 + 门禁骨架的设计准入（D4，责任方 2026-10-24）

本节为历史设计准入与探针记录，保留原日期和结果；不证明 2026-11-03 Issue 双入口、多 run、Teamflow、受控写或验收新链路已经实测。当前实现与验证入口见[设计索引 §2.2](../README.md#22-实现与验证入口)。

责任方决定 #15 的实现范围按"只读查询 + 门禁骨架"先行。本节即该范围的**设计准入**，随后才建清单、源码与测试（动作标识同[工程工具契约 §3](../../contracts/engineering-tools.md)，不另立命名）。

| 项 | 决定 |
|---|---|
| 范围 | 只读查询面：`change.read`、`repository.read`、`issue.read`、`pr.read`；**不含任何写**，写动作按[策略设计 §5.1.1](forge-policy.md#511-写动作资源分类登记d1责任方-2026-10-24)登记另行准入 |
| 模块 | 落在 `packages/forge-devops`：只做**端口 + 门禁接线**，不内置企业 CLI/HTTP 实现 |
| 提供方实现 | CLI/HTTP 适配器由提供方证据到位后以端口注入；仓库内只提供离线假端口用于测试，**假端口不得作为企业证据** |
| DSH 依赖 | 策略服务为硬依赖（缺则工具不挂载、入口关闭）；只读工具经 `ctx.tools` 注册，走同一门禁与审计前置；不新增核心补丁、不自建第二授权 |
| 未登记/未开放 | 与写一致地在 guard 处拒绝、零副作用；空目录等价于全部关闭 |
| 失败语义 | CLI 不可用、非 JSON、输出截断、exit 0 但缺必要事实、目标不存在 → 显式 `unknown`/拒绝，**不自动成功**；只读的 `retry` 为 `read_recheck`，不自动重放 |
| 结论与凭据 | 只读结论必须带来源版本与核验时间；日志不含令牌、argv 与业务敏感原文 |

**落地进展（2026-10-24）**：清单、只读端口、门禁骨架与四个只读工具已建立，19 例离线测试通过（含 `inject` 声明的防回归断言）。工具参数名刻意取 `target`——策略门禁只读 `exec.arguments.target`，用 `command`/`path` 之类名字会让 `target-required` 永远无法满足（同期实测的目录缺口）；模型可见面**只注册读工具，没有任何写工具**，因此在该面上无从发起任何写动作。

**宿主证据（2026-10-24）**：`node scripts/probe/devops-read-probe.mjs with-reader|no-reader` 把本包真的挂进宿主 profile，两种模式都通过——`with-reader`：模型自决调用 `forge_devops_issue_read` 经策略门禁到达适配器**恰好一次**（适配器日志 `{action: issue.read, target: group/repo#1}`，工具结果 `status=succeeded`、`source_revision=probe-rev-1`）；`no-reader`：无适配器时适配器日志为空、工具结果可见地报 `NO_READER`，且没有任何写工具调用。

**探针抓到的两种失败模式（已修）**：插件的依赖必须由 `inject` 声明——少了 `tools` 时 `ctx.tools` 不可见，工具会**静默不注册**（模型侧表现为 `unknown tool`）；少了 `policy` 时 `apply` 在策略挂载前运行，整项 `POLICY_REQUIRED` 不激活。两者都不会有任何"看起来成功"的假象，但都不会自报，必须靠宿主级证据发现。

**准入证据**：设计准入（本节）+ 设计索引登记 + 离线测试（假端口 + 门禁负测：未登记动作拒绝、缺目标拒绝、缺必要事实不报成功）。企业 CLI 实证、双端产物与权限证据仍属第三方，**不因骨架通过而写成已联调**。

## 7. 权限、数据与失败行为

| 场景 | 处置 | 用户可见结果 |
|---|---|---|
| 变更号无效、要求不可读、仓库不符 | 不承接；不靠旧上下文猜测 | 具体缺口及责任方 |
| 写开关关闭、权限不足、必要审计不可用 | 拒绝该动作；不借服务账号或换通道 | 没有发生写入或结果待核对 |
| 401/403、非结构化输出、超时/取消 | 区分未执行、失败、部分、未知 | 未知不当成功，也不自动重试写 |
| 创建 Issue 成功而建 PR 失败 | 保留已创建关联，查询后继续剩余动作 | 部分成功；不自动删对象“回滚” |
| 人确认后目标要求/PR 版本改变 | 原确认不再覆盖新版本 | 重取差异，按影响重新确认 |
| PR 未合入或远端 CI 未知 | 不冒充已合入/CI 通过；遵守实际必要 CI/分支规则 | 本地验证与独立 AI 审查通过可形成待验收交付；用户按实际版本验收，关闭另授权 |
| UAT 是别的版本、状态缺失 | 不宣布本变更 UAT 就绪 | 缺少交付关联，unknown |
| 指标上报失败 | 指标独立降级，不放宽必要审计 | 丢弃/缺失计数，不阻塞研发 |

凭据与工具正文按既有 C1–C4 和策略设计处理。操作审计记录主体、动作、目标引用、决定、结果及时间，不记录 token、提示词、代码、diff 或需求正文；业务所需内容在获准的业务写通道传递，不复制进指标事件。采集实现归属见 §9。

## 9. 研发效能与过程指标

### 9.1 目录与边界

以下为候选观察口径，不作为绩效或准入评分；本项目用途由用户决定，DevOps/PMO 等既有平台维护方只核实实际数据语义与分母，企业强制控制仍适用。分母缺失即不可计算，不补 0；各来源均带覆盖范围与口径版本。DORA 的五项定义以[官方指南](https://dora.dev/guides/dora-metrics/)为参考（2026-10-22 文档核对，不代表企业已具备数据），本项目不扩大生产访问以采数。

| 指标 | 候选口径与分母 | 权威采集点 | 状态/误用风险 |
|---|---|---|---|
| 部署频率 | 指定系统/环境窗口内成功生产部署数 ÷ 窗口时长 | DevOps 已有发布记录 | 平台计算待确认；不按个人排名，不把 UAT 当生产 |
| 变更前置时间 | 各已进入生产的提交从提交到首次成功生产交付的时长分布；分母为关联完整的提交集 | Git + 发布记录，DevOps 关联 | 待确认；缺关联样本单列，不混入故事业务等待 |
| 变更失败率 | 需要立即干预的失败生产部署数 ÷ 同窗口生产部署总数 | 变更/故障记录 | 分类待确认；不以流水线单测失败代替 |
| 失败部署恢复时间 | 失败部署至服务恢复的时长分布；分母为有完整起止记录的失败部署 | 变更/故障平台 | 待确认；不是全部故障的通用 MTTR |
| 部署返工率 | 为处理生产问题而进行的非计划部署数 ÷ 生产部署总数 | DevOps 已有分类 | 待确认；不把正常 PR 修订当部署返工 |
| 需求输入就绪时间 | 显式承接到有效要求取得/澄清回写确认的时长分布；分母为结束该环节且事件齐全的变更 | 客户端补起点 + DevOps 要求版本 | 候选；缺输入就绪事件时不可计算，需先冻结事件/版本关联；反映沟通等待，非模型能力评分 |
| PR 等待合入时间 | PR 正式可评审至合入的时长分布；分母为有起止记录的合入 PR | Gitee / DevOps | 平台计算；不归因为 DSH 编码耗时 |
| UAT 交付就绪时间 | 约定合入版本至对应制品 UAT 成功的时长分布；分母为关联完整的交付单元 | DevOps | 待确认；不表示业务验收或故事完成 |
| 工程修订率 | 交叉/人工审查后需工程修订的 PR 数 ÷ 有结构化审查分类的 PR 数 | Gitee 结构化分类；客户端补充分类须另冻结事件/字段 | 候选；缺有效分类时不可计算，评审发布成功不代表无需修订，正常迭代不直接算质量失败 |
| 工具动作成功率 | 已确认成功动作数 ÷ 全部终结逻辑动作数；同时列 failed/partial/unknown 比例 | 策略审计投影 | 候选最小集；重试不当新动作，未获准动作单列 |
| 人工决策请求率 | 发生明确业务决策请求的已承接变更数 ÷ 可观察的已承接变更数 | 仅结构化确认事件 | 候选 AI 子集；不从聊天轮数推导，不把必需评审/合并当低效 |
| AI 辅助变更占比 | 明确由 DSH 入口承接且关联有效的变更数 ÷ 同期同系统全部变更数 | DevOps 全量分母 + 客户端承接关联 | 分母/跨会话去重待确认；只看到 DSH 样本时不得计算 |
| 关联完整率 | 所需关联齐全的交付单元数 ÷ 同期应有关联的交付单元数 | DevOps / Gitee | 最小数据质量项；丢失/不适用分开 |

本表是选定的最小观察目录，不是企业全部指标台账。DORA 项保留用于行业口径对照，不表示 DSH 取得生产访问或承担采集；流水线时长/成功率/排队时间、测试反馈时间、不稳定用例率、逃逸缺陷率及体验问卷由既有平台/问卷侧负责，因不引入本方案新增客户端采集需求而不在本表重列，不等于已具备或已批准计算。若需纳入本观察目录，先由用户确认用途，再核实平台口径、分母与强制控制；不影响既有试点指标及问卷采集。

“最小集”先利用已有平台数据，并补动作结果和关联质量；人工决策请求、AI 辅助占比在定义与分母落实前不采。主体维度默认系统/项目/团队；个人如需本人可见须由用户确认用途并核验真实权限和适用企业隐私规则，不生成个人排名。指标不能替换登录、安装、活跃、故障、继续使用意愿等试点指标；M4 的撤销状态不恢复。

### 9.2 采集器归属

选择**并入 `forge-policy` 既有 OTel 操作审计设计的独立观察投影**，不新增采集包/服务。“既有”指既有方案职责，不表示该插件或摄取通路已经实现和可用。理由：同一工具结果和关联事实已有来源，再建独立 SDK/队列会重复计数并增加维护面。平台能算的指标不由客户端重算，不能从 Agent 自述补全平台事实。

评审动作投影按事件契约归入 `review_write`，并由完整 `action` 区分 AI/人工，不采评审正文。该动作投影仅观察发布/记录的执行结果，不补造工程修订分类；客户端补充分类事件在用途与 schema 冻结前不采，缺少平台有效分类时不计算工程修订率。

必要审计与可选指标导出严格分离：前者按安全规则关闭动作，后者可有界缓冲/丢弃且不阻塞研发。若既有 OTel 路径不能独立降级或缺少摄取协议，关闭观察导出并列缺口，不默默新建独立采集器。事件、上报、保留及拒绝内容字段的契约唯一真源见[metrics-events](../../contracts/metrics-events.md)。

### 9.3 最小配置职责（不是已存在的配置键）

| 配置概念 | 默认与约束 | 维护者 |
|---|---|---|
| 观察导出开关 | 默认关闭；用户确认用途且真实通道、权限与企业强制控制核验后启用；与必要审计分开，停用不删除业务记录 | 用户决策；Agent 核验 |
| 事件允许集 | 仅版本化事件/schema；AI 子集用途、分母未定不采；不接受自由扩展字段 | 用户确认用途；Agent 核验平台事实 |
| 出口及身份引用 | 复用现有获准 OTel 路由与机器出口身份；不把业务访问令牌借给摄取端 | Agent 核验；IT/IAM/DevOps 提供真实通道与权限事实 |

| 生效/降级 | 随现有配置生命周期生效；版本不兼容则关闭投影，必要审计仍独立执行 | Agent 核验既有宿主能力 |

具体配置键、SDK 挂点和热更新能力均待目标宿主核验，不因这张职责表新增配置管理系统。

## 11. 打包、兼容与退出

本稿是跨模块能力设计，不创建 `forge-devops-lifecycle` 包；配置与 Skill 仍按现有分发机制。`forge-sdd` 已于 2026-11-03 全量退役：包、企业组合依赖与 bin 已删除；已安装 profile 与已发布制品不动。历史兼容语义仅留档，不构成默认交付或新冻结需求。DSH 目标版本和 SDK 挂点以对应模块实测为准，不从旧项目推导。停用某企业动作不删除 DevOps/Gitee 正式对象；停用观察指标不影响权威业务记录。契约草案需经提供方映射并冻结版本后才能实现；升级不得把未知旧字段默认解释成已批准。
